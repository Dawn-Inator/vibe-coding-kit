# Optional Components

Optional components extend the Kit for projects that need them. Their registry is [`catalog.json`](catalog.json); the Kit installer reads that catalog to resolve the categories below. New installs leave the first three categories off by default. Project settings live in `.vibe-coding/project.config.json` under `optional` and do not override project-specific policies.

The directory tree groups sources by physical type:

```text
optional/
├── catalog.json
├── plugins/
│   └── codex-task-progress/
└── skills/
    ├── aliyun-skill-discovery/
    ├── hyperframes/
    ├── lark/
    └── presentations/
```

These folders do not change the four installation-purpose categories. `catalog.json` maps `task-progress` to the plugin, `aliyun` to its skill component, `lark` to its skill component, and `non-code` to both `hyperframes` and `presentations`.

Choose categories during a new interactive install, or pass repeated flags in scripted installs:

```sh
vibe-coding-kit install --project-root . --identity-name 'Your Project AI' --identity-email 'ai@example.org' \
  --optional aliyun=off --optional lark=on --optional non-code=off --optional task-progress=on
```

For an initialized project, set a category explicitly with:

```sh
node .vibe-coding/kit/cli.mjs optional configure --project-root . --optional lark=on
```

Only selected components are projected or installed. Enabling a component does not log in to an account, provision a repository or cloud resource, or create project-specific policy. Missing or unsupported component setup is reported as such. Disabling a category removes only Kit-generated mirrors and routes; project-owned files, history, credentials, and custom skill content remain under project ownership. Existing explicit preferences are retained. For legacy projects without `optional` preferences, Kit detects already-selected optional skill sources and preserves their skill decisions and pack layout when first saving preferences. For example, if only `animated-presentations` was selected, enabling `aliyun` preserves that skill without expanding the whole `non-code` bundle; explicitly enabling `non-code` later adds its full skill set while preserving user exclusions and local or replacement overrides. Only exclusions generated by the Kit migration are cleared when their category is explicitly enabled. A detected Task Progress installation is reused unless explicitly disabled. File conflicts are preserved and reported for review.

For a registered project, ordinary `install` checks the pinned Kit and current projections. Passing `--optional <group>=on|off` explicitly updates the category preferences and selected projections. Add `--check` to preview the proposed preferences without writing config or installing the components. `optional configure --check --optional <group>=on|off` provides the same read-only preview for an initialized project.

## Categories

| Category | Components | Use |
| --- | --- | --- |
| `aliyun` | `aliyun-skill-discovery` | Discover applicable Alibaba Cloud skills for a project. |
| `lark` | `lark` | Use the Lark skill entry point and its documented operations. |
| `non-code` | `hyperframes`, `presentations` | Add the HyperFrames video workflow and presentation authoring guidance. |
| `task-progress` | `codex-task-progress` | Add Codex chat task progress and its optional project Heartbeat view. |

The `task-progress` category is offered only on supported Apple Silicon macOS with Codex Desktop. A fresh explicit category selection uses `install --defer-connection --json` to prepare the plugin for managed-launcher setup without first requiring CDP. During an interactive install or optional-category wizard, if Task Progress is selected and an already-installed helper supports the launcher but has no configured launcher, Kit asks a separate purpose-level, default-No, one-click question before configuring the Dock launcher. Declining leaves both the plugin installation and project category selection unchanged. This is independent of signing consent. For an existing plugin, passing `--optional task-progress=on` explicitly requests launcher configuration directly. A non-interactive run with saved or auto-detected preferences only reuses the existing install; it does not configure the launcher. An unrelated explicit category update does not trigger the launcher question. Ordinary Kit installation does not automatically upgrade an existing plugin. An older helper without launcher support returns setup-required, and Kit leaves upgrades explicit. Launcher setup never silently restarts Codex. When the category is selected and supported but the plugin is missing, Kit invokes [`plugins/codex-task-progress/scripts/install-from-kit.mjs`](plugins/codex-task-progress/scripts/install-from-kit.mjs) from the pinned Kit checkout. That installer builds and installs from the component embedded in Kit; it does not depend on cloning another repository. The plugin package is built with its separate Node.js 22+ toolchain, while Kit itself uses Node.js 20; generated output is self-contained and derives from the checked-out Kit revision. No prebuilt release asset is implied by this source-install path. The installer automatically reuses a previously confirmed signing identity and places the Helper at the real stable `install/bin/goal-progress` path while retaining versioned release assets.

Before a missing plugin is installed, an interactive TTY offers one explicit confirmation to select an eligible local signing certificate. In non-interactive use, Kit reports that signing setup is required and prints the command sequence instead of guessing an identity. To inspect signing status and available local candidates without writing anything, run:

```sh
node .vibe-coding/kit/optional/plugins/codex-task-progress/scripts/install-from-kit.mjs --check
```

To explicitly validate and persist a chosen certificate fingerprint:

```sh
node .vibe-coding/kit/optional/plugins/codex-task-progress/scripts/install-from-kit.mjs --configure-signing --identity '<certificate fingerprint>'
```

This command changes only the private signing configuration; it does not build, sign, install or restart Codex. An invalid or unavailable certificate produces actionable setup guidance. Once selected, later local builds reuse the saved identity automatically. Stable-path installation does not transfer TCC permissions; first migration from a versioned executable may still require user approval, and future prompts are not ruled out. Kit does not create certificates, export private keys or grant macOS privacy permissions.

The Task Progress component retains its upstream license and attribution notices. Its source is maintained here with the Kit; projects should follow the component's own setup and compatibility instructions in [`plugins/codex-task-progress/README.md`](plugins/codex-task-progress/README.md). The plugin does not silently restart Codex; distinguish installer health checks from confirmation that the panel is visible in the UI.

## Project-specific boundaries

These components are reusable sources, not a declaration of project policy. In particular, selecting Alibaba Cloud discovery or Lark does not copy LingoFly account, region, project, incident, or tracker conventions into another project. Projects decide their own credentials, authorization, account setup, and operating procedures.
