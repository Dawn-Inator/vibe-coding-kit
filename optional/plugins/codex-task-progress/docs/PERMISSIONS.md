# Task Progress permissions

This derivative uses a private Unix socket, a loopback CDP connection owned by the verified Codex process, a launchd Helper, local plugin hooks, and Codex App Server reads for trusted chat identity and native Goals. It does not modify Codex application files or signatures.

Release data, Helper runtime files, logs, install manifest, preferences and Helper-owned workspace-routing history are under `~/Library/Application Support/CodexTaskProgress`. Versioned release assets remain in `install/releases/<version>/`; the active Helper is atomically installed as a verified real executable at `install/bin/goal-progress`, with a snapshot available for rollback. launchd, MCP and new Hooks use that stable path. Doctor verifies the executable hash and rejects a symlink. The launchd label is `com.codextaskprogress.helper`; the listener identity is `com.codextaskprogress.listener`. Ordinary chat task history is stored in the trusted chat cwd under `.workspace/codex-task-progress/tasks/v3/<thread-sha256>/taskhistory.md`. `heartbeat.md` is a readable projection, not a substitute event log. Rebuildable cache files use `.tmp/codex-task-progress/<thread-sha256>/`; they are not task authority. These records are separate from upstream native Goal records and stay local.

The Heartbeat adapter reads discovered project ledgers through the canonical Kit inspection API. Selected paths, cached views and observed hashes are stored in private application data. Project ledger observation does not edit ledger content or create Heartbeat schedules. The rebuildable workspace cache is separate from both the canonical task files and project Heartbeat history.

Background startup recovery consults only Helper-owned recoverability hints to decide whether recovery should be attempted. A hint is not task content, a trusted chat identity or source authority. After establishing trusted identity for the visible chat, recovery reads and validates that chat's canonical task files through Kit. It does not treat the hint as a substitute for those reads or scan arbitrary project task files at startup.

The older persisted startup-recovery policy is disabled by `goal-progress launcher --install --dock --json` and is no longer recommended as reliable automatic recovery. Use the explicit managed launcher flow instead. It never force-restarts an existing Codex process.

If Codex is already running without CDP, launcher use can only activate that process; a later full cold launch through the managed launcher is needed to establish CDP. The launcher never forces an existing Codex restart and never bootstraps CDP into an already running app. When verified CDP is already present, it reuses the connection. First access to a macOS-protected folder requires the user's approval in the system prompt. A transition from an older version-specific Helper path to `install/bin/goal-progress` may require separate approval: TCC authorization is not transferred, and stable-path use has not established that prompts cannot recur later. Permission grants are never automated; do not edit or reset the TCC database or default to Full Disk Access.

The managed launcher is a separately signed app with its own bundle identifier; its displayed name and icon are derived from the detected Codex vendor app. It does not modify Codex's bundle, and a launch command does not restart Codex. Dock replacement is explicit (`--dock`), preserves unrelated Dock entries and the current session, and does not guarantee that macOS will display only one Codex-like icon. The original app remains usable and direct launches are not intercepted.

Kit reuses an existing Task Progress installation without asking to sign or reinstall it. In an interactive install or optional-category wizard, selecting Task Progress when an installed helper supports the launcher but has no launcher configured can trigger a separate purpose-level, default-No, one-click prompt to configure the Dock launcher. Declining leaves the plugin and project selection unchanged. Non-interactive runs with saved or auto-detected preferences only reuse the installation; unrelated explicit category updates do not prompt. Explicit `--optional task-progress=on` requests launcher setup directly. For a selected but missing component, interactive setup separately asks for explicit confirmation of an eligible local signing certificate; non-interactive setup reports that signing setup is required and provides the commands. The helper's `--check` displays signing status and certificate candidates read-only. `--configure-signing --identity <fingerprint>` validates the explicit choice and writes only the private signing config; it does not sign, build, install or restart Codex. Later local builds reuse this choice, but this does not guarantee macOS protected-folder consent will carry across updates. TCC may associate consent with the executable's physical version path, and inheritance across upgrades has not been verified. Setup never creates certificates, exports private keys or grants privacy permissions.

Local signing can use `GOAL_PROGRESS_CODESIGN_IDENTITY` or `release-signing.json` under the Task Progress application-support directory. The JSON schema is `{ "schemaVersion": 1, "identity": "..." }`; `GOAL_PROGRESS_CODESIGN_CONFIG` selects an explicit absolute path. Keep identity values out of source and docs. With no configured identity, ad-hoc signing remains available with a warning that macOS may ask for permission again. An Apple Development signature supports local development only and is not a Developer ID or publicly notarized release. A configured but invalid explicit config or identity must fail closed rather than silently falling back.

See [installation and removal](../INSTALL-FOR-AI.md) and [README](../README.md). On launcher-capable releases, uninstall first removes the owned launcher and Dock entry. If cleanup fails or a user-edited entry must be retained, Helper removal is blocked to avoid a broken launcher; older helpers keep legacy uninstall behavior. To uninstall while preserving task/history data, use the installed `bin/goal-progress uninstall --json --keep-history`. Native Codex Goals and chats are separate from this plugin's data.

The canonical pinned Kit contract determines the trusted workspace paths. `WorkspaceTaskStorage` writes durable per-chat task history under `.workspace/codex-task-progress/` and rebuildable cache data under `.tmp/codex-task-progress/`; workspace task directories self-ignore Git. Helper-owned routing history lives in the application-support `task-routing/` directory and supports trusted cwd changes. The older `workspace-storage-index.json` is read only as a compatibility/migration source. Migration preserves prior app-support files and fails closed on divergent workspace history. Original project Heartbeat ledgers remain read-only during display and observation.
