# Style discovery and representative proof

## 1. Establish the direction

Resolve purpose, audience, duration, content, and speaker-led versus reading-first density from the request. Ask only for missing information that changes the result. A clearly specified theme or narrow edit keeps the existing system instead of starting another selection process.

For a new direction, read [STYLE_PRESETS.md](../STYLE_PRESETS.md) and [the compact bold selection index](../bold-template-pack/selection-index.json). Shortlist relevant candidates; read only their `preview.md` cards. If the user wants alternative directions, show distinct real title-slide previews so they can choose. Do not force a three-option exercise when they have already chosen a template or ask for representative pages in one direction.

Once a primary direction is selected, read its full recipe before coding: the relevant preset section or the selected bold `design.md`. Index paths are relative to the skill root. Split long reads into ranges so every section is actually available; do not treat truncated output, an index, or a preview as the recipe. Do not read unrelated full recipes.

Keep a brief working record of the selected source, its defining design traits, justified adaptations, representative-page scope, and any user confirmation. The record supports execution; it is not evidence that the design looks good. Keep internal template names, paths, and approval metadata outside the slide artwork.

## 2. Preserve the design while adapting the content

Apply the recipe's composition system, palette roles, typography hierarchy, density, recurring graphic marks, and panel/component grammar. Dense visual composition need not mean dense text: use diagrams, large type, meaningful panels, and structured contrast while preserving legibility.

Do not remove the defining grid, signal colors, graphic devices, or visual density merely to make a deck "restrained", "internal", or easier to code. Do not quietly mix a second preset into an approved template. If the recipe conflicts with an explicit brand, language, accessibility, aspect-ratio, or offline requirement, make the minimum concrete adaptation and state it. Font substitution for CJK coverage or offline delivery is valid when the intended weight/hierarchy survives. A different composition/palette/motion direction is a material change: present it as such instead of claiming template fidelity.

If a custom direction is explicitly wanted or genuinely necessary, identify its primary reference and substantive departures before expansion. Preserve that custom system consistently once approved. Do not invoke "custom" after a draft is made to excuse missing recipe traits.

## 3. Prove representative pages and motion

For a new, unapproved direction, build a small representative set first: normally the cover, a process/diagram page, and a comparison or another demanding layout. Adapt this set to the actual story and requested scope; the purpose is to prove range, not to enforce three arbitrary layouts in every project. Use the user's real content.

Make the motion plan before implementation. State what the focal element represents, how related elements change across initial/middle/final states, the intended rhythm, and how the scene connects to the next. Use [motion direction](motion-direction.md) and, when requested, [function animation](function-animation.md). Deliver actual replayable motion, not only screenshots or a list of named effects. Pausing/seeking is useful when it makes a complex sequence reviewable.

Inspect the representative pages in a real browser before presenting them: recipe fidelity, composition, graphic hierarchy, actual motion, text/geometry overlap, rapid/reverse navigation, and reduced-motion final states. If visual quality misses the brief, revise these pages rather than expanding a weak direction. Mechanical checks and source-read receipts do not approve the design.

## 4. Confirmation and expansion

When the user asks to confirm a direction, present the concrete working proof and wait. Keep the proof limited to the agreed representative pages; do not build the rest in the background. User approval is the authority to expand, and approval covers the direction shown, not later material changes. Incorporate feedback into the proof first, then propagate the approved system.

"Choose for me" delegates selection; it does not cancel an explicit request to review representative pages. An explicit user request for the complete deck without intermediate review can waive the conversational checkpoint. In that case, still read the full recipe, build and inspect representative pages internally, and only then expand. Do not add "no questions", "skip selection", or similar convenience language to a worker/test brief to manufacture authorization that the actual request did not give. Existing authorization and explicit user instructions take precedence over this workflow.

After approval, preserve the approved design and motion language and verify the expanded deck. Reopen direction review only for a material departure or when the user requests it; ordinary edits and repairs need no repeated approval.

Keep previews separate from final artifacts, retain the approved proof while it guides expansion, and remove only task-generated temporary files when no longer needed. Preserve user assets and prior work.
