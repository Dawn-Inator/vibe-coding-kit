# Style discovery and representative proof

## 1. Establish the direction

Resolve purpose, audience, duration, content, and speaker-led versus reading-first density from the request. Ask only for missing information that changes the result. A clearly specified theme or narrow edit keeps the existing system instead of starting another selection process.

First outline the story and each slide's job, focal relationship, hierarchy, and breathing room. Use audience, duration, density, diagram and comparison needs, and any user reference to choose a direction that serves the content. A library recipe, a custom system, or a user reference can each be the primary direction; none is an exceptional fallback. When the user requests the library, consult it and explain the choice. When authorized, refer to user-approved prior work and retain its advantages.

For a sequence of explanations, note what the audience should understand, the main object, the evidence source if any, the presenter trigger, the readable landing state, and what carries into the next scene. This can be a compact storyboard, not a second document. Design a chapter as a sequence: a large opening object can become a map or recurring anchor, while a process, comparison, and real screenshot use different compositions. Distinguish a real source image from an original explanatory drawing or atmospheric illustration; label illustrative examples rather than presenting them as evidence.

For library exploration, read [STYLE_PRESETS.md](../STYLE_PRESETS.md) and [the compact bold selection index](../bold-template-pack/selection-index.json), shortlist candidates, then read relevant `preview.md` cards. If the user wants alternatives, read each selected recipe completely before rendering its distinct real title-slide preview. Do not force an options exercise when a direction is already chosen or representative pages are requested in one direction.

Kit-authored directions are also selectable: [Delivery Practice](delivery-practice.md) and [Deep Space Theatre](deep-space-theatre.md). The latter bundles a reusable celestial stage and a complete example; choosing it is a design decision, not an installation-wide theme setting. General storytelling and presenter controls apply to other visual directions without copying planets, colors, or layout.

For a selected library direction, read the full relevant preset section or bold `design.md` before writing any slide in that direction. Index paths are relative to the skill root. Split long reads into ranges so every section is available; a truncated read, index, or preview is not the recipe. Read unrelated full recipes only when useful to selection.

Keep a brief working record of the selected source, its defining design traits, justified adaptations, representative-page scope, and any user confirmation. The record supports execution; it is not evidence that the design looks good. Keep internal template names, paths, and approval metadata outside the slide artwork.

## 2. Preserve the design while adapting the content

For a selected recipe, apply its composition system, palette roles, typography hierarchy, density, recurring graphic marks, and panel/component grammar. Dense visual composition need not mean dense text: use diagrams, large type, meaningful panels, and structured contrast while preserving legibility.

Do not remove the defining grid, signal colors, graphic devices, or visual density merely to make a deck "restrained", "internal", or easier to code. Do not quietly mix a second preset into an approved template. If the recipe conflicts with an explicit brand, language, accessibility, aspect-ratio, or offline requirement, make the minimum concrete adaptation and state it. Font substitution for CJK coverage or offline delivery is valid when the intended weight/hierarchy survives. A different composition/palette/motion direction is a material change: present it as such instead of claiming template fidelity.

A custom or user-referenced direction should identify its primary reference and design system before expansion. Preserve it consistently once approved; do not relabel a draft as custom to excuse missing traits of a selected recipe. Optional motifs need not appear in every scene, and blank space need not be filled to satisfy density. Choose a better-fitting direction when content and recipe are at odds.

Keep stable chapter typography, light, or an object where it helps orientation; vary the main explanatory metaphor with the subject. A route explains a handoff, a changing workpiece explains transformation, and a full image supports observation. Repeating a card grid with different headings does not reproduce that range. Give screenshots and dense materials the space they need, retain their captions and source context, and reduce surrounding ambient motion while people inspect them.

## 3. Prove representative pages and motion

For a new, unapproved direction, build a small representative set first: normally the cover, a process/diagram page, and a comparison or another demanding layout. Adapt this set to the actual story and requested scope; the purpose is to prove range, not to enforce three arbitrary layouts in every project. Use the user's real content.

Make the motion plan before implementation. State what the focal element represents, how related elements change across initial/middle/final states, the intended rhythm, and how the scene connects to the next. For a new live talk, divide explanations into speaker-triggered semantic steps with readable resting states; do not make the presenter race a long page timer. Use [motion direction](motion-direction.md) and [function animation](function-animation.md) for deterministic step renderers. Deliver actual replayable motion, not only screenshots or a list of named effects. Pausing/seeking is useful when it makes a complex sequence reviewable.

Inspect the representative pages in a real browser before presenting them: direction fidelity, composition, graphic hierarchy, and actual motion; separately check text/geometry overlap, rapid/reverse navigation, and reduced-motion final states. If an unapproved proof repeatedly misses the aesthetic goal, determine whether composition can be fixed within the grammar or the art direction is wrong. For the latter, openly return to selection before expansion. Mechanical checks and source-read receipts do not approve the design; judge aesthetic quality separately from technical behavior.

## 4. Confirmation and expansion

When the user asks to confirm a direction, present the concrete working proof and wait. Keep the proof limited to the agreed representative pages; do not build the rest in the background. User approval is the authority to expand, and approval covers the direction shown, not later material changes. Incorporate feedback into the proof first, then propagate the approved system.

"Choose for me" delegates selection; it does not cancel an explicit request to review representative pages. An explicit user request for the complete deck without intermediate review can waive the conversational checkpoint. In that case, still read any selected library recipe in full, build and inspect representative pages internally, and only then expand. Do not add "no questions", "skip selection", or similar convenience language to a worker/test brief to manufacture authorization that the actual request did not give. Existing authorization and explicit user instructions take precedence over this workflow.

After approval, preserve the approved design and motion language and verify the expanded deck. Review a continuous 3–5-page passage as well as isolated representative pages: check whether an expressive opening, explanation, evidence, and quiet landing form a useful rhythm. For a smaller authorized proof, review its available sequence without generating extra pages. Reopen direction review only for a material departure or when the user requests it; ordinary edits and repairs need no repeated approval.

Keep previews separate from final artifacts, retain the approved proof while it guides expansion, and remove only task-generated temporary files when no longer needed. Preserve user assets and prior work.
