# Artifact 路由:新内容该进哪个产物

## 问题

有了 Skill、Memory、History、Doc 四类产物的清晰定义之后,还剩一个实际操作时天天会遇到的问题:
AI 在一次会话里学到了新东西、或者要记录一个决定,**当下就该判断它该写进哪个产物**——写错了地方
比不写更糟糕,因为会造成重复内容散落在多处、后续检索时找不全,甚至出现互相矛盾的两份"权威说法"。
同时还有一类更隐蔽的丢失:开发者当面拒绝了 AI 的某个建议,如果这次拒绝没有被以某种方式记录下来,
未来的会话(甚至同一个人的下一次会话)很可能会不知道这件事已经问过、被拒绝过,重新把同一个建议
再提一遍——这对开发者是一种持续的骚扰。

## 设计原理(通用、可泛化)

路由问题的本质是一个分类决策,分类决策最容易出错的地方不在"规则本身够不够清楚",而在"每次都靠
临时判断、没有固定检查清单,导致同一类内容在不同时间被路由到不同产物"。解决办法是把分类过程本身
**卡片化**——用一张固定字段的卡片,强制每次路由前回答同样几个问题,而不是每次自由发挥判断。

拒绝建议的记录同样是一个通用问题:**任何会持续给出建议的系统,都需要一种机制记住"这条建议已经被
明确拒绝过"**,否则拒绝会不断被重新触发。这个问题的关键不在"要不要记录",而在"记录在哪里才能在
下次真正需要的时候被读到"——记录本身如果无法被检索到,等于没有记录。

## 可复用技术模式

### Artifact Decision Card

在创建、修改、拆分、合并、或退役任何一份长期知识产物之前,先过一遍固定流程:

1. **判断性质**:这次交流是纯讨论(不需要落地),还是确实要写入某个产物?
2. **先搜索、后新建**:在 Skill / Doc / History / 临时任务清单里搜索有没有同主题的已有内容——
   **优先修改已有的权威来源,而不是新建一个内容近似重复的产物**。重复的权威来源比没有权威来源更
   危险,因为无法保证两份内容会同步更新。
3. **填卡片**:确定这次内容落到 `README.md` 里那张"内容性质 × 生命周期"矩阵的哪个象限。
4. **按结果推进,不问**:除非出现实质性的权威冲突(两处已有内容互相矛盾),或者"这份东西是否该
   退役"处于真正的模糊地带,否则不需要停下来跟人确认——按卡片判断结果直接执行。这条设计是为了
   避免把本可以自主完成的日常知识维护动作变成频繁打断人类的琐碎提问。
5. **分流写入**:长期知识(Skill / Doc / History,以及连带的规则文件、代码、配置、测试改动)写进
   受版本控制管理的工作区;纯粹属于"这次会话内部执行进度"的临时清单(todo/task list)不进版本控制,
   留在会话自己的临时文件里——这条边界防止临时的执行态笔记污染长期知识库。
6. **套用专门流程**:确定要写 Skill 就走 Skill 创建流程,确定要写 History 就走 History 记录流程
   (即前两篇文件里各自的格式和纪律)。
7. **统一收尾**:在一次改动的编排边界(比如一次任务全部完成时),统一跑一次索引/生成投影的更新
   命令和轻量校验,而不是每写一个文件就跑一次——降低高频小改动的操作摩擦。

### "拒绝建议归档"范式

当开发者明确拒绝了 AI 的某个建议时,这次拒绝要被写进"AI 下一次很可能会再次提出同样建议时,原本
就会打开的那份文档"里——用 **co-location test** 来判断该写在哪份文档:不是"哪份文档主题最相关",
而是"AI 下次准备重提这个建议之前,最可能已经在读哪份文档"。记录三件事:

```markdown
### Owner 拒绝:XXX 建议

- **被拒绝的内容**:AI 建议了什么
- **开发者的理由**:为什么拒绝
- **防重复指引**:未来会话遇到类似场景时,不要重复提出这个建议,应该怎么做
```

**必须用标题(Markdown `###`/`####` 级别),不能只用加粗文字**——因为检索这类记录的方式通常是对
标题模式做全文 grep(比如搜索所有 "### Owner 拒绝:" 开头的标题),如果写成正文里的加粗文字,
全文 grep 会漏掉,这条记录实质上等于没写。这个小细节决定了整个范式是否真的有效。

## Nova 案例参考

Nova 的 Artifact Decision Card 流程写在 `manage-knowledge-artifacts` 这个 skill 里,"拒绝建议归档"
的具体案例散落在多份规则文件和 skill 里(比如某次开发者明确拒绝"修 bug 可以不补自动化测试"这个
默认假设后,这次拒绝被写进了项目每轮必读的核心规则文件里,因为那正是 AI 下次准备"要不要问要不要
补测试"时最可能已经打开的地方)。`README.md` 提到的 `claude-only`/`agent-only` 平台条件标记技巧
在这类路由文档里同样适用,但**不适用于 doc/ 下的规范性文档**——那些文档要保持平台中立的纯散文,
不掺杂特定 AI 工具的专属细节。这些都是 Nova 按自己项目节奏和真实发生过的分歧总结出的具体案例;
新项目应该在自己第一次遇到"开发者拒绝了一个建议"时,重新判断该写进哪份文档,而不是照抄 Nova 选的
那份文件。
