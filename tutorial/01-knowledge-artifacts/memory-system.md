# Memory 系统:纠正认知的活文档

## 问题

AI 会话在工作过程中经常会踩坑,并从坑里学到一个具体的教训——"这个字段其实是聚合出来的,不是权威
数据源""这类任务不该自己决定,该走某个既定流程"。如果这些教训只存在于当次会话的对话历史里,下一次
新会话(甚至同一个人几小时后开的新会话)大概率会重蹈覆辙,因为 AI 完全不记得上次学到了什么。需要
一种机制,把"AI 学到的、会跨会话复用的认知修正"沉淀成可检索、可信任的持久记录。

## 设计原理(通用、可泛化)

Memory 记录的不是"发生了什么事"(那是 history 的职责,见 `history-system.md`),而是**"AI 下一次
可能会想错的一个瞬间,以及正确答案是什么"**。这个定位决定了它的两个关键特征:

1. **原地可编辑**:一条 memory 描述的是"当前状态下什么是对的",一旦底层事实变了(代码重构了、
   规则改了),这条记忆本身也该跟着更新或标记失效——它不是历史记录,不需要保留"过去曾经是对的"这个
   版本。
2. **分两种纠正对象**:纠正的可以是"AI 对代码库/业务的事实性认知"(比如以为某个 API 是权威数据源,
   实际不是),也可以是"AI 自己的工作方法"(比如以为该主动问,实际上项目要求默认自主推进)。这两种
   纠正的"证据来源"完全不同——前者的证据是代码库里的某处真实实现,后者的证据是 AI 自己曾经的错误
   行为和随后收到的反馈——所以值得拆成两个类型分别标注,方便按可信度和检索场景过滤。

## 可复用技术模式

### Frontmatter 契约

```yaml
---
name: project_backend_openapi_is_aggregate_contract   # 必须等于文件名(不含扩展名)
description: '写这条是为了纠正哪个"会想错的瞬间"——不是"这条讲了什么"'
type: project                                          # project | feedback
status: active                                         # active | superseded
canonical_source:                                      # project 类型必填;feedback 类型填 'self'
  - 'doc/xxx.md#锚点'
related_files: []
redaction: none                                        # none | redacted | safe-placeholders
updated: '2026-08-07'
---
```

`description` 字段的写法是这套系统里最容易被误解的一点:它不是"这条 memory 讲了什么内容"的摘要,
而是**"AI 在什么心理状态下应该被这条记忆拦住"**——写成检索触发条件,而不是内容简介,才能在
AI 即将犯同一个错误的那一刻被匹配到。

`canonical_source` 强制每条 `project_*` 类型的 memory 指回代码库里真实存在的权威来源(文档锚点、
配置文件路径等),而不是让 memory 自己成为唯一真源——memory 的角色是"提醒有这么一个容易想错的点,
以及去哪里核实",而不是复制一份可能过时的事实副本。

### 正文范式:证据 → 结论 → 指针

正文遵循固定顺序:先给出让这条记忆成立的具体证据(一段真实发生过的代码/对话/事故片段),再给出
从证据推出的结论,最后指向 `canonical_source` 里权威来源的具体位置。结尾必须有一行:

```markdown
How to apply: 在什么场景下、遇到什么信号,应该主动想起这条记忆
```

这行是整条 memory 存在的意义所在——没有它,这条记忆退化成一段孤立的历史陈述,AI 读到时不知道该在
什么场景下调用它。

正文内可以用 `[[wikilink]]`(下划线形式,对应目标文件名)语法互相引用其他 memory 条目,让相关的
认知修正之间形成显式关联,而不是各自孤立。

### "永不删除,只标 superseded"

一条 memory 过时后**不删除**,理由是删除会留下死链接(别的 memory 或代码注释可能引用过它的文件名),
而且直接消失会让人以为"这个问题从没被发现过"。正确做法:

1. `status` 改为 `superseded`。
2. 正文开头插入一行:`⚠️ 本条已失效(日期)+ 原因 + 接替条 [[新条目名]]`。
3. 索引文件里用删除线 `~~名字~~` 标出,让人一眼看出这条不再是当前答案,但仍能点进去看历史脉络
   和"为什么曾经这么想、后来为什么变了"。

### 两份生成索引

- `MEMORY.md`:harness 启动时自动加载的精简索引,只列名字,**有硬上限**(约 200 行 / 25KB,超出会
  被静默截断)——这个硬上限本身是一种设计压力,倒逼团队保持 memory 数量可控、及时清退 superseded
  条目,而不是无限堆积。
- `CATALOG.md`:无大小限制的完整索引,每条附带 `description`,用于人工或 AI 按关键词浏览全集。

两者都是生成产物,由专门脚本从每个 memory 文件的 frontmatter 重新生成,并有对应 check 脚本校验
索引和文件系统实际内容是否漂移——这正是 `README.md` 里提到的"索引是生成产物"模式的第二次落地。

## Nova 案例参考

Nova 把 memory 目录按业务模块拆分(`agent/`、`backend/`、`deploy/`、`gate/`、`test/`、`worktree/`
等),每个文件命名为 `<module>/<type>_<slug>.md`。这是 Nova 按自己团队的业务边界做的具体切分;
新项目应该按自己项目实际的模块划分方式重新决定目录结构,核心可复用的是 frontmatter 契约本身
(`project_`/`feedback_` 二分、`status: active|superseded`、`How to apply:` 收尾)和两份生成索引的
机制,而不是 Nova 具体选了哪几个模块名。
