# 知识产物系统:总览

## 问题

AI agent 协作开发跟人类团队协作开发有一个根本差异:人类团队靠"老员工的经验"和"口口相传"就能维持
知识连续性,但 AI 会话是**无状态的**——每一轮新会话打开时,除了仓库里能读到的文件,什么都不记得。
如果项目积累的经验、规则、历史事件全靠塞进一份越来越长的说明文件,会撞上两个硬问题:

1. **上下文窗口有限**:说明文件塞得越多,AI 每轮要读的无关内容就越多,真正相关的规则反而被稀释。
2. **知识的"新鲜度"和"权威性"分不清**:一条三个月前的经验教训,和一条上周定下的硬规则,如果混在
   同一份文件里,AI 没有办法判断哪条还作数、哪条已经过时。

于是需要把"AI 需要记住的东西"按**用途**拆成不同的产物类型,每种类型有自己的生命周期、检索方式和
更新纪律,而不是一股脑塞进一个大文件。

## 设计原理(通用、可泛化)

把 AI 协作项目要沉淀的知识按两个维度分类,能推导出四种基本产物:

| 维度 | 取值 |
| --- | --- |
| 内容性质 | **规程**(该怎么做一类事) vs **事实/经验**(关于某个具体判断的认知) |
| 生命周期 | **可编辑更新**(原地修正) vs **只增不改**(按时间顺序追加) |

四种组合对应四类产物:

| | 规程 | 事实/经验 |
| --- | --- | --- |
| 可编辑更新 | **Skill**(如何做某类任务的操作手册) | **Memory**(纠正一个认知,过时后原地标记失效) |
| 只增不改 | **Doc**(项目某个领域的规范性说明,可被 skill 索引) | **History**(叙述一次具体事件,永远新开记录) |

这个分类本身就是一条判断规则:新内容要落地前,先问"这是教 AI 怎么做一类事,还是记录一次具体发生的
事情?再问"它会不会随时间被修正,还是应该保留发生时的原始记录?"——落到哪个象限,就该进哪个产物。

## 可复用技术模式:索引是生成产物,真源分散在各文件自己的元数据里

四类产物有一个完全一致的架构模式,值得作为贯穿整个模块的核心设计哲学单独点出:

- 每一份具体文件(每个 skill、每条 memory、每条 history、每篇 doc)自己携带元数据(YAML frontmatter),
  声明自己的名字、用途、触发条件、状态。
- **没有任何一份需要人工维护的"总目录"文件**——所有索引(skill 的自动触发、memory 的 `CATALOG.md`、
  history 的月度 `index.md`、doc 的 `README.md`)都是脚本扫描全部文件的元数据后**重新生成**出来的
  投影,顶部带"生成文件,勿手改"的注释。
- 好处是:新增一份文件只需要写好这份文件自己的元数据,不需要记得去改某个中心化列表——不会因为
  漏改索引而产生"文件存在但检索不到"的死角;而且索引和真实内容不可能出现人工维护导致的漂移
  (跑一次生成+校验脚本就能证伪)。

这个模式在下面四篇文件里各有一次具体落地,读完 `skills-system.md`、`memory-system.md`、
`history-system.md`、`doc-governance.md` 后可以回头对照,会发现它们是同一套骨架的四次重复。

## Nova 案例参考

Nova(化名)把这套骨架落在 `.vibe-coding/` 目录下:`skills/` 存放操作手册、`memory/<module>/` 按业务
模块存放认知修正条目、`history/YYYY-MM/` 按月存放事件记录,项目自己的 `doc/` 目录存放规范性说明并被
一份生成的 `doc/README.md` 索引。四类产物的具体格式、生成流水线、写作纪律,分别在本模块接下来的四篇
文件里展开;第五篇 `artifact-routing.md` 讲的是"新内容该进哪一类"的决策流程,读完前四篇再看会更清楚
它们之间怎么互相配合。这是 Nova 在自己业务场景下的具体选择,新项目应该按自己的规模、团队习惯重新
决定目录名、拆分粒度、生成脚本的实现方式,但"元数据驱动的生成索引"这条骨架具有普遍适用性。
