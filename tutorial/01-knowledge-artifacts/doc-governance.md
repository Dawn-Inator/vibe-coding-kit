# Doc 治理:frontmatter 驱动的索引与硬约定

## 问题

一个项目积累到一定规模后,规范性说明文档(架构说明、领域规则、流程手册)会散落在 `doc/` 目录下
几十篇文件里。这时会出现两个典型问题:一是新人(不管是人类还是 AI)不知道从哪篇文档开始看,只能
翻文件名瞎猜;二是有一部分文档的内容不是"参考资料"而是"强制规则"——AI 在碰某个领域之前必须先读它,
否则大概率会做错(比如密钥处理规则、CI/CD 成本红线),但如果这类"必读文档"和普通参考文档混在一起、
没有任何标记,AI 很容易漏读。

## 设计原理(通用、可泛化)

Doc 治理要解决的本质是"发现性"(discoverability)和"强制性"(authority)两个独立的问题,而这套机制
用同一个手段——**每篇文档自己声明的元数据**——同时解决了两者:

- **发现性**:靠一份自动生成的索引,从所有文档的元数据里提取标题和摘要汇总而成,人和 AI 都能一眼
  看到全貌,不需要打开每个文件。
- **强制性**:靠元数据里一个专门的等级字段,把"仅供参考"和"必须先读"两类文档区分开,索引生成时
  自动分组,让"必读清单"始终保持独立、显眼、不被淹没在大量参考文档里。

这两件事都不需要人工维护一份中心化列表——都是从文档自身的元数据机械推导出来的,这正是
`README.md` 里提到的"索引是生成产物,真源分散在各文件自己的元数据里"这条核心哲学在 doc 场景下的
第三次落地(前两次分别是 skill 的自触发描述和 memory 的两份索引)。

## 可复用技术模式

### frontmatter 三字段驱动索引生成

每篇文档在自己的 YAML frontmatter 里声明:

```yaml
---
title: '文档标题'
description: '摘要,同时也是"什么场景该打开这篇文档"的触发条件'
authority: hard   # hard 表示强制先读;省略或其他值表示普通参考文档
---
```

生成脚本扫描 `doc/` 下所有文档的 frontmatter,产出一份索引文件,分两段:

- **硬约定段**(`authority: hard`):列出所有强制先读的文档,通常单独置顶或加粗标记。
- **其余文档段**:同样的 title/description 格式,按文件名排序,供按需查阅。

新增一篇文档只需要在文档自己顶部写好这三个字段,然后跑一次生成命令——**不允许手动编辑索引文件
本身**去添加新文档的条目,索引文件顶部会有生成器注释明确写着"运行 xxx 命令来更新;永远不要在这里
加一个原文档里没有的判断",防止索引和文档内容出现人工维护导致的不一致。

### `description` 字段身兼两职

这是这套机制里一个值得单独强调的巧思:`description` 字段既是给人看的摘要,**也是**"AI 判断当前
任务是否需要打开这篇文档"的触发条件。这意味着不需要额外维护一张"任务类型 → 该读哪篇文档"的路由表
——只要 `description` 写得足够精确(比如"改动密钥轮转流程之前必读",而不是笼统的"密钥相关文档"),
AI 在规划任务时就能靠语义匹配自己判断要不要打开它。这跟 skill 系统靠 `description` 自触发是同一套
思路在不同产物类型上的复用。

### authority: hard 的使用边界

不是所有"重要"的文档都该标 `authority: hard`——如果标记过于宽泛,"必读清单"会重新膨胀到失去筛选
意义。这个等级应该只留给"不读就会导致 AI 做出不可逆或高成本错误"的领域(比如涉及资金操作、密钥、
生产环境变更的规则),而普通的架构说明、模块介绍即使很重要,也应该留在"其余文档"段,依赖
`description` 的语义触发被按需读取,而不是全部升格为强制项。

## Nova 案例参考

Nova 的 `doc/README.md` 本身就是一份"生成的、非规范的投影",由 `pnpm docs:index`(化名的具体实现)
从每篇 `doc/*.md` 的 frontmatter 扫描生成,`authority: hard` 目前用在 CI/CD 规则、密钥治理等少数
几篇文档上。这是 Nova 按自己项目的实际风险点做的具体取舍;新项目应该重新盘点自己领域里"不读就会
出大问题"的文档有哪些,再决定哪些该标 `hard`——核心可复用的是"三字段驱动生成索引 + 硬约定单独分组"
这套机制,不是 Nova 具体标记了哪几篇文档。
