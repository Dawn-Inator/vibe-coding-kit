# Skill 系统:自触发的操作手册

## 问题

规程类知识("怎么部署""怎么改数据库 schema""怎么处理密钥")如果写进每轮都注入的核心规则文件,
文件会迅速膨胀到无法维护;但如果只写在某个人才知道位置的文档里,AI 大概率想不起来在做相关任务前
去翻它。需要一种机制,让"任务相关的操作手册"能在**恰好需要它的那一刻**被 AI 自己找到并加载,既不
占用平时的上下文,又不依赖 AI 主动记得去查。

## 设计原理(通用、可泛化)

Skill 的核心设计是**自触发**:每个 skill 自带一段"什么情况下应该打开我"的描述,AI 框架在决定下一步
动作前,会用任务的自然语言描述去匹配所有 skill 的触发描述,匹配上的才加载进上下文。这把"路由"的
责任从"人工维护一张全局路由表"转移到"每个 skill 自己声明触发条件",带来两个好处:

- **可扩展性**:新增一个 skill 不需要修改任何中心文件,只要这个 skill 自己的触发描述写得准确。
- **按需加载**:没被触发的 skill 完全不占上下文,一个项目可以积累几十个 skill 而不拖慢每轮响应。

但自触发不是万能的——对于"做 X 之前必须先做 Y"这种强制关系,单靠"寄希望于描述匹配"不够可靠,
所以项目通常还会在每轮必注入的规则文件里放一张**兜底路由表**("做 X 之前先读 Y"),作为自触发失败
时的最后一道保险,而不是取代自触发。

## 可复用技术模式

### 1. 单一真源 + 多份生成投影

不同的 AI 工具(不同厂商的 CLI、不同编辑器插件)可能约定了不同的技能文件位置和格式差异
(比如某个字段只有特定工具认识)。与其为每个工具手写一份技能文件、后续改动时四处同步,不如只维护
**一份真源**,其余全部标记为生成产物、禁止手改:

```
<skills源目录>/<name>/SKILL.md        ← 真源
<工具A的技能目录>/<name>/SKILL.md      ← 恒等复制,但剥掉工具A专属 frontmatter 字段
<工具B的技能目录>/<name>/SKILL.md      ← 文本替换转换(比如把工具A的产物文件名换成工具B的)
<项目根>/AGENTS.md                    ← 恒等复制自核心规则源文件
<项目根>/CLAUDE.md                    ← 同样做文本替换转换
```

每个生成文件顶部固定写一行"GENERATED FILE - DO NOT EDIT / 改完源文件后请跑 xxx:sync"的注释头,
防止有人直接手改生成文件导致下次同步时改动被覆盖丢失。

**做文本替换转换时的一个坑**:如果替换规则是"把字符串 A 换成字符串 B",要注意"A 和 B 两个词恰好连续
出现在同一句话里"的边界情况——朴素的全局替换可能把已经是 B 的地方也误伤,或者把 "A...B" 整段替换
成两份 B。写转换脚本时要单独测试这种边界。

### 2. 平台条件内容标记

同一份 SKILL.md 源文件,内容可能只对某一个 AI 工具有意义(比如某工具专属的定时任务能力、另一工具
专属的私有消息通道规则)。用注释标记包裹这部分内容:

```markdown
<!-- BEGIN: claude-only -->
(只有工具 A 关心的内容,比如它专属的某个能力说明)
<!-- END: claude-only -->

<!-- BEGIN: agent-only -->
(只有工具 B 关心的内容)
<!-- END: agent-only -->
```

生成脚本为每个目标产物渲染时,只保留匹配当前平台的标记内容,丢弃其余标记块(以及标记本身)。这样
一份源文件就能同时服务多个 AI 工具,不需要维护多份几乎相同、只有局部差异的文件。

### 3. sync / check 两件套

- `sync`:先删除所有不在"预期产物列表"里的过期生成文件(避免残留已废弃 skill 的旧投影),再重新
  写入每个预期产物的内容和文件权限。
- `check`:计算同一份"预期产物集合"跟磁盘上实际内容做 diff(内容 + 权限两个维度),报告
  missing / changed / mode / extra 四类差异,有差异就非零退出——可以接进 CI 或提交前钩子,防止真源
  改了但忘记跑 sync。

### 4. 反向入库(逆向治理第三方技能)

如果生态里存在第三方脚手架命令,能直接把一个技能安装到某个工具的技能目录(绕过你的真源),会造成
"游离在治理体系外"的技能——没有真源、sync 时会被当成 extra 文件删除。解决办法是提供一个"逆向"命令:
读取被第三方工具直接安装的技能,对已知的正向转换规则做**逆变换**,把它规范化写回真源目录,再跑一次
正向 sync 让它重新纳入统一管理。这样无论技能是自己写的还是第三方装的,最终都收敛到同一套治理流程。

### 5. 项目 → 模板的反向回哺

前面三条讲的都是"单一真源 + 生成投影"这套骨架在**同一个仓库内部**的同步。但如果这个项目本身是从
一个独立的模板仓库(脚手架/starter kit)启动的,还存在另一条容易被忽略的同步关系:**项目自己在
实践中改进的 skill/规则,要不要、以及怎么回推给上游模板**。这条关系的方向和"从模板拉取更新到项目"
正好相反,但重要性是对称的——如果只单向从模板往项目同步,项目自己踩坑之后固化下来的改进(修好的
gap、新增的硬规则、纠正过的默认值)就只活在这一个项目里,模板仍然带着同样的坑,下一个从模板启动
的新项目会重新踩一遍。

这条同步关系不需要额外发明新机制,复用的是同一套"改真源、不改生成投影"的纪律,只是把"真源"和
"投影"的角色在两个仓库之间对调了一次:项目里手改的 skill/`loading.md` 源文件是这一轮改动的真源,
模板仓库里对应的文件是需要跟进的投影——但模板文件不能被整份复制过去覆盖,因为模板文件通常还留有
项目特有内容需要在合并时剥离(具体项目的名字、路径、域名),而且模板可能已经有其它项目回推过的、
项目这边还没见过的改动,整份覆盖会把那些改动一起冲掉。安全的做法是**按段落合并**:只把这次新增/
修改的具体段落原样搬过去,项目专属的具体名字换成占位符或者"示例值",硬性要求(比如"必须显式指定
一个数字")保留,但把具体数字改成"参考值,按自己项目实际情况调整"的措辞。

**触发时机**:这条检查应该跟"改 skill / `loading.md` / 治理类文档"这个动作绑在一起,而不是等到
专门想起来才做一次批量补齐——写完一次改动的当下,顺手判断一句"这条改动是不是这个项目独有的事实,
还是换一个项目也成立的通用规则/模式",通用的部分就在同一批改动里一起回推,不通用的就不用管。

### 6. Skill 分包:入口 + 按需读取

自触发有一个隐含成本:Claude Code、Codex 这类工具每轮都会把**所有**已安装 skill 的 name + description
注入一份"技能清单",而这份清单有很小的上下文预算(Claude Code 约为上下文的 1%)。超出预算后,工具会从
最少用的 skill 开始砍 description——被砍的往往正是你最想让它被触发的核心工程 skill。一个领域专用的
大组 skill(例如某个厂商 CLI 配套的十几个子 skill、一整套视频制作工具链)只在特定任务才用,却天天占着
清单预算,是最典型的诱因。

两家工具都没有原生的"子 skill"概念,只支持 skill 里按需读附属文件,所以解法是**分包**:

- **何时分包**:同一领域、成组(约 10 个以上)、只在特定任务才用、日常工程不需要直接触发。其它 skill
  不分包——分包是清单预算的应急阀,不是目录整理工具。
- **注册表是唯一真源**:`skill-packs.mjs` 里每个包登记 `id` / `entry`(入口 skill)/ `members`(成员)/
  `memberPrefix`(可选的命名前缀)。`memberPrefix` 是 fail closed 的关键:源目录里出现带该前缀却没登记的
  skill 时 `check` 直接失败,第三方安装器新装的上游 skill 因此永远不会悄悄混进每轮清单。
- **源不动,只改镜像位置**:源仍是扁平的 `.vibe-coding/skills/<name>/`。sync 把成员镜像到
  `<工具目录>/skill-packs/<name>/`(不被工具扫描,所以不进清单),入口留在 `<工具目录>/skills/<entry>/`。
- **入口 description 写宽**:覆盖整个领域的各种说法,AI 命中入口之后才去读成员。sync 自动往入口镜像
  追加一张"本包子 skill"索引表,往每个成员镜像追加回指入口的页脚,并重算跨 `skills/` ↔ `skill-packs/`
  的相对链接(同类链接保持逐字节不变,代码围栏里的链接不改)。
- **成员不能再被 Skill 工具直接调用**:AI 只用 Read 读当前任务需要的那一个成员,不要整包读;成员正文里
  写"走 xxx skill"时同样指读对应路径。
- **反向入库照旧**:安装器仍把上游 skill 写成扁平的 `skills/<name>`;`vendor` 优先取扁平副本、没有时
  才取 `skill-packs/<name>`,并剥离生成的索引 / 页脚、还原链接,sync 再把它挪回 `skill-packs/`。

没有登记任何包时 `sync` / `check` / `vendor` 的行为和没有这个机制时完全一致。

## Nova 案例参考

Nova 的真源是 `.vibe-coding/skills/**` 和 `.vibe-coding/loading.md`,生成投影包括
`.agents/skills/`、`.claude/skills/`、仓库根的 `AGENTS.md` 和 `CLAUDE.md`。`claude-only` /
`agent-only` 标记用来处理两个具体 AI 工具之间的能力差异(比如其中一个工具有原生定时唤醒能力、
另一个没有,相关说明只应该出现在有该能力的工具的产物里)。这是 Nova 当前接入的两个具体工具的
选择;新项目要接入哪些 AI 工具、需要几套投影、平台标记要分几类,都应该按自己实际用到的工具集
重新决定——核心可复用的是"单一真源 + 生成投影 + sync/check 双命令"这套骨架,不是具体的工具名单。
