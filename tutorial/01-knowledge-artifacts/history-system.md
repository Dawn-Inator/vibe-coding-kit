# History 系统:叙述事件的追加式记录

## 问题

有些知识不是"一个会被反复修正的判断",而是"一件具体发生过的事情"——一次事故、一次架构改动、一次
排查过程。如果把这类内容也塞进 memory 那种"原地编辑更新"的产物里,会出现两个问题:一是事件的细节
(时间点、当时用的哪个 commit、当时收集到的哪些证据)会在反复编辑中被简化甚至丢失;二是"这件事发生
过"这个事实本身不应该被后来的理解修正掉——它是历史,不是活文档。需要一种**只增不改**的记录形式,
专门承载"叙述一次具体事件"这类知识。

## 设计原理(通用、可泛化)

History 和 memory 的分界是这个知识产物体系里最容易混淆、但也最值得讲清楚的一条线:

| | Memory | History |
| --- | --- | --- |
| 记录的是 | 一个**判断**("这件事该怎么想是对的") | 一个**事件**("这件事发生过,经过是这样") |
| 生命周期 | 可编辑,过时后原地标记 superseded | 永远新开一条带日期的记录,不回改旧记录 |
| 检索方式 | 按"会想错的场景"匹配 | 按时间顺序 + 分类浏览 |
| 典型触发词 | "以后遇到 X 场景要记得 Y" | "上个月发生了一次 Z 事故,修复经过是..." |

这个区分背后是一个更通用的原则:**判断需要保鲜(否则误导未来),事件需要保真(否则丢失还原能力)**。
一个系统如果只有 memory 没有 history,会倾向于把每次事故都简化压缩成一条"教训",丢失了具体的
排查路径和证据链,导致同类问题再次出现时无法复用上次的排查方法;反过来只有 history 没有 memory,
则会让"该怎么做"这类判断散落在大量事件记录里,每次都要翻旧记录才能找到当前答案。

## 可复用技术模式

### 目录布局:按月分区 + 自动生成月度索引

```
history/
├── README.md
└── YYYY-MM/
    ├── index.md          # 自动生成:表格(日期/条目/分类/范围/状态/摘要)
    └── DD-简短slug.md     # 具体条目
```

按月分区的好处是天然限制了单个索引文件的大小(不会像"全部事件放一个大列表"那样无限增长),而且
"最近发生的事"和"历史存档"能靠目录名快速区分优先级。

### Frontmatter 契约

```yaml
---
title: '简短标题'
date: 'YYYY-MM-DD'
author: 'codex | claude | 人类名字'
purpose: '为什么要写这条'
category: 'architecture | workflow | release | operations | security | data | ui | ai-collaboration | other'
scope:
  - '仓库路径或领域'
status: 'active | superseded | archived'
related_files:
  - '仓库内路径'   # 必须真实存在且被 git 跟踪,由校验脚本强制
redaction: 'none | redacted | safe-placeholders'
---
```

`related_files` 要求指向真实存在、被版本控制跟踪的路径,并由脚本强制校验——这避免了历史记录里出现
"引用了一个早就被删除或改名的文件"这种悬空指针,保证事件记录和代码库当前状态之间至少有一条可核实
的链接。

### 正文固定四段式,顺序不可变

```markdown
## Summary
问题现象是什么

## Changed
具体改了什么(每个 commit 带 SHA 和理由)

## Verification
怎么验证的(设备日志、截图、测试输出等具体证据)

## Follow-up
还没解决的遗留项,以及未来会话必须知道的结构性约束
```

这四段式结构是 history 区别于 memory 最直观的标志——**memory 的写作规范明确禁止使用这种四段式**,
这是两种产物在格式层面刻意做出的区分,防止写作时把两种产物的内容写混。一个真实结构的例子:某条
history 记录了两起叠加的运维事故,`Summary` 描述现象("A 服务和 B 服务先后出现了两个相关但不同的
故障"),`Changed` 按时间顺序列出每次修复用的 commit(SHA + 为什么这么修),`Verification` 列出
真实验证证据(设备日志摘录、关键截图路径),`Follow-up` 写清哪些结构性问题还没根治、下一个处理这块
代码的会话需要提前知道什么。

## Nova 案例参考

Nova 用 `.vibe-coding/history/YYYY-MM/DD-slug.md` 的布局,`category` 取值覆盖了架构、发布、运维、
安全、数据、UI、AI 协作等 Nova 业务里实际出现过的事件类型。这套 category 分类是 Nova 按自己项目
历史上真实发生过的事件类型总结出来的,新项目不需要照搬这份分类清单,应该等自己积累几次真实事件后
再回头总结出适合自己项目的分类维度——核心可复用的是"月度目录 + 四段式正文 + 只增不改"这套骨架,
不是具体的 category 枚举值。
