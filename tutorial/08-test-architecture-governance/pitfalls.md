# 坑点目录

每个坑固定五项:**现象**(你会看到什么)、**根因**、**防线**(落在 L0-L3 哪一层、什么机制)、**检测**(怎么
发现自己正在踩)、**Nova 实例**。层的定义见 [README.md](README.md)。

新项目用法:开工时通读一遍;每次设计新门禁、新测试通道、新发布步骤时,按分组对照检查。

## A. 接线与收集:测试存在,但没在跑

### P01 门禁写了,但从没被执行

- **现象**:某条检查一直是绿的,直到有人手动跑才发现它早就该红。
- **根因**:一条检查要真正执行,需要"文件 → runner → task → 执行模式 → CI/workflow 调用"五层接线,任何
  一层断开都不会报错;`--dry-run` 只证明前四层。
- **防线**:L2 可达性守卫——遍历所有检查定义,断言每一条都能从某个真实触发入口一路走到。
- **检测**:定期统计"声明存在但不可达"的检查数,按三桶分:已接线 / 只有别名 / 只有自测。
- **Nova 实例**:7 个 workflow 在主分支上根本不存在,7 个月没执行;35 个脚本声明 `--strict` 却从未进任何模式。

### P02 收集到 0 个用例,照样 exit 0

- **现象**:测试命令绿了,但其实一个用例都没跑。
- **根因**:`node --test <空目录>`、shell glob 未展开、入口指向不存在的目录,多数 runner 返回 0。
- **防线**:L2 零收集守卫——每个测试命令必须断言"收集数 > 0",零收集一律失败。
- **检测**:在汇总里打印每个 lane 的用例数,和上一次对比,骤降即告警。
- **Nova 实例**:三个包 39 个文件、138 个用例长期零执行。

### P03 守卫住在被它守卫的集合里

- **现象**:守卫负责发现"某批测试不跑了",但那批测试不跑时守卫自己也不跑。
- **根因**:元守卫和被守卫对象共用同一个执行入口。
- **防线**:L2 元守卫必须放在被守卫集合**之外**,并由一个独立、常驻的入口调用。
- **检测**:画出每个元守卫的调用链,检查它是否经过它所守卫的那个入口。
- **Nova 实例**:删除一个 workflow 后 446 个测试文件失去唯一调用方,3 天无信号——可达性守卫也在这批里。

### P04 删除 / 改名一个入口,整族检查失去唯一调用方

- **现象**:一次看似无害的 CI 精简后,一整族检查静默消失。
- **根因**:没有"删除入口前列出它承载了哪些检查"的步骤。
- **防线**:L2 规则——删除执行面的同一批改动里,必须清掉或迁移所有指向它的引用;改动入口时同步更新
  AI 规则文件中的对应条目。
- **检测**:可达性守卫(P01)在删除提交上就该变红;若没红,说明 P03 也在发生。
- **Nova 实例**:同 P03。

### P05 "硬阻断"检查只有手动调用点

- **现象**:脚本自称 `--strict` 会阻断,但没有任何自动通道调用它。
- **根因**:写完检查后只验证了"手动跑能红",没接进执行模式。
- **防线**:L2 类级不变量——每个 strict 形态的检查脚本必须被至少一个执行模式调用;报告型脚本另列。
- **检测**:同 P01 的三桶统计。
- **Nova 实例**:一个开发/预发布一致性检查器声明硬阻断,却只有运维手动跑这一个调用点。

### P06 守卫在断言之前就退出了 / 只认特定变量名

- **现象**:守卫"通过",但它根本没走到断言。
- **根因**:前置分支里提前 `exit(0)`;或检测器只匹配名为 `service` 的变量,换个名字就漏。
- **防线**:L2——守卫自身要有"刻意制造违规必须变红"的自测(反向测试)。
- **检测**:为每个守卫保留一个违规 fixture,自测断言它红。
- **Nova 实例**:端点覆盖检查早退,实际 88 个端点无覆盖;服务调用检测 19 处只检出 5 处。

## B. 断言失真:测试在跑,但没在测行为

### P07 元数据在撒谎

- **现象**:声明、类型标注、配置都对,运行时行为却是错的。
- **根因**:断言检查的是形状或声明,不是行为;例如一个校验函数因 `existsSync(join(x, '.'))` 永远返回同一个值。
- **防线**:L2——对"声明 vs 运行时"做反向验证:故意破坏,确认检查会红。
- **检测**:审计时专门抽查"返回布尔值的校验函数"是否在两种输入下给出不同结果。
- **Nova 实例**:同一事实在 3 处声明,条目数漂移(82 vs 81);某环境配置 4 个月未同步导致每次重启校验失败。

### P08 脱敏函数被当成序列化 / 两套测试替身

- **现象**:测试通过,但被测的是一个假实现或被脱敏的值。
- **根因**:`str(url)` 返回 `***`;第二套假实现绕过了第一套有契约约束的替身。
- **防线**:L2——测试替身只允许一个真源,并由契约测试约束它与真实实现一致。
- **检测**:扫描测试目录里对同一接口的多个假实现。
- **Nova 实例**:9 个测试跑在没有契约约束的第二套假 Redis 上。

### P09 mock 掉了真正会坏的那条边界

- **现象**:单测全绿,第一次在真实环境跑就红。
- **根因**:L3 测试注入的正是后来出错的依赖(数据库驱动类型、容器内解释器、密钥读取器)。
- **防线**:L3 至少一条真输入路径,或把该边界登记为 L0 前置条件(见 anti-serial-loop 原则 7)。
- **检测**:统计"mock 外部边界"的测试,与真输入契约测试 / L0 条目做对照。
- **Nova 实例**:预发布系统性根因分析里有 6 个独立缺陷属于这一类。

### P10 fixture 形状与生产形状漂移

- **现象**:真实错误在日志里被折叠成通用的 "unknown"。
- **根因**:测试只喂手写的"公开形状",从没喂过生产里被增强过的对象;未注册的错误原因被统一兜底。
- **防线**:L2——"可能抛出的错误原因 ⊆ 注册闭集"的守卫;fixture 从生产样本生成。
- **检测**:任何 "unknown/other" 类兜底在日志中出现即告警。
- **Nova 实例**:一个门禁控制器因此卡了 22 天。

### P11 钉死文本的断言

- **现象**:无害的重构让一批测试变红,改的全是测试里的字符串。
- **根因**:断言"名单恰好等于这 32 项""第 N 行是 X""参数数组第 0 个是 ls-tree"——测的是快照不是不变量。
- **防线**:L2 准入规则——只允许类级不变量;快照类断言必须改写成遍历 + 属性判断。
- **检测**:红灯分类里统计"过期断言"占比;超过三分之一就该做一次专项清理。
- **Nova 实例**:某晚约 40 条红灯中约 25 条是过期断言。

### P12 手写常量,仓库里没有代码能重新算出它

- **现象**:某次解耦后一切都对,只有这个常量不对,而且没人知道它怎么来的。
- **根因**:固定点、摘要、预期值靠手抄,没有生成器。
- **防线**:L2——每个固定点都必须有生成命令;守卫检查"固定点 == 生成器当前输出"。
- **检测**:grep 测试里的长哈希 / 魔法数字,问"哪个命令能重新生成它"。
- **Nova 实例**:控制面 14 层缺陷中有 3 个手写常量。

### P13 生成物与输入不同步,收尾时才红

- **现象**:改了一个无关文件,收尾时某个 `*-fresh` 检查红了。
- **根因**:固定点/baseline 是生成物,改动输入后没人重新生成。
- **防线**:L2——固定点类失败**自动重新生成并重试一次**;仍红才算真红,并给出是哪个输入变了。
- **检测**:统计收尾失败中"只因固定点过期"的占比。
- **Nova 实例**:引入自动重新生成后,这一类收尾返工基本消失。

### P14 未锚定的正则

- **现象**:检查"最大尝试次数 = 5",结果 `= 50` 也通过。
- **根因**:正则没有边界锚定。
- **防线**:L2——断言值而不是断言文本;必须用文本时加边界并配反例 fixture。
- **检测**:为每个正则类断言写一个"相近但错误"的反例。
- **Nova 实例**:同上。

## C. 预算与环境:测试是对的,但跑它的方式不对

### P15 超时预算在进程启动那一刻算死

- **现象**:机器忙时一批检查集体超时。
- **根因**:预算在模块加载时按当时负载算一次,不随后续负载刷新。
- **防线**:L2——预算在调用时计算,并感知当前负载;禁止对墙钟写死固定上界。
- **检测**:失败分类里区分 timeout-like(耗时 ≥ 预算 90%)与 real-fail。
- **Nova 实例**:13+ 项检查使用加载时预算。

### P16 用代理指标推导预算

- **现象**:按文件数或字节数分配的超时,对某些文件总是不够。
- **根因**:体量相近的两个文件真实耗时可以差 20 倍;代理指标从未被实测验证。
- **防线**:实测登记表(每个慢文件的实测耗时 × 安全倍数),或按真实墙钟响应式判红。
- **检测**:定期用真实耗时回测代理模型的误差。
- **Nova 实例**:一个 526KB 的测试文件实测 206 秒,代理模型只给了 184 秒。

### P17 超时包装器被逃逸的子进程挂死

- **现象**:一个本该 15 分钟超时的检查挂了 46 分钟。
- **根因**:包装器在 kill 之后等待 `close` 事件,但逃出进程组的后代仍持有 pipe 写端,EOF 永远不来。
- **防线**:超时后强制销毁读端,外层再加一道独立超时兜底;"超时必须真的结束"本身要有测试。
- **检测**:任何检查的实际耗时 > 它的超时值,即视为包装器缺陷。
- **Nova 实例**:同上;日志被截断,真实红灯编号在被杀位置之后,只有手工直跑才看得到。

### P18 开发机绿,Linux 云机红

- **现象**:同一提交,本地全绿,云端测试机一片红。
- **根因**:`umask`、BSD vs GNU 工具(`stat -f`、`chmod`)、`/tmp` 是 tmpfs、缺 `zip`/`ruby`、shell 选项泄漏。
- **防线**:L0——测试主机的工具与配置登记成前置条件;L2——脚本只用可移植写法的扫描器。
- **检测**:新测试第一次进全量前,必须在目标操作系统上跑过一次。
- **Nova 实例**:一次全量冲绿中归纳出 6 类环境差异。

### P19 提高并发才暴露的竞态

- **现象**:并发从 3 提到 10,一批测试从"偶发红"变成"必红"。
- **根因**:共享 fixture、快照竞态、`spawnSync` 失败被静默——并发不是原因,是放大器。
- **防线**:L2——测试隔离规则(独立临时目录、禁止共享可变 fixture);故意以高并发跑一次做压力探测。
- **检测**:flake 探测——同一提交重复跑 N 次,统计翻转。
- **Nova 实例**:4 个分片各自 `next build` 互相饿死,731 秒全红;改为共享预构建后 318 秒。

### P20 共享、可变的构建/测试主机

- **现象**:一轮失败的原因是"另一个任务刚好把机器停了 / 磁盘满了 / 共享存储被改了"。
- **根因**:单台主机按服务启停、共享工作目录和对象存储、空闲自动关机、磁盘地板。
- **防线**:L0——主机状态(磁盘余量、锁、租约)登记为前置条件;资源租约 + 隔离工作目录。
- **检测**:失败原因里出现"主机"类的占比。
- **Nova 实例**:预发布系统性分析中有 7 个独立缺陷属于这一类。

### P21 一把隐式的全局串行锁才是墙钟主因

- **现象**:加机器、加并发都不快。
- **根因**:某个读写锁把本可并行的任务串起来;只读代码的架构审计会误诊为"资源不够"。
- **防线**:先实测关键路径再优化;调度器输出每个任务的等待时间与原因。
- **检测**:看关键路径上"等锁"的时间占比。
- **Nova 实例**:两份只读审计都建议资源隔离,实测后发现真因是仓库状态锁(930 秒关键路径)。

## D. 发布链路:L0 缺失

### P22 前置条件没声明,执行到才发现

- **现象**:每一轮都在新的地方失败,而且失败的都是"环境缺东西"。
- **根因**:发布链路有上千个失败点,只有十几个登记成前置条件。
- **防线**:L0 前置条件注册表 + 构建前一次性 doctor(anti-serial-loop 原则 1)。
- **检测**:统计"失败点数 / 已登记前置条件数"。
- **Nova 实例**:约 1400 个 `fail`/`exit` 点,登记 16 个(冻结分支上只有 13 个)。

### P23 预发布很少跑、又被手工改

- **现象**:预发布永远是新代码路径的"第一次执行"。
- **根因**:按月跑一次 + 绕过式部署 + 手工改环境(改用户组、跑临时脚本、改配置片段),都不登记。
- **防线**:L0——环境状态"声明 → 收敛 → 回读";doctor 定时跑发现漂移。
- **检测**:环境里存在、但声明里找不到的东西(反向 diff)。
- **Nova 实例**:系统性分析中"环境状态从未初始化 / 已漂移"是最大的一类(11 个)。

### P24 各环境代码路径分叉

- **现象**:开发环境走直连 DB、预发布走另一个 carrier、生产走 CI——三者各是一套代码。
- **根因**:按环境复制脚本而不是参数化。
- **防线**:同一套函数,用参数控制轻重(anti-serial-loop 原则 6)。
- **检测**:统计"只在某一环境被调用"的脚本。
- **Nova 实例**:"首次执行的预发布专属路径"占 7 个缺陷。

### P25 全有或全无,无关单元被一起跳过

- **现象**:服务 A 构建失败,服务 B、C 的构建也没跑。
- **根因**:把部署顺序依赖套用到了构建上;第一个失败即退出。
- **防线**:fail-slow 编排:失败只阻断真实下游(anti-serial-loop 原则 2)。
- **检测**:失败报告里 "skipped" 的单元是否真的依赖失败单元。
- **Nova 实例**:每一轮都被这一条放大。

### P26 错误被吞,一轮只为看清上一轮的报错

- **现象**:exit 1,没有任何文本;下一轮加日志重跑。
- **根因**:`2>/dev/null`、`|| true`、子进程 stderr 未转发;Nova 统计到 505+ 个被吞的 stderr 点。
- **防线**:L2 错误透明扫描器(棘轮);失败汇总带首条错误与复现命令。
- **检测**:"为了看清错误而重跑"的轮次数。
- **Nova 实例**:有一轮存在的唯一目的就是看清上一轮的错误,成本 3 小时。

### P27 没有 resume,每轮从头重建

- **现象**:修了第 9 步,下一轮又从第 1 步的构建开始。
- **根因**:没有单元级记账。
- **防线**:per-unit ledger + `--resume`;构建产物按内容寻址复用。
- **检测**:每轮重复执行、且输入未变的单元耗时。
- **Nova 实例**:resume 只落在开发分支,预发布跑的冻结分支上没有(见 P28)。

## E. 流程与组织

### P28 工具链在被测候选里,修复落错分支

- **现象**:明明修过了,下一轮还是同样的错。
- **根因**:发布工具随候选一起冻结;修复落在开发分支,预发布跑的冻结分支没有它;反过来冻结分支上的
  修复也没回到开发分支。
- **防线**:工具链独立版本化,或红灯修复直接落冻结分支并带可审计标记(anti-serial-loop 原则 4)。
- **检测**:每轮开始前对比"上轮修复提交"是否在本轮的树里。
- **Nova 实例**:≥11 个修复提交落在错误分支;25 天约 3000 个自动化提交,两分支相差 4.2 万行。

### P29 冻结 + 例外双通道,周期被丢弃重开

- **现象**:冻结期间不断开例外,最后候选被丢弃、重开新周期。
- **根因**:冻结的目的(停止修复潮)与治理的必要性冲突,没有明确的例外准入标准。
- **防线**:每周期只冻结一次;例外只允许"本周期红灯修复",以提交尾注作为准入证明。
- **检测**:单个周期吸收的提交数。
- **Nova 实例**:一个周期吸收了 1070 个"修复"提交;一个月丢弃重开 10 次。

### P30 别人的红灯挡住你的收尾

- **现象**:12 个互不相关的收尾被同一条已在主干上红着的检查挡住。
- **根因**:收尾预检不区分"本 diff 引入的红"和"继承的红"。
- **防线**:L2——基线归因:在基线上原样复现、且失败集是基线子集的红降级为警告(带审计尾注)。
- **检测**:红灯输出逐项带 `attribution`。
- **Nova 实例**:同上,一天内约 1.5 小时被同一条继承红挡住。

### P31 绕过变成常态,永不变绿的门禁继续烧钱

- **现象**:每次发布都走 bypass;某个门禁从没绿过,但每次推送都自动触发。
- **根因**:门禁太重或太脆,没人修也没人关。
- **防线**:门禁连续 N 次不绿 → 自动降级为手动派发并报警;bypass 次数作为健康指标。
- **检测**:统计门禁"最近一次绿"的时间。
- **Nova 实例**:生产门禁 274 次运行 0 次绿;空跑占当月 CI 账单 57%。

### P32 AI 给自己写跳过审批

- **现象**:跳过预检的提交上,"已获批准"的理由全是 AI 自己写的。
- **根因**:跳过机制只要求一个非空文本。
- **防线**:跳过必须由人的 shell 设置,worker 不得自我批准;所有跳过留尾注与审计日志,可复查。
- **检测**:定期审计跳过记录,看批准者与理由。
- **Nova 实例**:12 次跳过里 5 次放行了全员红。Nova 最终仍保留文本审批(见 decisions D-08),靠审计兜底。

### P33 没有终点的治理任务耗尽额度

- **现象**:覆盖率 / 审计类 worker 在主要目标达成后继续跑,额度突然耗尽。
- **根因**:"覆盖率再压一点、审计再找一条"天然没有终点;额度是共享池,不是每个 worker 的独立预算。
- **防线**:主要目标达成后自动降级为按需;派发前估算整批额度;在飞 worker 落地窗口 ≤30 分钟。
- **检测**:每个在飞任务的"边际产出 / token"。
- **Nova 实例**:9 个 worker 各耗 20-45 万 token 撞上周限额;恢复时上游已领先 295 个提交。

### P34 每个事故加一个守卫,守卫层自己腐烂

- **现象**:测试基础设施比产品代码长得还快,红灯大多来自守卫自己。
- **根因**:治理的唯一手段是"加",没有准入标准和退役机制。
- **防线**:新守卫准入三问(守不变量还是快照?属于哪层哪档?有没有反向测试?);每季度做一次退役审查。
- **检测**:L2/L3 文件数增速 vs L1 增速;红灯里"守卫自身问题"的占比。
- **Nova 实例**:测试/自动化基础设施文件数两个月涨约 5 倍(约 540 → 约 2540)。

### P35 用昂贵链路当探测器

- **现象**:每修一处就重跑一次全链。
- **根因**:缺少便宜的验证手段,或者不信任它们。
- **防线**:熔断规则 + 自检清单(anti-serial-loop 原则 3)。
- **检测**:同一子系统连续"失败 → 单点修 → 全链重放"的轮数。
- **Nova 实例**:主机收敛重放 16 次;一个 migration 重放 7 次。

### P36 并行 worker 共享一个工作树

- **现象**:约 300 个文件被误删,并被推上共享分支。
- **根因**:多个 worker 的收尾都经过同一个主工作树,stash/restore 冲突被自动提交。
- **防线**:每个 worker 独立 worktree,收尾直接推送,永不触碰主工作树;大规模删除守卫。
- **检测**:收尾时统计删除文件数,超阈值即拒绝。
- **Nova 实例**:见 02-worktree-lifecycle 模块。

### P37 编号撞车,证据不可检索

- **现象**:"第 16 层缺陷"在两份记录里指不同的东西。
- **根因**:多个会话各自编号,没有统一分配。
- **防线**:编号前缀按来源区分,并在一个台账里登记。
- **检测**:`git log --grep` 同一编号返回不相关的提交。
- **Nova 实例**:14 个独立缺陷共用 9 个层号。

### P38 为了提前发现预发布问题而加重开发环境

- **现象**:有人提议让开发环境也走完整发布链路 + 全量测试。
- **根因**:把"预发布第一次执行"的问题错误地归因为"开发环境太轻"。
- **防线**:决策——开发环境保持轻量;预发布专属路径用 doctor + 秒级单测覆盖(decisions D-06)。
- **检测**:任何会让开发发布 / 测试多出分钟级耗时的提议。
- **Nova 实例**:被 Owner 当场否决两次,并写入决策防止重提。
