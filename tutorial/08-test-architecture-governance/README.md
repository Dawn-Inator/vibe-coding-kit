# 08 Test Architecture Governance:自动化测试的分层、腐烂与"测一次修一次"

AI agent 写测试很快,写门禁也很快——快到测试体系本身会变成项目里增长最快、腐烂最快的那部分代码。
这一节讲 Nova 用两个月(约 1.4 万个提交,其中约 1.1 万个与测试/门禁相关)治理测试架构腐烂的过程、
为什么拖了那么久,以及从中抽出的分层模型和防串行链路方法。

## 一、问题

最初的直觉是"测试越多越安全"。实际发生的是:

- 大量测试**绿得没有意义**——没接进任何执行通道、收集到 0 个用例照样 exit 0、守卫在断言之前就退出了。
- 发现这些问题后,每次事故都补一道"防腐守卫",守卫本身又带来新的 baseline、固定点和钉死文本的断言,
  这些东西后来成了**假红的主要来源**。
- 预发布环境的发布链路每跑一轮(约 1.5 小时)只能暴露**下一个**缺口,一个月里没有完成过一次端到端发布。

一句话:测试体系没有分层的概念,所有问题都被当成"再加一个测试/守卫"来解决。

## 二、四层模型(按"守什么"分)

| 层 | 守什么 | 典型形态 | 失效时的样子 |
| --- | --- | --- | --- |
| **L0 前置条件层** | 真实环境是否具备执行条件:主机工具、权限、密钥条目、DB migration 状态、反代配置、账号 | 一份声明式前置条件清单 + 一次性跑完的 doctor | 执行到第 N 步才撞墙,一轮只暴露一个缺口 |
| **L1 业务测试** | 产品行为对不对 | 单元 / 集成 / E2E | 产品 bug 漏到线上 |
| **L2 防腐测试** | L1 还有没有意义:有没有被执行、收集是不是空、断言是不是在测行为、生成物是否与输入同步 | 接线可达性守卫、零收集守卫、固定点新鲜度检查 | 绿得没意义;或者自己变成假红源 |
| **L3 工具链自测** | 部署、远端测试、发布脚本这些"工程代码"本身对不对 | 对脚本的单元测试 | mock 掉了真实出错的边界,单测绿、首次真跑红 |

Nova 的实际比例(治理结束时):L1 约 2600 个测试文件;L2 约 300 个;L3 约 800 个;**L0 在治理高峰期几乎
为零**——发布链路里有约 1400 个 `fail`/`exit` 点,事先登记的前置检查只有 16 个。系统性根因分析之后 Nova
才补建了 doctor(几十个检查 + "每个失败点必须标注由哪个检查覆盖"的棘轮),此后预发布才第一次走通。

三个关键判断:

1. **串行链路发生在 L0 和 L3 的接缝处**,L2 加多少都拦不住。环境缺什么只能执行到那一步才知道(L0 缺失),
   而 L3 的测试恰好 mock 掉了那条边界。
2. **L2 是最容易自己腐烂的一层。** Nova 某晚核实约 40 条红灯:约 25 条是 L2 的过期断言,约 6 条是主机
   环境假设,只有约 6 条是真缺陷。L2 必须有准入规则(见 [decisions.md](decisions.md) D-03)。
3. **L1 不是这场治理的主角。** 两个月里 L1 发现的产品 bug 屈指可数,几乎所有成本都花在 L0/L2/L3。

## 三、第二条轴(按"什么时候、在哪跑"分)

分层回答"守什么",还有一条正交的轴回答"什么时候跑、在哪跑"。两条轴混在一起说是后来很多误解的来源
——Nova 仓库里曾有一份叫"两层防护"的文档,讲的其实是第二条轴:

| 档 | 时机 | 地点 | 预算 |
| --- | --- | --- | --- |
| 秒级 | 保存 / 提交 | 本机 | 秒 |
| 收尾预检 | 每个 worker 合入前,按 diff 选择 | 本机 | 分钟 |
| 全量 | 候选冻结后一次 | 云端大机器并行 | ≤10 分钟目标 |
| 发布前 doctor | 构建之前 | 只读探测目标环境 | 分钟 |

每一个检查都应该能同时回答两个问题:它属于哪一层?它在哪一档跑?回答不了的检查就是候选的腐烂点。

## 四、Nova 的治理过程(两个月,五个阶段)

**阶段 1(第 1-3 周):发现"绿得没意义"。** 三个包的 138 个用例因入口指向不存在的目录长期零执行;新门禁
写好了但没接进任何 lane;一次排查出六类静默失效,其中一个端点覆盖检查在断言前就 `sys.exit`,实际有 88
个端点没有覆盖。预发布分支 6 天 539 个提交里,用户可见新功能不到 1.5%,约 65% 是门禁/契约/部署。

**阶段 2(第 3-5 周):门禁越加越多,接线反而断了。** 一个门禁控制器卡了 22 天,因为测试 fixture 只用
手写的公开形状,从没喂过生产增强形状,真实错误被折叠成 "unknown"。一次删除 workflow 让 446 个门禁测试
文件失去唯一 CI 调用方,3 天没人发现——本该发现它的可达性守卫自己也在那批不跑的测试里。

**阶段 3(第 5-6 周):全量冲绿战役。** 冻结测试工具链(当时测试/工具修复已占开发分支提交的 51.6%),
4 天开了约 50 个候选,第一次在云端大机器全绿(835 秒),次日第一次零红(566 秒)。控制面暴露 14 层同形
缺陷,其中三个手写常量在仓库里没有任何代码能重新算出来。期间多个并行 worker 共享主工作树,一次收尾把
约 300 个文件误删推上了共享分支。

**阶段 4(第 6-9 周):额度耗尽,预发布发不出去。** 9 个 worker 在主要目标达成后继续抠覆盖率和审计,
耗尽周额度,恢复时上游已领先 295 个提交。两次只读审计结论一致:大多数检查本身是对的。但预发布分支
停在原地近三周,一个候选周期吸收了 1070 个"修复"提交仍未出绿色回执,另一个周期跑了 32 轮约 50 小时;
生产发布门禁 274 次运行 0 次绿。系统性根因分析的结论是"发布没有自己的前置条件模型"。

**阶段 5(第 9 周):收敛。** 定下开发环境只做轻量测试、生产门禁改为手动派发(此前每次推送自动触发、
从未变绿,空跑占当月 CI 账单 57%)、收尾预检单体脚本(6000+ 行)拆分、测试默认按 diff 精准选择。
每周提交数从峰值 3600+ 回落到约 330。

## 五、为什么要那么久

按影响排序(每条在 [pitfalls.md](pitfalls.md) 里都有对应条目):

1. **发现是串行的。** 没有前置条件模型,每轮只能撞到下一个缺口;每轮约 1.5 小时。(P22、P25-P27)
2. **候选在测试过程中一直在变。** 发布/测试工具放在被测候选里,同时 25 天里落了约 3000 个自动化提交;
   修复落在开发分支,但预发布跑的是冻结分支;周期被丢弃重开 10 次。(P28、P29)
3. **治理方式是"出一个事故加一个守卫"。** 守卫层自己膨胀、自己腐烂:测试/自动化基础设施文件数在治理
   期间从约 540 涨到约 2540。(P11-P13、P34)
4. **"接好线了"不等于"真跑过"。** mock 恰好替掉真实边界;门禁写了却没有调用方,反复发生。(P01-P09)
5. **真实问题只在真实机器上出现。** Linux 云机与开发机差异、手工改过的预发布环境。(P18-P20、P23)
6. **AI 编排在放大成本。** 无终点目标烧额度、贵链路当探测器、并行 worker 互相踩踏。(P33、P35、P36)

## 六、可复用的方法

- **先分层再加测试。** 新增任何检查前先回答:属于 L0-L3 哪一层?在哪一档跑?它守的是不变量还是快照?
- **L0 先于一切。** 在任何昂贵的端到端链路启用之前,先建前置条件清单和一次性 doctor。见
  [anti-serial-loop.md](anti-serial-loop.md)。
- **L2 只守类级不变量。** "每个 strict 脚本都必须被某个执行模式调用"是不变量;"spec 名单恰好等于这 32
  个"是快照,快照迟早变成假红。
- **L3 至少有一条真输入路径。** 每个 mock 掉外部边界的测试,要么配一条在真实依赖上跑的契约测试,要么
  把这条边界登记成 L0 前置条件。
- **治理本身要有预算和终点。** 覆盖率/审计类任务在主要目标达成后自动降级为"按需"。
