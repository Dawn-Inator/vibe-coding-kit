# 防止"测一次修一次"的串行链路

## 问题

串行链路长这样:

```
跑全链(1.5h) → 第 7 步红 → 修第 7 步 → 再跑全链(1.5h) → 第 9 步红 → 修 → 再跑 → 第 12 步红 → ...
```

每一轮只暴露一个缺口,总耗时 = 缺口数 × 单轮时长。Nova 的一个预发布候选这样跑了 32 轮、约 50 小时,
一个月没有完成过一次端到端发布。它不是"运气差"或"bug 多",而是四个结构性因素相乘:

| 因素 | 含义 | 乘到哪里 |
| --- | --- | --- |
| **发现是串行的** | 前置条件没声明,只能执行到才知道 | 缺口数 |
| **单轮昂贵** | 构建 + 部署 + 全量测试,一轮 1.5h | 单轮时长 |
| **目标在移动** | 被测候选和工具链在测试过程中持续变化 | 缺口持续补充 |
| **错误不透明** | exit 1 无文本、stderr 被吞 | 一轮只为看清上一轮的错 |

任何一个因素降到接近零,串行链路都会大幅缩短。下面七条原则各自针对其中一个或多个因素。

## 原则 1:前置条件先于执行(L0)

**设计原理**:环境需要的每一样东西——主机上的 CLI、用户组、密钥条目、DB migration 到第几版、反代配置
片段、日志索引、测试账号——都登记成一份**声明式清单**,在任何构建开始之前由一个 doctor 一次性只读检查
完,输出**全部**不满足项,而不是第一个。

```text
# 伪代码:前置条件注册表
PRECONDITIONS = [
  { id: 'host.tool.zip',         stages: [stg, prod], probe: ssh('command -v zip'),            fix: 'install via host bootstrap' },
  { id: 'secret.payments-key',   stages: [stg, prod], probe: secret_store_has('<stage>/payments/key'), fix: 'write via secret tool' },
  { id: 'db.migration.head',     stages: [all],       probe: db_version() == repo_head(),       fix: 'apply migrations' },
  ...
]
doctor(stage):
  results = parallel(PRECONDITIONS.filter(stage).map(p => p.probe()))   # 全部跑,不短路
  print_table(results); exit(count_failed(results))                       # 一次看到所有缺口
```

**可复用技术模式**:

- 注册表是唯一真源;发布脚本里每一个 `fail "<原因>"` 都应能对应到注册表里的某个 id。可以写一个 L2 守卫
  统计"发布脚本里的失败点 vs 注册表条目"的覆盖率,作为棘轮只增不减。
- doctor 只读、可以随时跑、跑得快(分钟级),所以可以放在**每次**发布前,也可以定时跑来发现环境漂移。
- 环境状态改动(装工具、建用户组、改配置)走"声明 → 收敛 → 回读"流程,不允许手工改完不登记。

## 原则 2:一次暴露全部问题(fail-slow)

**设计原理**:全量测试和发布编排默认 `--keep-going`:一个单元失败只标记它的下游为 blocked,其他单元继续
跑。最后输出一张表,列出全部失败,而不是在第一个失败处退出。

- 不要把"部署顺序依赖"套到"构建"上——服务 A 部署依赖服务 B,不代表 A 的构建失败要跳过 B 的构建。
- 每个单元记账(ledger),支持 `--resume` 只重跑失败单元,不重建已成功的。

## 原则 3:贵链路只做验收,不当探测器

**设计原理**:单轮 1.5 小时的链路不能用来"试试看修好没有"。修复必须先在便宜的层面验证:

| 要验证的东西 | 便宜的验证方式 |
| --- | --- |
| 某个脚本改对了没 | 本地直接跑该脚本 / 它的单测 |
| 某个环境条件满足了没 | doctor 单项探测 |
| 某个门禁不再假红 | 本地直跑该门禁(不经整条收尾流程) |
| 一批修复合起来是否兼容 | 收尾预检(分钟级) |

只有全部便宜验证都绿,才允许启动一轮昂贵链路。**熔断规则**:同一子系统连续两轮"失败 → 单点修 → 全链
重放",立刻停下换策略(全树审计 / 本地复现 / 批量修完再跑一次)。

## 原则 4:候选冻结,修复落在实际在跑的那棵树上

**设计原理**:被测的候选一旦冻结,它的代码和它的**工具链版本**都不再变化。

- 发布/测试工具不要放在被测候选里随候选一起变化;要么工具链独立版本化,要么冻结时一并冻结。
- 红灯修复直接落在冻结分支(带可审计的标记,例如提交尾注 `Candidate-Fix: <cycle>`),之后再回合到开发
  分支;不要"修在开发分支,等下一次冻结再带过去"——那样下一轮跑的仍是没修的树。
- 每个周期只冻结一次;周期内不再吸收新功能。一个周期吸收上千个"修复"提交,说明它早就不是冻结状态了。

## 原则 5:错误必须透明

**设计原理**:任何失败都必须带一行人能看懂的原因和复现命令。

- 禁止 `2>/dev/null` / `|| true` 吞掉错误,除非登记了理由;可以写一个 L2 扫描器统计被吞的 stderr 点并作棘轮。
- 失败汇总放在日志末尾(`[summary] 检查名 / 首条错误 / 复现命令`),不需要翻完整日志。
- 被超时杀掉的进程要打印"在哪一步被杀",不要让后续步骤的真实红灯因为日志被截断而看不到。

## 原则 6:环境对等,但不加重开发环境

**设计原理**:预发布是代码路径第一次执行的地方,就会一直是串行链路的源头。对策是让开发、预发布、生产
走**同一套函数/脚本**,用参数控制轻重,而不是在开发环境跑完整预发布链路。

- 预发布/生产专属的路径,用 doctor 做前提体检,用秒级单测覆盖分支逻辑。
- **不要**为了提前发现预发布问题把开发环境升级成完整发布链路——Nova 明确否决过这个方向
  (见 [decisions.md](decisions.md) D-06)。

## 原则 7:把真实输入喂给 L3

**设计原理**:L3 工具链测试最常见的失败是 mock 掉了真正会坏的那条边界(数据库驱动类型、容器内的解释器、
密钥读取器)。每条这样的 mock 至少配一样:

- 一条在真实依赖上跑的契约测试(可以放在全量档,不必每次跑);或
- 把这条边界登记成 L0 前置条件,由 doctor 探测。

"已经接成硬门禁"不等于"在真实输入上证明过"。新门禁上线时,刻意制造一次违规,确认它真的会红。

## 落地顺序(给新项目)

1. 列出发布链路的全部失败点,先登记最常撞的 20 条前置条件,写 doctor。
2. 全量测试和发布编排改成 fail-slow + 汇总表 + resume。
3. 定熔断规则,写进 AI 协作规则文件。
4. 冻结策略:工具链与候选的关系、修复落点。
5. 错误透明扫描器作为 L2 棘轮。
6. 逐条把 L3 的 mock 边界配上真输入或登记进 L0。

## 自检清单(每次准备跑昂贵链路之前)

- [ ] doctor 对目标环境全绿?
- [ ] 本轮的每个修复都已在便宜层面验证过?
- [ ] 候选和工具链从上一轮到现在没有变化,或者变化只包含本轮修复?
- [ ] 上一轮的所有失败都有明确原因(没有"看不清,再跑一次")?
- [ ] 这是同一子系统第几轮重放?≥3 就停下换策略。
