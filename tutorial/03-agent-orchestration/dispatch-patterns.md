# 派发模式:结果落地渠道、Wave Batching 与 Task Packet

## 问题:为什么需要这个机制

当编排者需要决定"这批任务该用什么机制派发"时,如果只有一种派发工具,很容易出现两类问题:一是把不该
打断人类的场景做成了会打断人类的场景(比如让每个 worker 都有权限自己决定要不要跳出来问"要不要授权"),
二是把该集中验证的场景做成了各自为战的场景(每个 worker 各自跑一遍验证,重复消耗资源,还可能得出不
一致的结论)。这两类问题的根源是同一个:**没有一个清晰的决策依据来选择派发机制**,只能凭经验或者顺手
选一个工具。

另外,当很多个 worker 同时在跑,又缺少一份统一的"任务包"格式时,派发指令容易变成口头描述,依赖派发者
和执行者之间的隐含默契——责任边界模糊、验收标准不清楚、出了问题该不该升级给编排者没有约定,导致协作
的一致性完全依赖每个人的自觉,而不是依赖流程本身。

## 设计原理:按"结果最终落在哪里"选机制

选择编排机制的通用决策框架,核心问题是:**这批任务的结果,最终应该落到哪里?**

- **返回给当前会话上下文,供后续综合处理**——这是最常见的场景,适合中等规模(比如 3-15 个)的子任务
  并行派发,子任务完成后各自的产出会汇总回发起者这里,由发起者统一整合、验证、决策。
- **大规模扇出、结果集中回来做统一综合**——适合结构化的批量编排(比如脚本化的工作流引擎),用于任务
  粒度更细、数量更多、需要机器化编排而非会话式来回的场景。
- **结果不返回、独立执行、需要人工监督**——这类机制应该保留给真正的高风险场景(比如涉及大规模重构、
  需要人在旁边盯着的任务)。**普通的 worker/subagent 不应该有权限自己调用这种"不回传结果"的派发
  机制**——这条边界背后是一次真实的开发者反馈:不应该让"AI 内部的分工决策"变成一个会打断人类、跳出来
  问"要不要授权"的弹窗,那种打断应该只保留给真正需要人决策的场合,不能被下放到每一层 worker 自己
  判断"我要不要也弹一个"。

**顺手发现的问题永远走"报告",不要另起炉灶。** 一个 worker 在执行过程中如果顺手发现了任务范围之外的
问题(比如代码里的另一个 bug),应该把这个发现写进自己**最终的结构化汇报里**,交给编排者决定后续怎么
处理,而不是自己再另开一个独立的、会打断人类的派发通道去处理它。

## 可复用技术模式:Wave Batching + Task Packet

**Wave Batching(分波派发)**——把一整批 worker 的派发拆成"健康检查波"和"铺开波"两步:

1. 先用一个有代表性的、低风险的小任务,对整批 worker 即将使用的"打法"(prompt 模板、工具权限、验收
   标准)做一次健康检查,确认没问题之后再铺开一整波,避免"一次性派 15 个 worker,结果全部踩中同一个
   坑"的情况。
2. 每个 worker 分配互不重叠的责任范围(比如各自负责哪些文件、哪个模块),从源头避免写冲突。
3. 各自私下汇报结果给编排者,不要中途互相广播——广播容易造成 worker 之间互相干扰彼此的执行状态。
4. 编排者收齐所有结果之后,**统一、集中地跑一次验证**——不要让每个 worker 各自跑一遍验证,那样既
   重复消耗资源,又可能因为验证环境/时机不同得出不一致的结论。

**Task Packet(任务包)**——每份派发指令应该自解释,不依赖派发者和执行者之间的隐含默契。一个任务包
至少应该包含:

```
- 范围边界:这个 worker 具体负责哪些文件/模块,不得越界修改
- 版本基线:基于哪个 SHA / 哪个版本出发
- 验收标准:什么状态算"做对了"
- 执行身份:以什么身份提交(署名、权限范围)
- 尝试次数:这是第几次尝试,之前失败过几次、为什么
- 证据要求:完成时需要附带什么证据(日志、测试结果、截图等)
- 升级条件:遇到什么情况必须停下来升级给编排者,而不是自己硬闯
```

**对 worker 的禁止清单**——每份派发指令还应该显式写明 worker **不能**做的事,而不是假设 worker 会
自觉守规矩。典型的禁止项包括:不能自己再去监听长任务的完成通知、不能把命令丢到后台自己不管、不能碰
共享的临时暂存区、不能自己再另开一个"不回传结果"的独立执行通道、不能杀掉进程、不能读取敏感的环境
变量、不能未经批准就自己跳过质量门禁。这份清单存在的原因很直接:如果不显式写清楚,一个能力较强的
worker 很容易"自己发挥",做出一些编排者完全无法预期和追踪的动作,而这类动作出问题时往往很难复盘。

## 可复用技术模式:上下文卸载与单元画布

worker 的上下文窗口是工作记忆,不是存储。两类东西最容易把它撑爆:只需要其中几行的原始工具输出(测试日志、
全仓搜索、网页),以及只存在于 worker 脑子里的进度——后者一旦上下文耗尽或进程死掉,重新派发就只能从零开始。

做法很朴素:大输出写文件,只回读锚点片段,上下文里留一行"路径 + 是什么 + 关键数字";多步骤单元维护一份
Markdown 画布(目标与验收判据、步骤清单、已确认事实、最近提交、下一步),在步骤边界更新;重新派发时指向旧
画布,写明"从画布状态继续"。

落点不需要一个跨 agent 的共享存储:每个 agent 写在**自己的工作区**里就够,别人按路径读。理由是这些文件只在
两种情况下有用——worker 还活着(它自己读),或者 worker 没收尾就死了(工作区这时还在,续派复用同一个工作区即可);
成功收尾之后它们本来就没有保留价值,随工作区一起删掉正好。唯一要守住的是续派必须复用原工作区,新开一个就没有
画布可接。

## Nova 案例参考

Nova 项目里,"结果不返回、独立执行"这一类机制被限定为只有顶层编排者能调用,且只用于真正的高风险大
重构场景;普通 worker 完全没有这个工具的调用权限。任务包里额外要求写明"这是第几次尝试"这一项,是
因为观察到同一个 bug 反复失败又反复用同一种策略重试,是一种需要被显式识别和打断的模式——写清楚尝试
次数能让编排者一眼看出"该不该换策略了",而不是无限重试下去。这是 Nova 按自己的协作规模和风险偏好做的
具体配置,新项目应该按自己的任务粒度和团队规模,重新决定"结果落地渠道"对应到哪些具体工具、任务包里
哪些字段是必填的。

Nova 项目还观察到一种更隐蔽的失败模式:被派发的 worker 在回复里说完"接下来该做什么"就结束了当轮,
既没有真的开始执行,也没有起任何后台任务——比如说完"现在开始改这处代码"或"接下来我去查一下 X"就
收工。回复一结束,worker 就静默卡住,没有人执行那句"接下来",直到编排者自己发现某个 worker 的最新
报告里只有一句宣告、没有下文,才手动把它推醒。这与另一种正常、需要保留的模式——worker 起了一个真实的
长跑后台任务(比如一次合并收尾、一次远端预检),然后正确地结束当轮等待那个任务自己的完成通知——表面
相似、实质相反:区别只在于当轮结束时是否真的有一个后台子任务在跑,不在于"这轮是否结束了"。更值得
记录的是,这条规则被写进任务包禁止清单之后,同一个编排会话在紧接着的下一轮里又无意识地犯了一次同样
的错误——说完"现在开始改"就结束了当轮、手上没有任何在途操作。这说明单靠任务包里的一句禁止性 prose
不足以可靠杜绝这个模式,连刚写下这条规则的会话自己都会在下一轮忘记遵守。Nova 因此在此基础上加了一层
范围很窄的机械检测:对 worker 的回复文本做启发式正则匹配,末句命中"现在开始…"/"接下来我去…"这类已经
实测出现过的宣告式开头、且全文没有出现后台等待或执行证据关键词时,判定为疑似卡死并在同一轮里提示
编排者复核——这不是语义理解,只是一个零依赖、几乎零成本的二次提示,漏判或偶尔误判都是可接受的代价,
换来的是不再完全依赖编排者自己每次都记得检查这一条。
