# 配额硬约束、跨会话资源归属、编排者不能亲自修 bug、唤醒节奏的配额代价、编排进程退出后的恢复

这几条规则被合并成一篇,是因为它们有一个共同的失效形状:**编排者/宿主平台默认的"乐观假设"没有被
显式覆盖,后果要等到损失已经发生才被发现**。五个真实事故各自印证了这一点。

## 事故一:配额不是"软约束",一次审查工作流忘记传 model 参数把预算烧穿了

宿主平台的系统提示词经常自带一种默认口径:"token 成本不是约束,遇到重要任务就该用最贵的档位"。
这条默认口径在仓库外部,项目自己改不了——所以项目自己的规则必须显式压过它,而不是指望它"大概率
不会被触发"。

一次真实事故:一个"多 reviewer + 每条发现配一个独立证伪 worker"的审查工作流,**每一次派发调用都
没有传 `model` 参数**。全部 worker 因此静默继承了编排者自己那个最贵的档位,一直跑到中途被人工发现
"这些任务其实中档模型就够用",才停下来重新起một个更便宜的档位继续跑。宿主平台"不用担心成本"的默认
引导,反而让这次事故更难被及时发现——它移除了本该促使人在派发前多想一步的那一点"成本焦虑"。

结论落到规则上很直接:**配额消耗到 95% 就停止新派发,到 97% 直接停掉所有 agent、转入合并交接**,
每次心跳唤醒点和每次大规模 fan-out 之前都要单独查一次,大规模 fan-out 之前还要先估算一次 token
成本、写进派发计划里——不能先派发再事后看账单。

## 事故二:两个会话同时接管了同一份基础设施资源

如果不止一个 AI 会话/平台可能操作同一个共享环境、分支或者机器/身份链,资源归属必须是**单一指派制**,
而不是"大家默契一下就好"。

一次真实事故里,一个编排会话接手了一份基础设施工作(一台机器、一条身份链、一次数据库迁移),而这份
资源当时正被另一个并发会话占用。两个会话在很短的时间窗口内对同一份资源各自发出了操作命令,期间还
观察到一次状态回读中途闪烁——跟"两个会话在抢同一份远程状态"这个现象完全吻合。**接手的那个会话没有
任何确凿信号证明对方已经停手**,只是从"对方安静了一阵"这一点推断出"对方大概做完了"。代价是两边操作
互相干扰,真实浪费的时间只能靠人工介入澄清归属才收场。

这个事故的教训被浓缩成一条纪律:**"对方看起来安静了""大概率做完了"从来都不是交接的证据**——唯一
能改变资源归属的,是负责监督这份工作的人**明确说出来**。发现资源被卡在别人的地盘上,正确动作是把
证据(commit/candidate 标识、观察到的现象、日志位置、当前阶段)交接出去,而不是自己动手接管。

## 事故三:编排者亲自"顺手"改了几处一行修复,又把 build 和 finish 无条件串联

编排者的职责是派发、整合、集中验证、验收——不是亲自写代码。这条规则最容易在"这就一行,派 worker
反而更麻烦"的心理下被绕过。

一次真实事故里,编排者在一场大型多 agent 会话中,亲自手改了好几处看起来"就一行"的修复(一个测试的
类型注解、构建系统的文件/依赖清单、一个编译期宏开关),然后又把 build 命令和 finish/merge 命令无条件
串联在一起,没有在中间检查 build 的真实结果。结果两个编译不过的 commit 直接落到了共享分支上——
一个连项目自己的原生构建工具都编译不过,另一个在别的 package 里有类型检查错误——事后额外花了好几轮
修复才补救回来。

两个失败根子相同:**编排者把自己当成了实现者,而不是派发者**;**finish 建立在"构建大概率会成功"这个
假设上,而不是建立在真正检查过的结果上**。落到规则上:编排者只能编辑它自己拥有的编排类文件(交接/
计划/状态文档、自己发起的 rebase 冲突解决),碰源码/测试/配置一律派发给带验收标准的 worker,不因为
"看起来很小"就破例;finish/merge 链条必须先跑验收命令、检查它的真实退出码,再决定要不要 finish,
不能无条件串联。

## 事故四:每一条通知都单独反应,一天烧掉配额的四分之三

心跳机制原本的设计是"事件锚定检查始终强制执行"——每收到一次 subagent 完成通知、每一次后台 shell
完成通知,都当场同步跑一遍完整审计。这条规则本身没错,但没人算过它的真实代价。

一次真实测量:24 小时内周配额烧到 75%(约每小时 4.4%),而且编排者自己(某个前沿档位模型)那部分
消耗,比所有 worker 模型加起来还多。查下来根因是编排主循环在**每一次唤醒**时都要重新读一遍完整
上下文——那天大约有 80 次 worker 完成通知 + 35 次后台 shell 完成通知 + 6 次定时器触发,合计 121 次
唤醒,每次都要花 2-5 次工具调用去处理,而当时上下文已经从 170k token 涨到 770k——四百多次"重新读一遍
几十万 token 上下文"的往返,大部分只是为了处理一条并不紧急的通知。

修复思路是把"唤醒"和"要不要立刻反应"这两件事分开:通知先攒着,不逐条反应;但攒多久这个数字,第一版
实现留了一个坑——单独给"定时兜底"开了一条 30 分钟的线,又给"合并批处理"开了一条 15 分钟的线,两条
线各自独立触发。这个设计乍看合理,细想会发现:如果定时器触发的那一下被当成"攒起来的通知之一"而不是
立刻处理,安静时段里最坏情况的响应延迟就变成了 30+15=45 分钟——比原本"30 分钟内保证有人看一眼"这个
承诺还差,而且两条独立的定时线本身还需要各自的唤醒机制去驱动,相位对不上时问题更明显。

最终方案是把两条线合并成一条:**一个统一的 15 分钟周期,同时承担"保证安静时段有人来看"和"把这段
时间攒的通知合并处理、拆解派发"两个职责**——不再有独立的"更长的兜底定时器"。这样最坏延迟从有缺陷的
45 分钟,变成有保证的 15 分钟,比原始的 30 分钟兜底还更快,同时配额消耗量级上依然比"每条通知都单独
反应"省得多(一天最多 96 次合并处理,而不是 121 次独立反应,且每次只读一遍上下文而不是逐条重复读)。
唯一必须显式划清的例外是:**人类发来的新消息永远不能被塞进这个合并周期**——那是另一个独立的唤醒点,
必须立刻回应,不能因为"凑批处理"而延迟对话响应。

这次事故还暴露了一个容易被忽略的陷阱:修复方案第一版里,原本还写了"上下文占用到某个百分比就该主动
少做事、等着被压缩"这条规则,理由是想进一步省配额。但这条规则本身有问题——它没法区分"可以省的多余
动作"和"该做的核实动作",一旦被理解成"上下文紧张就可以降低核查标准",就会制造出一个新的、更隐蔽的
失效模式:该发现的问题因为"省配额"这个借口没被发现。真正有价值、且不牺牲质量的收尾动作("把手头正在
处理的东西做完、别半途丢下""留一份能让后续会话接得上的记录")跟上下文占用百分比无关,不需要单独
开一个按阈值触发的模块——它们本来就该是编排者持续维护的在飞任务登记表(worktree 路径+预期产物,
随派发/落地实时更新,而不是靠某个百分比阈值才想起来做)的一部分,常态化执行比"到了 40% 才触发"
更可靠,也不会制造出"省配额可以降低核查标准"这个误解空间。

## 事故五:编排进程自己退出了,却没人知道该去哪找那个还在飞的 worker

"接管前先判活"这条纪律解决的是:另一个会话要不要接管一个看起来空闲的 worktree 之前,先确认那个
**worker** 是不是真的死了。但它有一个没被覆盖的场景:如果死掉、重启的不是 worker,而是**编排进程
自己**呢?

一次真实事故:编排会话在中途退出,当时有一个在飞的长时间运行合并 worker 还在跑。关于这个 worker
的所有进程内状态——它的 worktree 路径、预期产物、它到底跑完了没有——全都跟着编排进程一起丢了。
重启后的会话光靠"接管前先判活"这条纪律完全没用:**你没法判断一件东西是不是还活着,如果你已经不
知道它存在**。"先判活"这条规则本身没错,只是隐含了一个前提——你得先知道要判活的是谁,而这个前提
在编排者自己意外退出的场景下恰恰被打破了。

修复思路是给"两边"都留痕迹,不能只靠 worker 单方面的存在证明自己:
1. worker 端:每一个可交付的子步骤都提交一次,不等到最后——这样哪怕 worker 自己的进程没了,它
   真实的进度也能从它自己 worktree 的 `git log` 里恢复出来。
2. 编排者端:维护一份在飞 worker 的实时登记表(复用项目已有的临时性/backlog 跟踪约定,不另开一个
   存储位置),每个 worker 一行,写清楚 worktree 路径和预期产物,随派发/落地更新。
3. 重启后:把这份登记表跟每个 worktree 的真实 `git log`/状态逐条比对,再决定恢复、重新派发、还是
   接管——本质上是把"接管前先判活"的判断逻辑,延伸到"编排者自己重启之后,必须从磁盘上重新推导出
   完整的 worker 名单,不能指望已经没有了的进程内记忆"。
