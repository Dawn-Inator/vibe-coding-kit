# 审查 Fan-Out 分级:证伪预算只配给真正重要的发现

## 问题:为什么需要这个机制

独立审查/证伪 fan-out 是多 agent 协作里性价比最容易被高估的一环。直觉上"审查得越细、证伪得越彻底
越安全",但审查本身也要消耗 agent 预算,而且这份消耗跟它能防住的风险并不成正比——真正会导致线上
事故的问题,往往集中在少数几类地方,其余大量发现即使是真的,代价也很小。如果不对审查范围和证伪
做分级,很容易出现"审查成本花了不少,但没有花在刀刃上"的结果:大量低严重度发现被同等对待、逐条
配一个独立证伪者去核实,而真正致命的问题反而混在同一批产出里,没有获得更高的关注度。

另一个容易被忽略的问题是:审查者本身读到的代码版本是不是最新的。如果审查者读的是一份已经落后于
真实候选提交的工作区,它给出的"结论"从一开始就建立在错误的输入上——不管审查过程多严谨,结论本身
就是错的。

## 设计原理

**审查预算应该按"四类高风险场景"分配,而不是对所有改动一视同仁地深挖。** 这四类场景的共同点是:
它们的错误代价高,而且**单元测试大概率发现不了**——资金/计费路径算错一次就是真金白银的损失;安全
边界一旦被绕过,影响面通常在事后才会暴露;从未在真实数据库上执行过的 SQL,语法正确不代表语义正确
(参数类型、时区、边界值这些问题往往只有连到真实实例才会暴露);只有真机/真浏览器才能验证的交互,
在自动化测试的模拟环境里天然测不出来(布局撑不开、手势冲突、渲染层级这类问题)。这四类之外的发现
不是不重要,而是"重要程度和证伪成本不成正比"这件事在这四类之外体现得没那么明显。

**证伪(独立复核发现是否成立)应该分级,而不是每条发现都配一个独立证伪者。** 让审查者自己先给出
严重度自评(blocking / major / minor),只有自评到 blocking 或 major 的发现才值得再派一个独立
worker 去交叉验证——这个交叉验证本身的目的是防止审查者自己看错、误报。minor 级发现即使真的看错了,
代价也很小,直接带着"未证伪"标记进清单即可,不需要为它单独花一次独立 worker 的预算。**证伪的价值
和它防住的风险成正比,不是和发现的数量成正比。**

**审查者必须读真正的候选版本,不能读可能落后的共享工作区。** 一个审查者如果直接读一个多方共用的
工作区目录,那个目录的内容可能落后于真正要发布的候选提交(比如另一个 worker 还没 push、或者刚刚
rebase 过)。正确做法是让审查者始终针对"已推送的候选引用"(比如某个分支的远端最新提交)去读代码,
而不是相信本地目录当下的状态。

## 可复用技术模式

1. **四类审查范围**:资金/计费路径、安全边界、从未在真实数据库上执行过的 SQL、只有真机/真浏览器
   才能验证的交互。派发审查任务时显式写明这四类,而不是让审查者自己判断"什么值得深挖"。
2. **审查者先自评严重度,证伪只配给 blocking/major**:派发指令要求审查者产出时附带严重度自评;
   编排者据此决定要不要为这条发现单独派一个独立证伪 worker。minor 级发现直接进清单,标注"未
   证伪"即可上报。
3. **审查者读远端候选引用,不读共享工作区**:派发指令里显式指定"从 `origin/<branch>`(或等价的
   已推送引用)读取代码",而不是假设审查者会自己判断该读哪个版本。
4. **在审查 prompt 里写明项目的"既有共识"**:哪些建议已经被开发者明确拒绝过、哪些模式是项目故意
   这样设计的——不写清楚,审查者会不断产出一堆已经被否决过的"加固建议",稀释掉真正有价值的发现。

## Nova 案例参考

Nova 项目里,两轮独立审查覆盖了 13 个提交,一共花费约 690 万 subagent token,产出 35 条发现——
3 条 blocking、11 条 major、21 条 minor。这 21 条 minor 发现,当时每一条都配了一个独立证伪者去
核实,事后复盘认为这部分预算的性价比很低:证伪一条 minor 发现的成本,和证伪一条 blocking 发现的
成本几乎一样贵,但两者一旦看错造成的后果完全不对等。与此同时,真正的 3 条 blocking 缺陷全部落在
"四类高风险场景"里——一处数据库交互参数从未在真实实例上跑过,类型编码方式和假设的不一致;一个
需要在真机上操作的表单页面缺少可滚动容器,导致提交按钮在小屏幕上永远够不到;一张背景图在渲染层级
上盖住了另一个可交互画布。三者的共同点是"单元测试全绿,一到真实环境就必现"——这正是四类审查范围
覆盖的问题类型,也是这次复盘之后把证伪预算集中到 blocking/major 的直接依据。

这是 Nova 一次具体事故复盘出的分级标准;新项目应该按自己业务实际的高风险场景重新定义"哪四类值得
深挖",但"审查预算要按风险分级、证伪成本要和防住的风险成正比"这条原则是可迁移的。
