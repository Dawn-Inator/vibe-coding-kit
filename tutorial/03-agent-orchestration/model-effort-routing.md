# 模型/效力路由:按"档位维度"选模型,而不是按任务重要性

## 问题:为什么需要这个机制

一旦开始大规模派发 subagent,很自然会遇到一个问题:每个 subagent 该用什么模型档位?最省事的做法是
"顶层编排者用什么模型,子任务也默默继承同一个档位"——这样最省思考成本,但代价是昂贵的顶层模型档位被
大量用在了根本不需要那么强判断力的机械性任务上,长期下来是显著的浪费。

另一个常见的认知偏差是:人容易把"这个任务感觉很重要"错误地等同于"这个任务很难、需要更贵的模型"。
但现实中很多"重要"的任务,执行路径其实是完全清晰的、不涉及任何需要拿主意的分叉——比如"把这十个文件里
的某个过时函数名批量替换掉",这件事很重要(关系到构建能不能过),但不需要顶级判断力,只需要正确执行。
如果不建立一个独立于"任务感觉上重不重要"的路由标准,很容易在派发时系统性地升档。

## 设计原理:三档心智模型

不依赖任何具体厂商的模型命名,可以用一个通用的三档框架来描述"什么任务用什么档位":

| 档位 | 适用场景 | 权限边界 | 模型档位 |
| --- | --- | --- | --- |
| 只读探索档 | 搜索、定位、摘要,不涉及任何写操作 | 严格禁止编辑/提交/标记任务完成 | 最便宜档位 |
| 写操作档 | 从机械式批量修改到完整功能实现,大多数"实现型"任务 | 有写权限,在自己声明的责任范围内工作 | 中等能力档位 |
| 顶层编排/判断档 | 掌管全局目标、任务分解、架构分叉决策、结果整合、最终验收 | 通常只有一个实例,不应被下放 | 最贵/最强档位 |

**判断分叉是升档的唯一理由,任务"听起来重要"不是。** 每次派发前,只需要回答一个问题:

> 这个 worker 的任务里,有没有一个时刻,两条路都说得通,需要有人拿主意选哪条?

- 没有 → 用最便宜能胜任的档位(只读探索用最低档,写操作用中间档,即便任务本身工作量很大)。
- 有 → 才需要升档,而且这种"真正的判断分叉"应该**优先交回顶层编排者自己做决策**,而不是继续往下
  委托给另一个子 agent 去"帮忙拿主意"——判断权下放得越深,顶层编排者对全局质量的控制力就越弱。

**顶层编排者即使需要派发"审查/审计"类子任务,子任务也只应该返回判断结论,不应该直接写代码。** 这一点
的目的是保护顶层编排者的上下文不被大量原始 diff 塞满——审查类 worker 的产出应该是"我看了这段代码,
结论是 X,理由是 Y",而不是把整段修改后的代码原样搬运回来。

## 可复用技术模式

**每次派发调用必须显式声明档位,禁止让子任务"默默继承"调用者自己的档位。** 具体做法是把路由决策拆成
两个显式问题,写进派发前的检查步骤:

1. 这个子任务有没有写权限?(没有 → 只读探索档;有 → 至少写操作档)
2. 这个子任务里有没有一处真正的判断分叉?(有 → 考虑升档或把判断权收回顶层编排者)

**可数的自检机制**:如果一个编排会话里,派发给顶层档位模型的 worker 数量接近或超过了总派发数的一半,
应该停下来重新审视自己的派发决策是不是普遍升档了。这个自检指标的价值在于它是可量化、可复查的——不需要
凭印象判断"是不是升档太多了",直接数一下比例就知道。

## 设计原理的延伸:项目自己的额度红线,要显式压过宿主的"成本不是约束"

"没写档位就默默继承调用者自己的档位"这个失败模式,再往前追一步,根源往往不是执行者疏忽,而是**执行
环境本身给的默认导向就是"不用在意成本"**——不少 AI 工具的宿主系统提示、或者内置的工作流编写类说明,
会直接告诉模型"token 成本不是约束",目的是不让模型因为担心成本而畏手畏脚,不敢做该做的事。这类文案
本身没有错,但它是**宿主平台的通用默认值**,不是针对某个具体项目的实际资源状况说的——它活在项目仓库
之外,项目改不了它,也没法指望它替项目考虑真实的额度上限。

这就带来一个推论:如果一个项目确实有真实的额度约束(比如按周结算的调用配额),那么"额度是硬约束"这条
规则必须写成**显式压过宿主默认值**的项目规则,而不是含糊地"跟宿主默认值并存"——两者字面上不冲突时,
执行者会默认采信更省事的那条(通常就是"不用在意成本"),真正的额度上限反而被架空。可操作的做法是
定义**两档阈值**(比如"接近上限就停止派新任务","逼近耗尽就停掉所有任务转入收尾"),把它写进每轮
必读的规则文件,而不是只写在某篇按需加载的 skill 里——因为大规模派发决策往往发生在"要不要开一大波
调研/审查 fan-out"的那个瞬间,如果压过默认值的规则不在场,那个瞬间就会默认继承宿主的乐观假设。

## Nova 案例参考

Nova 项目里,这条自检机制来自一次真实事故的复盘:一次编排会话中,9 个 subagent **全部**不自觉地继承了
顶层编排者自己的模型档位,而不是各自按任务复杂度重新判断——相当于路由规则形同虚设,退化成了"一刀切用
最贵的模型"。事后这条经验被固化成两条强制要求:

- 每次派发调用必须传入显式的模型参数,不允许留空让平台默认继承调用者档位;
- 编排会话结束前复查一次顶层档位占比,接近或超过半数就触发重新审视。

另一次类似的事故发生在一个"审查 + 证伪"的批量派发场景:七个审查者加若干个证伪者的一整套派发,同样
因为没写模型参数,全部继承了主会话自己最贵的档位,直到运行中途被人工发现"其实用中间档也能胜任"才停下
重派。这次事后复盘多加了一条:项目把"额度是硬约束"写成了两档阈值(接近上限停止派新任务、逼近耗尽停掉
全部任务转入收尾+推送),并且明确这条规则要压过宿主提示里"不用在意成本"式的默认导向——因为那类默认值
不在仓库里、AI 改不了,只能靠项目自己的规则显式压过它。

这是 Nova 的具体处置方式,新项目应该按自己实际用到的模型产品线和成本结构,重新设计三档到具体模型型号
的映射表、自检的具体比例阈值,以及自己真实的额度阈值数字——三档框架本身(只读/写操作/顶层判断)、
"判断分叉才升档"这条原则、以及"项目额度规则必须显式压过宿主默认值"这条优先级关系是可迁移的,具体
映射、阈值和额度数字不是。

## 失败成本 ≠ 判断分叉:"改错代价大"不是升档的理由

另一类升档误判比"忘记传模型参数"更隐蔽:任务确实有写权限、确实需要中间档执行,编排者也正确传了模型
参数——但传的是顶层判断档,理由是"这块东西(固件/二进制格式/跨服务契约)出错代价很高,得用最强模型"。
这个理由听起来合理,实际上混淆了两件不同的事:**任务有多难(该用哪一档模型执行)**,和**任务出错影响
多大(该配多少验证强度)**。设计已经在方案文档里定好格式和做法的实现任务,不管它触碰的子系统听起来
多"高风险",判断分叉都已经在设计阶段解决完了,剩下的是照方案执行——这正是中间档写操作 worker 该做
的事,"出错代价大"这个顾虑,应该体现在派发独立审查/证伪 worker 和编排者自己做集中验收上,而不是体现
在把实现者本身换成更贵的模型。用模型档位去买风险缓释,买的是错的东西:审查和验证本来就该覆盖这个
风险,再多付一次模型差价并不会让验证更充分,只是把预算花在了不该花的地方。

Nova 项目里一次固件相关的重构留下过这样的记录:设计文档已经把每一处格式和做法定死之后,编排者仍然把
五个实现型任务包(一次管线删除、一个二进制格式写入器、一次固件网络同步、一次小型固件修复、一次固件
渲染重写)派给了顶层判断档,理由写的是"固件/二进制格式出错代价高"。事后复盘时对照同一场会话里两个
真正需要顶层判断档的调用——一次涉及注册重放校验的安全审查、一次原因未知的设备重绑定 bug 排查——才
发现前五个任务其实完全不满足"判断分叉"这条唯一升档理由:方案已经写死,审查和集中验证也都在场。这次
复盘之后,项目把升档理由收紧成三类穷举(审查/证伪类工作、原因未知的根因调查、worker 自己必须做出的
安全边界设计决策),并要求每次派发顶层判断档之前先写一行自检——说不出属于哪一类,就必须改用中间档。

同样,三档框架和"审查/验证兜底风险、模型档位只解决判断分叉"这条原则是可迁移的,具体项目该把哪些任务
类型算作"设计已锁定的高风险实现"、审查覆盖哪四类,需要按自己的领域重新列。
