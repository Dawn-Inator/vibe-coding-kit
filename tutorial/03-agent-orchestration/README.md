# 派发判据、独立性检验与资源解耦

## 问题:为什么需要这个机制

多 agent 协作开发的第一个直觉误区,是把「能派几个 agent 同时干活」和「机器能扛住几个重进程」当成同一个
约束来调。结果往往是:因为担心内存/CPU 扛不住一次 `tsc`/`next build`/端到端测试的峰值消耗,连带把
「要不要拆多个 subagent 并行探索/编辑」这件事也一起保守化了——只派 1-2 个 agent,理由是「机器吃不消」。
但 agent 的读/查/编辑操作本身几乎不消耗计算资源,真正吃资源的是它们各自触发的**重进程**(编译类型检查、
开发服务器、端到端测试、构建、依赖安装)。把这两件事混为一谈,代价是白白牺牲了并行度——而并行度才是
多 agent 协作相对单线程人工开发的核心杠杆。

第二个直觉误区走向另一个极端:为了避免"怕麻烦就不拆",给并行度写一个数字下限(比如"小任务至少
几个、大任务至少几个 subagent")。Nova 试过这样的数字下限,结果是简单任务被注水——为了凑够数,把
本来一个人十分钟改完的事拆成互相等待、互相踩文件的几份——于是我们撤销了数字下限,换成了"独立性
检验":能不能拆,看的是工作单元是否真的独立、拆开是否真的更快,而不是看某个数字。

## 设计原理

**核心原则:agent 并行数量和重进程并发数量是两个完全独立的资源维度,分别设置各自的上限,不要互相牵制。**

- **agent 并行度**:上限主要由"任务是否可安全拆分、拆开后是否互不写冲突"决定,而不是由机器算力决定。
  只要任务单元之间读写边界清晰,理论上可以派出远超机器核数的 agent 数量,因为大部分 agent 时间花在
  等待模型推理和执行轻量读写操作上。
- **重进程并发度**:上限由宿主机的实际算力(内存峰值、CPU、I/O)决定,和当前有多少个 agent 在跑没有
  直接关系——不管背后有 3 个 agent 还是 30 个 agent 在编排,某台机器能同时扛住的"编译+跑测试"数量是
  一个和 agent 数无关的物理常数。不同类型的重进程之间也不能一刀切用同一个上限:同样是"重进程",
  端到端测试(通常涉及浏览器自动化)的内存/CPU 峰值消耗往往显著高于普通单元测试,即便机器本身能同时
  跑两组常规重任务,也可能仍然把端到端测试单独限制为同时只能跑一个。

把这两个维度拆开之后,决策就变得清晰:**agent 并行度按任务的独立性决定(不被机器算力牵制),重进程数量按机器实测能力单独限流**,
不要因为后者保守就连带牺牲前者。

**并行派发由独立性检验决定,不由数字决定。** 判据很简单:

- 讨论、解释、status、有限的只读探查:单 agent 就够,不派。
- 只有同时满足两条才 fan-out:(1)存在**真正独立、写入边界互不重叠**的工作单元;(2)并行有
  **可量化的墙钟收益**(比如几个单元各自要跑很久,串行会明显更慢)。
- fan-out 时按编号的 **Wave(批次)** 组织:同一 wave 内的 agent 互不依赖、写入边界不重叠;下一批依赖
  上一批产出时才开下一个 wave。当前并发槽位装不下时,**分批**依次跑完,而不是缩小整体规划或把它们
  硬塞进同一批。
- 永远不要为了凑一个数字而拆分;也不要因为任务"模块多"就自动拆——模块多但改动强耦合的任务,拆开
  只会制造合并冲突和重复验证。
- 所有分支的产出最终要回到顶层编排者那里做一次**统一验证**,不应该让每个 worker 各自验证、各自下
  结论——这样容易出现验证口径不一致、或者重复消耗验证资源。

## 可复用技术模式:小任务走单 agent

不是所有任务都值得走"拆分+派发+等待+核对"这套完整流程。当一个任务**同时满足**以下几个条件时,
默认由主 session 直接改,不派 subagent:

- 改动量很小;
- 局限在单一模块内,不跨边界;
- 不涉及需要额外治理的高风险变更类型(例如不改数据库结构、不改公开 API 契约)。

经济学依据是:对这类任务,"写清楚派发说明→等待完成通知→核对结果"这套流程本身的开销,可能反而
超过直接手改的成本。判断应该在动手前对照清单明确核对,而不是凭感觉;更稳妥的做法是让项目的 gate
工具给出 lite / full 分类(见 `coding-gate-preflight`),agent 不自行改判。

## 重进程限流数字怎么定:一次真实的"压垮主机"事故

"重进程并发度按机器实测能力单独限流"这条原则,光讲道理容易被低估——直到真的撞上一次主机被压垮的
事故,才会理解这个上限不是保守起见的锦上添花,而是防止"所有人一起变慢"的硬约束。

一次真实事故里,一台 10 核主机上同时跑着:一个原生移动端构建、一个嵌入式固件工具链的构建、一次
golden 文件回放流水线重跑、外加好几个后端单测/前端构建进程——没有人单独去限流,因为每个 worker
看起来都只是"跑自己那部分的验证"。结果 load average 冲到核数的 15 倍以上,所有在跑的进程一起变慢,
包括那些跟这几个重进程完全无关的 worker 的测试也开始超时。这里有个容易被误判的细节:**这些超时
本身不是代码缺陷**,是主机过载导致的假阳性——如果这时候有人把"测试超时"当成一个需要修的 bug 去
排查,排查的是一个根本不存在的问题,浪费的是整轮调试的时间。正确的处理方式是在负载降下来之后单独
重跑一次那个测试再下结论,而不是当场就开始"修"。

这次事故之后固化出的具体数字是:**同一台主机,核数 ≥10 时同时最多允许 2 个重进程组,核数更少时
最多 1 个**——这是一个可以直接拿来当起点的默认值,不是要求逐字照抄,新项目应该用自己真实的核数和
内存峰值重新校准,但"先定一个具体数字,而不是留给感觉"这件事本身值得直接搬。

## Nova 案例参考

Nova 项目的具体选择(仅供参考,新项目应按自身机器规格和业务复杂度重新决策):

- 本地开发机配置有限,重进程(类型检查、构建、端到端测试、依赖安装)全局并发限流为 1;
- 云端专用测试机算力更强,可以同时跑 2 组常规重进程,但端到端测试仍然单独限制为同时最多 1 个,
  因为浏览器自动化的内存峰值远高于普通单元测试;
- 不管重进程限流设置成多少,agent 的派发判据(独立性检验)不因此改变——两个维度在实践中被严格
  分开配置,不共用同一个"并发数"参数。
- 小任务的判定标准被写成一份显式清单,几个条件必须同时成立才默认单 agent,平时执行任务前先核对
  清单再决定要不要派 subagent,避免凭感觉做决定。
- 心跳/监督机制(如果项目有的话)顺带扫一眼主机 load:超过核数的 2 倍就暂停派发新的重任务,直到
  负载降下来,而不是继续按原计划铺开下一波重进程。
