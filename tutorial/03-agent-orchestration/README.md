# 派发判据、独立性检验与资源解耦

需要把任务面板记录与项目工作区放在一起时，参见[当前工作目录中的任务进度记录](task-progress-storage.md)。

## 问题:为什么需要这个机制

多 agent 协作开发的第一个直觉误区,是把「能派几个 agent 同时干活」和「机器能扛住几个重进程」当成同一个
约束来调。结果往往是:因为担心内存/CPU 扛不住一次 `tsc`/`next build`/端到端测试的峰值消耗,连带把
「要不要拆多个 subagent 并行探索/编辑」这件事也一起保守化了——只派 1-2 个 agent,理由是「机器吃不消」。
但 agent 的读/查/编辑操作本身几乎不消耗计算资源,真正吃资源的是它们各自触发的**重进程**(编译类型检查、
开发服务器、端到端测试、构建、依赖安装)。把这两件事混为一谈,代价是白白牺牲了并行度——而并行度才是
多 agent 协作相对单线程人工开发的核心杠杆。

第二个直觉误区走向另一个极端:为了避免"怕麻烦就不拆",给并行度写一个数字下限(比如"小任务至少
几个、大任务至少几个 subagent")。Nova 试过这样的数字下限,结果是简单任务被注水——为了凑够数,把
本来一个人十分钟改完的事拆成互相等待、互相踩文件的几份——于是我们撤销了数字下限,换成了"独立性
检验":能不能拆,看的是工作单元是否真的独立、拆开是否真的更快,而不是看某个数字。

## 设计原理

**核心原则:agent 并行数量和重进程并发数量是两个完全独立的资源维度,分别设置各自的上限,不要互相牵制。**

- **agent 并行度**:上限主要由"任务是否可安全拆分、拆开后是否互不写冲突"决定,而不是由机器算力决定。
  只要任务单元之间读写边界清晰,理论上可以派出远超机器核数的 agent 数量,因为大部分 agent 时间花在
  等待模型推理和执行轻量读写操作上。
- **重进程并发度**:上限由宿主机的实际算力(内存峰值、CPU、I/O)决定,和当前有多少个 agent 在跑没有
  直接关系——不管背后有 3 个 agent 还是 30 个 agent 在编排,某台机器能同时扛住的"编译+跑测试"数量是
  一个和 agent 数无关的物理常数。不同类型的重进程之间也不能一刀切用同一个上限:同样是"重进程",
  端到端测试(通常涉及浏览器自动化)的内存/CPU 峰值消耗往往显著高于普通单元测试,即便机器本身能同时
  跑两组常规重任务,也可能仍然把端到端测试单独限制为同时只能跑一个。

把这两个维度拆开之后,决策就变得清晰:**agent 并行度按任务的独立性决定(不被机器算力牵制),重进程数量按机器实测能力单独限流**,
不要因为后者保守就连带牺牲前者。

**并行派发由独立性检验决定,不由数字决定。** 判据很简单:

- 讨论、解释、status、有限的只读探查:单 agent 就够,不派。
- 只有同时满足两条才 fan-out:(1)存在**真正独立、写入边界互不重叠**的工作单元;(2)并行有
  **可量化的墙钟收益**(比如几个单元各自要跑很久,串行会明显更慢)。
- fan-out 时按编号的 **Wave(批次)** 组织:同一 wave 内的 agent 互不依赖、写入边界不重叠;下一批依赖
  上一批产出时才开下一个 wave。当前并发槽位装不下时,**分批**依次跑完,而不是缩小整体规划或把它们
  硬塞进同一批。
- 永远不要为了凑一个数字而拆分;也不要因为任务"模块多"就自动拆——模块多但改动强耦合的任务,拆开
  只会制造合并冲突和重复验证。
- 每个模块 owner 负责需求覆盖、实现、获准的测试、修复和复测；顶层编排者逐个独立验收候选，再整合并执行
  选定的共享检查。模块自验、主 agent 验收和已合并推送分别记录，统一门禁不替代模块自验。

## 按模块交付闭环派单

授权并行实施后，从第一次派单就指定持续负责的模块 owner，例如“完成带权限、分页、真实查询接线和异常测试的
订单查询”，而不是只派“探索目录”“写接口文件”或“运行测试”。探索和审查可以辅助，交付责任始终有人承担。
owner 在批准的契约内决定局部实现，内部依赖缺失由编排者协调对应 owner 继续开发；跨模块决策才升级。

每轮执行可返回候选、未完成检查点或具体阻塞。一轮 agent 结束不解除模块责任；验收退回后由原 owner 修复复测，
需要换人时明确交接代码、证据和下一步。测试权限与资源槽位分别确认：重检查只有精确命令、准备好的隔离环境和
实际槽位都具备时才执行；排队时保存可续作检查点，主 agent 获得容量后续派，不能把等待写成通过或卡死。

心跳审计复用同一账本和关联派单，检查每个模块的实现、测试、修复、待验收与落地阶段。验收积压时优先收口已有
候选，不以增加 agent 数作为进度。具体执行约定见
[模块交付](../../skills/agent-orchestration-guardrails/references/module-delivery.md)和
[模块闭环审计](../../skills/agent-task-supervision/references/module-delivery-audit.md)。

接线、执行和验收的投入随瓶颈调整，试验配置及证据口径统一见
[容量平衡规则](../../skills/agent-orchestration-guardrails/references/capacity-balance.md)。例如多个模块等待同一个启动
接线时先推进该依赖；候选堆积时优先验收；重测试槽位已满时调整检查范围与调度。模块 owner 继续负责自己的
内部接线和修复，新增接线席位也必须有独立写入边界。每次调整记录预期效果和复查点，按实际依赖解除、等待时间
及已验收和已落地模块变化判断效果，不能把活跃 agent 数或参考比例当成效率证明。

没有项目测量时不预设人数比例；按独立候选、跨 owner 依赖和验收工作安排一次有复查点的小范围试验。
跨模块候选尽早指定接线负责人，提前核对基线、实际调用链、测试适配、契约指纹、架构登记和验收入口，
共享文件仍由唯一 owner 修改。心跳区分资源等待与返工原因，复查同范围完整功能交付、首次提交的验收结果
及返工轮次；报告比率时给出分子、分母和仍待裁决的候选。单次队列为零不能证明全程没有资源瓶颈。

## 编排者读结论，不读原始 diff

编排者的上下文要装下目标、契约、依赖顺序和所有待裁决的问题。如果每个候选交回时它都亲自读 diff、日志和
完整文件，上下文很快被底层细节塞满，整轮的验收吞吐也会卡在这一个会话上。所以不管顶层是哪个模型，候选交回
时编排者默认只读审查者按固定格式交回的结论：建议接受、退回还是阻塞，问题定位，涉及的风险类别，看了什么、
没看什么，置信度，以及完整证据的文件路径。

只有五种情况才打开原始 diff：结论标了风险类别（钱、权限、迁移、密钥、不可逆操作，这类内容照旧逐字进编排者
上下文）；结论和 owner 的证据对不上，或者置信度不高；跨模块契约、共享文件或架构边界有变动；按比例抽检，
起始值是每 5 个常规候选至少抽 1 个；候选里有编排者自己写的集成或合并改动。最终拍板权不变，变的只是编排者
读什么。审查者首选和 owner 不同厂商的模型，因为同一家模型的盲点往往相关。格式和规则见
[审查结论与编排者输入](../../skills/agent-orchestration-guardrails/references/review-verdict.md)。

## 只派单模式的触发条件

单 agent 自主运行的会话，满足任一条件就切换为只派单：已经或预计运行超过两小时（包括过夜和无人值守），或者
在还有实现工作没做完时已经发生过一次上下文压缩。这个模式要保护的是编排者的上下文不被实现细节污染，而上下文
消耗和时长没有必然关系：一个小时的大重构可能早就塞满了，三个小时的小修可能还很干净，所以上下文压缩也算触发
条件。心跳监督的启用条件没有变，仍然按时长判断，两者是不同的机制。

## 编排规则的假设与退役

这里的红线几乎都是从事故里长出来的，每一条背后都有一个"模型自己做不到什么"的假设。规则只增不减，就会在它防
的那种行为早已消失之后继续占用上下文和注意力。所以每条红线都要登记它编码的假设、来源事故和复审条件；换代模型
成为编排者或某一档 worker 的默认模型时，挑最多三条允许试验的规则，按容量平衡里的规则做一次有复查点的小范围
试验，有证据之后再决定保留、收窄还是删除。涉及钱、安全边界、不可逆操作、人类主工作区、跨会话资源和配额硬停的
规则不在真实工作上做放宽试验，只根据事故和审计证据复审。登记表见
[规则假设与退役](../../skills/agent-orchestration-guardrails/references/rule-assumptions.md)。

## 把固定规则交给运行时

只写在文字里的规则，要靠编排者在每个派单 prompt 里重抄一遍、再靠 worker 读到并遵守，漏抄一条就等于这条规则
失效。所以能交给运行时的部分，kit 现在交给运行时：

- **角色定义。** `skills sync` 会把四个 Claude 角色写进项目的 `.claude/agents/`：只读探索者、模块 owner、
  审查者和子规划者。每个角色固定了模型和工具白名单，worker 的固定规则写在角色正文里，派单时只填这次任务的
  变量。只读角色根本没有编辑、shell 和派单工具，模块 owner 没有派单工具，所以嵌套层数受限不靠自觉。审查者
  没有 shell，编排者要先把候选 diff 和日志导出成文件交给它。
- **派单守卫。** 一个挂在 `Agent|Task` 上的 PreToolUse hook：调用里没写 `model`、用的也不是固定了模型的
  角色，就拒绝；`fork` 派单一律拒绝，因为它只能沿用调用者的模型和完整上下文。项目可以在配置里关掉某条规则
  或追加提示。它管不到 Codex 派单和工作流脚本里起的 agent，这两处仍然靠文字规则。
- **交付格式校验。** 任务包、worker 最终交付和审查结论都有 JSON Schema 和一个零依赖的校验器。校验不过的
  交付按阻塞处理，校验不过的审查结论按没审过处理；校验器还会直接给出这次候选要不要打开 diff。

细节见[运行时约束](../../skills/agent-orchestration-guardrails/references/runtime-enforcement.md)。

## 子规划者：大规模扇出时的中间层

所有模块都直接汇报给顶层编排者时，模块一多，顶层就是单点。子规划者负责一个领域子树：拆分子树里的模块、写
任务包、根据审查结论裁决常规模块，自己不写代码，也没有合并和发布权限。高风险类别、跨领域契约变更和架构岔路
一律上报顶层；一个子树需要另一个子树改东西时，也只能经顶层转达。层数仍然最多两层。

规模换算只数同时在跑的模块 owner，探索者和审查者是辅助，不算在内。两条限制同时成立：每个子规划者管 3 到 6 个
活跃 owner；顶层直接管的对象（子规划者加上它自己直接带的 owner）不超过 6 个。

| 同时在跑的模块 owner | 子规划者 | 顶层直接管 |
| --- | --- | --- |
| 1 到 6 | 0 | 所有模块 |
| 7 到 12 | 2 到 3 | 子规划者、跨领域契约 owner、跨模块接线 owner |
| 13 到 24 | 3 到 4 | 同上 |
| 25 个以上 | 不再加 | 拆成几个独立批次 |

区间里取几个，看业务有几个自然领域；不到 3 个模块的小领域并进相邻子树或留在顶层，绝不为了凑数去拆领域。
案例：会员积分体系有 12 个模块、3 个领域。顶层直接管 5 个对象：跨领域契约 owner（积分 API 和积分事件
schema）、启动组装的接线 owner，以及账本域、客户端域、事件与运营域三个子规划者，各带 4 个模块 owner。第 0
波先冻结跨领域契约，第 1 波三个子树并行。埋点、报表这类常规模块由子规划者根据审查结论拍板；账本、迁移、兑换
涉及钱和迁移，上报顶层，加一次跨厂商审查，原始材料逐字进顶层。客户端域要给兑换 API 加字段时，先上报，契约
owner 改契约，账本域再跟进。顶层上下文里只有三份子树摘要和几条上报，不再是 12 份 diff。只有 5 个模块时不设
子规划者。

这些数字是起始值，状态是试验：第一次用在一个至少 8 个模块的真实任务上，记录顶层验收排队时长、上报次数、每个
模块的返工轮次和首次提交通过的模块数，再和之前规模相当的一次对比，按结果调整。详见
[子规划者](../../skills/agent-orchestration-guardrails/references/sub-planner.md)。

## 可复用技术模式:小任务走单 agent

不是所有任务都值得走"拆分+派发+等待+核对"这套完整流程。当一个任务**同时满足**以下几个条件时,
默认由主 session 直接改,不派 subagent:

- 改动量很小;
- 局限在单一模块内,不跨边界;
- 不涉及需要额外治理的高风险变更类型(例如不改数据库结构、不改公开 API 契约)。

经济学依据是:对这类任务,"写清楚派发说明→等待完成通知→核对结果"这套流程本身的开销,可能反而
超过直接手改的成本。判断应该在动手前对照清单明确核对,而不是凭感觉;更稳妥的做法是让项目的 gate
工具给出 lite / full 分类(见 `coding-gate-preflight`),agent 不自行改判。

## 重进程限流数字怎么定:一次真实的"压垮主机"事故

"重进程并发度按机器实测能力单独限流"这条原则,光讲道理容易被低估——直到真的撞上一次主机被压垮的
事故,才会理解这个上限不是保守起见的锦上添花,而是防止"所有人一起变慢"的硬约束。

一次真实事故里,一台 10 核主机上同时跑着:一个原生移动端构建、一个嵌入式固件工具链的构建、一次
golden 文件回放流水线重跑、外加好几个后端单测/前端构建进程——没有人单独去限流,因为每个 worker
看起来都只是"跑自己那部分的验证"。结果 load average 冲到核数的 15 倍以上,所有在跑的进程一起变慢,
包括那些跟这几个重进程完全无关的 worker 的测试也开始超时。这里有个容易被误判的细节:**这些超时
本身不是代码缺陷**,是主机过载导致的假阳性——如果这时候有人把"测试超时"当成一个需要修的 bug 去
排查,排查的是一个根本不存在的问题,浪费的是整轮调试的时间。正确的处理方式是在负载降下来之后单独
重跑一次那个测试再下结论,而不是当场就开始"修"。

这次事故之后固化出的具体数字是:**同一台主机,核数 ≥10 时同时最多允许 2 个重进程组,核数更少时
最多 1 个**——这是一个可以直接拿来当起点的默认值,不是要求逐字照抄,新项目应该用自己真实的核数和
内存峰值重新校准,但"先定一个具体数字,而不是留给感觉"这件事本身值得直接搬。

## Nova 案例参考

Nova 项目的具体选择(仅供参考,新项目应按自身机器规格和业务复杂度重新决策):

- 本地开发机配置有限,重进程(类型检查、构建、端到端测试、依赖安装)全局并发限流为 1;
- 云端专用测试机算力更强,可以同时跑 2 组常规重进程,但端到端测试仍然单独限制为同时最多 1 个,
  因为浏览器自动化的内存峰值远高于普通单元测试;
- 不管重进程限流设置成多少,agent 的派发判据(独立性检验)不因此改变——两个维度在实践中被严格
  分开配置,不共用同一个"并发数"参数。
- 小任务的判定标准被写成一份显式清单,几个条件必须同时成立才默认单 agent,平时执行任务前先核对
  清单再决定要不要派 subagent,避免凭感觉做决定。
- 心跳/监督机制(如果项目有的话)顺带扫一眼主机 load:超过核数的 2 倍就暂停派发新的重任务,直到
  负载降下来,而不是继续按原计划铺开下一波重进程。
