# 大规模规划调研:先裁决,后调研

## 问题:为什么需要这个机制

大型需求的多文档规划(拆出多个模块文档、跨多个 AI session 执行)通常会先派一批调研员摸清现状,再
由主 agent 综合成总体规划。这个顺序本身没问题,但如果调研员拿到的任务边界太宽——尤其是那种"跨
模块该怎么设计"这类开放性问题——就会出现一个反直觉的浪费模式:**多个调研员会各自把同一件跨模块的
事整套设计一遍**。比如"鉴权该怎么做"这种问题,调研员甲会给出一套完整方案,调研员乙、丙也各自给出
一套完整方案,三套方案互斥,主 agent 最后要读完三份摘要才能选一个——调研阶段名义上是"收集事实",
实际上变成了"多个 agent 并行设计、主 agent 事后裁决",裁决成本被放大了好几倍,而且调研员在设计
方案时消耗的 token,并没有换来任何一份被采纳的最终结论。

另一个常见问题是调研数量的锚定效应:一旦"调研深度至少要 XX 个 explorer"这类数字被写成一条硬性下限,执行
者容易机械套用这个数字,而不是按任务实际的独立问题数去判断——需求本身只有 4-5 个真正独立的视角
时,依然会凑够两位数的调研员,其中大部分产出彼此重叠,徒增裁决和阅读成本。

## 设计原理:裁决先行,调研只做"事实 + 路径"

**把"设计"和"调研"拆成两个不同的阶段,顺序不能反。** 在派出任何一个调研员之前,主 agent 先做一轮
"裁决先行":列出这次任务里所有跨模块的决策点(鉴权方式、URL/命名前缀、部署位置、凭证存放口径、
数据放哪个库、同步还是异步……),对每一项:

- 项目已经有常设口径的,直接引用现有规则定死,不需要重新论证;
- 没有常设口径、但判断需要一点现状证据的,派 1-2 个"侦察型"调研员去确认事实(只找事实,不设计
  方案),回来后由主 agent 自己裁决;
- 真正拿不准、且落在项目决策者的决策域内的(比如安全参数、成本、产品口径这类),才正式提出来问。

这一步做完之后,才进入常规调研阶段。此时调研员的职责被**收窄**为:在已经裁决的约束下回答"现状
事实(文件:行号)→ 实现路径/技术框架 → 风险 → 测试建议",不允许在已裁决的事项上重新展开设计——
真正有价值的调研产出是"这个模块现在长什么样、要怎么改",不是"这个模块应该怎么设计"。

**调研数量按真正独立的问题数确定,可以设一个项目自定的上限防止膨胀,但不设数字下限。** 每多派一个
调研员都应该对应一个真实存在、且没被其它调研员覆盖的独立问题,而不是为了"看起来更全面"而凑数;
独立问题少,就少派。

## 可复用技术模式

1. **共享事实底稿**:调研正式派发之前,主 agent 先写一页"底稿"——关键文件路径、项目既有约定、
   裁决先行阶段已经定下的结论——发给所有调研员,避免每个调研员重复读同一批基础文件,把调研预算
   花在真正需要各自深挖的部分上。
2. **结论卡**:每份调研报告顶部放一张字数上限很小的"结论卡"(结论、关键文件、最大风险、对其它
   模块的接口假设)。主 agent 综合规划时先读结论卡做初步判断,只在需要细节时才回头读正文——不必
   为了做裁决而逐字通读每一份完整报告。
3. **契约先冻结**:当两个以上模块要共享一个接口(API 形状、字段、命名前缀……)时,在写其它模块
   文档之前,先由主 agent 把这份契约单独写死成一份独立文档。前后端(或任何两个并行开发的模块)
   都基于这份已冻结的契约各自并行实现、写 fixture 做单测——这样等到最后集成/审查阶段,不会再
   出现"两边对同一个接口的理解不一样"这类本可以在设计阶段就避免的问题。
4. **模块文档引用调研报告,不整段复制**:模块级文档里涉及具体文件路径、代码片段的部分,直接指向
   对应调研报告的绝对路径和小节,模块文档本身只保留决策结论、接口约定、文件改动计划、测试计划、
   派发指令——避免同一份事实被抄写两遍,抄写的第二份还可能因为后续调研报告更新而与原文脱节。
5. **Wave 划分要同时满足两个约束**:模块间的文件级写冲突(避免两个并行 worker 同时改同一个文件),
   以及主机重进程上限(见同模块"重进程限流"相关文章)——只按模块依赖关系划 Wave 而不考虑后者,
   容易在某个 Wave 里意外并发起好几个构建/端到端测试/回放流水线,把主机拖垮。
6. **计划本身自带预算,而不是等执行时才发现超支**:总体规划文档里应该预先写出调研阶段和实现后
   审查阶段各自的 token 预算,并在每个 Wave 的边界检查一次实际消耗相对于项目额度阈值的位置——
   把"要不要继续大规模并行"这个判断提前到计划阶段就想清楚,而不是执行到一半才发现要紧急收缩。

## Nova 案例参考

Nova 项目的一次大型规划里,调研阶段派了 14 个调研员,消耗约 220 万 token。事后复盘发现,多个调研员
各自把同一件跨模块的事整套设计了一遍:出现过 3 种互斥的管理端鉴权方案、2 种 URL 前缀方案、2 种密码
存放口径、2 种通知架构——四套"设计选项"分别来自不同的调研员,主 agent 要读完约 14 万字的报告摘要
才能逐项裁决。真正对最终规划有直接价值的,是调研员给出的具体文件路径和实现路径,而不是这些互斥的
整体设计方案本身。这次复盘之后,"裁决先行"被固化成规划流程里必须先跑完、且明确排在调研之前的一步;
调研数量从"下限起步、无上限"改成了"按独立问题数确定 + 明确上限";并新增了"契约先冻结"这一步——采用
之后的一次规划里,契约文档在开始并行实现之前就已经写死,后续的实现后审查没有再发现任何一条因为
前后端对接口理解不一致导致的缺陷。

这是 Nova 一次具体规划复盘出的经验;新项目应该按自己任务的实际规模重新决定调研数量的上限、
共享事实底稿要放哪些内容、结论卡的具体字数上限——但"先裁决、后调研,调研职责收窄为事实与实现路径"
这条顺序原则,以及"跨模块共享接口要先冻结契约"这条模式,是可以直接迁移的。
