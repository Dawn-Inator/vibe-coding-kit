# 长任务心跳监督机制

## 问题:为什么需要这个机制

当一个编排会话同时管理多个 subagent、跨越较长时间运行时,会出现两类单靠编排者的"当下注意力"很难
自己发现的问题:

1. **孤儿/卡死状态**——某个 worker 因为等待一个永远不会到来的通知、或者在汇报里写下"接下来我要做 X"
   就结束了本轮,悄悄停滞,而编排者的注意力正放在别的任务上,没有人注意到它已经不动了。
2. **并行度隐性下降**——编排者因为盯着手头几个具体任务,不知不觉忘记了"我本可以派更多并行任务"这
   件事:待办的工作单元数量其实还有很多,但当前同时在跑的 agent 数量却很少,墙钟时间被白白浪费。

这两类问题的共同点是:它们都不是任何单个任务执行失败导致的,而是**编排层面的状态漂移**——没有人在
专门看"整体协调得好不好"这件事本身。如果不建立一个独立于具体任务的监督视角,这类问题只能靠编排者
偶然想起来才会被发现。

**这两类问题不是"多 agent 编排"独有的**——一个**单个** agent 自主推进一个长任务(比如无人值守跑一
整晚)同样会遇到"方向已经跑偏了但没人发现"这个问题,只是表现形式不是"卡住的 worker",而是"这个
agent 自己陷入了某种重复但低效的模式,而当时没有任何机制会去检查这件事"。只从"agent 数量"这个维度
定义触发条件,会漏掉这整整一类场景。

## 设计原理

需要一个**周期性的自我审计机制**,内容包括:

- 检查有没有卡住/孤儿状态的 subagent;
- 检查当前的并行派发程度相对于待办任务量是不是明显不足——"待办工作单元数很多,但同时在跑的
  agent 数很少",这种状态本身就是在浪费时间,应该被主动识别出来并触发补派;
- **顺带做一次"方向还对不对"的轻量检查**——复用项目已有的反逐点循环/推进过慢诊断(如果有的话):
  同一个子系统是不是连续几轮都在"修一次、全链重放一次"却没换策略,或者进度是不是明显停滞。
  **这一步只负责判断"要不要转介",不负责承担转介之后那份审查的成本**:没命中就到此为止;命中了先按
  已有的处置方式去做(换批量策略、先拆架构瓶颈);只有处置完之后判断确实需要一次**跨维度、可复核的
  完整评估**,才由编排者**显式**发起一次独立的重量级架构审查——那次审查永远是单独触发的,不能被
  心跳自动带出来,也不能塞进心跳自己的节奏里跑。

**这个机制本身是"建议性的",不应该有阻断权。** 它只负责发现问题、提醒编排者,不阻止任何收尾/推送类
操作,也不自己产出"通过/不通过"这种裁决。决策权始终在编排者手里:如果让它拥有阻断权,它就从一个轻量的
监督视角变成了另一个需要被绕过或对抗的门禁,增加协作摩擦而不是减少。

## 什么时候需要注册:量化门槛,而不是凭感觉

"这个任务感觉跑得比较久"没法在不同会话之间保持一致。**给触发条件定具体数字**,本身就是一种可复用的设计:

- **多 agent 编排**:同时在飞的 agent 数达到某个门槛(比如 ≥3 个),**并且**预计总耗时超过某个时长
  (比如 >2 小时)——两个条件同时满足才触发。
- **单 agent 自主任务**:即使只有一个 agent 在跑,只要它是无人值守地自主推进(比如"跑一整晚"),并且
  已经跑了、或者预计会跑超过同一个时长,也应该触发——**不需要凑够 agent 数量**。

两条门槛都**机械判断**:开发者是不是明确说了"跑一整晚""无人值守";待办量按经验估算是不是明显超过
阈值;或者干脆比较挂钟时间。低于两个门槛的普通任务,不注册这个机制,也不欠一条心跳状态。具体的数字
不是重点,重点是**要有具体数字**,让"要不要触发监督"不必每次重新讨论;新项目按自己的任务规模定数字。

## 机制:一个入口,一份账本,一行状态

Nova 的心跳最终收敛成三件事,每一件都是被前几版的失败逼出来的。

### 单一武装入口

心跳只有一个入口:`heartbeat:arm`。编排者用后台 shell 运行它,它睡满一个间隔(默认 20 分钟),打印审计
清单后退出;**这条后台命令的完成通知,就是唤醒会话的那个事件**。它是一次性的:每次唤醒的顺序固定为
"**先续上下一次,再做审计**",这样审计被打断也不会断链。清单里直接给出本次唤醒要追加的账本段落标题和
状态行格式,模型每个周期都会在眼前重新看到一遍该做什么。

为什么不让模型手写 `sleep 1200; echo HEARTBEAT`?因为手写的定时器什么都不带:没有清单、没有账本路径、
没有状态行格式,会话很快就退化成"定时器照响,但没人审计、也不留记录,对话框里堆满长篇状态说明"。把
"怎么武装"固定成一个脚本,等于把审计流程的入口也固定下来了。

为什么不用平台的 cron 式调度器?因为它"接受了任务、列表里也看得到",不等于"会真的叫醒你"——Nova 和另一个
采用方项目各自独立撞上过:调度器全程显示任务存在,应触发的时点却一次都没送达。受后台任务机制追踪、结束
即通知的定时器,是唯一经过实测的通路。所以仍然保留**投递探针**:`heartbeat:arm -- --probe` 是一个约一分钟
半的、不需要账本的短计时,先武装它、让出空闲窗口,探针送达了才武装真正的心跳;没送达就如实说"这条通路在
当前环境不投递",并退回只靠事件锚点,而不是留一个不会响的"心跳"然后汇报说已启动。

### 账本与续期门

每次唤醒的详细内容只追加进一个会话级账本文件(放在会话草稿目录下,例如
`.workspace/task/<session>/heartbeat.md`)。每段以 `----` 分隔,标题固定为 `## <ISO 时间> wake (10-row ledger)`,
带一行 `sources:` 说明这次查了哪些发现渠道,再加一张十类目逐行表。表里每一行只能是几种固定状态之一,
`blocked` 必须点名一个排他资源,`deferred` 必须写明它在等的输入和不超过 20 分钟的预计时间,同一个输入连续
两次唤醒都在 deferred 就必须升级——这些判据由一个机械检查器逐行验证,因为"自己给自己打分的账本"迟早会
变成文字游戏。检查器只看最新一段(`--latest`),历史段落作为记录保留、永不为了过检查被改写。

状态里有一个省字的写法:`` unchanged — `<本次唤醒重跑的命令>` ``,只给第 2 到 9 行用,表示"这一行自上次唤醒没变"。
它有三道边界,都由检查器卡住:第一次唤醒没有"上次"可沿用;上次唤醒是 `deferred` 的行必须重新写出来,否则
"同一输入连续 deferred"的规则就看不见它;目标行(1a/1b)和漂移行(第 10 行)每次都要写全。而且它必须带一条
反引号包住的、本次真的重跑过的命令——不带命令的"没变",只是一句没人验证过的断言。

`sources:` 这一行在 `--latest` 下也会被逐项验:每个发现渠道的记号都要在、都要标成已查;外部缺陷队列另有
节奏——会话开始时读一次,之后至少每 6 小时读一次,所以它的记号带着真正读取的时间;读不到时写成
`blocked ← <原因>`,并且在登记表里开一条 `owner ←` 的条目点名这个阻塞,否则就是一条没人认领的盲区。漂移行
同理,要么引用你声明的"阶段 x 单元"矩阵做过的核对,要么点名哪些单元没查。没加 `--latest` 时,检查器对
`sources:` 只要求这一行存在。

**续期门**把"写账本"变成"继续续期"的前置条件:每次真正武装都会往账本旁边的 `heartbeat.arms` 文件追加
一行;第 k+1 次武装,要求账本里至少已经有 k-1 个唤醒段落,否则脚本拒绝(退出码 3)并提示"上一次唤醒没写
账本段"。因为顺序是"先续上、再审计",这个门天然落后一个周期,正好卡住"只续期、不留记录"的会话。

计数为什么单独放在 `heartbeat.arms` 里,而不是账本里的标记?因为早期版本把标记写在账本中,结果某次
测试会话用脚本整份重写了账本,标记跟着消失,门形同虚设。**独立的、只由武装脚本追加的计数文件,抗得住
"某个脚本把账本整个重新生成"这种操作。**

### "能不能拆"的默认答案是能

检查器如果只问"有没有可拆的?",得到的答案是写给检查器的:上一次唤醒写了 `blocked ← <另一个单元> unlanded output`,
这一次照抄,检查器看到"点名了一个资源"就放行,而这条阻塞其实可以直接基于那个未落地分支开工、只让最后的落地等待。
真实事故里这样的行挂了几个小时,主人一句"看看能不能拆解并行"就立刻翻出一批当场可开工的单元。根因有四层:答案是写给检查器而不是主人的;
问题是开放式的而不是预设式的;上一轮的答案成了下一轮的锚,检查只在很久之后才变红;写"没有"没有任何代价。

所以规则反过来:**默认答案是能拆,"不能"才是例外,而且要逐项证明。** 每次唤醒,表里每个 `blocked ←` / `deferred ←` 行
(以及登记表里每个 `blocked ←` 行)都要在唤醒段落的 `re-split:` 行里拿到一个裁决:`split→dispatched <单元>`,或者
`cannot-split: <带标签的证明>`。证明只有几种固定标签:`needs-landed: production effect`(这一步要生产影响,必须等已落地的 SHA)、
`branch-unstable: <分支> rewritten in the last 60 min`、`owner-gated`、`same-file conflict: <文件路径>`。
只在等另一个单元的未落地分支或产出,而没有这些标签,检查器直接判红(`blocked-on-unlanded-branch-defaults-free`),
`heartbeat:sweep` 则把它列为空闲候选,第一步是"begin on <branch>, land after it"。
只要还有行没有合法裁决,`prep-ahead(none — …)` 和 `audit(none — …)` 就被拒绝。唤醒段落还要写
`splittable: <本次派发数>/<带证明的阻塞行数>`,检查器核对它与裁决一致,对话框状态行也带上它。

### 对话框每次只一行

账本是详细记录的地方,对话框只回一行:`[heartbeat] in-flight N · xx% · splittable: D/P · blocked: <none|item>`,其中的
数字和百分比必须是真实的,只有出现异常时才展开。这条规则的背景很朴素:状态长文每次唤醒都要消耗一整轮
上下文,而且没人读;把详情放进账本、把对话框压到一行,既保住了可审计性,又省下了每个周期的成本。
同样的道理也适用于 worker 的中间通知:后台工作还在跑、没有终态结果的通知,回复为空,不复述、不重打状态行。

## 前置 guard hook:只检查前提,不持有状态

模型有时会在从未读过监督 skill 的情况下直接武装心跳,于是 skill 里写的所有规则都落空。解法是一个
PreToolUse hook:**当一个会话第一次运行 `heartbeat:arm` 时,检查对话记录里是否已经加载过这份 skill,
没有就拒绝,并告诉模型先去读它**;它同时拒绝手写的 `sleep ...; echo HEARTBEAT` 定时器,把它们引回唯一入口。

这个 hook 刻意**只检查一个前提条件,不持有任何状态、不跑定时器、不写任何文件**:判断完全来自它当次拿到的
对话记录,没有什么东西会和现实脱节。任何读不出来的情况(没有记录路径、文件读不开、输入不是合法 JSON)都
放行——守卫自己的 bug 永远不应该挡住一次正当的工具调用,所以它总是退出 0、按 hook 约定打印一段 JSON。

## 公告式收尾检测:每次唤醒对每条完成通知都跑

文字规则"worker 不要以下一步的公告收尾"挡不住这种失败:worker 报完"接下来我要实现修复",本轮就结束了,
没有任何东西在跑,也没有任何东西会叫醒它。所以每次唤醒,编排者对本窗口内**每一条**已完成的 worker 通知
运行 `heartbeat:check-stall`——不是只对"看起来卡住"的那几条,因为卡住的 worker 在外面往往恰恰看起来
一切正常。检测器是一个零依赖的启发式:通知以公告式的下一步结尾、没有任何执行证据、也没有提到自己起了
后台任务,就判为疑似停滞。它宁可漏报也不误报(误把合法的后台等待标成卡住,会让编排者学会无视它),
**阳性的含义是"去看一眼这条通知",不是裁决**;确认停滞后,同一次唤醒就推它一把。

## 机械发现:每次唤醒先跑 `heartbeat:sweep`

账本检查器只验证账本"写得对不对",从来不会发现"本该有、却没有的条目"。Nova 早期的发现全凭编排者当下的
记忆:哪些提交落地了还没复盘、哪些 worktree 早已落地却没人清、哪一行被追加到了登记表之外。结果是
有人反复追问"还能拆解吗",才一件件翻出遗漏。**凭记忆回忆"我漏了什么",天生不可靠**——漏掉的恰恰是
记忆里没有的东西;而一条只读、几秒内跑完的命令,每次都会把同样的问题问全。

所以每次需要决策的唤醒(定时器到点、worker 落地或最终汇报、人类来消息;不含只有中间进展的通知)都先跑:

```
node .vibe-coding/kit/src/supervision/heartbeat-sweep.mjs --ledger <账本路径>
```

它只读、不联网(从不 `git fetch`;要新鲜的远端引用,调用前自己拉一次),对登记表里**还没有覆盖**的候选各
打印一行,格式就是 `## Items` 表自己的行格式,状态固定为 `ready`;退出码 0 表示没有候选,1 表示至少有一个,
2 表示用法错误。编排者要做的只有一件事:把每一行摄入登记表,并在同一次唤醒里派发它,或者带证据改判成
`blocked ←` / `owner ←`。看见了却留到"下次唤醒"的候选,等于没发现。

kit 自带三类基线发现,都与具体项目无关:

- **落地(landings)**:对每个被跟踪的基线分支(`--base <ref>` 可重复,默认取远端默认分支的追踪引用),
  找出"上次复盘点"——已标记 `done` 的 `landing:<sha>` 条目里,既是分支祖先、又离分支末端最近的那个——
  然后列出之后还没有任何 `landing:` 条目点名的连续提交区间。区间打印的行数有上限,超出的部分汇总成一行。
- **worktree**:已登记的受管 worktree 里,kit 自己的回收判据会放行的那些——HEAD 已落地、工作区干净、没有
  进程把它当工作目录、**且不在最近活跃窗口内**。证据栏直接给出回收命令的试运行形式;活跃的树永远不会被提议。
- **登记表卫生**:被追加到 `## Items` 表之外的条目行,以及重复的 id。

**扩展点**在 `--probes <文件>`(或环境变量 `HEARTBEAT_SWEEP_PROBES`):项目自己的漂移探针放在这里——
已部署版本落后于分支末端、外部缺陷队列里的新条目,等等。文件可以是一个 JSON 数组,或一个默认导出函数的
ES 模块,返回额外的候选行;它们和基线候选走同一套去重与摄入。**探针自己抛错时,sweep 会把这个错误本身
变成一行候选**——一个悄悄失效的探针,等于把它本该发现的漂移一起藏了起来。kit 不预设任何项目专属探针;
这条边界是刻意的,探针依赖的是你的部署和你的缺陷系统。

## 两条边界

- **一次性条件等待器不得顶替心跳。** 等一个健康检查通过、等一次部署完成,需要另起一条独立的链;它不能
  取代心跳自己的续期,也不能把续期吞掉。每次唤醒的第 0 步除了配额和负载,还要确认心跳链本身还活着,
  断了就当场重新武装。
- **清理。** 任务或会话结束前停止续期、取消所有已武装的计时器和探针,不留孤儿定时器。

## 建议权的边界:能标记异常,不能自己动手处理

监督机制发现异常之后,**只能标记出来,不能自己代替编排者去处理**。这两个动作在很多场景下看起来是同一件
事的两半,顺手就做了,但在多 agent 并发的场景下必须严格分开:

- **监督者可以做的**:发现某个 worker 的状态信息缺失、过期、或者跟其它证据自相矛盾,把这个发现报告给
  编排者。
- **监督者不能做的**:代替编排者去强制结束那个存疑的进程、代替调用者去执行本该由它自己执行的收尾动作、
  或者直接删除看起来"有问题"的资源(它认为已经不需要的 worktree、分支)。

原理是:**监督者能看到的信息天然是不完整的**——它看不到编排者掌握的完整上下文(比如这个"看起来卡住"
的 worker 是不是正在等一个编排者知道、监督者不知道的合法长耗时操作)。凭不完整的信息去执行有副作用的
动作,一旦判断出错,造成的影响比"没有及时发现问题"更严重;而"晚一点被人工确认"永远是可逆的。

配套的另一条原则是:**判断"某件事有没有完成",只能依据这件事本身产生的终端结果,不能依据描述这件事
的元数据**。任务 ID、会话 ID、某个身份字段只是方便事后归因的标注,不是"已经按预期跑完"的证明。手头只有
元数据、没有终端结果记录时,正确的结论是"证据不足,无法判断",而不是乐观地推断"应该是完成了"。

## Nova 的落地选择

Nova 的门槛定的是"同时 ≥3 个 agent 在飞、且预计总耗时 >2 小时",或"单个 agent 自主推进、已经跑了或预计
会跑 >2 小时(无人值守)",满足其一就触发。**单 agent 这一条是后补的**:最初的门槛只看 agent 数量,直到真实
撞上一次跑了很久的单 agent 自主会话——它从来没凑够"多 agent"这个条件,整场会话没有触发过任何一次方向
检查——才发现"只看数量"这个设计本身有盲区。新项目定自己的门槛时,可以直接把"单 agent 长任务"也算进去。

方向检查的转介边界也是补了一版才定型的:最初只写了"顺带检查一下方向对不对",没说清楚"检查完发现真有
问题"之后该怎么办,留下的空子是这个轻量检查被悄悄升级成一次完整的架构审查,把每次心跳都拖成重量级动作。
Nova 后来把边界写死:心跳这一步的唯一职责是"要不要转介"的判断,转介出去的是一次编排者显式发起、独立
触发的审查,既不允许心跳把它顺带做了,也不允许审查因为心跳命中信号就自动跑起来。

采用时需要自己决定的只有这几样:门槛的具体数字、间隔(默认 20 分钟)、账本的位置、十类目里哪些对你的项目
有意义,以及你自己的漂移探针。工具和规则本身——单一武装入口、续期门、一行状态、前置 hook、公告式收尾检测、
机械发现——可以原样使用。
