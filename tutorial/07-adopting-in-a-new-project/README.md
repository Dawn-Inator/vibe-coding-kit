# 07. 在新项目里落地这套方法论

前面六个模块分别拆解了「AI agent 协作开发」方法论的六个切面——知识产物治理、worktree
隔离、多 agent 编排、质量门禁与发布、bugfix 闭环、代码架构决策。本模块回答最后一个问题:
**如果我现在要在一个全新项目里重建这套骨架,应该按什么顺序做、哪些能直接抄、哪些必须自己
想清楚?**

本文档中的示例项目一律用代号 **Nova** 指代——它是这套方法论最初被摸索出来的那个真实项目,
文中出现的目录名、文件名、字段名(如 `.vibe-coding/`、`gate-cycle`、`frontmatter`)都是纯技术
命名,可以直接照抄。

---

## 阶段 0:先决条件——这套方法论值不值得引入

不是每个项目都需要这一整套骨架。完整版本(worktree 隔离 + 双门冻结 + 多 agent 编排纪律)是为了
解决「多个独立工作单元并发修改同一份状态」而生的工程问题——如果这个问题根本不存在,引入这套机制
就是纯粹的过度设计,只会增加认知负担和维护成本。

**一个简单的判断标准:下面三条只要有一条成立,就值得开始引入(至少从阶段 1、2 开始);三条都不
成立,就先不要碰 02/03/04 这几层机制,单人单会话直接在主分支上写代码就好。**

1. **并发**——会有不止一个 AI 会话(或人类协作者)同时对同一个仓库做非只读修改。哪怕现在只有
   你一个人,但你习惯开多个终端标签同时跑好几个 AI 会话处理不同任务,这条也算成立。
2. **长期演进**——项目预期会持续开发数月以上,而不是一次性脚本或短期原型。短命项目里,任何治理
   机制的建设成本都收不回来。
3. **经验复用**——你希望「AI 在这次会话里踩过的坑、做过的判断」能被下一次会话(不管是你自己重新
   开一个会话,还是别的协作者)直接读到,而不是每次都从零摸索一遍。

只有当协作规模、项目寿命、经验复用需求这三者共同达到一定量级时,治理成本才会被后续省下来的
协调成本覆盖。判断错了也不是灾难——方法论本身是分层的,阶段 2(知识产物骨架)几乎没有引入成本,
可以作为默认起点;真正有明显搭建和维护成本的是阶段 3(worktree)和阶段 4 的复杂形态(双门冻结),
这两层可以随时往后推,等痛点出现了再补。

## 阶段 1:先搭代码架构骨架,再谈 AI 协作机制

**对应模块:[`06-codebase-architecture`](../06-codebase-architecture/)**

这是最容易被跳过、但最不该跳过的一步。原因很直接:后面几层 AI 协作机制——尤其是质量门禁、
preflight card 类型的预检——检查的对象是「代码是不是符合架构约定」。如果架构约定还没定下来,
门禁没有东西可以对照检查,写出来的门禁要么是空壳,要么检查的是错误的东西,后续推翻重来的成本
比一开始就想清楚高得多。

这一步要在动手写协作机制之前做完的具体内容:

1. **monorepo 顶层目录所有权划分**——哪些目录归哪个子项目/子团队负责,新增目录要挂在哪一层。
2. **五层术语分离**,想清楚服务边界要不要拆:业务概念(business capability)、代码
   (package/module)、进程(deployable process)、部署(deployment target)、数据库
   (logical/physical database)这五层是可以独立变化的——一个业务概念不一定要对应一个独立进程,
   一个逻辑数据库不一定要对应一个物理数据库。先用这五层各自回答清楚,再决定要不要拆分服务,
   避免「过早物理拆分」或「该拆的时候拆不动」两种极端。
3. **API 规范**——RPC over HTTP 还是传统 REST,方法集合怎么限定,URL/路径命名规则怎么和代码
   结构对应。选哪种不重要,重要的是想清楚取舍并写下来,而不是让每个开发者(人类或 AI)各自发挥。
4. **后端读写分层约定**——查询路径和写入路径要不要分开、DTO 组装放在哪一层、跨服务调用走什么
   通道,定成硬约定而不是靠代码评审临场判断。
5. **schema / migration 治理方式**——用什么形式记录 schema 变更(单文件 SQL、版本化目录、还是
   ORM migration),谁是执行真源(migration 历史本身,还是一份独立的 ledger)。

想清楚这五件事之后,阶段 4 的质量门禁才有明确的检查对象,阶段 2 的 skill/memory 才有具体的
业务领域可以挂载分类。

## 阶段 2:知识产物骨架

**对应模块:[`01-knowledge-artifacts`](../01-knowledge-artifacts/)**

建三个目录 + 一份入口文件:

```
.vibe-coding/
├── skills/       # 触发式的操作指南——"做 X 之前先读这个"
├── memory/       # 经验判断——"上次踩过的坑,下次怎么绕开"
├── history/      # 事件记录——"什么时候做了什么、为什么、怎么验证的"
└── loading.md    # 入口文件:每轮注入的最小纪律 + 触发索引(角色对应 Nova 的 CLAUDE.md)
```

`bootstrap-templates.md` 里给了这四样东西的最小可用模板,可以直接复制过去改。

**关键心态:不需要一开始就有一大堆技能文件。** 技能库是随着项目实际踩坑逐步积累起来的,不是
坐下来先穷举写完「我们可能需要哪些 skill」。阶段 2 只需要:

- 三个目录建好、结构对(frontmatter 契约、生成投影+校验脚本的模式先抄过来);
- `loading.md` 写出最小骨架(见下方 loading.md 骨架清单),哪怕大部分小节暂时只有一句占位说明;
- 第一条 skill/memory/history 什么时候该写,等真的发生「AI 又在同一个地方摔了一次跤」或
  「一次值得记录的架构决策/事件发生了」的时候再写,不要提前臆造。

## 阶段 3:worktree 隔离机制

**对应模块:[`02-worktree-lifecycle`](../02-worktree-lifecycle/)**

**只有当阶段 0 的判断标准里「并发」这条真的成立——即真的出现多个 AI 会话/协作者需要同时在
同一个仓库工作——才需要引入这一层。** 单人单会话断续开发的阶段,直接在主分支(比如
`develop`)上工作完全没问题,不需要 worktree 隔离带来的额外认知负担(begin/end/guard 命令族、
身份注入、并发写冲突处理)。

一旦真的开始并发,才谈得上具体怎么搭:

- worktree 存放路径怎么定;
- begin/end/finish/guard 这套命令族要不要自己实现,还是先手动 `git worktree add`/`remove`
  凑合用一段时间;
- 需不需要 reference-transaction hook 这类技术拦截(防止 AI 会话在共享分支上误操作),还是先
  靠文字纪律观察一段时间,等真的出现误操作事故再升级成技术拦截。

这一层的搭建成本和维护成本都不低,晚一点引入没有坏处——工程实践上,"先吃到并发写冲突的苦头,
再针对性引入隔离机制",比"一上来就搭一套没人真正需要的隔离系统"更容易让团队理解为什么需要它。

## 阶段 4:质量门禁与发布节奏

**对应模块:[`04-gate-and-release`](../04-gate-and-release/)**

建议的起点是最简单的两级映射:

```
develop → dev 环境
main    → prod 环境
```

一个分支对应一个环境,门禁就是「这个分支上的检查过了没有」,没有额外的中间态。

**双门冻结(`gate/develop` → `gate/staging` → `staging` 这种三分支模式 + `gate-cycle`
状态机)是用来解决一个具体痛点的:验证过程中,目标分支被别的提交污染,导致"我验证的代码"和
"最终发布的代码"对不上。** 这个痛点只有在下面这种场景下才会真的发生:多个 worker 并行往同一个
目标分支推送,验证周期又足够长(比如要跑全量测试),导致验证开始和验证结束之间,分支 tip 已经
往前移动了好几次。

**不要一上来就复制最复杂的版本。** 建议路径:

1. 先用两级分支映射跑一段时间;
2. 观察是否真的遇到「验证的代码和发布的代码对不上」「验证到一半分支被污染」这类具体事故;
3. 遇到了,再引入冻结指针的概念——先只加一个冻结点(比如"发布前打个 tag,只对 tag 跑门禁"),
   不需要一步到位上双门 + 状态机;
4. 如果连单个冻结点都不够用(比如需要一个独立的验证线,允许在验证线上做红灯修复而不推回开发
   分支),再考虑双门冻结的完整形态,并且把冻结周期的强制关闭机制(比如用一个共享 git ref 记录
   周期状态,防止有人绕开纪律重新冻结)加上。

机制的复杂度应该跟着团队实际遇到的问题增长,不是跟着「这份教程写了什么」增长。

**唯一建议提前做的是 L0 前置条件层(见 [`08-test-architecture-governance`](../08-test-architecture-governance/)):**
在第一条需要构建 + 部署 + 测试的昂贵链路上线之前,就把它依赖的环境条件登记成清单、写一个只读 doctor。
冻结机制可以等事故出现再加,但 L0 缺失的代价是"每跑一轮只暴露一个新缺口"的串行链路——这个代价在事故
出现时已经付出了。同样建议从第一天起给测试和门禁设 L2 准入规则(只守不变量、必须有反向测试),
否则守卫层会比业务代码长得更快。

## 阶段 5:多 agent 编排纪律

**对应模块:[`03-agent-orchestration`](../03-agent-orchestration/)**

这一层是六个阶段里对前置条件依赖最少的——**几乎可以在任何阶段引入**,包括阶段 0 判断为
「单人单会话」的项目也可以部分采纳。原因是它的核心内容更多是「怎么写派发指令」「怎么给
不同任务分配模型档位」这类使用习惯,而不是需要预先搭好的基础设施:

- **三档模型路由的判断框架**——"这个任务有没有写权限""有没有一处需要判断的分叉"——哪怕你
  自己一个人操作单个 AI 会话,也可以借用这套框架决定要不要开一个只读的探索型子任务,还是直接
  自己上手写代码。
- **wave batching / task packet 模式**——按写入边界拆分任务、批量派发、统一回收验证——这套
  组织方式在有多个 subagent 并行工作时才真正发挥威力,但即使只有一个主 agent,也可以先按这套
  框架把任务拆清楚,为将来引入并行铺路。

真正依赖前置条件的只有"派发去哪"这个执行细节(比如派到独立 worktree 还是共享目录),那部分
要等阶段 3 就绪之后才能落地;派发纪律本身现在就可以开始用。

## 阶段 6:bugfix 闭环

**对应模块:[`05-bugfix-discipline`](../05-bugfix-discipline/)**

建议在项目开始收到第一个真实用户反馈的 bug 之后,就尽早引入这条规则:

> 修 bug 必须补两层自动化回归覆盖——本处回归(证明这一个 bug 确实被修好了)+
> 同类防线(证明这一类问题在其它地方不会再发生)。

理由是这条纪律的收益曲线非常陡:越早养成习惯,越早把「用户反馈的每一个 bug 都有对应的自动化
测试」变成默认动作,团队(和 AI 会话)就越不容易在项目变大之后靠“肉眼 + 真机冒烟”去赌运气。
反过来,如果拖到项目已经有几十个手动验证过、但从没写自动化测试的历史 bug 之后才引入,不仅要
补的技术债更多,团队心态上也更容易把这条规则当成「事后加的官僚流程」而不是默认习惯。

这一层不依赖前面任何阶段是否搭好——不需要 worktree、不需要复杂门禁,只需要项目已经有一个可以
跑自动化测试的地方。唯一值得同步定义的,是「拒绝 AI 建议要怎么归档」这条配套范式(即使决定
不采纳某个自动化建议,也要把决策理由记下来,避免同一个建议被反复提出又反复口头拒绝)。

## 一句话总结

整套方法论最值得抽象出来复用的,不是任何一个具体的目录名、命令名或触发条件的数值,而是几个
在教程六个模块里反复出现、只是每次穿着不同的具体外衣登场的**设计模式**:

- **唯一真源 + 生成投影 + 校验脚本**——手写一份权威内容,其它形态都是自动生成的投影,靠脚本
  保证两者不会漂移(01 的 frontmatter/汇总文件,06 的 OpenAPI 生成)。
- **共享状态用远程 git ref,而不是本地文件**——需要让多个独立会话都能读到"当前真实状态"时,
  本地文件天然只在一个工作目录里可见,远程 ref 才是真正的共享真源(02 的 worktree 身份、04 的
  gate-cycle 状态机)。
- **机器可校验的门禁优于纯文档纪律**——文字规则会被遗忘、被绕过,把它变成一个脚本会失败的检查
  (哪怕只是一个 hook 或一条 CI 断言),才能真正稳定生效(02 的 reference-transaction hook、04 的
  身份检查、06 的 governance 测试)。
- **先例外注册、后默认放开**——遇到需要绕过纪律的场景时,先要求显式登记例外(谁、为什么、什么
  时候),而不是默认允许所有人随时绕过(02 的逃生舱变量、04 的冻结周期强制关闭)。
- **三层防御(预防 + 复核 + 最后关卡)**——任何一层都可能被漏过,所以关键规则要在不同阶段各设
  一道检查,而不是只在入口把一次关(02 的多层身份注入、04 的 AI 提交身份三层机制)。

新项目落地这套方法论时,**理解这几个反复出现的模式,比逐字照抄任何一个具体机制更重要**——具体
的目录名、分支名、阈值数字换一个项目就要重新定,但「唯一真源」「远程 ref 共享状态」「机器可
校验门禁」「先例外后放开」「三层防御」这几个模式,换到任何工程场景都成立。
