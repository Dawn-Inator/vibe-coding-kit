# 05 Bugfix Discipline:让一次修复真的封住这类 bug

AI agent 改代码快,但"改完了"和"改好了、以后不会再坏"是两件事。这一节讲两个互相配合的机制:
**两层回归覆盖**(修 bug 必须补自动化测试)和**拒绝建议归档范式**(开发者否决过的做法不能被反复重提)。
两者共同解决同一个更底层的问题:AI 的"这次做对了"无法自动转化为"下次也会做对",除非有机制把
这次的判断固化下来。

## 一、两层回归覆盖

### 问题

修 bug 最常见的失败模式不是"没修对",而是"修对了这一次,但没有阻止它再发生"。人工验证——真机
截图、手动冒烟、"部署上去看起来正常"——证明的只是"这一次、这一台设备上是好的",完全证明不了
"下一次改动不会让它悄悄再坏一次"。而且用户点出的往往只是这类 bug 在系统里的一个可见实例,如果
AI 只盯着这一个点修,代码里其它同样错误的实现会原封不动地留着,等下一次触发。

### 设计原理

把"修复是否闭环"拆成两个独立可验证的层次,而不是一个笼统的"测试通过":

1. **本处回归**——针对具体这一个 bug 写一个测试,这个测试在修复前必须真的失败(红),修复后必须
   变绿。不能先写代码修好、再补一个"证明现在是对的"的测试——那种测试在修复前也是绿的,根本没有
   验证到 bug 本身,是假回归。
2. **同类防线**——把"用户点名一处"当作"要求扫描整类同样实现"的信号。如果有共享 hook / 工具函数 /
   中间件,把修复收敛到共享层,一次修复覆盖所有调用方;如果确认只能修一处、其它相似的地方其实不
   受影响,必须在交付时写清楚"为什么它们不受影响"——不解释就跳过等于没有核实过。

两层缺一不可:只有本处回归,防不住同类扩散;只有"扫了一遍说没问题",没有可重放的证据。

### 可复用技术模式:入口一致性校验

这条规则真正的风险不在"要不要写测试"这个判断本身,而在于**同一个判断点在实际流程里有多个入口**
(比如从外部 bug 追踪系统同步过来的修复任务、编码前预检清单、测试路由决策、常规任务规划)。如果
规则只写进其中一个入口,走另一个入口进来的 AI 会话完全读不到它,会重新问一遍"要不要加测试"。

通用做法是:不要指望文档覆盖率,而是写一个**机器可校验的一致性检查**,专门断言"这条规则是否被所有
已知入口引用",漏掉任意一个就直接报错。这把"靠人记住要同步维护"变成"靠脚本拦截遗漏",适用于任何
"容易被绕过一次就会造成真实损失"的规则,不限于 bugfix 场景。

```text
# 伪代码示意:一致性校验的骨架
required_entrypoints = [feishu_bugfix_entry, coding_preflight_entry,
                         test_router_entry, task_planning_entry]
for entry in required_entrypoints:
    assert rule_id("must-add-regression-tests") in entry.referenced_rules, \
        f"{entry.name} 缺少 bugfix 回归测试规则引用"
```

### Nova 案例参考

Nova 曾经历过一次真实反馈:AI 修完一批 bug、做完真机验证后,还在问开发者"要不要顺便加自动化测试",
开发者当场拒绝了这种把测试当可选项来问的做法,理由是"复发一次 bug 的成本远高于当场补测试的成本,
而且这次没主动提测试不等于不需要"。Nova 因此把"修 bug 必须补两层回归"写成硬规则,并配了一个扫描
"待修复入口 / 预检清单 / 测试路由 / 任务规划"四个已知入口是否都引用了这条规则的校验脚本。这是 Nova
自己的入口清单和校验实现,新项目要按自己实际有几个"进入 bugfix 流程的门"重新列一遍,不是照抄这四个。

## 二、拒绝建议归档范式

### 问题

开发者拒绝 AI 的某个建议(比如上面"要不要加自动化测试"),如果这次拒绝只停留在当次对话里,换一个
会话、换一个时间,AI 大概率会重新提出同一个已经被否决过的建议——因为 AI 没有跨会话记忆,唯一能
让它"记住"的方式是把决策写进它下次很可能会打开的那份文档里。这个问题在 bugfix 场景里格外突出,
因为 bugfix 是高频重复动作,同一类判断点(要不要测试、要不要扫同类、要不要先问开发者)会被反复
路过,一次遗漏就是一次重复消耗开发者的时间。

### 设计原理

把"被拒绝"当作和"被采纳"同等重要的决策产出来记录,而不是当作对话里一次性的情绪反馈。记录必须包含
三部分,缺一部分都会让未来的 AI 会话误用这条记录:

- **被拒绝的具体内容**——不是"AI 提了个建议",而是精确到"AI 建议了 X"。
- **开发者给出的理由**——只记录"被拒绝"这个事实、不记录理由,未来会话没法判断这条拒绝是否适用于
  一个稍微不同的新场景,容易把窄范围的否决错误地套用到宽范围,或者反过来漏掉本该适用的情况。
- **给未来 AI 会话的具体指引**——直接写"遇到这种情况不要再问,直接按 X 做",让下一次会话不需要
  重新推理"这条历史决策现在还适不适用"。

### 可复用技术模式:标题级结构 + 全文检索

这类记录必须用 Markdown 的标题(`##` / `###`)承载,而不是正文段落里的一句加粗文字。原因是可检索性:
如果检索机制是"按标题模式扫描全文找既定决策",一条埋在段落中间的加粗句子对这种检索是不可见的——
检索不到的规则,对下一次会话来说等同于不存在。标题结构同时天然满足了三段式的组织需要:

```markdown
### Owner 既定决策:<一句话概括被拒绝的建议>

<日期>:<触发场景一句话背景>

- **被拒绝的内容**:<AI 具体建议了什么>
- **开发者的理由**:<为什么拒绝,理由本身要可迁移到相似场景做判断>
- **防重复指引**:<未来会话遇到同类判断点该怎么做,而不是重新问>
```

这个模式和"01-knowledge-artifacts"模块里讲的 artifact-routing(新内容该归档到哪个文件)是同一套
知识治理体系的两个环节:artifact-routing 解决"写在哪",这里解决"以什么结构写、为什么标题级结构对
可检索性是必要的"。两者配合,才能保证"开发者说过一次"真正等于"以后不用再说"。

### Nova 案例参考

Nova 把"修 bug 必须补自动化测试"这条既定决策,以 `### Owner 既定决策:...` 的标题格式记录在项目约定
文件里,三段内容分别对应"AI 问了要不要加测试被拒绝""开发者认为复发成本高于补测成本、沉默不等于
不需要""任何 bugfix 相关入口都不得再把测试当可选项来问"。这是 Nova 自己选择的落点(项目约定文件 +
特定标题格式),新项目应该按自己实际的文档体系决定这类记录放在哪、用什么检索机制,只要保证"标题
级结构 + 全文可检索"这条设计原理不丢。
