# gate-cycle:用共享 remote ref 把纪律状态机机械化

## 问题:纯靠文档的纪律迟早会被违反

上一篇讲到,双门冻结流程里最关键的一条规则是:验证跑红了,要在修复线上就地修复,**绝不能**因为想
让红灯消失就重新把修复线指向开发分支的最新头。这条规则一开始只是写在文档里的一条纪律,靠 AI 自觉
遵守。

但这种纯靠自觉的纪律有一个结构性弱点:AI 完全可能"忘记"这条规则。尤其是当红灯确实很棘手、开发
分支上又恰好有其他会话刚推上来的、看起来可能相关的修复时,"干脆重新指向最新头,说不定顺便就把
红灯带过去了"是一个很有诱惑力的近路。一旦真的这么做了,正在进行中的验证证据就会悄悄失效——因为
候选提交的内容已经变了,但"这是第 N 次候选周期"这个计数、"红灯数量在周期之间可比较"这个前提,
都已经不成立了,而且没有任何机制会主动报错提醒。文档写得再详细、警告语气再重,也挡不住一次
"这次应该没事"的侥幸心理。

## 设计原理:把纪律状态化,让底层工具自己拒绝违规

真正可靠的解法不是把文档写得更长、警告写得更狠,而是把这条纪律从"AI 需要记住的一件事"变成
"系统本身就会强制的一个约束"。具体做法是:把"当前有没有一个正在进行中的验证周期"这件事,存成
一个**所有并发会话都能看到的共享状态**,并且让状态转移的每一步都通过底层版本控制系统的原生并发
安全机制来保护,而不是额外发明一套加锁逻辑。

这里的关键选择是用 **git 的一个自定义 remote ref**(而不是分支、不是本地文件、不是某个 worktree
私有的状态)来存这个共享状态。选它的原因是:

- ref 天然是所有克隆了这个仓库、能访问这个远端的会话都能看到的共享状态,不需要额外搭一个数据库
  或协调服务。
- ref 独立于普通分支树,不会和 `develop`/`staging` 等实际承载代码内容的分支产生混淆或误操作。
- git 对 ref 的推送本身自带一套天然的并发安全原语——快进推送(fast-forward push)在远端已经领先
  时会被拒绝,这正好可以用来实现"谁先谁后 git 说了算,而不是后写的直接覆盖前写的"这种效果。

## 可复用技术模式:一条只追加的状态提交链

具体实现上,这个共享状态引用(可以理解成 `refs/<namespace>/gate-cycle` 这样一个自定义引用路径,
而不是普通分支)指向一条只追加的小提交链。每条提交携带一份结构化的状态描述,典型字段包括:

- 候选提交 SHA
- 验证线当前指向
- 周期开始时间 / 发起者
- 上一次验证结果是红是绿
- 已经应用了哪些修复
- 这个周期有没有被正式关闭

**关键的并发安全设计**在于:对这个状态引用的推送永远是普通的、非强制的快进推送。这样一来,如果
两个并发会话同时想开启一个新周期,git 本身的"非快进推送会被拒绝"机制就会自然而然地拒绝掉其中
一个——不需要额外写加锁逻辑,也不会出现"谁先谁后无所谓、后写的直接覆盖前写的"这种悄悄丢失状态
的情况。后到的那个会话会收到一个明确的推送失败,只能拉取最新状态、看清楚已经有一个周期在进行中,
再决定下一步怎么做,而不是在不知情的情况下把自己的状态覆盖上去。

### 四个状态转移点

这条状态链只允许在四个明确的时机被追加,每个时机各自只负责状态机的一步,互不越权:

1. **冻结**:开启一个新周期。如果发现已经有一个周期开着还没关闭,直接拒绝执行——唯一的例外口子
   是显式传一个"开新周期"的参数、外加一段写明原因的说明,而且这个"强行开新周期"的操作本身也会
   被记录成一条追加的状态,而不是覆盖旧状态,保证审计链条不断。
2. **验证运行结束**:把这次跑的红/绿结果写进状态里。
3. **应用修复**:对应上一篇讲的"就地修复"步骤,把应用了哪些修复追加进状态。
4. **从验证线同步到部署登记点**:在同步成功之后正式关闭这个周期,并把它归档到一个永久的历史引用
   里,按时间戳区分不同周期,留下完整的历史记录可供事后查询。

这四个转移点合起来,把"一个候选周期从开始到结束"的完整生命周期,变成了一条可以被机器读取、
机器校验、机器拒绝违规操作的状态链,而不再是一份只能靠人或 AI 自己去对照检查的文档条款。

### 配套的"应用修复"操作,而不是"重新冻结"

有了这套机械化的状态机之后,"红灯要就地修复"这条规则也有了配套的正确操作路径:修复不是重新把
修复线指向开发分支最新头(会把无关提交一起拖进来,破坏候选周期之间"红灯数量可比较"的基础),
而是把修复正常先落到开发分支上,再单独把这一个提交(只是这一个,不是一整段)cherry-pick 到验证线
上——同样是"只追加"的操作,不重写已有的候选提交历史。

## 通用洞见

这套机制提炼出的核心洞见是:**当一条纪律纯粹靠文档和 AI 自觉执行时,它迟早会被违反;把这条纪律
状态化、存成一个所有并发方都能读到的共享引用、并且让底层的版本控制系统(git 的快进推送)自然而然
地拒绝掉冲突的并发操作,比继续加长文档里的警告文字要可靠得多。**这个模式不局限于"验证周期"这一个
场景——任何"多个 AI 会话并发操作、需要有一个共享的、防冲突的进度状态"的场景,都可以考虑用类似的
"自定义 ref + 只追加提交链 + 非强制快进推送"的方式来实现,而不是发明一个额外的锁服务或数据库表。

## Nova 案例参考

在 Nova 的实现里,这个共享状态存在 `refs/nova/gate-cycle` 这个自定义引用里,`gate:freeze
--push` 这类命令在周期未关闭时会直接拒绝执行,把这条纪律从文字约定变成了机械强制(内部编号
GATE-3 记录了这次从"纯文档纪律"升级到"机械强制"的变更)。**具体的 ref 命名空间(`refs/nova/...`)
和字段集合是 Nova 按自己的治理需求设计的,新项目应该用自己的命名空间、按自己需要跟踪的字段重新
设计这条状态链**——真正可复用的是"用非强制快进推送到共享 ref 来实现无锁并发状态机"这个技术模式
本身。
