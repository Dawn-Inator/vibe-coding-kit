# 04 · 门禁与发布(Gate & Release)

本模块讲的是:当多个 AI 会话并发往同一个仓库写代码时,如何保证"进了 `develop` 的东西质量可控、
"进了 `staging` 的东西真的被验证过、"进了 `main` 的东西不会把生产环境炸掉。本目录的文档分别讲:

- `README.md`(本文件):分支→环境映射的设计原则,以及"preflight card"这个动手写代码之前先想清楚
  会触发哪些治理流程的规划工具。
- `dual-gate-freeze.md`:双门冻结机制——如何避免"验证套件正在跑的时候,目标分支又被推了新提交"
  这种竞态。
- `gate-cycle-mechanism.md`:如何用一个所有并发会话都能看到的共享 git 引用,把"发现红灯要就地修复、
  不要重新指向最新头"这条纯靠自觉的纪律,变成 git 本身就会拒绝违规操作的机械约束。
- `ai-commit-identity.md`:多个 AI 会话共享同一个仓库时,如何用三层机制保证每个 AI 提交都带着统一、
  可审计的身份,而不会污染人类的提交历史或串错身份。
- `personal-branches.md`:AI worktree 隔离解决的是"会话之间打架",这篇讲的是多人协作时额外需要
  的一层——"人与人之间"的隔离,给每个协作者一条镜像分支,把"隔离在个人视野里"和"确认可以给别人看"
  拆成两个独立判断。
- `prod-ops-tiered-authorization.md`:代码发布之外,线上已有环境的运维操作(看日志、重启、改配置、
  订正数据)怎么授权——按爆炸半径拆成三级,成本随风险递增,并讲清楚为什么拒绝了云端硬隔离、
  新项目第一天该只做哪两级。文末说明 `store-review-monitor`(商店审核的只读监控)与
  `incident-evidence-triage`(事故的只读取证)如何接在发布链的两端:
  [store-review-monitor](../../skills/store-review-monitor/SKILL.md)、
  [incident-evidence-triage](../../skills/incident-evidence-triage/SKILL.md)。

## 问题:AI agent 需要一张"环境地图"

人类开发者协作时,"这段代码现在处于什么阶段"这件事很多时候是靠团队默契、口头约定、或者盯着 CI
面板反应过来的。但 AI agent 没有这种默契——每一个新会话打开仓库时,都是从零开始重新理解"现在
应该把代码放哪、这个分支意味着什么、下一步该跑什么检查"。如果没有一个显式、机器可读的地图,
不同的 AI 会话很容易做出互相冲突的判断:一个会话以为 `develop` 就是"能跑的代码就往上推",另一个
会话以为改动必须先过完整测试套件才能碰 `develop`,两边各按各的理解推进,最后在共享分支上打架。

## 设计原理:分支即环境,是一个可复用的心智模型

最基础也最通用的做法是让分支名直接对应部署环境,让"这段代码处于什么阶段"这个问题变成"它在哪个
分支上"这个可以用一条 `git log` 回答的机器可读事实,而不是需要人或 AI 去猜测、去问、去翻聊天记录
才能确定的隐性状态。典型映射:

| 分支 | 对应环境 | 含义 |
| --- | --- | --- |
| `develop` | 开发环境(dev) | 日常快速迭代的主线,轻量检查即可合入 |
| `staging`(或经验证的 `gate/staging`) | 预发布环境(stg) | 面向真实发布前的完整验证 |
| `main` | 生产环境(prod) | 最终对外服务的代码,变更最审慎 |

这个映射本身是通用的、几乎可以直接搬进任何新项目——**但"分支对应环境"和"环境具体怎么部署"是
两个独立的决策维度,后者不应该被前者绑死**。很多项目的默认直觉是"推送到某分支 → CI 自动触发部署",
这是一个合理的默认选项,但不是唯一选项,下面的 Nova 案例展示了一个刻意偏离这个默认选项的选择。

## 容易被遗漏的第四类分支:预览沙盒(sandbox)

上面三条(dev/stg/prod)回答的都是"这段代码离生产环境还有多远"这个问题,面向的是工程师自己。
但很多项目还有另一类完全不同的需求:**让不懂代码、不该碰真实分支的人(产品经理、设计师、客户),
提前看一眼某个还在开发中的界面长什么样**。如果没有单独想清楚这件事,常见的两种坏结果是:①逼着
非技术角色去理解 `develop`/`staging` 这套分支语义,徒增沟通成本;②图省事直接把开发中的东西部署到
一个真实环境给对方看,结果这个"临时给人看一眼"的需求,意外绕过了本该走的质量门禁。

通用解法是单独开一条**沙盒分支**,专门服务"预览",跟 dev/stg/prod 那条质量递进的流水线完全隔离:

- **不参与门禁递进**——沙盒分支不是"比 develop 更早的一个阶段",它压根不在 dev→stg→prod 这条链路
  上,合并方向是单向的(从某个开发分支拉一份快照过去预览,不会被合并回主干)。
- **部署链路要刻意做"减法"**——沙盒环境的部署机制应该比真实环境更简单、暴露面更小,比如不注入
  真实密钥、只提供一个免密的只读预览,因为它面向的是可能不熟悉安全操作规范的人,并且访问对象
  往往不止工程师内部。
- **生命周期是一次性的**——一条沙盒分支/一次沙盒部署通常对应一次具体的"给谁看一下"需求,看完之后
  这条分支就该被清理掉,不应该长期存在、积累成第二个 `develop`。

这个"给非工程角色一个隔离预览通道"的模式本身是通用的,任何"需要向非技术干系人展示进行中的 UI
工作"的项目都用得上;具体谁来发起预览请求、请求走什么形式(自然语言描述 / 设计稿 / 工单),这部分
高度依赖每个团队自己的协作习惯,是需要按自己团队重新设计的部分,不属于这里要讲的通用机制。

## Nova 案例:发布触发从 CI 自动化解耦成本地显式操作

Nova 在 `develop` / `staging` 两级环境上做了一个反直觉的选择:**这两个环境的实际发布完全不通过
CI 自动触发**,而是靠一个本地的发布控制脚本,绑定"精确的提交 SHA + 固定的部署 provider + 目标主机 +
部署后的健康检查读回验证"作为发布准入的证据。做出这个选择的理由有两条:

1. **成本**:CI 平台大多按运行时长计费,而且是按每个 job 单独计费、向上取整。如果每次 push 都自动
   触发一整套流水线,那种"改一行代码 → 触发 CI → 看红灯 → 再改一行 → 再触发"的低效调试循环,会在
   CI 账单上被放大很多倍。
2. **可控性**:把发布从"每次 push 都可能触发"的自动化里解耦出来,变成一个显式、按需触发的本地操作,
   反而更容易保证"这次发布对应的就是我验证过的那个 SHA",而不是被并发推送悄悄绕过。

`main`(生产环境)则保留了更传统、更审慎的发布路径,不套用同一套"本地脚本"的逻辑——这也说明
这个选择不是"处处都要绕开 CI"的教条,而是针对"迭代频率高、发布频率高的环境"专门做的成本/可控性
权衡。**这是 Nova 具体业务节奏下的具体选择,新项目要按自己的发布频率、CI 计费模式、团队规模重新
决策**——如果你的 CI 是按分钟数包月而不是按次计费,或者你的团队更依赖"push 即部署"的即时反馈,
CI 自动触发完全可能是更合适的默认选项。真正可复用的洞见是:**"CI 触发部署"不是唯一选项,
"本地脚本绑定 SHA + 目标 + 读回验证"是一个同样严谨的替代方案,尤其适合迭代快、发布频繁的阶段**。

## 可复用技术模式:Preflight Card

无论选择哪种发布路径,AI 在真正动手写代码之前,都应该先在自己的任务规划里过一遍一张固定字段的
"预检清单"——不需要真的提交进仓库,只是强制自己在动手之前一次性想清楚"这次改动会触发哪些额外的
治理流程、文档同步、门禁检查",而不是等改完代码、门禁跑红了才发现漏掉了什么。这是一种"把隐性
知识显式化"的技术模式,本质上是给 AI agent 的一份检查表,把容易漏掉的判断点固定成必答字段。

典型字段包括:

- 改动范围与风险等级
- 是否涉及需要额外治理卡片的新业务能力 / 新持久化存储
- 是否涉及第三方集成 / 队列改动
- 用哪个 worktree 命令起步、能不能拆给 subagent 并行
- 会不会触发文档同步
- 会不会改动公开 API 契约
- 会不会牵扯数据库 schema 迁移
- 要新增/改哪些测试——尤其是修 bug 场景,通常需要区分"这一处的回归测试"和"同类问题的防御测试"
  两层,缺一层不能算完成
- 验证计划打算在本地跑还是挪到云端跑、为什么

**命令本身要分层**是这个模式里容易被忽略但很关键的一点:便宜的、只是给建议的检查(比如只检查
改动涉及文件的代码风格、测试选择器)应该默认跑、留在本地;更重的门禁(完整测试套件、预发布全量
检查、端到端浏览器测试)应该默认不跑,只在满足特定触发条件或用户明确要求时才跑。把这两类检查
混在一起、不分轻重地全部默认跑,是很多项目 CI 变慢、变贵的直接原因。

对于改动量很小、影响面很窄、不触碰任何高风险类型的场景,还可以准备一份"精简版卡片"——只需要
填 2-3 个字段而不是完整的一长串,避免让小改动也背上和大改动同样重的规划负担。**卡片字段的具体
内容要按项目自己的治理体系重新设计**,这里列的是 Nova 的字段集合,不是一份放之四海皆准的模板。
