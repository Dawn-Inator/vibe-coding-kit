# AI 提交身份:三层强制机制

## 问题:多个 AI 会话共享一个仓库,身份会串

当多个 AI 会话(可能运行在不同账号、不同机器、不同身份配置下)都在往同一个仓库贡献代码时,会
浮现出一个在纯人类协作里不太会遇到的问题:**谁提交的这件事,需要有一个清晰、一致、可审计的答案**。

这里面藏着两个方向相反的风险:一是 AI 的提交如果不做区分,会直接淹没在人类真实身份的提交历史里,
让人事后没法一眼分清哪些改动经过了人的手、哪些是 AI 自主完成的;二是更危险的情形——AI 在配置
或切换身份的过程中出了差错,不小心把提交署上了某个真实人类开发者的名字和邮箱,这不仅是审计意义
上的错误归属,还可能牵扯到"这个人到底有没有做过这次改动"的责任认定问题。两种风险都指向同一个
结论:AI 的 git 身份不能是一个"顺手配一下就行"的细节,需要专门设计。

## 设计原理:定义一个独立身份,再用纵深防御强制它落地

解法的第一步是概念上很直接的一步:定义一个专门的、独立于任何真实人类身份的 git 身份(姓名 +
专用邮箱),在一个集中的地方定义一次,供所有相关脚本引用,不允许各处各写各的散落配置——这样
"AI 身份具体是什么"永远只有一个权威来源,不会出现"脚本 A 用的邮箱和脚本 B 用的邮箱不一致"这种
低级但很容易发生的漂移。

真正的难点在第二步:怎么保证这个身份**一定**会被用上,而不会因为某个环节的疏忽被绕过。这里
采用的是纵深防御(defense in depth)的思路——不指望某一个检查点能覆盖所有情况,而是在流程的
不同阶段各设一道独立的关卡,前一道没拦住,后一道也有机会拦住,而不是"只要闯过第一关就永远安全"。

## 可复用技术模式:预防 → 复核 → 拦截,三层纵深防御

这个模式可以拆成三层,分别对应"创建时""收尾时""推送时"三个不同的时间点,每一层都独立生效:

### 第一层(预防):worktree 创建时就配好身份

在给 AI worker 创建 worktree 的那一刻,就把这个 worktree 独立的 git 身份配置设成 AI 身份——注意
这里的关键细节是**worktree 级别**的配置,不是全局共享的配置,而且**明确不会去动主工作区的身份
配置**(主工作区属于人类,不应该被自动化流程改身份)。这样,worker 在这个 worktree 里正常提交时,
自然而然就带着 AI 身份,不需要每次手动指定,把"用对身份"这件事从"每次都要记得做"降级成"环境
本身就是对的,什么都不用做"。

### 第二层(复核/兜底):收尾流程里的身份检查与改写

在"收尾"流程里、rebase 完成之后、真正推送之前,检查这一批还没推送的提交,看提交者身份是否符合
预期。这一步分三种情况处理:

1. **发现身份匹配某种"已知的测试用/占位符身份特征"**(比如带着某个测试固件专用的域名后缀)——
   直接判定为异常、拒绝继续。这里的处理原则很值得注意:把"测试身份意外泄漏进真实提交历史"当成
   一个真正的 bug 来处理,而不是自动帮它悄悄改成 AI 身份糊弄过去。悄悄纠正看起来更"友好",但会
   掩盖掉背后真正的配置错误,让同样的错误下次还会发生。
2. **所有提交已经都是 AI 身份**——不做任何事,直接放行。
3. **其他情况**——通过 rebase 加上"每个提交都用 AI 身份重新署名"的方式,把整段提交历史的作者和
   提交者都改写成 AI 身份,保证最终推送出去的历史是干净、一致的。

### 第三层(推送时的最后关卡):pre-push hook

一个独立于上面两层、在"推送前"这个 git hook 时机触发的检查,专门针对推送到关键共享分支(比如
`develop`)的场景:

- 如果是从一个"worker 角色"的上下文发起的推送,要求这一批提交**必须全部**是 AI 身份。
- 如果是从"非 worker"(也就是人类自己的主工作区)发起的推送,允许是 AI 身份、也允许是这台机器
  配置的人类真实身份中的任意一种。
- 不管是哪种上下文,只要检测到"已知的测试固件身份特征",一律拒绝。

这一层的价值在于它完全独立于前两层——即使某个 worktree 的初始配置出了差错、收尾流程的检查也
恰好被绕过了,pre-push hook 依然会在代码真正离开本地、进入共享分支之前做最后一次拦截,是整条
链路里最后、也是最不可绕过的一道关卡(因为它挂在 git 的原生 hook 机制上,而不是某个可以被跳过
的自定义脚本步骤)。

## 额外的保护层:共享级配置的"逢值就拒绝"

除了上面三层针对提交身份本身的检查,还有一层更基础的保护:几个关键入口(建 worktree、收尾、
预检)在执行前都会检查主工作区的**共享**级别的 git 配置(不是 worktree 级别的)里有没有被意外
写入任何 `user.*` 相关的覆盖值。这个检查是"逢值就拒绝",不局限于已知的几种可疑模式——原因是
一次不小心写在错误作用域(共享配置而不是 worktree 私有配置)的身份设置,会污染这个仓库所有其他
worktree 共享的那一份配置,影响面是全局性的,所以这里选择了比"匹配已知坏模式"更严格的"只要有值
就拒绝"策略,防止任何未预见到的污染方式漏网。

## 跳过检查必须留痕

纵深防御不等于"绝不允许跳过"——现实中总会有需要临时绕过某道检查的合理场景。但这套机制的设计
原则是:**跳过永远是可以的,但永远是留痕的、可追溯的,不能是静默的**。任何一次被批准的"跳过预检
门禁"操作(不管是 worker 自己申请跳过,还是推送前钩子层面的跳过),都必须同时带上"原因"和
"批准人是谁"两项信息,并且这两项信息会被写进对应提交的元数据以及一个独立的审计日志文件里。
这样即使某次跳过是合理的,事后也能完整还原"谁在什么情况下批准了这次跳过、原因是什么",而不是
留下一个无法解释的例外。

## Nova 案例参考

Nova 的具体实现里,统一的 AI 提交身份是 `Nova AI Bot <ai-bot@example.com>`,由
`begin`/`end`/`preflight` 三个 guard 入口共同维护第二层复核逻辑,pre-push hook 挂在推送到
`develop` 等共享分支的路径上,几个逃生舱环境变量(比如 `AI_PRIMARY_LOCK_ALLOW`、
`AI_SYNC_PRIMARY_APPROVED_BY`)对应"批准人是谁"这个字段,审计日志落在
`.git/nova-primary-audit.log` 等文件里。**这组具体的身份字符串、环境变量名、日志路径都是
Nova 按自己的品牌和目录结构起的,新项目要用自己的域名、自己的审计存储位置重新定义**——真正需要
照搬的是"预防在先、复核兜底、推送时最后拦截,外加逢跳过必留痕"这套三层纵深防御 + 审计的设计
模式,而不是这些具体的字符串。核心哲学可以概括为一句话:**把"谁提交的"这件事从"靠人自觉遵守
约定"升级成"多层机制自动强制 + 自动纠正 + 失败时留痕",这样即使某个环节疏忽了,后面的环节还能
兜底发现问题,而不是让一个错误的身份悄悄进入永久的提交历史。**
