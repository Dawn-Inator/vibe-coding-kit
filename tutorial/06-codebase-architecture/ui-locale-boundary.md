# UI 语言轴 vs 内容语言轴:一个很容易被混为一谈、后果很大的边界

如果一个产品同时有"界面显示成什么语言"和"内容本身是什么语言"这两个概念,几乎所有关于
i18n 的困惑和事故,根源都是把这两条轴混在一起。这篇讲的是这条边界本身,以及围绕它的几个
类型系统机制——这些机制通用可复用;具体语言集合(中文/英文)、具体产品语境(语言学习类
应用)是 Nova 案例的场景,换一个产品会有自己的两条轴内容,但"先分清楚在哪条轴上"这个步骤
不会变。

## 两条轴,长得像,语义完全不同

| | **UI locale 轴** | **内容语言轴** |
| --- | --- | --- |
| 回答的问题 | 界面显示成哪国语言? | 这条内容(视频/帖子/字幕)本身是哪国语言? |
| 谁决定 | 用户(设置里选,或系统语言/地区兜底) | 内容作者,创建时选择 |

混淆的代价具体是什么:一个"给界面加一门新语言"的请求,如果不小心落到了内容语言轴的代码
路径上,会静默变成"给内容加一门新语言"——这是完全不同量级的产品决策,通常意味着需要对应
语料、翻译/语音识别管线、内容审核能力,而不是加一条菜单文案。**动手之前先大声确认自己在哪条
轴上**,是这整篇教程唯一真正重要的一句话。

Nova 案例里这两条轴的默认值甚至**互为反函数**(界面语言 = 用户母语,内容语言 = 用户要学的
外语,国内版和海外版的默认值刚好相反)——第一次看到这种"看起来矛盾"的默认值组合时,容易
产生"对齐一下"的冲动,但这类反直觉恰恰经常是刻意设计,动手"修"之前先确认自己真的看懂了
两条轴各自的语义,而不是凭直觉判断哪个看起来不对。

## 单一真源 = 每个独立部署的 runtime 各一份,不是全仓一份

如果产品有多个独立构建/部署的 runtime(比如一个移动端、一个 web 端、一个后端服务),"单一
真源"指的是**每个 runtime 内部**只有一份手写的语言集合,不是要求整个仓库只有一个变量。三个
runtime 各自维护自己的一份是**故意的**——它们独立构建、独立部署,没有共享运行时,不是"抄了
三遍"。真正要消灭的是**单个 runtime 内部**同时存在的多份平行表示法(Nova 曾经在一个移动端
里同时存在四套互不派生的 UI locale 表示法,没有一处文档说清楚哪个是真源,于是没人发现它们
早就不一致了)。三份真源之间**集合必须保持一致**,靠的是一份显式的"加语言步骤清单",而不是
共享导入。

## 派生数组不是护栏,带 key 约束的 record 类型才是

这是这套机制里最容易被误解、也最值得记住的一条。给定一份手写的语言集合源:

```ts
const OPTIONS = LOCALES.map(toOption); // 看起来是"派生的",看起来安全
```

**这种"派生"对新增语言时的类型检查提供零保护。** map 只是多跑一次,不会强迫任何人去
补"这门新语言在选择器里叫什么"这类必须回答的问题——新语言可能就这样从界面上**静默消失**,
用户切不过去,也没有任何报错。真正的护栏是一个**每个成员都必须显式赋值**的 record 类型:

```ts
const LOCALE_META: Record<Locale, LocaleMeta> = {
  en: { nativeName: 'English' },
  zh: { nativeName: '简体中文' },
  // 往 Locale 加一个新成员,这个对象字面量会编译报错,直到你补上对应条目
};
```

往联合类型加一个成员,会让代码里**每一处**这样的 record 编译失败,直到有人补上新成员的
条目——这才是真正强迫"这门新语言在这里需要一个决策"这件事在编译期暴露出来,而不是留到线上
让某个具体用户撞见。**千万不要为了让某处报错消失,把这类 record 松绑成 `Partial<Record<...>>`
或者加一个 index signature**——那等于把护栏本身悄悄拆掉。

## 跨包镜像需要显式的编译期断言,不能只靠"记得同步"

如果两个包各自需要一份相同的语言联合类型(常见于依赖方向不允许其中一个反向 import 另一个),
不要只靠"改的时候记得两边都改"来维持同步,而是加一条编译期互相赋值断言:

```ts
type MutuallyAssignable<A, B> = [A] extends [B] ? ([B] extends [A] ? true : false) : false;
export type LocalesStayInSync = Assert<MutuallyAssignable<LocaleA, LocaleB>>;
```

这类纯类型声明编译后完全擦除、零运行时成本——不要因为"它什么都不做"就删掉它,它唯一的
工作就是把"有人往一个包加了语言、忘了另一个包"从一次线上 `undefined` 提前变成一次编译报错。

## 两个容易被忽略的边界

- **locale 不该出现在已经是外部契约的 URL 里**——如果分享链接、邮件回跳链接、OAuth 回调
  URL 已经印在第三方控制台的白名单或者已发出的邮件里,给这些 URL 加一段 locale 路径段
  不是"顺手接入 i18n 框架默认路由"这么简单,而是会让每一条已发出的链接、每一条已注册的
  回调白名单同时失效。
- **数据库列宽和 CHECK 约束是两个不同的契约**——一个声明成能装下完整 BCP-47 语言标签的
  宽字段,底层 CHECK 约束完全可能只放行两位小写字母。列宽只是意图广告,真正说了算的是
  约束本身,加语言前必须逐条核对约束,而不是看到列足够宽就假设能存更长的标签格式。

## 错误消息的语言 fallback 需要一条明确的安全边界

如果系统按错误码分类展示消息,把"少数精心维护翻译的高危错误码"和"大量可以回落到后端原始
消息的普通错误码"分成两条独立分支,而不是写成一条"先查译文表、查不到就回落原始消息"的单一
链路。单一链路会把"这个 locale 没注册"和"这个错误码还没人工翻译"两种完全不同的原因塌缩成
同一个 fallback 分支——一旦 locale 归一化出现 bug,就可能让一条来自上游服务、可能携带内部
实现细节的原始错误消息,直接以任意语言泄漏给终端用户。至少让最高危的一类错误码(通常是
5xx/内部失败类)强制要求人工翻译,并用一条门禁测试钉死这个要求。
