# Schema / Migration 治理

数据库 schema 变更是所有架构决策里最难撤销的一类——代码可以随时回滚,数据一旦写坏,
往往没有干净的"撤销"。这篇讲的三件事——什么时候需要正式登记一次 schema 决策、
migration 文件应该怎么组织、"当前到底跑到哪一步了"这个问题该由谁来回答——都是通用
可复用的治理机制,可以直接搬到任何用版本化 migration 管理 schema 的项目里。

## Data Architecture Card:什么时候必须登记

**触发场景**(命中任意一条就必须产出一张数据架构卡):

- 创建或实质性改动一张 PostgreSQL 表、一个物化视图、一个消息队列、一个逻辑数据库、
  一个外部数据汇聚点、跨数据库的投影
- 新增事件/审计/outbox/账本/指标/数据集市/快照/日志类的存储
- 把某个存储改成无界增长、改动它的数据保留策略、改动它的数据库分区/分片边界

**明确排除的场景**(允许标记"不适用"跳过这张卡):纯粹加索引、纯粹 ALTER 已有结构、
纯粹的种子数据/回填/修复类迁移——这些不创建任何新的持久化运行时对象。

反过来,**明确禁止**用"不适用"来跳过建表/建物化视图/建队列这类真正新增持久化对象的
迁移——这条边界的设计意图很清楚:允许卡片被跳过的,是那些"改动幅度小、不引入新的
所有权/一致性/容量问题"的变更;一旦涉及新建一个会长期存在、会积累数据的存储对象,
就必须走完整的决策流程,不能靠"这只是个小改动"的主观判断绕过去。

**卡片必填字段**(概览,不逐字段展开):稳定 ID、归属系统/归属模块、每个存储条目的
边界归属决策(**至少要写清楚一个被拒绝的替代方案、并给出可复核的理由**)、一致性决策
(事务边界/outbox 模式/投影器/幂等/对账机制怎么设计)、至少两条独立的、可量化的
"未来重新评估阈值"(指标名 + 比较符 + 数值 + 触发的动作)、每个存储的容量类型(有界
还是无界,两种类型各自要求的字段集合不能混用)、证据强度(已实测/已估算/未知——新建
的存储如果证据是"未知",在严格模式下直接不通过)、每个存储的热数据保留天数/总保留
天数/到期后执行什么动作/对应的可执行入口。

这里"至少写清楚一个被拒绝的替代方案"这个要求,跟服务边界决策框架里的逻辑是一致的:
逼着决策者证明自己认真比较过其它选项,而不是直接写下第一个想到的方案。

## version migration 的目录结构:通用设计模式

这套目录结构本身是可以直接复用的通用设计模式:

- **正向的、只增不改的迁移文件链**,按目标版本号分目录存放。
- **一份"清单"文件**作为声明状态的总账,记录目标版本、几类特殊的"允许跳跃点"(每个
  跳跃点都要求写明原因,通常是历史上迁移顺序调整留下的痕迹)、以及每个部署阶段各自
  的状态。
- **一份"记录"目录**,按"部署阶段/目标版本"存放已经在该阶段真正执行过的迁移的审计
  快照(这份记录本身也纳入版本控制,方便追溯)。
- **一个"手工恢复"目录**,专门存放需要运维人员手动执行的恢复类 SQL——这个目录**不
  属于**正向迁移链的一部分,不会被自动执行,也不计入声明状态总账。把它跟正向迁移链
  物理隔离开,是为了防止自动化流程不小心把恢复脚本当成正向迁移执行。
- **一份"可逆性登记表"**,专门给"已经在某个阶段被验证执行过、内容已经通过校验和冻结"
  的迁移文件补充记录它的可逆性分类——这样做是为了不用回头修改一份已经冻结的 SQL
  文件本身。已经执行过的迁移文件应该被当成不可变的历史记录,任何补充信息都应该写
  在外部的登记表里,而不是回头改动文件内容。
- **一份"历史遗留破坏性变更登记表"**,给早期(引入这套治理体系之前)遗留下来的、已经
  包含破坏性操作(比如直接删表删列)的历史迁移文件,逐条补记它们的校验和/操作清单/
  处置结论/恢复路径——这是承认"历史债务确实存在"的诚实做法,而不是假装它们从未
  发生过。
- **每个拥有自己独立数据库的服务,各自维护一份"schema 初始化脚本"**,这个脚本只回放
  属于这个服务自己的那部分迁移文件(明确不回放其它服务的迁移),配一个校验脚本确保
  "每个数据库都恰好被一个服务的初始化脚本认领,而且这个认领关系是真的被导入和调用了
  的,不是声明了但没接上"——这条校验直接呼应服务边界决策框架里"逻辑数据库"这一级的
  隔离要求:数据库的所有权边界必须能被机械验证,不能只停留在文档描述。

## 可逆性 header 契约

每一份新的版本迁移 SQL,文件头部除了常见的"用途/是否幂等/所属数据库/怎么验证"这几
行注释之外,**必须再加一行明确声明这次迁移属于三种可逆性分类里的哪一种**:

| 分类 | 含义 |
| --- | --- |
| **只进不退** | 绝大多数迁移属于这一类,比如加一个可空字段、加一个"不存在才建"的索引——这类迁移的"回滚"策略就是"不回滚,往前修",而不是往后退 |
| **可逆** | 破坏性/类型转换/数据重写/改名操作,但配有一份真正能机械执行的"反向脚本"(可以是独立的手工恢复文件,也可以是同一次改动里的一段"down"脚本头) |
| **不可逆** | 一旦执行就没法机械撤销,比如物理删表且数据已经真的没了,或者产生了外部副作用——这类必须写清楚为什么不可逆、以及万一真出问题该往哪个方向人工恢复(比如"从某个时间点的快照恢复") |

**一个不直观的分类案例**值得记录:给一个数值字段新增一个"取值范围检查约束"(比如
收紧金额的合法区间),即使这个操作的效果是"让未来的写入变得更严格",但因为撤销这个
约束本身是一个干净的、无损的反向操作,所以它仍然被归类成"可逆"而不是"只进不退"。
这个案例提醒:分类的判断标准是"反向操作是否存在且干净",而不是"这个改动听起来是
收紧还是放松"。

**"down"脚本编写范围有一条容易被忽略的细节**:只应该回滚这次迁移**真正改动过**的
字段。如果一次批量回填操作里,某个字段其实本来就已经等于它的默认值(这次迁移对它
其实没有产生真实改动),那么对应的回滚脚本就不应该把这个字段重置回默认值——否则
可能会误伤后来由其它渠道(比如后台管理系统)真实写入的值。这是一个很容易在"图省事"
时踩中的坑:写 down 脚本最简单的方式是"把 up 脚本反过来做一遍",但如果 up 脚本本身
是幂等/条件性的(只改动满足某个条件的行),down 脚本也必须保持同样的条件性,不能
简单粗暴地"全量重置"。

## DB ledger 是执行真源(全篇最重要的原则)

判断"这个环境的迁移到底跑到哪一步了"这件事,**唯一权威的答案来自直接读取目标部署
环境里数据库自身记录的、真实执行过的迁移账本**。这条原则需要跟另外两个容易被误认为
"权威"的地方划清界限:

- ❌ **不是**版本控制系统里那份"记录"目录——那只是账本的**派生审计快照**,写入时间
  滞后于账本本身。
- ❌ **也不是**声明状态总账里写的状态字段——那同样只是账本的一份**滞后的派生副本**,
  不是权威源头。

换句话说,真正的"事实"永远只活在数据库里,任何存在于代码库/文档里的"状态记录"都是
对这个事实的转述,转述就有可能滞后或出错。**手写 SQL 直接改这份账本是被明确禁止的**——
账本本身的写入必须只通过迁移工具自身的执行路径完成,不允许人工"手动订正"账本记录来
让状态看起来对得上。

**Nova 真实踩过的事故**,进一步印证了这条原则的必要性:曾经发生过一次真实事故——因为
"把账本回写进声明状态总账"这一步骤本身存在竞态问题,导致几十条已经在数据库账本里被
正确标记为"已验证"的迁移,却在声明状态总账里连续好几周被错误地显示成"待处理"。这次
事故没有推翻"DB ledger 是权威源头"这条原则,反而进一步证明了它——如果当时习惯性地
信任声明状态总账、按它的"待处理"标记去重新执行这些迁移,后果会比"总账显示滞后"严重
得多。这次事故最终推动的修复方向,也不是"让声明状态总账更快同步",而是重申"声明状态
总账只能是账本的派生视图,永远不能反过来被信任为权威源头"。

**对账/同步操作的纪律**:

- 只能通过官方封装好的命令来做。
- 这个命令必须同时完成两件事:读取部署环境真实的账本 + 同步写回记录目录和声明状态
  总账。**这两步必须绑在一起做**,只做其中一步会触发"声明状态总账领先于记录"的漂移
  检测失败。
- 不允许从任意一个位置断点续跑,也不允许跳过某些迁移。
- 还有一个专门的、不可逆的 **"terminal failure"状态**——一旦触发就会硬性锁住整条
  迁移链,宁可完全卡住等人工介入,也不愿意冒着乱序重放非幂等 SQL 的风险自动往前冲。
  这是"宁可停机等人、不要自动做错事"的保守设计,在迁移这种难以撤销的操作上是正确的
  取舍方向。

## 回滚优先级:从便宜到昂贵

出问题时应该按下面这个顺序尝试恢复,而不是一上来就想着"回滚数据库":

1. **代码回滚优先**——大多数"migration 把生产搞坏了"的真实情况,其实是应用代码跟一个
   仍然向前兼容的数据库 schema 不匹配。回滚应用代码本身(比如切回上一个部署版本)
   往往比动数据库更快更安全,而且代价几乎总是最低的。
2. **前向修复**——写一个新的迁移去修正问题,永远不要试图"倒转"迁移账本本身。这跟
   "只进不退"分类的设计意图是一致的:账本的历史应该保持单调递增,修正错误也应该
   是往前追加一条新记录,而不是回头篡改历史。
3. **手工执行"不可逆"目录里的恢复脚本**——仅限于那些被正式标记为"可逆"的破坏性
   迁移。而且执行完之后**必须**紧接着再走一次前向迁移或者对账记录,让声明状态总账
   和真实账本重新对齐,不能执行完手工恢复就撒手不管。
4. **从环境快照/时间点恢复**——留给真正的"不可逆"数据丢失场景,是最后一道防线。

这个优先级顺序背后的通用原则是:**恢复手段的选择应该跟"代价"和"确定性"挂钩,而不是
跟"看起来最直接"挂钩**。直接动数据库看起来是"从根源解决问题",但实际上往往是代价
最高、风险最大的选项,应该留到其它更便宜的手段都试过、确认无效之后再用。
