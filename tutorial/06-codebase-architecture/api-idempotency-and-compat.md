# API 幂等、版本兼容与强制升级

这篇用 Nova 的几次真实取舍,讲三件事:有副作用的请求为什么要做成"幂等三件套"、强制升级和
灰度发布是什么关系、"URL 版本 + URL 与代码包一一对应"这套约定在移动端上要付的代价。
具体检查脚本和代码形态见 skill `api-contract-change` 的 `references/`;这里只讲**为什么这样设计**。

## 一、幂等三件套:为什么是这三件

Nova 的发布、充值、后台写命令都是有副作用的 POST。移动端网络不稳,请求发出去、响应丢了,
客户端或网关就会重放。没有幂等,用户就会重复发帖、重复付款。Nova 的做法有三件,缺一不可。

### 1. 幂等键:客户端对"一次意图"生成一个稳定的 key

同一个用户动作的所有重试用同一个 key;不同动作用不同 key。缺 key 直接返回 400,而且用自己的
错误码,不用框架默认的 422。原因很实际:重试逻辑和监控是按状态码分类的,"客户端忘了带 key"
如果混在一堆"请求体字段不合法"里,就没人发现某个客户端版本根本没接幂等。

### 2. 请求指纹:同键异 payload 返回 409,而不是返回旧结果

服务端把规范化后的请求体(键排序、去掉无意义空白)做 SHA-256,和 key 一起存。重放时:

- key 相同、指纹相同:真重放,原样返回第一次的结果。
- key 相同、指纹**不同**:返回 **409**。

为什么不返回旧结果?想象客户端有个 bug:草稿换了内容却复用了上一次的 key。如果服务端
返回旧结果,客户端会以为"新内容已经发布成功",实际上什么都没发生,用户的新内容丢了,
而且没有任何报错能暴露这个 bug。为什么不干脆当新请求执行?因为那样 key 就失去了"同一
意图"的含义,重放保护形同虚设。409 是唯一让客户端 bug **在开发阶段就响亮暴露**的选择。

### 3. 缓存只存"已提交"的结果,持久层是事实

真正的幂等记录写在数据库里,和业务写入在**同一个事务**:"结果存在"和"副作用存在"是同一个
事实。并发的重复请求在同一个 key 上串行(advisory lock 或唯一约束)。

前面可以放 Redis 加速,但有三条规则:

- **只缓存已提交的成功结果,且只在事务提交之后写缓存。** 如果缓存里存"处理中"或提交前的
  状态,进程在写缓存和提交之间崩溃,就会为一个从未发生的副作用返回"成功"。
- **缓存故障、缓存值损坏一律当 miss,回退数据库。** 缓存只是优化,它挂了不能改变正确性。
- **持久层的幂等读失败时 fail closed,返回 503。** "查不到"不能当成"第一次请求"——这正是
  用户被扣两次钱的来路。

### 副产品:审计去重

后台命令的审计行主键由 `action + actor + 幂等键` 派生。重放重新算出同一个主键,和第一次写入
撞车,天然去重,不需要再写一段"是否已记录"的判断。代价是:一个 key 只能对应一次审计写入;
批量操作要给每个目标派生独立 key,否则后面的行会被当成重放吞掉。

### 客户端的另一半

共享传输层只自动重放两类请求:GET/HEAD,以及带幂等键的 POST。没有键的 POST 失败后只交还给
调用方,不自动重试。服务端对外调用同理:非幂等调用不挂重试策略。

## 二、强制升级与灰度:紧急旁路,而不是另一套放量

Nova 的发布记录里有 `version_code`、`min_supported_version_code`、`force_update` 和一个放量百分比。
这里有两个独立问题:

1. 这个客户端有新版本可更新吗?`current < latest`。
2. 这个客户端**必须**更新吗?`must_update = force || current < min_supported`。

灰度控制的是"谁先被提示更新"。强制升级是对灰度的**紧急旁路**:当一个版本已经不再受支持,或
已知有严重缺陷时,放量比例和白名单都不再起作用,必须全部提示。判定里命中旁路时要在日志里记原因。

白名单有一条硬规则:**只认已登录账号 id,匿名设备 id 永远不命中白名单。**设备 id 可伪造、
可共用,命中白名单意味着提前拿到新版,匿名流量一旦能命中就等于白名单对所有人开放。实现上
把 uid 和分桶用的标识分成两个参数传,类型上就分开,不容易混。分桶用 `release_id + 标识` 的稳定哈希,
同一个用户不会在放量里忽进忽出。

## 三、URL 与代码包一一对应的代价

前面的文章讲过,Nova 让 URL 的服务/模块/对象三段严格对应后端代码包路径,收益是路由自文档化。
代价是:**内部重构会变成公开的破坏性变更。**把一个对象从一个模块挪到另一个模块,URL 就变了。

在 Web 上这还好,发一版前端就换掉了。移动端不行:旧版本安装包会在线几个月,它们仍然调用旧路径。
所以 Nova 的做法是:

- 重构搬走的路由,在旧路径上保留一个薄的兼容路由,而不是直接删。
- 兼容路由和兼容动作词记在登记表里,有预算,**只减不增**;删除前要有按客户端版本统计的调用量证据,
  证明受支持的版本都不再调用。
- 优先做加法(新增可选字段、新增路由),语义变更尽量不原地改。
- 把"最低受支持版本"调高(强制升级)作为清理旧路径的前提条件,而不是反过来。

这三件事其实是同一件事的三个侧面:服务端要能安全地被重放,客户端版本要能被主动收敛,而路径的
兼容债要有明确的上限和退出计划。
