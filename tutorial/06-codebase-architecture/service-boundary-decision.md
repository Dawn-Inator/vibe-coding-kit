# 服务边界决策框架:Business/Service Materialization Card

这是本模块信息密度最高的一篇。它讲的是"要不要把一个业务能力拆成独立服务"这个问题的
完整决策框架——不是一条经验法则,而是一套两张卡片 + 五道门 + 触发条件分类 + 隔离顺序
的完整机制。这套机制本身是**通用可复用的**,可以直接搬到任何项目;Nova 最终拆出的
具体服务拓扑,是它自己业务下的具体答案,新项目需要重新走一遍框架、得出自己的答案。

## 为什么需要两张卡片,而不是一张

拆服务的决策经常被简化成一句话讨论——"这个模块要不要独立出去",然后凭直觉拍板。问题是
这句话背后其实压缩了两个性质完全不同的问题:"这个能力在业务上应该归谁所有、边界在哪",
和"这个能力现在有没有必要被物理拆开"。这两个问题的证据类型不一样、变化频率也不一样,
混在一起判断容易出现"因为业务概念听起来独立,就顺手把它物理拆开了"这种过度拆分。

所以框架把决策拆成两张**必填、分开产出、有先后顺序**的卡片:先确定业务边界,再决定
物化程度。

### Business Boundary Card(业务边界卡)

回答的是纯粹的业务/所有权问题,不涉及部署形态:

- 谁是这个能力的主要使用者?业务目标是什么?
- 归属哪个限界上下文?谁是权威所有者?
- 权威状态和不变量是什么?
- 流入的查询/命令/事件有哪些?流出的事件/副作用有哪些?
- 允许哪些同步依赖?**禁止**哪些跨上下文的读写/引用?
- 有什么权限/审计/合规风险?
- 有没有独立失败/独立扩容/独立发布的需求?
- 当前是不是跟别的东西挤在一起?有没有迁移债务?
- 物理部署现状是什么?未来触发升级的条件是什么?
- 对契约/测试/文档有什么影响?

### Service Materialization Card(服务物化卡)

在业务边界确定之后,回答"现在应该物化到哪一层"的问题:

- 目标限界上下文/所有者是谁?
- 当前代码/进程/部署/数据库现状是什么?
- 需不需要跨边界的本地事务或 JOIN?能不能接受异步/可重放/可重建?
- 核心路径的超时和降级策略是什么?
- 有没有真实的负载证据——**这个证据是"已实测"、"预估"、还是"未知"**?
- 有没有安全/合规/容灾需求?有没有独立扩容/独立发布/独立迁移的需求?
- 命中了哪些硬触发条件?命中了哪些强触发条件?
- 当前选择停在哪一级(代码/包边界、进程角色、独立服务、逻辑数据库、独立物理机/数据库实例)?
  为什么不选更高一级?
- 禁止跨边界的哪些导入/会话/数据库写?
- 独立启动/健康检查/回滚证明是什么?独立测试集合的根目录在哪?数据库初始化脚本是什么
  (或明确声明没有)?
- 影响哪些测试选择器映射?有哪些契约测试和故障隔离测试?
- 有没有低内存/快速扇出场景下的性能证明?
- 量化的"未来需要重新评估"门槛是什么?

一个容易被忽略但很关键的设计:卡片要求**三个独立的、不能合并成一个字符串的状态**——
物化状态(目标态/已配置)、每个环境各自的部署状态(未部署/已部署)、每个环境各自的健康
状态(未知/健康/不健康)。代码写完、测试跑通,只能证明代码结构本身是健康的,既证明不了
它真的被部署了,也证明不了部署之后运行时是健康的。把这三件事分开填写,是为了防止"代码
合并了"被误读成"已经上线且健康"。

## M0-M4:五道物化门

只有全部满足才应该建成一个独立的服务;哪一级都没满足,就应该老老实实停在更低的、
已经证明成立的那一层。这是通用可复用的分级判断框架。

| 门 | 要求 |
| --- | --- |
| **M0 归属清晰** | 限界上下文、唯一所有者、权威范围、禁止的跨域写操作,都已写清楚、没有歧义 |
| **M1 边界已就绪** | 跨边界的事务/JOIN 都已改造成通过所有者暴露的查询/命令/事件/投影/编排来访问,不存在跨域直接用私有 ORM/共享会话/共享写入通道的情况(所有者自己内部的本地事务不受影响,这条只管跨边界的部分) |
| **M2 有真实的物理拆分需求** | 命中至少一个硬触发条件,或者命中至少两个互相独立的强触发条件 |
| **M3 具备独立运维能力** | 独立的启动/健康检查/就绪探测/超时/降级/可观测性/发布/回滚/任务防重入机制都已具备 |
| **M4 具备独立可测性** | 独立的测试根目录、所有者自己的数据库初始化脚本、对应的测试选择器映射、契约测试和故障隔离测试,正常/高并发拓扑下都跑得通 |

证据只允许三种状态:**已实测 / 已估算 / 未知**——"未知"永远不能作为拆分的理由。这条
纪律直接堵住了"感觉以后可能需要拆"这种没有证据支撑的物化冲动。

## 硬触发条件与强触发条件

### 硬触发条件(任意命中一条就构成拆分的必要性)

- 涉及 GPU/模型推理/长时间运行的第三方服务调用,一旦出问题可能不受控地拖垮核心 API 的
  内存/CPU。
- 追加写入为主、批量扫描的高写入量工作负载,资源消耗曲线跟一般的在线事务处理完全不同。
- 涉及支付/安全/合规/凭证/审计/灾难恢复演练,需要独立的权限边界和失败域。
- 某个能力必须能够独立下线/迁移,同时保证核心路径不受影响,但当前部署方式做不到。
- 运行时环境/地域/硬件/供应商依赖跟核心后端不兼容,没法部署在一起。

命中硬触发条件,只是说明拆分**有必要**,仍然需要同时满足 M0/M1/M3/M4 才能真正建成
独立服务——必要性不能替代准备程度。

### 强触发条件(至少同时命中两条、且不能是同一个事实被重复计算)

- 需要独立的水平扩容/独立消费积压队列/独立的单例调度器。
- 依赖的技术栈/发布节奏/回滚方式/值班归属跟核心后端不一样。
- 需要独立的 SLO/容量规划/连接数预算,或者有跨机器迁移的需求。
- 有实测数据或可追溯的估算,证明 CPU/内存/写入量/延迟分位数/数据库扫描量需要被隔离。
- 需要独立的凭证/权限模型/容灾演练,但还没到合规硬性要求的门槛。

## 最小充分隔离顺序

不能跳级,也不能用后面的层级反推更早的层级已经成立——必须按顺序往上走,能停在低层级
就不要往上升:

1. 业务规则/权威不一样 → 只需要**限界上下文**层面的划分
2. 需要阻止跨域导入/写入 → **代码/包边界**
3. 需要隔离积压/CPU/内存/单例调度 → **进程角色**(同一个部署镜像里的不同角色)
4. 需要独立发布/扩容/迁移/失败域 → **独立服务**
5. 需要独立连接池/数据保留策略/容灾/权限/扫描隔离 → **逻辑数据库**
6. 只有"机器故障域/容量/地域/容灾边界"这个理由才能证成 → **独立物理机/独立数据库实例**
   (放在同一台机器上的多个容器,故障域仍然是同一个)

## 防过度拆分清单

单独任何一条都**不足以**构成拆分理由:

- 有自己的业务名词/自己的目录/自己的 schema
- "代码量/表数量看起来很多"
- 带了一个队列/第三方服务对接/webhook/定时任务
- "以后可能要扩容"
- "微服务看起来更像大公司的做法"
- "反正能容器化"
- "想让目录看起来更整洁"

## 防拆分不足的触发信号

如果命中了却选择不拆,必须写清楚理由 + 一个量化的"未来重新评估"门槛:

- 一个本可以是可选的能力,它的内存溢出/CPU 占满/第三方超时能直接拖垮核心 API
- 无边界的事件写入/分析类扫描持续跟核心业务的在线事务处理抢资源
- 某个后台任务需要独立扩容,但仍然跟 web 服务/调度器挤在同一个进程里
- 虽然设计了兜底降级,但某个可选能力部署失败时核心路径还是会被一起拖下去
- 涉及支付/安全/合规,需要独立的凭证/容灾/审计
- 已经因为别的原因被要求迁移到另一台服务器,但现状连独立启动/独立测试都做不到

## Nova 案例

> 以下是 Nova 的具体选择——用来展示这套框架实际怎么用,新项目要按自己的业务重新走一遍,
> 不需要照抄结论。

Nova 最终把 9 个 app 归纳成 6 个独立服务家族 + 6 个逻辑数据库(反向代理层不计入服务数)。
两个反直觉的真实决策例子:

**例子一:资金/交易类服务,零流量证据下就完整物化。** 一个负责资金/交易类业务的服务,
在完全没有生产流量、没有任何吞吐量证据的情况下,就被完整物化成独立服务 + 独立数据库 +
独立运行时身份。原因是它命中的是"支付/安全/合规/凭证/审计/独立容灾"这条硬触发条件,
而这条触发条件本来就不是靠吞吐量来论证的——证据类型不需要是"已实测的量",可以是"合规
要求本身"就是充分的证据。这个服务内部保持**单一写入者**、不再进一步细拆成子服务,是因为
它内部一个业务操作需要多个状态在同一个本地事务里原子地变化,拆开反而会破坏这个事务边界。

**例子二:推荐/召回排序服务,物化了但故意保持单进程。** 一个负责推荐/召回排序类业务的
服务,虽然物化成了独立服务 + 独立数据库,但**内部故意保持单进程**——没有按角色拆成多个
独立跑的子进程,没有做灰度发布。原因是它当时的负载数据只是"预估"而非"已实测",预估的
证据强度不够支撑进一步拆成多角色进程带来的额外复杂度。这个更细粒度的拆分被明确记录成
"未来的目标状态",而不是现在就做。

这两个例子共同说明:**同一个"要不要拆"的框架,面对不同强度的证据、不同类型的触发条件,
可以合理地得出完全不同的答案**——框架不是用来得出统一答案的,是用来让每一次"拆"或
"不拆"的决定都有据可查、可以被下一个读到这份文档的人重新验证。这正是这套机制相比"团队
里资深工程师凭经验拍板"的核心优势:决策过程本身被留档,而不只是决策结果。
