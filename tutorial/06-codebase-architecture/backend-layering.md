# 后端服务内部读写分层

服务边界解决的是"这个能力归谁所有、要不要物理拆开"。这篇讲的是更细一层的问题:
**一个服务内部**,单个业务对象的代码应该怎么组织,才能让"读"和"写"的边界机械可验证,
而不只是靠代码评审人工留意。这套六槽位分层设计和它带来的自动化门禁能力,是通用可复用
的机制,可以直接搬到任何后端服务的内部组织里;下面举例用到的具体文件名(`operate.py`、
`query.py` 等)是 Nova 用的 Python 命名习惯,换一种语言/框架可以用别的文件名或模块名,
只要保留"槽位职责单一、命名可被机器识别"这个核心设计。

## 六个槽位

Nova 的后端服务内部,每个业务对象的代码按六个槽位分层(适用范围是每个服务自己的
业务逻辑目录):

| 槽位 | 文件 | 职责 |
| --- | --- | --- |
| 写操作槽 | `operate.py` | 这个业务对象私有的创建/更新/删除/发布/领取/退款等写操作,以及需要在一个事务里跨表写的逻辑 |
| 查询组合槽 | `query.py` | list/detail/search/query 这类读取路径,负责 where/排序/分页/游标/过滤条件的组合,返回内部记录或中间读模型 |
| 批量组装槽 | `projection.py` | 把一批内部记录批量组装成对外 DTO,明确允许在这里做批量聚合查询以避免 N+1 |
| 纯组装槽 | `assembler.py` | 纯粹的字段改名/默认值填充/脱敏转换,**不允许**发起额外数据库查询或持有数据库会话 |
| 门面槽 | `facade.py` | 只有当另一个顶层业务领域需要稳定读取/操作这个领域的数据时才需要,暴露稳定方法和 DTO |
| 编排入口槽 | `service.py` | 只负责应用层流程编排,**明确禁止**出现任何原始 SQL 或复杂数据库查询构造 |

几条槽位之间的判断细节:

- **写操作槽的退化判断**:如果 `operate.py` 里的某段逻辑其实已经退化成"就是对某张表做
  通用的增删改",没有真正的业务编排价值,应该下沉到数据库层自己的写操作文件里,业务层
  这个文件只保留真正需要业务规则介入的写操作。
- **所有权迁移后,查询组合槽应该被删除,而不是改造成远程调用的包装壳**——这是一条容易
  被忽略、但代价很大的原则。当某个数据源的所有权被迁移到了另一个独立服务之后,原来的
  `query.py` **应该被整个删掉**,而不是偷偷改造成一个远程调用另一个服务 HTTP 接口的壳子。
  原因是这个槽位的语义本来就是"进程内直接查数据库";如果把它悄悄改造成跨服务 HTTP 调用,
  会让"这段代码到底在查本地数据库,还是在调远程服务"这件事对自动化门禁扫描工具彻底
  判断错误——门禁看到文件名是 `query.py`,就会假设它在查本地库,继续按本地查询的规则去
  校验它,产生一个**它自己都不知道自己错了**的架构盲区。正确做法是所有权迁移之后,让
  编排层(`service.py`)改为调用一个专门的、类型安全的内部网关客户端,而不是让 `query.py`
  这个槽位名不副实地继续存在。
- **批量组装槽明确允许批量聚合查询**,这是它和纯组装槽的核心区别:比如给一批 feed 内容
  批量附加作者信息/点赞状态/关注状态,这种批量聚合应该放在 `projection.py` 里一次性做完,
  而不是在循环里逐条查(N+1)。
- **纯组装槽升级的判断标准**:`assembler.py` 如果开始需要拿数据库会话再去查一次数据,
  说明它该升级成批量组装槽;如果它开始组织 where/排序/分页这些查询条件,说明它该归到
  查询组合槽。这两条判断标准本身可以直接写进代码评审 checklist,不需要每次都重新讨论。

## 为什么要这样分层:自动化门禁,而不是人工留意

分层规则本身不是最有价值的部分,真正的价值在于**这套分层设计带来的能力**:把"读"和"写"
严格分开放进各自命名规范的文件里之后,就可以写一个自动化的静态扫描工具,机械地遍历每一个
业务逻辑文件——

- 只允许"查询组合槽/批量组装槽"这类命名规范的文件里出现数据库读操作;
- 只允许"写操作槽"这类命名规范的文件里出现数据库写操作;
- 其它任何文件(编排入口、共享工具、定时任务等)一旦出现原始 SQL 或数据库会话调用,
  直接被自动化门禁拦下来。

这比"代码评审时人工留意有没有乱写 SQL"可靠得多、也便宜得多——人工评审依赖评审者当时
是否留意到、是否熟悉这条规则,而机械扫描每次都是同一个标准,不会疲劳、不会遗漏。

对于分层规则落地之前就已经存在的历史违规,只能**精确地、逐条地**加进一个明确写清楚
"这是技术债"的临时白名单,不能变成新代码可以效仿的先例——白名单是用来承认历史债务的
存在,不是用来给新代码开口子的。

## 跨领域导入边界

除了槽位内部的读写分层,还有一条跨领域的导入边界:**禁止跨领域直接引用另一个领域内部
更深层的编排入口文件**,只能通过对方的门面槽(`facade.py`)或者中立的公共层来交互。
这条规则和服务边界决策框架里 M1 门("跨边界的事务/JOIN 都已改造成通过所有者暴露的
查询/命令/事件/投影/编排来访问")是同一个思路在更小粒度上的延伸——即使两个领域现在
都跑在同一个进程里、还没有物理拆分的必要,也应该提前维持"只能通过稳定接口交互"的纪律,
这样将来真的需要把某个领域物化成独立服务时,迁移成本会小得多。
