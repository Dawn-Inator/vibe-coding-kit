# API 契约规范:RPC over HTTP

这篇讲的是 API 设计风格的一次具体取舍,以及围绕这个取舍建立起来的一整套机器强制纪律。
"RPC over HTTP 这个具体风格"是 Nova 的选择,新项目完全可以选传统 RESTful,或者别的风格——
**真正值得学的是"做出取舍时要考虑什么、怎么把取舍用机器强制落地"这套思路**,而不是
"照抄 URL 该长什么样"。

## 取舍:为什么不用 RESTful

Nova 采用"RPC over HTTP"风格,而不是传统的 RESTful 风格——这是一个明确放弃了某种约定的
决策,值得讲清楚取舍本身,而不是当成理所当然的默认选择。

RESTful 风格用 HTTP 方法(GET/POST/PUT/PATCH/DELETE)表达语义,一个资源的增删改查
对应四种不同的方法 + 同一个 URL。Nova 放弃了这套约定,改成**只用 GET/POST 两种方法,
用 URL 最后一段的动词来表达语义**。这个取舍的核心考量是:当 URL 结构本身承担了更多的
语义表达职责之后,可以让"URL 结构"和"后端代码的包结构"建立起严格的一一对应关系
(见下一节),这种自文档化的收益,在 Nova 看来大于遵循 RESTful 惯例本身带来的收益。
这不是说 RESTful 不好,而是"URL = 代码路径的直接映射"这个目标,跟"用 HTTP 方法表达
语义"这个 RESTful 核心约定,在实践中会互相拉扯——一旦选定了前者,后者自然就要让路。

## 通用机制:URL 结构与代码包路径一一对应

固定形状:

```
/api/{版本}/{服务}/{模块}/{对象}/{动作}
```

还有几个变体:带一个资源 ID、带多层链式 ID、或者省略"对象"这一级。

`{服务}` / `{模块}` / `{对象}` 三段**跟后端代码的包路径严格一一对应**。比如:

```
URL:  /api/v1/taobao/shop/product/list
代码: app.service.taobao.shop.product
```

这个"URL 结构 = 代码包结构"的映射本身就是一种自文档化设计——看到一个 API 路径,不需要
额外查文档就知道去代码的哪个目录找实现,反过来,看到一个业务对象的代码目录,也能立刻
猜出它对外暴露的 URL 前缀长什么样。这个映射关系是**通用可复用**的机制,只要项目采用
"按服务/模块/对象组织代码包"这种结构,就可以直接套用。

`{动作}` 固定是一个单词的、小写下划线风格的动词,不允许出现"多段路径拼成一个动作"这种
写法——动作必须是一个原子的语义单元,不能靠拼接多段路径来表达复合语义。

## 只用 GET/POST,机器强制

明确放弃了 RESTful 风格里"用 HTTP 方法表达语义"的约定,改成用 URL 最后一段的动词来
表达语义。这条规则**是机器强制的**——有专门的门禁脚本扫描路由定义,而不是只靠代码评审
人工把关。这一点值得强调:任何"只用 GET/POST"这类约定,如果只写在文档里、不配套机器
校验,长期来看必然会被打破,因为总会有开发者出于习惯写出 `PUT` 或 `DELETE`,评审时又
未必总能捕捉到。

- `GET` 严格对应无副作用的读,参数放 query string。
- `POST` 严格对应有副作用的写,参数放请求体。

**一个命名清晰的例外场景**:某些只读接口的查询参数会随着会话状态线性增长——比如无限
滚动场景下,前端需要把"已经看过的内容 ID 列表"整个传回来做去重,这个列表会越滚越长,
长到可能超出 URL 长度限制导致请求失败。这种情况允许用 POST 携带请求体,但前提是两个
条件同时成立:①参数确实会随会话增长;②这个接口本身没有任何状态改变的副作用。这类
例外必须**逐个显式登记在一份专门的例外清单里**,不能变成一个默认就能用的万能借口——
换句话说,"参数有点长所以我用 POST 更方便"不能作为理由,必须真的命中"会话增长"这个
具体场景,并且留档。

## 动作词表

常用动词按语义分类复用,同一个业务对象内部的动词使用要保持一致(比如不能一边用
`like`/`unlike`,一边在语义等价的另一个地方用 `add`/`remove`):

| 分类 | 常用动词 |
| --- | --- |
| 读类 | `list` / `detail` / `search` / `query` / `export` / `summary` |
| 写类 | `create` / `update` / `delete` / `edit` / `submit` |
| 关系类 | `add` / `remove` / `accept` / `reject` / `approve` |
| 状态迁移类 | `publish` / `release` / `claim` / `refund` 等 |

维护一份共享词表的价值在于,避免同一个语义在不同业务对象上被不同的词表达——这会让
调用方(尤其是前端)每接入一个新对象都要重新学习一套动词习惯,而不是能够直接复用已经
建立起来的直觉。

## OpenAPI"生成后一起提交"纪律

OpenAPI 规范文件和给前端用的类型定义文件都是**从后端代码自动生成的产物,永远不手改**。
每次改动 API 之后,要按固定顺序执行:

1. 重新生成 OpenAPI
2. 重新生成前端类型
3. 跑一次"改动影响面"检查

这几步生成的产物**要在同一次提交里一起进去,不能拆开分几次提交**——不然会出现"代码
已经改了,但 OpenAPI 产物还是旧的"这种漂移状态,而漂移状态是所有"生成物"类型的产物
最容易腐烂的地方:一旦允许分开提交,总会有人图省事先提交代码、"回头再生成",然后就
忘了。把生成步骤和代码改动绑定成同一次提交,是用流程纪律弥补"生成物容易被遗忘"这个
人性弱点,这条纪律同样是通用机制,适用于任何"从代码生成契约文件"的场景(不只是 OpenAPI)。

## DTO/状态码/鉴权治理

- 请求/响应的数据结构和成功/失败状态语义要一起声明清楚。
- 领域内部的失败原因要转换成稳定的、面向外部的错误码,**绝不能**把底层异常信息/SQL
  语句/凭证/调用栈/第三方服务的原始响应直接暴露给调用方——这既是安全问题,也是契约
  稳定性问题:底层异常信息的措辞会随实现变化,一旦被外部依赖,就等于把内部实现细节
  变成了事实上的公开契约。
- 每个操作的鉴权策略必须显式声明,**默认是"需要鉴权"**;任何放宽鉴权要求的改动都必须
  经过一份专门维护的、经过安全评审的白名单——鉴权只能收紧或维持,不能悄悄放宽。这是一条
  典型的"默认安全"设计:显式声明 + 白名单放宽,比"默认公开、需要时才加鉴权"安全得多,
  因为遗漏的成本方向不对称——忘了给一个该公开的接口加白名单,顶多是多一次审批延迟;
  忘了给一个该鉴权的接口加鉴权,是真实的安全漏洞。
- 一个不兼容的公开接口改动,必须在动手实现之前就先确认清楚受影响的调用方,不允许悄悄
  改 URL 或者悄悄加一个别名敷衍过去。

## Nova 案例:一次真实的改名

> 以下是 Nova 的具体经历,展示"URL 结构 = 代码包结构"这条纪律在真实改动里是怎么被
> 一次性、原子性地贯彻的。

Nova 有一批资金相关的路由,最初用的是一种"分组名词短语"的 URL 形状,不完全符合标准
四段式结构。后来这批路由被作为**一次原子性的改动**,统一重命名成标准的"服务/模块/
对象/动作"四段式结构。这次改动**同时**完成了以下几件事,没有分批:

- 后端路由定义
- 重新生成的 OpenAPI 文件
- 前端的 API 客户端包
- 生成的前端类型定义
- 一份记录"哪些改动是允许的破坏性变更"的白名单
- 对应的文档

这次改动里还留下了几个值得记录的具体判断:

- **每个业务对象只应该有一个对应的路由文件**——不允许在"模块"这一级再建一个额外的
  组合路由,因为自动发现路由的机制会把它重复挂载两次,导致路由冲突。
- 有几个原本想合并成一个对象的子概念,最后决定**各自独立成对象**,而不是嵌套的名词
  短语——嵌套名词短语看起来"更整洁",但会让 URL 到代码包路径的映射变得不再是简单的
  一一对应。
- 有一个批量查询接口,即使查询参数会随批量数量增长,但因为实际业务场景下这批数量有一个
  较小的上限,权衡之后决定**仍然保留标准的 GET + 重复 query 参数写法**,而不是套用前面
  讲的"允许 POST"的例外——这个决定说明例外条款不是"参数会变长就能用",而是要结合真实
  的增长上限来判断值不值得为此打破 GET-only 的默认约定。
