# 迁移的线上安全:两个"默认值"事故

迁移脚本写对了,不代表发布是安全的。发布发生在**有流量、新旧版本并存**的时间窗里,很多事故不是
SQL 错了,而是"某个默认行为"在这个窗口里做了和作者想的不一样的事。这篇用化名项目 Nova 讲两个
真实形态的事故,以及它们背后可迁移的推理方式。

配套规范见 [migration-downpath](../../skills/migration-downpath/SKILL.md) 与
[cross-service-event-contract](../../skills/cross-service-event-contract/SKILL.md)。

## 事故一:没写 phase,被默认成 pre-deploy

### 背景

Nova 的发布分两个阶段:

- **pre-deploy**:新版本启动之前执行迁移;
- **post-deploy**:所有新版本上线、旧版本退场之后执行迁移。

每条迁移在 manifest 里登记自己属于哪个阶段。Nova 的服务在每次建立数据库连接时,会拿"自己镜像里带的
权限矩阵"和数据库里的实际权限做**精确双向比对**,不一致就拒绝连接。

### 经过

1. 工程师写了一条迁移:撤销某张审计表上的 `DELETE` 权限(收紧)。这是正确的安全加固。
2. 他在 manifest 里登记这条迁移,**没有写 phase 字段**。
3. 解析器的实现是 `phase = declared or "pre_deploy"`——缺省即 pre-deploy。这个默认值是更早引入阶段切分时
   为了让存量条目继续工作而加的,当时是合理的。
4. 发布开始:先按 pre-deploy 执行迁移,权限被撤掉。
5. 此时线上还跑着**旧镜像**,它带的权限矩阵仍然认为那张表"应该有 DELETE"。旧镜像在每条新连接
   (连接池每几分钟回收一次)上比对,发现不一致,**拒绝所有新连接**。
6. 旧镜像的健康检查开始 503,管理端出现 5xx。镜像回滚被禁止,窗口只能等新镜像完全接管。

### 推理:为什么这不是"某个人漏写了字段"

- **默认值是沉默的**。漏写字段时没有任何报错,系统选了一个"看起来安全"的阶段——而对于"收紧"类迁移,
  pre-deploy 恰恰是最不安全的阶段。
- **同一个字段,对加性迁移无所谓,对收紧迁移致命**。所以不能用"大多数迁移无所谓"来论证默认值合理;
  默认值的风险由**最坏的那类**迁移决定。
- 正确规则:在某个「激活序号」之后新增的条目,**必须显式声明 phase,缺失就报错**;解析器遇到未知值抛错,
  不回退。历史条目因为不能改(校验和已冻结),在登记表里逐条写明放行理由。
- 同时把"收紧类变更只能在 post-deploy"变成**自动校验**:见下一节。

## 为什么要用线上旧版本自己的校验器

修复上面的事故,最直觉的做法是"人读 SQL,判断旧版本会不会拒绝"。这条路走不通,原因有三:

1. **旧版本的拒绝条件在旧版本的代码里**,不在候选分支里。候选分支的校验器是新规则,它说"通过",
   只证明新版本接受,不证明旧版本接受。
2. **人读 SQL 会漏掉间接影响**:一条迁移触及的对象,和旧版本校验器关心的对象,可能通过视图、授权继承、
   角色成员关系间接相关。
3. **事故的因果链是"线上现在跑的那份代码 × 即将执行的迁移"**——要验证它,最直接的做法就是把线上那份
   代码原样拿出来跑。

Nova 的做法:

1. 取出线上正在运行的提交的校验器与权限矩阵(`git archive <线上 SHA>` 到临时目录,原样加载);
2. 候选 manifest 中、线上 manifest 里没有的迁移 = 本次发布的待执行集;
3. 对每个 pre-deploy 待执行项,推出"执行后"的预期状态;
4. **用线上校验器去验证这个状态**,拒绝就阻断发布,并提示"改成两步走:先发布同时接受新旧两种形态的新版本,
   再在 post-deploy 阶段收紧";
5. 反方向再验一次:post-deploy 执行之前,新版本已上线,候选自己的校验器必须接受"还没收紧"的状态。

**无法评估时怎么办**:取不到线上 SHA、线上矩阵读不出来、解析异常——退出码是第三态"无法评估",
发布门禁按**失败**处理(fail closed)。检查器自己没法工作,不能被读成"没发现问题"。

## 事故二:never-dead-letter 被理解成"平坦重试"

### 背景

Nova 有一类合规事件(账号隐私擦除)通过 outbox 队列异步处理。这类事件**绝不能被丢弃**,否则就有人的
数据没被删除。所以注册这类消费者时设置了 `never_dead_letter=True`:关闭"重试 N 次后进死信"。

### 经过

1. 设计意图是"不丢"。实际行为是:处理失败 → 不确认、不进死信、**不写任何字段** → 队列在可见性超时
   (比如 60 秒)后重新投递 → 再失败……
2. 一个依赖服务下线两天,某些擦除事件每分钟重放一次,共几千次。行上没有失败原因、次数、时间;
   日志里每次一行异常,淹没在噪音里。
3. 值班同学想问"有哪些擦除事件卡住了"——SQL 查不出来,因为状态仍是"待处理"。
4. 团队后来加了 `parked` 状态和告警,但告警写成了"死信数量 > 0"。而不丢弃事件的死信数**恒为 0**,
   告警永远不响。
5. 再后来,告警改成按 `parked_count` 判断,查询里引用了一个**没有在日志索引里声明**的字段——查询运行时
   直接报错,告警规则状态永远是 error,没人注意到它其实没在工作。

### 推理

- **"不丢弃"和"无限热重试"是两个需求**。开关只表达前者;后者是关掉判死后的**默认行为**。
  凡是靠默认行为兜底的需求,都要问"默认行为是不是我想要的"。
- **不丢弃的事件需要一整套配套**:失败写行、指数退避、`parked` 状态、以状态/年龄为 key 的告警。
  `parked` 与 `dead_letter` **分开计数**,因为死信对法定义务等同于丢弃,而 parked 是"还在重试、但需要人看"。
- **退避只给不丢弃的事件**:退避会让队列的读取计数归零,普通事件靠读取计数累积才会被判死——给它们退避,
  毒消息就永远判不了死。
- **告警要验证"自己能响"**:告警引用的字段必须在索引里声明;规则必须带环境过滤;用静态测试读告警模板确认
  "存在以 parked 为阈值的规则"。

### 为什么需要类级测试

修完后,团队给原来的消费者补了回归测试。但注意:**这个测试只跑它自己注册的那个事件类型**。

下一个同学要注册第三个 never-dead-letter 消费者,他会照抄前两个的写法——而前两个现在是对的。但如果照抄的是
**更早的、还没改的那份**呢?或者新写法漏了一项配套呢?旧测试在新文件里什么都碰不到。

判据只有一句:**"同一个错误换个文件再犯一次,现有测试拦得住吗?"** 拦不住,就需要类级防线:

1. 全仓扫描所有 never-dead-letter 注册点(**排除测试文件**,它们会注册一次性事件类型);
2. 断言发现集合非空——扫描路径坏了,不能变成"空集合上的恒真";
3. 对**每一个**注册者断言配套设施存在;
4. 另有一条测试断言告警模板里存在以 parked 为 key、带环境过滤、字段已声明的规则。

## 两个事故的共同点

| | 事故一 | 事故二 |
| --- | --- | --- |
| 沉默的默认值 | 缺失的 phase → pre-deploy | 不丢弃 → 平坦无限重试 |
| 为什么当初合理 | 保持存量条目可用 | 先保证"不丢" |
| 为什么致命 | 最坏类的变更(收紧)被放到了最差的阶段 | 失败既不可见也不可查 |
| 本处修复 | 补上那条迁移的 phase | 给那个消费者补退避和 parked |
| 同类防线 | 激活序号之后 phase 必填 + 用线上校验器验证 + 无法评估即失败 | 全仓枚举注册点的类级测试 + 告警字段声明校验 |

两层都要做:只做"本处修复",下一个人会在别处再犯一次;只做"类级防线"而没有本处修复,眼前的问题还在。

## 带走的几条原则

1. 找出你系统里的**沉默默认值**,问"最坏的使用者会遇到什么"。
2. 验证"新旧并存"的安全性,要**运行旧版本自己的检查**,而不是推理。
3. 检查器无法评估时,**失败**,不是通过。
4. 告警本身也是代码——要有测试证明它**会响**。
5. 修 bug 交两层:本处回归 + 同类防线。
