# Monorepo 根目录布局

## 通用原则:根目录 = 明确的所有权边界,不是随手起的名字

一个 monorepo 活得越久,根目录下的顶层目录就越容易变成"谁想放哪个新东西就随手建一个
目录"的产物——今天有人建了一个 `scripts/`,明天又有人建了一个 `tools/`,过一阵子这两个
目录里的东西开始互相重叠,没人说得清新脚本到底该放哪个。

这个问题的通用解法有两步,缺一不可:

1. **写一份文档,给每个顶层目录一句话说清楚它的所有权边界和职责**。不是"这里放脚本"这种
   模糊描述,而是要精确到"这个目录只装什么、明确不装什么"。
2. **配一个机器校验脚本,扫描根目录实际存在的每一项,判断它是否落在已声明的分类规则里**。
   不符合就直接报错,而不是留给代码评审去人工发现。

第二步是这套机制真正有约束力的地方。只有文档、没有机器校验,文档很快就会跟实际目录结构
脱节,变成没人再读的历史文件。有了机器校验之后,"往根目录随手加一个新目录"这件事就不再是
零成本的——新增一个顶层目录,必须先想清楚它属于哪个所有权边界、要不要现有分类规则覆盖它,
否则校验脚本会挡住它。这个机制本身(文档 + 校验脚本的组合)是可以直接搬到任何 monorepo
项目里的,不依赖具体业务。

## Nova 案例:顶层目录表

> 以下是 Nova 的具体选择,新项目应该按自己的业务重新划分,不需要照抄目录名。

| 目录 | 用途 |
| --- | --- |
| `apps/` | 可运行的产品/服务——3 个前端客户端 + 6 个后端服务,共 9 个 app |
| `packages/` | 跨 app 共享的库(前端 JS/TS workspace 包,以及至少一个共享的 Python 可观测性包) |
| `infra/` | 可部署的基础设施(云资源、网络、运行时配置)——不包含测试选择器/门禁/端到端测试编排这类东西 |
| `engineering/automation/` | 工程自动化脚本(开发/部署/生成/安全/worktree 相关脚本) |
| `engineering/testing/` | 测试选择器、门禁编排、端到端测试编排、共享测试固件 |
| `registries/product/` | 产品侧的"机器可读事实"(功能模块清单、需求、UI、验收标准) |
| `registries/architecture/` | 架构侧的"机器可读事实"(服务拓扑声明、缓存键、迁移基线快照) |
| `registries/data/` | 数据架构的登记表/schema(这个目录本身不改变真实数据库,只是声明) |
| `doc/` | 长期维护的、给人看的规范性文档 |
| `supabase/` | 数据库配置、函数、版本化的 schema migration——作为"运行时/安全/边界投影"的例外,特意留在根目录而不是塞进 `infra/` |
| `env/` | 各环境的配置**形状**(具体密钥由专门的密钥管理系统注入,不会存在这里) |
| `release/`、`release-signing/` | 受控的交付物/证据路径;移动端签名相关的元数据(单独改名成这个名字,而不是更容易引起误解的名字,是为了避免和真正存密钥的目录混淆) |
| AI 工具控制面目录(各 AI agent 各自读取的技能/配置目录) | AI agent 的技能库——严格来说是执行入口,内容路由指向 `doc/` 里的规范源头,不是知识本身的真源 |

从这张表可以看出几个值得注意的设计判断:

- `infra/` 和 `engineering/testing/` 分开,是因为"可部署的基础设施"和"测试/门禁编排"虽然都
  跟"工程"相关,但所有权和变更节奏不一样——改测试选择器不应该被当成基础设施变更来审查。
- `supabase/` 没有被塞进 `infra/`,是因为数据库 migration 有自己独特的、比一般基础设施配置
  严格得多的治理要求(见 [schema-migration-governance.md](./schema-migration-governance.md)),
  值得单独在根目录留一个位置,而不是被"基础设施"这个大类稀释掉。
- `release-signing/` 这个名字本身是刻意选的——如果叫成更直觉的名字(比如带 "keys" 或
  "secrets" 字样),容易让人误以为这里真的存放密钥本体,从而产生错误的安全预期。目录命名本身
  也是一种沟通,应该主动避免误导。
- AI 工具的技能库目录被明确定位成"执行入口",不是"知识源头"——真正的规范内容住在 `doc/`
  里,技能库只是路由。这避免了同一份规范被复制到两个地方、然后逐渐漂移出两份不一致的版本。
- `engineering/automation/` 是 Nova 项目放置可运行自动化的目录。采用本 kit 时,初始化只在
  `engineering/automation/vibe-coding/` 生成项目自有的薄 bootstrap / adapter;可复用 runtime 仍留在
  `.vibe-coding/kit/` 子模块里。新项目可以按自己的规模决定自动化目录和薄 adapter 的组织方式,
  不需要把 kit runtime 拷贝进项目。

## Nova 案例:一次性脚本单独开一个根目录,不混进 app 自己的 `script/`

Nova 的每个后端服务(`apps/<service>/`)自己都有一个 `script/` 目录,装长期维护的开发/运维工具
(建种子数据、Supabase 配置同步、各种 dev 检查),这些脚本大量 `import app.xxx`、用该服务自己的
`uv` venv 跑,被 ruff/mypy 豁免规则和专门的 `*:script-selftest` 测试任务覆盖——它们是正式代码,
只是不部署到生产环境。

问题是团队里还会不断冒出**真正一次性**的脚本:某次数据修复、某次临时排查。这类脚本如果随手扔进
某个服务的 `script/` 里,时间一长就分不清哪些还有用、哪些早该删——`script/` 目录因此越堆越大,
变成一个事实上的"脚本垃圾场"。Nova 的做法是单独开一个仓库根目录 `.script/<module-name>/`
专门装这类脚本,跟各服务的 `script/` 从三个维度区分开:

- 点号前缀,一眼看出是临时的、不是正式代码。
- 不打包、不提供 `__init__.py`,直接跑文件(`uv run python .script/<module>/run.py`;需要用到
  某个服务的依赖时显式 `uv run --project apps/<service> python .script/<module>/run.py`),点号
  前缀本身也不是合法的 Python 模块名,刻意不让它能被当成正式模块导入。
- 不进 lint/type/test 门禁,没有兼容性保证,随时可以删除。仍然纳入版本控制,方便后来的人或者
  其它 AI 会话查到"这个问题之前有没有人写过一次性脚本处理过"。

这个目录放在仓库根目录、而不是某个 `apps/<service>/` 下面,是因为一次性脚本通常不需要深度复用
某个服务内部的实现——直连数据库、调已有接口这类轻量操作居多,没必要绑定在某个服务目录下面。
真正需要复用某个服务能力的脚本,说明它已经不是"一次性"的了,应该按上面 `script/` 的标准正式
落地到那个服务里,而不是继续留在 `.script/`。

## Nova 案例:云资源命名跟目录命名是同一套原则

> 以下是 Nova 的具体命名规则,新项目应该按自己的资源类型和阶段划分重新设计,不需要照抄段位。

Nova 把"目录命名是一种沟通"这条原则延伸到了云资源上,写成一条通用规则:

```
nova-<资源类型>-[<环境>-]<用途/角色>-<区域>[-序号]
```

真实例子:

| 资源 | 命名 | 说明 |
| --- | --- | --- |
| 生产 API 服务器(ECS) | `nova-ecs-prod-api-sz` | 环境 + 用途都在 |
| 共享控制面机器(ECS) | `nova-ecs-hub-sz` | 不分环境,省略环境段 |
| 测试机池(ECS) | `nova-ecs-heavy-test-sz-2` | 不分环境,序号区分池内多台 |
| dev 数据库(单实例阶段) | `nova-pg-dev-sz` | 单实例,省略角色段 |
| prod 业务库(多实例阶段) | `nova-pg-prod-business-sz` | 多实例才需要角色段区分是哪个逻辑库 |

这张表体现的设计判断:

- **可选段真的可以不出现**,不是"填不满就留空"——`hub` 和测试机池没有环境概念,dev 数据库当时
  还是单实例、没有"角色"这个区分维度,这两段就该直接省略,而不是硬塞一个不传达任何信息的占位值。
- **"用途/角色"这一段的具体含义按资源类型自己定**,不强行统一成一个词——ECS 上是"跑哪个工作
  负载",数据库上是"承载哪个逻辑库",两者是不同的分类轴,只是刚好都落在命名的同一个槽位里。
- **约定是随实际情况演进的,不是一开始就写死**——Nova 的数据库角色段就是后来数据库从单实例变成
  多实例之后才补上的新约定,之前几个实例的历史命名(比如按逻辑库直接叫 `nova-prod-primary-rds`
  这类)在约定写清楚之后被逐步迁移对齐,而不是留着不管。

**一个更能说明问题的对比是 Nova 的 6 个后端服务在 dev 和 prod 上的机器数量差异**,同一套命名
规则在两边呈现出完全不同的物理形状:

| 环境 | 机器 | 上面跑的服务 |
| --- | --- | --- |
| dev | `nova-ecs-dev-api-sz`(1 台) | 全部 6 个后端服务共居同一台机器 |
| prod | `nova-ecs-prod-api-sz` | 核心业务服务 + 反向代理 + 统一出口连接器 |
| prod | `nova-ecs-prod-ai-sz` | 推荐 + 数据分析 + AI 计算,三个服务共居 |
| prod | `nova-ecs-prod-admin-sz` | 管理后台,单独一台 |

dev 图省成本,6 个服务全挤在一台标着 `api` 角色的机器上;prod 按负载/隔离需求拆成了 3 台,但
`prod-api-sz` 这台机器**依然是共居的**,同时跑着好几个服务,并不是"一台机器只能对应一个服务"。
`用途/角色`这一段命名的始终是**这台机器承担的角色定位**,不是它上面精确挂了几个进程——不需要
因为一台机器上跑了 6 个服务就编 6 个资源名,也不需要等哪天真的按 workload 拆分成 3 台时把
之前的名字推倒重来:`prod-api-sz`、`prod-ai-sz`、`prod-admin-sz` 是在原有"api 角色"这个概念上
新增出来的名字,不是重命名的结果。

## 环境名、分支名、产物 channel 名:三套独立词表,靠映射表连接,不靠拼写相同

云资源命名之外,还有一层更容易被想当然的命名维度:**git 分支名、环境名、构建产物的 channel
名,是三套服务不同目的的独立词表**,允许两两不同——

- **分支名**服务协作流程,常年沿用团队自己的历史习惯(`develop`/`staging`/`main`)。
- **环境名**服务"这套配置指向哪里"这个运行时概念(`dev`/`stg`/`prod`),是配置文件和部署
  目标的索引键。
- **产物 channel 名**服务"这份构建产物是什么性质"(比如安卓的 `debug`/`release` build
  type),这套词表往往是平台/工具链自己规定的,项目未必能自由命名。

Nova 案例里三者的映射关系:

| 分支 | 环境 | 产物 channel |
| --- | --- | --- |
| `develop` | `dev` | `debug` |
| `staging`(或已验证的预发布候选分支) | `stg` | `preview` |
| `main` | `prod` | `release` |

这张映射表**本身就是契约**,一个真实踩过的坑:有人在环境 `dev` 上构建产物,直接去对象
存储里找 `.../dev/...` 目录,结果什么都没有——产物实际落在 `.../debug/...`,因为
`debug` 才是 `dev` 这个环境映射到的 channel 名,不是环境名字面本身。`dev`/`stg` 两个
环境甚至可以**共用同一个存储桶**,纯靠这段 channel 目录名区分——这是合法的简化(降低桶
数量和权限面),不是配置错误,前提是这张映射表写在显眼的地方,而不是只存在于某个上传脚本
的常量里,等人翻源码才发现。具体案例见
[mobile-native-build-pipeline.md](./mobile-native-build-pipeline.md)。

## 目录迁移无回退表

这是另一个可以直接复用的技巧。当决定要把某个旧目录重命名或迁移到新位置时(比如把散落的
脚本目录归并进统一的自动化目录),应该:

1. 在文档里维护一张**历史迁移记录表**(旧路径 → 新路径),让后来者能查到"这个东西以前在哪"。
2. **迁移必须用 `git mv` 一次性干净完成**,不允许中间状态长期存在。

这张表最关键的一条纪律是**明确禁止两种妥协方案**:

- ❌ 建一个符号链接兼容旧路径。
- ❌ 新旧两份都保留、之后再手动同步。

这两种做法看起来都能"暂时省事",但代价是根目录结构文档从此失去了"读起来就是当前准确状态"
这个性质——文档说的是新路径,但实际上还留着一堆兼容层,读文档的人没法单靠读文档判断
现实到底是什么样子,必须再去代码库里交叉核实。这种"认知负担"一旦引入就很难消除,因为每次
新增迁移都会再叠加一层。坚持"迁移只能一次性干净完成、不留后门"这条纪律,本质上是在保护
"文档 = 当前真实状态"这个更基础的不变量,值得任何 monorepo 项目照搬。
