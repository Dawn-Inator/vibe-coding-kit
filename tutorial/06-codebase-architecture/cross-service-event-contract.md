# 跨服务事件契约:两个没有共享包的服务,靠什么防止漂移

一个服务把事件异步投递给另一个服务(outbox 生产者 → inbox 消费者这类模式),而两个服务
**故意不共享任何代码包**时,两侧各自维护的 event_type allowlist 迟早会漂移——这不是理论
风险,是 Nova 真实发生过的事故:同一套契约信息散落在六份文档里各写一半,某次核查发现其中
六处口径**同时**已经失真。下面几条机制是通用可复用的框架,收敛自这次事故的复盘;具体字段名
(`aggregate_id`、`source_revision`)是 Nova 的选择,机制本身不依赖这些具体名字。

## 契约表:一处登记,而不是散落在多份文档里

维护**一张表**——event_type × aggregate_type × aggregate ID 来源 × 去重/修订值 × 生产者——
作为每一个跨界事件类型的唯一登记记录。新增一个事件类型,登记这张表和写代码必须是同一次改动。
分散在多份文档里描述同一份契约,正是它会悄悄失真的原因——收敛成一处,其它提到这份契约的地方
只保留指针,不重复描述。

## allowlist 一致性:靠"双向读对方源码"的测试,不是靠单侧字面量比较

两侧 allowlist 是否一致,必须由一条自动化测试保证,而且**必须是双向的**:A 服务的代码库里
有一条测试,**静态读取 B 服务的实际源码**(不是抄一份、不是重新声明一个字面量)去断言两个
集合相等;B 服务的代码库里也有一条镜像测试,反过来读 A。

为什么必须双向:两个服务通常跑在不同的 CI/gate 通道上。只放一条单向测试,就得靠"这次改动
会不会恰好触发那条通道"这种推理来判断漏配会不会被抓住——这正是这类测试存在的意义所在,不该
再引入一层不确定性。两条独立测试,各自绑定自己服务的 gate,保证不管哪一侧改动,那一侧自己的
测试都会立刻抓到不一致,不依赖另一侧的通道也跑一遍。

这类测试还要对"退化成空转"保持警惕:如果它要读的源文件不存在了、要找的常量消失了、要解析的
表达式形状变得认不出来,必须**响亮失败**,绝不能悄悄退化成空集合,让"集合相等"这个断言变成
恒真、毫无信息量的空操作。

单纯"某侧常量 vs 写在自己测试文件里的字面量"这种比较,只能抓住"改了常量却忘了同步描述",
对真正的跨服务漂移**没有任何保护**——不要把这类弱测试误当成跨服务保证。

## 去重轴:选真正会变化的那个维度,而不是最粗的那个

去重键要选真正保证唯一的最窄维度——通常是 `(aggregate_id, event_type)`,不是单独的
`aggregate_id`。选错这个维度有一个具体、危险的失效形状值得记住:如果两个不同的事件类型可以
合法共享同一个 `aggregate_id`,而投递本身不保证顺序(队列没有顺序保证是很常见的默认行为),
那么**只按 `aggregate_id` 去重**会导致"后到达的那个事件,不管它是什么类型,都会被误判成
前一个事件的重复,被静默丢弃"——而消费方仍然返回成功响应,生产方以为投递成功,没有任何报错、
重试或死信记录。这比明确拒绝更危险,因为它是静默且永久的。

用一条数据库层的 `UNIQUE` 约束作为这条去重逻辑的**兜底,不是主闸**——应用层"先读当前水位再
判断"式的逻辑,在并发下天然存在一个 check-then-act 竞态窗口,`UNIQUE` 约束本身堵不住这个
窗口(两个并发读者可以在任一方写入之前,都读到"还没有过"这个状态)。清楚区分哪一层是真正的
主闸、哪一层只是兜底,也不要把兜底约束的冲突判定范围收得太窄——一个不限定冲突目标、直接
响亮报错的约束,往往比一个精确瞄准某种冲突形状、却在遇到意外碰撞时悄悄放行的约束更安全。

## 宽度契约会跨服务链式传递,给 ID 加前缀是常见的破坏方式

如果一个标识符要流经多个服务各自的 schema 和 DTO 校验,必须确认链条上**每一环**都用同一个
最大长度,并且假设**零余量**。一个很容易忽略的错误:生产者为了可读性/命名空间给一个跨服务
共享的 ID 加前缀(比如 `sometype:<原始id>`),却没有确认链条上每一层的长度限制本来就是
按**不带前缀**的原始 ID 最大长度设计的。加前缀之后,只会在**最长的合法 ID** 上悄悄溢出——
所有用短示例 ID 跑的测试都会通过,只在生产环境遇到足够长的真实 ID 才会炸。给跨服务边界流动
的标识符加前缀之前,先重新核实一遍整条宽度链;不确定就保持原始不加前缀,把命名空间信息放进
另一个独立字段。

## 新增一个事件类型的接线清单:当成一次原子改动

漏掉任何一项,后果是**静默**丢弃或拒绝,不是报错,所以整份清单要当成一次不能拆开落地的改动:

1. 生产者这一侧的 payload 契约,包括消费方非空要求的每一个字段。
2. 加进生产者自己的出站 allowlist。
3. 加进消费者自己的入站 allowlist。
4. 在契约表里登记这个事件的 aggregate 命名空间/ID 来源/去重或修订值,并确认没有和同一维度
   下已有的事件相撞。
5. 让第 2 步和第 3 步是否一致这件事,完全靠上面那条双向测试来验证——如果它没有在只改一侧
   时红,说明它接线还不对。

## 失败分类:只有真正的契约拒绝算终态,其它一律可重试

把失败严格分成两类:接收方自己的校验明确说"这个请求结构性有问题,原样重发永远不会成功",
这一类才算终态(进死信、不再重试);认证抖动、部署窗口的路由问题、限流、瞬时的服务端错误,
一律必须可重试。这条边界要收窄的原因是真实发生过的事故:更早期"任何 4xx 都算终态"的策略,
意味着一次瞬时的鉴权 token 漂移,或者部署窗口里几分钟的路由 404,就能把那个窗口期内**全部**
在途事件永久打入死信——把几分钟的基础设施抖动变成了永久的数据丢失。终态范围收窄之后,
"投递卡住了"这件事的可见性应该靠监控和告警,不是靠悄悄丢事件。

## "刻意不报错"不等于"可以悄悄不管"

如果设计上刻意选择"遇到未登记的事件类型不抛异常"(这是合理的选择——一条坏事件不应该
卡死整条有序队列,拖累后面所有合法事件),这个"不让流水线崩溃"的决定,不能也意味着
"不告诉任何人"。把日志级别提到真正会被人看到的级别,附带一个结构化字段记录具体是哪个事件
类型被丢了(不能只记录日志模板,必须记录真实插值后的值,否则等于没记录),并且配一条
">0 即告警"的规则——在正常运行下这条路径永远不该被触发,出现一次就是信号本身,不需要
先攒够样本再调阈值。

## 幂等要靠多层独立机制叠加,不是靠一层检查

在事件流经的每一个阶段各自叠一层独立的幂等机制(首次记录点的唯一约束、投递/入队阶段的
独立幂等键、最终副作用/账本层的另一层唯一约束)。每一层堵住的是不同的并发窗口;只依赖
其中一层(尤其是应用层的 check-then-act)会让其它层的窗口继续敞开。选下游幂等键该按什么
维度派生时,选真正会产生并发竞争的那个维度(比如按"发起动作的用户"去重,如果同一用户的
两个并发请求才是真正的风险),而不是按一个每次都不同的请求 ID 去重——问题应该是"这里真正
会竞争的是哪个共享值",而不是"哪个 ID 用起来最顺手"。

## 对"收回已发放的一次性权益"保持谨慎

在给一个错误发放的一次性权益实现自动回收之前,先确认回收机制本身会不会造成比原始 bug 更大
的伤害。如果回收是通过追加一条负向账本条目实现的(而不是真的删除原始正向条目,这经常是
系统刻意的设计,为了保留审计轨迹),叠加上"每个主体只能领一次"的唯一约束,后果可能是:
回收之后,这个主体的这份一次性权益名额**永久、不可恢复地被占用**——即便之后完全合法地
重新满足条件,也再也拿不到这份权益,而且系统里往往根本没有一个后台补发入口。把"自动回收一个
不可逆的一次性发放"当成一个需要独立拍板的产品决策,而不是一次常规修复;把"什么条件下应该
重新评估这个决定"写下来,而不是默默决定"永远不做"。
