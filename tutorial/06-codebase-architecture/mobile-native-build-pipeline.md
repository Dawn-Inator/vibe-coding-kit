# 原生打包流程:一个 wrapper 命令、两个必答问题、一张命名映射表

这篇讲的是"怎么把一个 Capacitor/React Native 这类混合应用的原生打包流程,从一堆容易踩坑的
手工步骤,收敛成一条不容易用错的路径"。下面的三条机制是通用可复用的框架;涉及具体命令名
(`pnpm build:android`)、具体环境变量名(`BUILD_NUMBER`)、具体渠道名(`debug`/`preview`)
的地方,是 Nova 基于自己业务的具体选择,换一个项目会有自己的具体名字,但机制本身照搬。

## 机制一:一个 wrapper 命令,不让任何人直接碰原生工具链

原生打包实际要做的事情很多——编译 Web 静态产物、同步进原生项目、跑 Gradle/Fastlane、校验
产物、发布到一个按环境和 commit 分类的目录——如果这些步骤没有被收进一条命令,团队里迟早
会有人图省事直接 `cd android && ./gradlew assembleXxx`。这条手工路径绕过的不是"一步"而是
**四层守护**:环境注入校验(拒绝把 `localhost` 打进设备装的包)、环境选择、签名文件准备、
产物归位。绕过之后最常见的后果不是"报错",而是"看起来打包成功了,但产物在错误的目录、
文件名不规范、或者设备连不上任何后端"——这类静默失败比编译报错更贵,因为要等到有人真机
安装才会发现。

## 机制二:两个问题必须显式问,不能从 `.env` 默认值推断

打包请求**永远先问两件事**,不接受"按当前配置一把梭":

1. **环境**(决定构建类型,强绑定,不用问第二遍)——测试环境对应 debug 构建、生产环境对应
   release/店铺包构建。四类必须当场拒绝的错配:拿 `local` 环境打包(设备连不上你电脑的
   loopback)、`dev` 环境配 release 构建类型(把没混淆的调试包当正式包发)、`prod` 环境不加
   release/店铺标志(把没混淆的调试包发到生产域名)、忘记设置强制要求的构建号变量。
2. **区域/渠道维度**(如果产品有多市场/多品牌变体)——而且不能假设"全部一起打"这个能力在
   所有平台上都对称存在:同一个项目里,iOS 侧支持"两个区域一次打完",Android 侧可能明确
   拒绝这个参数、要求分别打两条命令。**旗标语义不能跨平台类比**,这条本身也是通用教训。

## 机制三:命名三层分离——文件名、目录、远程存储 key,各自服务不同读者

这是本篇分量最重的一段,也是这套机制被发现"缺了文档"的直接原因:**产物文件名、本地/CI
发布目录、远程对象存储的 key 路径,是三套可以彼此不同的命名体系**,各自服务不同的读者
(人 vs CI vs CDN/下载客户端),硬要求它们字面一致反而会束缚设计。

Nova 案例(具体值仅作示例):

```
本地/CI 发布目录:release/mobile/<stage>/<git-sha>/android/nova-cn-android-official-debug.apk
远程对象存储 key: android/{region}/official/{channel}/{versionMajor}/{versionDir}/{versionName}-{shortSha}-run-{runId}-attempt-{attempt}.apk
```

其中 `channel` 是一个**冻结成单一字面量**的历史遗留维度——这个项目曾经真的有多个安卓分发
渠道可选,后来收敛成只保留一个,但文件名模板里仍然写着这个字面量,是为了命名连续性,不代表
还能选别的值。真正容易踩坑的是这一层:**`channel` 目录名和触发这次构建的 `环境` 名字,
不是同一个词表**——

```js
const CHANNEL_BY_STAGE = Object.freeze({ dev: 'debug', stg: 'preview' });
```

有人在 `dev` 环境打完包,直接去对象存储里找 `.../dev/...` 目录,结果什么都没有——产物实际
落在 `.../debug/...`,因为 `debug` 才是 `dev` 环境映射到的渠道名。`dev`/`stg` 两个环境
甚至可以**共用同一个存储桶**,纯靠这段渠道目录名区分——这是合法的简化(减少桶数量和权限面),
不是配置错误,前提是这张映射表写在显眼的地方,而不是只存在于某个上传脚本的常量里等人发现。

这条映射表和更上一层的"分支名 ↔ 环境名 ↔ 渠道名"三角关系是同一个原则的两个层级,后者见
[monorepo-layout.md](./monorepo-layout.md) 的"环境名、分支名、产物 channel 名"一节。

## 签名指纹这类"不进 git、但也不该只存在某个人脑子里"的材料,放哪里也是命名问题

发布身份(bundle ID、签名指纹)第一次踩坑,往往不是"忘了记录",而是"记录了,但下次要用
的时候没人记得放在哪"——第三方 SDK 控制台(推送、OAuth、崩溃上报、地图)经常要求登记
一份签名指纹,如果每次都要重新从 keystore 现算一遍,迟早会有人图省事把指纹直接贴进某个
聊天记录或者一份不受控的本地文件里。

这其实是[monorepo-layout.md](./monorepo-layout.md)"目录命名本身也是一种沟通"这条原则
在更小尺度上的复用:开一个点前缀、明确 gitignore 掉的目录(比如 `.ci-secrets/`),就放在
它描述的原生工程目录旁边,里面按主题各放一份纯文本文件。**点前缀和目录名本身就在传递信息**——
任何人走到这个原生工程目录,光看名字就知道"这里面是本地/CI 专用的敏感参考资料,不是源码,
不是构建产物,换一个环境也不该直接照抄过去,而是要重新生成"。gitignore 要排除目录本身,
而不是只排除目录里的某几个文件——这样以后往里面加新文件,不需要再补一条新的 gitignore
规则也照样不进 git。

## "打包即发布"是一个明确的默认行为选择,不是隐含行为

对于快速迭代的环境(dev/staging),Nova 的选择是**打包命令默认直接发布**——上传一个不可变的
版本化产物、把一个可变的 "latest" 指针repoint 过去、刷新一份清单、通知团队常看的地方。不提供
"再手动跑一条发布命令"的两步流程,也不在每次打包时都问"要不要发布"——对这类环境而言,"打包"
和"发给正在等的人验收"在实践中是同一件事,所以把它设为默认行为,用 `--no-publish` 作为例外
开关。生产环境永远不走这条本地发布路径——上架产物必须来自受控、可审计的发布链路,不能是
一次笔记本电脑上的临时上传。
