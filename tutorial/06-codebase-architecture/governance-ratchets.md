# 存量债务棘轮:为什么基线要读 merge-base、为什么要有过期日

[backend-guardrails](backend-guardrails.md) 的结构检查是零债务的。现实里,多数项目是"先有代码,后有
规则"。棘轮(ratchet)是中间路线:**把已有违规冻结,保证只会变少**。机制与不变量见
[backend-governance-ratchets](../../skills/backend-governance-ratchets/SKILL.md);这篇用 Nova 团队的三个
推演,解释这些不变量不是洁癖,每条都对应一个真实会发生的漏洞。

## 推演一:同一个 PR 里既加违规又改基线

Nova 的检查器逻辑是"当前违规必须都在基线里,且基线不能比上一版大"。"上一版"从哪来?最省事的写法
是读工作树里的基线文件。

某个深夜的 PR:开发者新增了一处违规,检查器红了。他运行重生命令,基线被改写成包含新违规;再跑检查,
绿了。检查器拿来比较的"上一版"就是他刚改过的那份,所以"基线没有变大"这一条永远成立。

修法是读 **merge-base 的 git blob**(`git show <merge-base>:<path>`)。merge-base 是分支分叉点,
不在这次改动的控制之内:改动者能改自己分支的工作树,改不了历史。对比对象换成历史,"顺手改基线"就
会被看见——基线变大了。

配套要求:

- base ref 必须显式提供。缺失、为空、全 0 的 sha 都 fail closed,不能默默退回读工作树。
- 重生入口自己也有一道增长自检(条目变多、预算数字变大即拒写),放宽需要显式环境变量并打印理由。
  这是第二道防线:第一道防线(merge-base)在 CI 上拦,第二道在开发者本机重生那一刻就拦。

## 推演二:没有过期日的基线会变成永久特权

基线条目是对债务的承认。如果它没有 owner、没有计划、没有到期日,会发生什么?

半年后,没人记得为什么某个文件在基线里。新同事把它当作"这类写法是被允许的"先例,模仿着写。基线
没有变大(条目数没变),但它的语义从"待还的债"变成了"通行的风格"。

四个必填字段(`owner / expiry / issue / removal_plan`)把这件事变成机器可查的事实:谁负责、什么时候
必须复核、哪个工单在跟、怎么还。**过期必须硬失败,不是警告**——警告没有人读。同时避免所有基线都
撞同一天到期:有存量的棘轮约半年一审,已归零的守卫约一年一审,到期前 30 天(示例)给一条不改退出码
的提前预警。

还有一类对称的情况:**陈旧豁免**。债务已经还了,条目还挂在基线里。如果允许陈旧条目存在,它们就是
随时可被复用的空洞——将来有人写出同 key 的新违规,会被这个旧条目悄悄覆盖。所以"基线里有、扫描里
没命中"同样失败,强迫删除。

## 推演三:扫描塌缩,绿得最彻底的假绿

Nova 有一条"测试夹具里的 SQL 参数必须显式类型转换"的静态检查,扫描所有生产代码文件。某次重构把
目录 `src/` 改名,检查器里过滤路径的写法没同步。检查器照常运行、照常通过——因为它扫描了零个文件,
没有违规可报。几个月里没有人发现,直到真库上出现了本该被拦住的类型歧义错误。

这类事故的特点是**失败不产生任何信号**:没有红,没有警告,"无违规"和"没扫到东西"在输出上一模一样。
所以每个扫描型检查器都要断言"扫描规模不得塌缩"。

下限怎么定?手填一个魔法数("至少 50 个文件")会随代码增长过时,也会在改名那一天一起失效。更可靠的
是**独立盘点**:用另一套更宽松的规则(例如"路径任一段含 `test` 才排除")数出本该被扫的目标,要求扫描器
实际检查数 ≥ 盘点数 × 一个宽松比例(示例 0.5)。盘点和扫描走不同的路径规则,扫描侧的过滤写坏时,盘点侧
不会同步写坏;比例宽松,只拦"扫到 0 或近乎 0"。

同样的思路用在基线上:基线自己声明的 `scope` 也受 merge-base 约束,不允许相对旧版收窄——否则把
`scope` 缩小一点,"违规"就消失了。

## 小结

| 不变量 | 防的是 |
| --- | --- |
| 读 merge-base blob | 同一改动里顺手改基线 |
| 重生入口拒绝变大 | 一键登记全部新违规 |
| owner/expiry/issue/removal_plan + 过期硬失败 | 基线变成永久特权 |
| 陈旧条目失败 | 空洞被将来的新违规复用 |
| 独立盘点下限 | 扫描路径写坏导致假绿 |
| hard/advisory + 升级路径 | 新规则永远停在"只报不拦" |
