# 安全机制:reference-transaction hook、主工作区锁、大规模删除防护、收尾队列锁

## 问题

`README.md` 里提到,git worktree 能解决"独立工作目录"的隔离,但仓库里仍然有一部分状态是**结构性
共享**的——不管你在哪个 worktree 里,操作的其实是同一份东西。这部分共享状态如果不专门设计护栏,
会绕开 worktree 隔离本身带来的安全感,制造出比"没有 worktree"更隐蔽的事故(因为表面上看起来
每个任务都有自己独立的工作目录,实际出事的地方反而是那些"看起来独立、实际共享"的角落)。这篇
展开六类具体的护栏机制,以及它们各自依赖的一个通用 git 技巧。

## 设计原理(通用、可泛化)

护栏要解决的共享状态可以归成三类,每一类对应一组机制:

1. **共享引用**(`refs/stash`)——同一个仓库里所有 worktree 共享一份 stash 引用,一个 worktree 的
   `stash pop` 可能冲掉另一个 worktree 正在暂存的改动。
2. **共享的"人类主线"**(主工作区)——这是一个特殊的 worktree,它不是任务专属的,而是人类/编排者
   日常持续使用的,需要比普通 worker worktree 更强的保护,防止被误改。
3. **共享的目标分支**(收尾时要推送的分支)——收尾动作本身要能防呆(防止一次性删太多文件)、
   要能防并发踩踏(多个收尾请求排队)、要能保证质量(推送前先跑检查)。

## 可复用技术模式

### 1. `reference-transaction` hook 机制本身(通用技巧,任何项目都能直接抄)

这是整套安全机制里技术含量最高、也最值得单独理解原理的一块。git 支持给单个 worktree 单独配置
`core.hooksPath`,指向 `.git/worktrees/<name>/` 下的一个目录——**关键是这必须是 worktree 级别的
配置**(利用 git 的 `extensions.worktreeConfig` 扩展开启的"每 worktree 独立配置作用域"),而不能是
仓库共享的配置,也不能把 hook 目录放在工作目录本身里(那样会被当成普通文件,而且不同 worktree
之间也无法区分)。设置方式类似:

```
git config extensions.worktreeConfig true
git config --worktree core.hooksPath /path/to/this-worktree-only-hooks/
```

装好之后,`reference-transaction` hook 只对**这一个 worktree** 生效,可以在任何引用更新(创建/
更新/删除分支、tag、`refs/stash` 等)处于"准备中"状态时被调用,检查后决定放行还是拒绝。因为
`core.hooksPath` 指向的是一整个 hook 目录而不是单个 hook 文件,可以在这个目录里把其他真正需要的
hook(比如 `pre-commit`、`pre-push` 检查脚本)原样放进去转发调用,不会因为装了一个防护 hook 而
意外挡住其他 hook 的正常执行。

这个机制本身完全不依赖任何业务逻辑,是任何"需要按 worktree 差异化拦截 git 操作"的项目都可以直接
搬的通用技巧。

### 2. 防 `git stash` 误用的 hook

`begin` 创建 worktree 时,用上述机制给这个 worktree 单独装一个 `reference-transaction` hook,
拦截任何从这个 worktree 发起的、想要更新 `refs/stash` 的操作(`push`/`store`/`drop`/`clear`/
`pop` 里"写入或删除 stash 引用"的那一步)。

**有一个技术细节必须说清楚**:git 本身没有 `pre-stash` hook,`reference-transaction` 只能在引用
**真正发生变化**时触发。而 `stash apply`/`stash pop` 的完整语义是"把 stash 内容合并回工作区"
(不涉及引用变化的部分)+"如果成功就丢弃这条 stash 记录"(`pop` 才有,涉及引用变化)。所以这个
hook **拦不住** "合并回工作区" 这一半动作——如果 stash 内容本身会造成冲突或覆盖,hook 是挡不住的;
它只能拦住"最后丢弃/写入 stash 引用"的那一半。这是这个技巧的边界,需要如实告诉使用者,不要造成
"装了这个 hook 就绝对安全"的错觉。作为补充,还应该有一个只读的检测命令,专门扫描仓库里已经存在的、
或者绕开了这个 hook(比如直接操作底层引用)的游离 stash,供事后排查。

### 3. 主工作区多层锁

主工作区是人类/编排者共享使用的特殊工作区,需要比普通 worker worktree 更强的保护,设计成多层
叠加而不是单点防御:

- **分支漂移探测**:检测主工作区当前检出的分支是不是偏离了预期的基线分支(比如本该停在 `develop`
  却被切到了别的分支),这是一种事后能发现异常的兜底检测。
- **worker 角色感知的 hook**:同样用 `reference-transaction` 机制,但这次装在主工作区上,当调用
  进程被标记为"worker 角色"时,拦截任何对主工作区引用的改动。后续这层保护还做了增强:即使一个
  AI 会话忘了显式把自己标记成 worker,只要探测到"调用进程的父进程链里存在 AI CLI 的进程",同样
  会被拦下——这堵住了"忘记设置角色标记"这个最常见的漏洞,把"信任调用者自己声明身份"升级成
  "从进程树里客观判断身份"。通用版本的 `sync-primary` 判定 AI 调用者用两路信号,任一命中即可:AI CLI
  自己导出的环境变量标记(不受中间套了多少层包装进程影响),或向上走 8 层的祖先进程链。
  被判定为 AI 的**顶层**调用者(非 worker)在没有人工批准变量时,不是一律被拒,而是做一次 fail closed 的空闲
  扫描、全部安静才放行(理由见 `commands.md` 的 `sync-primary`);worker 上下文仍然无条件被拒。
- **审计日志**:每一次被允许、以及每一次被拦截的尝试,都追加写入一份审计日志文件,方便事后取证
  "谁、什么时候、试图对主工作区做了什么"。
- **命名规范的逃生舱环境变量**:有限的几个环境变量可以在真正需要时放行(比如编排者需要手动介入
  修复主工作区状态),但命名上要求写明"谁批准的",而且这些变量**只能由人类/编排者自己设置**——
  被拦截的 worker 没有权限给自己开这个后门,不然多层锁就形同虚设。

这一整套是一个可复用模式:任何"有一个共享的、需要保护的特殊工作区,又有一批权限较低的自动化调用者"
的场景,都可以套用"漂移探测 + 角色感知拦截 + 进程链兜底 + 审计日志 + 人工专属逃生舱"这五层结构,
具体力度(比如要不要做进程链探测)可以按项目的自动化调用者数量和风险等级调整。

### 4. 大规模删除防护

收尾命令在真正提交/推送之前做一次检查:如果这次改动相对合并基线**删除了很多个跟踪文件**(超过
一个数量阈值,比如 20 个),或者触碰到了一份**关键路径白名单**(基础设施配置目录、git hook 配置、
许可证文件、包管理清单、锁文件、版本声明文件、密钥/签名相关目录等),就拒绝执行,要求显式传一个
"确认允许大规模删除"的参数才放行。这是一种典型的"低成本、高召回"防呆设计:AI 会话偶尔会因为
理解偏差做出大范围误删(比如把整个目录当成废弃代码清理掉),这类检查不需要理解改动的语义,只要
统计数字和路径匹配就能拦住绝大多数事故。

### 5. 收尾队列锁

多个并发的收尾调用通过一个文件锁排队执行(先进先出),避免互相踩踏推送。这里有一个容易被忽略但
必须处理的边界情况:如果检测到当前持有锁的进程其实已经死掉了(比如异常退出没释放锁),要能自动
回收这个锁,而不是让后续所有收尾请求永远卡在等一个不会来的释放——这是任何"文件锁 + 长时间持有"
模式都要考虑的死锁预防设计。持锁期间同样要有边界:给持锁时长一个上限,每一步 git 拿剩余预算当硬
超时,预算耗尽就释放;收到中断信号时也要释放。排队的会话还应该能看到"谁在持锁、处于哪个阶段、
已经多久"。如果项目要在锁内跑很长的检查,这套预算不会替你杀掉并重新排队,需要让那一步异步跑、
自带超时,或自己补这个机制。

### 6. worker worktree 收尾时的自动预检门禁

"worker 模式"创建的 worktree 在收尾时,会自动先跑一遍相对轻量的测试选择器和本地静态检查,检查
不过就拒绝推送(fail-closed,而不是 fail-open)。如果确实需要跳过这个检查,要求**同时**传"跳过的
原因"和"批准跳过的人是谁"两个参数——只传原因不够,因为那样等于 worker 自己给自己找了个理由就
放行了自己;必须要有一个第三方批准的痕迹。作为纵深防御的第二层,人类直接手动推送到共享分支时,
git 的 `pre-push` hook 会独立地重新跑一遍同样的检查——保证不管改动是通过收尾命令还是被人手动推
上去的,质量门禁都不会被绕过。

## 补充说明:AI 提交身份与依赖目录完整性

- **AI 提交身份**这个话题只在这里提一句:worktree 生命周期和"AI 提交身份自动注入"机制是紧耦合的
  ——`begin` 时会把 AI 身份写入这个 worktree 独立的 git 身份配置,`end` 收尾推送前会重新署名任何
  意外带了人类身份的提交。完整机制留给专门讲知识产物/发布门禁的章节展开。
- **依赖对齐锁文件**:通用版本里的做法更轻——记录"上次成功安装时的锁文件哈希",`begin` 和 `end`
  (rebase 之后、推送之前)核对,不一致才重装;worker 角色不装,只收警告。
- **依赖目录完整性**:为了让 worker worktree 不用每次都完整重装一遍 `node_modules`/`.venv`,通常
  用受控的硬链接复制方式(而不是重新下载)从主工作区"借用"依赖目录,配套一个检测/修复命令处理
  复制到一半失败导致的目录状态不一致——避免这种基础设施层面的不一致被误判成代码本身的质量问题。

## Nova 案例参考

以上六类机制、具体的数量阈值(比如"20 个文件")、关键路径白名单的具体内容,都是 Nova 按自己仓库
的历史事故和业务敏感目录反推出来的具体选择。新项目要重建这套骨架,`reference-transaction` hook
机制本身、"多层叠加而不是单点防御"的主工作区保护思路、"低成本高召回"的大规模删除防护、以及
"fail-closed + 需要第三方批准才能跳过"的预检门禁设计,都是可以直接复用的通用模式;具体阈值和
白名单需要按自己项目的规模和历史踩坑经验重新标定。
