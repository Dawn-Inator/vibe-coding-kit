# 收尾纪律:commit + finish + push,不留手工作区

## 问题

即使有了 worktree 隔离、有了脚本化的 `begin`/`end` 命令、有了一整套安全机制,还剩最后一个漏洞:
**如果允许 AI 会话自己判断"这个任务要不要现在收尾"**,总会有会话选择"先放着,等我确认没问题/等下次
接着做"。这个选择单独看很合理——毕竟谁都不想把没验证过的代码推出去——但放到多会话并发的场景里,
它会制造一个更大的问题:另一个会话(不知道这份改动已经存在)完全可能重新领到同一个或者相近的任务,
从头再实现一遍。等两份改动都要合并的时候,才发现出现了重复劳动,甚至互相冲突。这类事故往往要等
到后期才会暴露,排查成本很高,而且很难靠"提醒 AI 要及时收尾"这种软性约束根治——因为"要不要现在
收尾"本身就是一个每次都可能被合理化成"再等等"的判断。

## 设计原理(通用、可泛化)

解法是把"任务完成"从一个**模糊的状态判断**,变成一条**没有例外的硬规则**:任务一旦被认为进入了
"完成/暂停/等待"这几种终态里的任何一种,代码就必须已经 commit + 收尾 + 推送到目标分支。"改好了
放在本地/worktree 里,等下次再继续"不是一个被允许存在的中间态。

这条规则背后有一个关键的认知纠正,值得单独说清楚:**推送这个动作的含义,不是"我已经 100% 验证
通过",而是"让其他协作者/会话看得到我在改什么"**。这两者是完全不同的两件事,但很容易被下意识
混为一谈,导致"还没验证完"被当成拖延推送的借口。验证是否充分,是可以在推送之后继续做、并且把
结论写进后续提交或收尾记录里的;但"是否让别人看到"这件事,没有等待验证完成的理由——恰恰相反,
让别人尽早看到,才能避免别人凭空重复造同一个轮子。

把这条认知拆开,可以推导出几条具体的执行规则:

- **收尾即上传,是纪律不是选项**——"任务完成"和"代码已推送"必须是同一件事的两个说法,不能有
  时间差。
- **验证结果是收尾记录的一部分,不是收尾的前置条件**——可以在提交信息或收尾说明里写清楚"目前验证
  到什么程度、还有什么没验证",但这不能成为不推送的理由。
- **例外必须极其明确、极其罕见**——只有当发出任务的人在当轮明确说了"不要提交",才构成例外;
  默认路径永远是收尾。

## 可复用技术模式

除了"必须收尾"这条核心规则,还有几条配套的执行细节,同样是可以直接复用的模式:

- **目标分支由 worktree 自己的分支决定,不是由调用者临场指定**——收尾时推送到哪个分支,应该是
  开始任务时(`begin`)就已经确定的属性,而不是收尾那一刻才决定。如果这个任务是从共享分支
  (`develop`/`staging`/`main`)直接分叉出来的,需要在开始阶段就有显式确认标记,呼应
  `commands.md` 里 `begin` 命令的"允许共享基线"参数。
- **临时分支只是过渡,永远不会被推送**——worktree 自己创建的那条临时分支(比如
  `<工具名>/<任务slug>`)只是任务执行期间的容器,真正被推送到远程的是"收尾合并进去之后的目标
  分支本身"。这条规则厘清了一个容易混淆的点:不要把"给 AI 任务分配的临时分支"和"最终要更新的
  共享分支"当成同一层概念,前者用完即弃,后者才是持久状态。
- **禁止用暴力删除绕过工具管理**——受管理机制创建的 worktree,必须用配套的收尾/结束命令清理,
  不受管理的手动 worktree 才允许用底层的 `git worktree remove`。原因很直接:收尾命令承担了
  "保证改动已经落地"的职责,直接 `rm -rf` 掉工作目录会跳过这层保证,把还没推送的改动直接销毁。
- **对特别大的改动,允许精确跳过某个已知会超时失败的本地检查**(比如用 `--no-verify` 之类的手段),
  但这必须是**精确针对一个已知边界情况的跳过**,而不是把所有检查都关掉。这条和"收尾必须做"这条
  硬规则并不矛盾——跳过的是某个检查工具本身在大 diff 上的已知缺陷,不是跳过收尾这件事本身。
- **多任务分波并行时,各自负责各自的收尾**——如果一次任务拆成多波、多个 AI 各自拿到一个 worktree
  并行处理,每个持有 worktree 的会话对自己那一份负责;等所有波次都完成后,需要有一次统一核对,
  确认没有遗留没收尾的 worktree(呼应 `commands.md` 里 `status` 命令的用途)。这条规则明确了
  "谁负责收尾"不会因为并行而变得模糊——不是最后统一收尾,而是各自收尾 + 事后核对。
- **受管理的 worktree 里禁止 `git stash`/`git stash pop`**——即使装了防误用 hook(见
  `safety-mechanisms.md`),也不应该主动去碰它,因为 `refs/stash` 是全仓库共享的,hook 只能挡住
  一部分风险,不能挡住全部。真正需要临时保存一份改动又不想提交时,应该用 `git diff > 补丁文件`
  把改动导出成一个独立文件,然后用 `git restore`/`git checkout --` 清空工作区——这条路径完全
  不涉及共享引用,不依赖 hook 兜底,是更安全的替代方案。

## 收尾证据:身份元数据不是身份认证,完成结论要看终端回执

这套收尾纪律成熟之后,后来又暴露出一个更细的漏洞:**"收尾"这个动作本身有没有真的发生,谁来证明?**
早期的做法是靠一堆记录下来的元数据——比如任务/会话 ID、Git 分支描述、某个配置字段里写的身份——来
判断"这个改动是不是某个任务做的、有没有走完收尾流程"。这个做法有一个隐藏的错误前提:**记录下来的
身份信息,不等于经过认证的身份**。任何调用方都可以在派发指令里自己写一个任务 ID、自己声明一个身份
字符串,这些字段的本质是"标注这是谁做的,方便事后归因",而不是"证明确实是这个调用方在操作,而且
操作确实按预期完成了"。同样的问题也出现在"监督者观察到的状态"上——如果监督机制只看某个进程自己
报告的生命周期状态(比如"已完成"),而不去看这个收尾命令自己产生的、独立于调用方声明的实际执行
结果,那么监督结论本身也建立在一个不可信的输入上。

**设计原理**:把"完成了吗"这个问题的证据来源,严格限定为**收尾命令自身产生的终端回执**——也就是
这条命令真正跑完之后,由命令本身(而不是调用方的自我声明)吐出的执行结果:退出码、最终状态、
涉及的提交哈希、推送和清理是否成功、日志或凭证文件路径。凡是达不到这个标准的输入——命令只是刚
启动、还在排队等锁、只有一个 UI 层面显示的"完成"状态、或者只有调用方自己私下汇报的一句"我做完了"
——都不能当作"已经收尾"的证据。**元数据(任务 ID、身份字符串、分支描述)永远只是归属标注,可能是
过期的、缺失的,甚至是调用方随手编的,不能把"记录了身份"当成"身份已经被认证"。**

这条原则还有一个配套的权限边界:**监督/观察机制本身只能是建议性的,不能有强制执行权**。它可以做的
事情,是标记出"这里的回执缺失/过期/自相矛盾"这类异常,但**不能**代替编排者去强制某个进程退出、
不能代替调用者去执行收尾命令、也不能自己动手删除 worktree 或分支——这些真正有副作用的动作,必须
由编排者或用户明确下达的收尾命令本身来完成,而且只有当那条命令自己的终端回执确认了执行结果,才能
对外宣称"已经清理干净"。这跟本仓库 `03-agent-orchestration/supervision-heartbeat.md` 里"心跳监督
不应该有阻断权"是同一个设计哲学在收尾场景下的延伸——观察和执行必须是两个独立的权限层级,不能因为
监督者"看起来发现了问题"就默认它有权自己动手处理。

## Nova 案例参考

这套收尾纪律是 Nova 在真实事故(同一个功能被两个会话重复实现)之后反推出来的规则,具体的"必须收尾"
措辞、"验证不构成阻塞理由"这条认知纠正,都写进了 Nova 的项目约定文件里作为一条不可绕过的红线。
新项目重建这套骨架时,"任务完成 = 代码已推送"这条核心认知,以及"临时分支不推送、目标分支才推送"
"暴力删除不能替代脚本化清理"这几条配套规则,建议原样保留——它们不依赖 Nova 的具体业务,而是任何
"多 AI 会话共享一个仓库"的项目迟早会撞上同一类事故后得出的通用结论。真正需要按项目重新决定的,
只是"多少个文件算大规模删除""哪个检查工具在大 diff 上会超时"这类具体阈值,骨架本身可以直接搬。

回过头看,这四篇文件其实讲的是同一件事的三个层面:`README.md` 讲的是为什么需要隔离(问题和原理),
`commands.md` 讲的是隔离和收尾如何变成固定的、可预期的操作(接口设计),`safety-mechanisms.md` 讲的
是隔离之外那些结构性共享的角落如何单独设防(纵深防御),这一篇讲的是"收尾"本身如何从一个可以被
拖延的软性判断,变成一条没有例外的硬规则(执行纪律)。四者合起来,才是"把任务的开始和结束都变成
脚本化、可审计、带护栏的操作"这条设计哲学的完整落地。
