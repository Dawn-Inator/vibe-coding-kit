# 命令族设计:begin / end / sync-primary / guard

## 问题

如果"用 git worktree 隔离每个 AI 任务"只是一个原则,而不是一套固定的命令,那么每个 AI 会话在
真正动手时,仍然要自己决定:worktree 建在哪个目录、分支怎么命名、从哪个基线分叉、怎么提交、
怎么推送、推送冲突了怎么办、什么时候可以清理。这些决定一旦交给每次调用临场发挥,就会出现两种
会话用两种不同的目录结构、两种命名规则,彼此认不出对方建的 worktree 是谁的、哪些还在用、哪些
已经可以清理——隔离机制本身又变成了一团新的混乱。所以需要把"开始一个任务"和"结束一个任务"这两个
最高频的动作,收敛成固定的、参数化的命令,任何 AI 会话调用效果都一致、都可预期。

## 设计原理(通用、可泛化)

把"任务生命周期"拆成几个边界清晰的动作,每个动作对应一个命令,命令之间通过约定的目录结构和分支
命名规则互相认得出彼此:

- **开始**:创建隔离工作区,记录"这个工作区属于谁、为了做什么"的溯源信息,从正确的基线分叉。
- **结束**:把改动合并回目标分支,处理并发推送冲突,清理已经不需要的工作区。
- **同步主线**:让"人类/编排者日常使用的那个工作区"跟上远端最新状态——但这必须是一个**独立于**
  普通任务结束流程的单独动作,不能自动发生。
- **诊断与修复**:护栏机制不可能永远不出问题,需要一族只读检测 + 修复的命令,供人工或编排者在
  出现异常时排查。
- **全局视角**:查看所有并发工作区的状态、批量清理——这类动作只应该由"看得到全局"的角色(编排者)
  调用,普通执行者不需要、也不应该有这个视角。

这个拆分背后有一条通用原则:**权限和视角要跟命令绑定,而不是靠调用者自觉**。比如"全局视角"类命令
如果谁都能调,一个只该关心自己任务的执行者可能会误读、误判其他任务的状态;"同步主线"如果谁都能调、
还自动发生,编排者自己正在盯着的工作区就可能被悄悄改变——这类设计上的越权口子,应该在命令职责划分
阶段就堵掉,而不是事后靠文档提醒"请不要调用"。

## 可复用技术模式:命令族的职责边界

下面是 Nova 具体命令的设计,可以作为"职责边界怎么划"的一个参照样本。

### `begin`——创建 worktree

- 在固定的目录下创建新 worktree,目录选择会自动探测"是哪个 AI 工具在调用"来分流(比如 Claude Code
  的任务放一个目录、Codex 的任务放另一个目录),避免不同工具的产物混在一起。
- 分支命名遵循 `<工具名>/<任务slug>` 这样的固定格式,任何人扫一眼分支名就知道这是哪个工具、为了
  什么任务开的。
- 在 git 配置里写入溯源元数据(会话 ID、线程 ID 等),即使后续只看到一个孤立的 worktree,也能倒查
  回是哪次会话创建的。
- 支持一个"worker 模式"标记:当编排者要预先为一个即将派发的实现型 subagent 建 worktree 时打开,
  这个模式下会跳过一些**只有编排者自己才需要**的检查(比如全量 typecheck)——因为这类检查通常
  很重,worker 任务不需要在"开始"这一步就跑一遍。
- 从共享基线分叉(`develop`/`staging`/`main`)需要显式传一个"允许共享基线"的确认参数,不能悄悄发生
  ——这是防呆设计:大部分任务应该从一个明确指定的、非共享的起点分叉,如果误用共享分支当基线,
  应该有一个动作提醒调用者"你正在这么做"。
- **依赖戳检查**:新 worktree 里装好的依赖必须对得上**这个 worktree 自己**的锁文件,而不是别的检出
  留下的版本。配置了锁文件路径后,每次成功安装都会把锁文件哈希写进依赖目录里的戳文件,`begin`
  在检出后核对戳,缺失或不一致就重装,重装失败则整条命令失败并打印修复命令。普通 worker 角色**永远
  不自己装**,只收到一条带修复命令的警告,由编排者决定重建还是修复(显式给了"带依赖"通道的 worker
  除外)。为什么用哈希戳而不是"每次都装一遍":核对只是读一个文件加算一次哈希,绝大多数情况是秒级
  空操作;而"从不核对"会让测试在错的依赖上悄悄通过或失败,排查成本远高于这一次哈希。

### `end`——收尾完成

这是命令族里最复杂的一个,完整流程是:

```
1. 提交 worktree 里所有未提交的改动
2. 拉取远程目标分支的最新状态
3. 把当前分支 rebase 到最新的目标分支之上(分支自带合并提交时走"保留合并"路径,见下)
4. 核对依赖戳(锁文件在 rebase 中可能变了),不一致就先修复
5. 直接推送到远程目标分支(push HEAD:refs/heads/<base>,不走 PR/合并请求)
6. 如果推送时发现 non-fast-forward(远程已经有新提交)
   → 回到步骤 2,重新拉取→整合→推送,最多重试若干次
7. 推送真正成功后,才删除这个 worktree 和它的分支
```

几个值得注意的设计点:

- **直接推送而不是走 PR**:这意味着"收尾"命令本身承担了通常由代码评审流程承担的"合入"职责,
  所以前置的护栏检查(见 `safety-mechanisms.md`)必须足够扎实,因为没有第二道人工审核。
- **失败重试而不是失败即弃**:多任务并发收尾时,后一个任务推送时前一个任务的改动可能刚刚落地,
  这是正常现象而不是异常——所以设计成自动重试而不是直接报错退出。
- **只有推送成功才清理**:保证一次失败的收尾不会丢失工作区里的改动,调用者随时能看到"这个 worktree
  还在,说明它还没有真正收尾成功"。
- **带合并提交的分支不 rebase**:rebase 只重放非合并提交,一个特意做的回合并
  (`git merge --no-ff <基线或别的分支>`)会被悄悄抹掉,而这个合并存在的唯一目的就是把祖先关系送到
  远程。所以只要 `<远程>/<目标>..HEAD` 的第一父链上有合并提交,`end` 就不 rebase:目标没动,就用
  `commit-tree` 保留父提交和树、只把作者重签成 AI 身份;目标动了,就在新的尖端上把合并重做一遍,
  冲突则中止、恢复 HEAD、什么都不推。已经被"共享历史引用"(配置项)覆盖的提交保持原 SHA,绝不改写。
  推送之后再取一次远程,逐个核对被合入的尖端确实成了目标的祖先,不信"推送成功"这句话本身。
  为什么不干脆一律 rebase:线性分支 rebase 最干净,但对带合并的分支它在静默丢信息;为什么不干脆一律
  merge:会把每个任务都变成一团合并提交,污染共享分支的线性历史。按分支实际形状二选一,代价是多一条
  分支路径要测。
- **推送之外的重试与超时**:底层 git 调用对一个封闭的瞬时故障集合(引用锁冲突;对 fetch/push 还有
  网络传输类错误)自动退避重试几次,认证失败、non-fast-forward、hook 拒绝这类"真答案"永不重试。
  持有收尾锁期间的每一步 git 都带着剩余持锁预算(`queue.maxHoldMs`)做硬超时,预算耗尽就释放锁并
  报错;收到 SIGINT/SIGTERM 也会释放锁——一个卡死的网络调用不应该让所有排队的会话陪葬。
- **必须放到后台跑、轮询进度**:因为在多任务同时收尾、互相排队等锁的情况下,这个流程可能要跑几分钟
  到一个多小时,前台阻塞等待会拖住整个会话。

### `sync-primary`——同步主工作区

这是唯一被允许把"主工作区"(人类/编排者日常操作的那个 checkout)的本地分支快进到远程最新状态的
命令,设计上刻意做了几个限制:

- **不自动发生**——其他任务收尾并推送成功之后,主工作区不会自动跟着前进,这是有意为之:避免编排者
  自己正盯着的工作区被悄悄改变分支状态,造成"我明明什么都没做,分支怎么变了"的困惑。
- **拒绝在有未提交改动时执行**——防止把编排者手头正在做的事冲掉。
- **永远只做快进,不强制更新**——如果远程和本地出现了没法快进的分叉,应该报错而不是强行覆盖。
- **拒绝在"worker 角色"上下文里被调用**——这条命令的语义只对"主工作区的持有者"有意义,worker
  没有理由、也不应该被允许调用它(详见 `safety-mechanisms.md` 的主工作区多层锁)。
- **顶层 AI 会话在"空闲"时可以自我授权(默认开启)**——没有显式批准变量的、非 worker 的 AI 调用者,
  会先做一次只读的空闲扫描:收尾锁/队列没人占、没有别的 AI 进程的工作目录落在仓库里、没有任何
  worktree 有未提交改动或刚提交的 commit;全部安静才放行,并在审计日志里记 `allowed-ai-idle`。
  设计理由有三条。第一,AI 卡在一个"只有人才能设置"的环境变量上本身就是设计缺陷——它既不能继续,
  又不该去伪造批准,最后只能停下来等人,而这条命令只是快进一个分支。第二,扫描必须 **fail closed**:
  任何探测出错(缺 `lsof`、锁文件读不了、进程列表失败)都算"忙",因为"没发现别人"和"没能去看"是两回事,
  放错的代价是两个会话同时抢主工作区,拒绝错的代价只是人手动设一次变量。第三,**worker 永远排除在外**
  ——worker 的"空闲"没有意义,它本来就不该碰主工作区,所以 worker 上下文无论多空闲都照旧被拒,
  显式批准变量也始终优先、不跑扫描。想回到"只认人工批准"就把配置项
  `syncPrimary.idleSelfAuthorize` 设成 `false`。

### `guard`——诊断与修复

一族排查/修复子命令:检测游离或被误放的 stash、给已存在的 worktree 补装防 stash 误用的 hook、
检测并修复依赖目录半程安装失败导致的硬链接完整性问题(通用版本里对应的是 `deps-sync`:按需把
当前 worktree 的依赖重新对齐到它的锁文件)、锁定/审计主工作区、审计"跳过检查"的历史记录。这一族命令的共同点是:它们都是**事后补救**或**只读排查**,不参与正常的任务开始/结束流程,
只在出现异常时被调用。

### `status` / `cleanup`——全局视角命令

查看所有 worktree 的状态、清理已完成的 worktree。这两个命令**只应该由编排者调用**,不应该由普通
worker/subagent 调用——因为它们要扫过整个共享的 worktree 集合,而普通 worker 只应该关心自己那一个
任务的状态,给它全局视角既没有必要,也容易诱发它误操作别人的工作区。

普通 `cleanup` 只清"自己收过尾"(生命周期标记为已合并)的 worktree,并且会跳过最近有文件活动的
那些——另一个会话可能正在里面干活。会话崩溃或被切走留下的"没人收尾"的 worktree,则由
`cleanup --reclaim-stale` 单独回收:

- **必须显式给天数,默认只演练**:`--stale-days` 每次都要传,不存在配置文件里的隐式年龄;不加
  `--apply` 只列清单。这样没有任何配置或一次手滑能让一条裸命令开始删东西。
- **"最近活动"保底线**:只要有文件或 git 管理文件在近几个小时内被改过,就当它还在被使用,除非调用者
  明说放行。这条线挡的是"一个会话误删另一个会话的活 worktree";光看闲置天数挡不住它——建得很早的
  worktree 完全可能刚被另一个会话接手继续改,所以保底线看的是最近的实际活动,而不是年龄。
  "实际活动"只认真正改了东西的信号:HEAD 或分支 reflog 的新条目(提交、切换、重置、rebase),或工作区文件
  被改。git 管理目录、index、FETCH_HEAD 的修改时间不算——`git status`、`git fetch` 这类只读命令、别的会话
  的巡检都会刷新它们,Nova 曾因此让几十棵已落地的干净 worktree 永远显示"0 分钟前活动",一棵都回收不掉。
- **不为收尾锁让路,但只在锁内删除**:有会话正在收尾时,演练照常分类(结论标为参考);`--apply` 与收尾
  共用同一个先到先得的排队锁,拿到锁后只复核几件便宜的事(tip 没动、仍然干净、没有收尾排队票点名它)再删,
  每轮持锁有上限,用完就释放重新排队。早期"见到锁就整轮跳过"的做法在多会话连续收尾时会让清理永远轮不上。
- **"已落地"要有证据**:HEAD 要么是目标分支的祖先,要么每个独有提交的补丁指纹都出现在目标上
  (覆盖 cherry-pick 和 rebase 之后的重放),判断只针对一个确定的基线引用,不是"试到有一个说是为止"。
  清理用不加 `--force` 的普通移除,中途变脏 git 自己会拒绝。

## Nova 案例参考

以上具体的子命令划分、参数名(比如"worker 模式"标记、"允许共享基线"标记)、目录分流规则,都是
Nova 按自己"Claude Code + Codex 双 AI 工具协作"的场景做出的具体选择。新项目如果只有一种 AI 工具、
或者并发规模小得多,不必照搬六个子命令的划分,但"开始"和"结束"必须是两个独立的、参数化的、
任何调用者效果一致的命令,这条骨架建议保留;"全局视角类命令只给编排者用"这条职责边界也建议保留,
它是防止 worker 越权操作的第一道、成本最低的防线。
