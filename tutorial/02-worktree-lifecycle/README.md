# Worktree 生命周期:多 AI 会话并发写一个仓库的坑

## 问题

AI agent 协作开发很快会走到这一步:不止一个会话在同时工作——可能是两个不同的 CLI 工具(比如一个
负责规划编排、一个负责具体实现),也可能是同一个工具开出的多个并发 subagent,各自领了一个任务,
同时对着**同一个 git 仓库**动手。这和人类团队的并发开发有本质区别:人类开发者天然知道"我这台机器上
只有我自己在改",而 AI 会话之间没有这种默认隔离,如果不做额外设计,会连续撞上几类问题:

1. **未提交改动互相踩踏**:如果多个会话共用同一个工作目录(同一份 checkout),一个会话切分支、
   一个会话改文件,另一个会话看到的工作区状态会是错的、甚至半路被覆盖。
2. **共享 git 引用上的竞态**:即便各自用了独立的工作目录,git 仓库里仍然有一部分引用是**全仓库共享**
   的,不因为你在哪个 worktree 而隔离——最典型的是 `refs/stash`,以及 `develop`/`staging` 这类
   长期共享分支。一个会话的 `git stash pop` 可能悄悄冲掉另一个会话正在暂存的改动;两个会话同时往
   同一个共享分支推送,后推的会覆盖先推的,或者直接被拒绝。
3. **破坏共享依赖目录**:`node_modules`/`.venv` 这类依赖目录体积大、重建成本高,如果多个会话各自
   完整安装一遍既浪费时间又浪费磁盘,但如果简单共享同一份目录,又会出现"一个会话正在装依赖、
   另一个会话读到了装到一半的半成品"这种状态污染。
4. **"任务完成"本身缺乏形式化定义**:如果收尾动作只是随手一句 `git commit && git push`,那么
   "这个任务到底算不算完成"、"验证到底做没做完就推了"、"推送失败要不要重试"这些问题全靠每次
   人工/AI 临场判断,没有一致的标准,也没有可审计的记录。

这些坑单独看都不难解决,但如果不成体系,靠"每个会话自己小心点"来规避,在并发数一高、任务节奏一快
之后必然会踩中——而且往往是那种事后很难复盘的踩踏事故(比如一份改动悄悄消失、一个功能被两个会话
重复实现)。

## 设计原理(通用、可泛化)

核心思路是把 git 原生就支持的机制用足:**一个 git 仓库可以有多个 worktree**——多个独立的工作目录,
各自可以检出不同的分支、各自有独立的工作区状态,但共享同一个 `.git` 数据库(对象、大部分引用、
配置的仓库级作用域)。这天然满足"隔离未提交改动"的需求,同时又不需要真的克隆多份仓库。

在此基础上,给"AI 任务"和"git worktree"建立一一对应关系:

- 每当有一个新的 AI 任务要开始动手改代码,就先创建一个专属于它的 worktree,而不是复用某个共享的
  工作目录。
- 任务做完之后,通过一个**脚本化的收尾流程**把这个 worktree 的改动合并回目标分支,再清理掉这个
  worktree——而不是留给每个会话自己决定什么时候提交、怎么提交、要不要处理推送冲突。

这个设计原理可以拆成两条更具体的子原则,后面两篇文件分别展开:

- **隔离原则**:worktree 解决"独立工作目录"的隔离,但仓库里仍然有一部分状态是**结构性共享**的
  (共享引用、共享分支、共享依赖目录),这部分不能靠"多开一个目录"解决,必须靠专门的护栏机制
  (见 `safety-mechanisms.md`)。
- **形式化收尾原则**:"任务完成"要被定义成一个具体的、可重复执行、可审计的操作序列(提交→拉取
  最新→变基(带合并提交的分支改为保留合并)→推送→重试→清理),而不是一个模糊的状态判断(见 `commands.md` 和 `closing-discipline.md`)。

这套模式不依赖任何具体项目的业务逻辑,任何用 git 管理代码、又要跑多个并发 AI 会话的项目都可以直接
搬:git worktree 是标准功能,"给每个任务分配独立工作目录 + 脚本化收尾"是一个通用的工程决策,只是
护栏的具体阈值、命名规则需要按项目自己的规模去调。

## Nova 案例参考

Nova(化名)把这套骨架实现成一族命令行工具(`begin`/`end`/`sync-primary`/`guard`/`status`/`cleanup`),
分别对应"开始一个任务"、"结束一个任务"、"让主工作区跟上远端"、"诊断与修复护栏"、"查看全局状态"、
"清理"这几个动作,统一收在 `.vibe-coding/` 相关的工具目录下,供 Claude Code 和 Codex 两种 AI CLI
共同调用。命令的具体参数、每个安全机制的实现细节、以及"任务完成必须收尾"这条纪律的执行标准,分别
展开在本模块接下来的三篇文件里。这是 Nova 在自己的双 AI 工具并发场景下做出的具体工程选择,新项目
如果只有单一 AI 工具、并发度也不高,完全可以用更轻量的方式实现同样的隔离原理——但"给每个任务一个
独立 worktree、把收尾变成脚本化操作"这条骨架本身,值得作为默认起点。
