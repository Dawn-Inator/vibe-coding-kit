# vibe-coding 方法论说明书

这份教程整理的是「Nova」项目(教程正文里对本项目的匿名代号,不出现真实项目名/品牌名/域名)在长期
由多个 AI agent 会话协作开发的过程中,摸索出来的一套工程方法论——涵盖两大类内容:

1. **AI agent 协作基础设施**:怎么让多个 AI 会话安全地在同一个仓库里并发工作,怎么让 AI 积累的经验
   跨会话保留下来,怎么派发和监督多个 subagent,怎么设计不容易被绕过的质量门禁和发布节奏。
2. **代码结构从 0 到 1**:怎么决策 monorepo 的目录所有权划分、服务边界要不要拆、后端怎么分层、API
   该用什么规范、schema/migration 怎么治理。

这两类内容互相支撑:第 2 类是骨架,第 1 类是长在这副骨架上的协作纪律——脱离具体代码架构去谈"质量
门禁"是空的,脱离协作纪律去谈"代码架构"又没法在多人多 AI 会话的场景下稳定演进。这也是本教程把
"代码架构"单独列成一个模块、而不是简单地当成"业务细节"一笔带过的原因。

## 核心理念

贯穿全部模块、反复出现的几个设计模式,比任何一个模块的具体机制细节都更值得记住:

- **唯一真源 + 生成投影 + 校验脚本**——凡是"给人看的索引/汇总/多份拷贝",都应该是从一份规范源头
  自动生成的产物,不能手改;配一个校验脚本检测生成产物有没有跟真源脱节。这个模式在知识产物治理
  (01)、API 契约(06)里都各自出现过一次。
- **共享状态用远程 git ref,而不是本地文件或数据库**——当多个并发的 AI 会话需要看到同一份"进度
  状态"时,把状态编码成一条只追加的 git 提交链、存在一个共享的自定义引用里,靠 git 原生的"非强制
  快进推送会自然拒绝冲突"这个特性,不需要额外发明一个锁服务。这个模式在门禁发布(04)里被讲得
  最透彻。
- **机器可校验的门禁优于纯文档纪律**——任何一条"重要但容易被遗忘/被绕过"的规则,如果只写在文档
  里靠自觉遵守,迟早会被违反;应该想办法把它变成一个自动化脚本能检测的不变量。worktree 隔离(02)
  的多层锁、门禁发布(04)的 gate-cycle 状态机、代码架构(06)的读写分层门禁,都是这个原则的具体
  应用。
- **先例外注册、后默认放开**——遇到"规则本身合理,但确实存在少数正当的例外场景"时,不要放宽默认
  规则本身,而是要求每一个例外都显式登记、写明理由,保持默认规则不变。API 契约(06)里 GET/POST
  的例外、门禁发布(04)里跳过预检的例外,都是这个模式。
- **三层防御:预防 + 复核 + 最后关卡**——重要的不变量(比如"谁提交的代码"、"这个 worktree 有没有
  被正确初始化")值得叠加三层独立的保护:创建时就设置好默认正确的状态(预防),流程中段再检查一次
  并纠正(复核),最后一个关卡再兜底拦截一次(最后关卡)。任何一层疏忽,后面的层还能兜底。

## 怎么用这份说明书

- **第一次接触、准备在新项目落地**:直接跳到 [07-adopting-in-a-new-project/README.md](07-adopting-in-a-new-project/README.md),它会告诉你按什么顺序引入其余模块、哪些不该一开始就照搬最复杂的版本(其中 08 的 L0 前置条件层建议提前做)。
- **只想搞清楚某一个具体机制**:直接用上面的地图表按需查——每个模块内部的文件都遵循同一个写作范式(问题 → 设计原理 → 可复用技术模式 → Nova 案例参考),案例部分会明确标注"这是 Nova 的具体选择,新项目按自己业务重新决策,不是照抄"。
- **判断一个具体细节能不能直接抄**:看它是不是被标成"Nova 案例参考"——是,就只是参考不是标准答案;不是(通常在"设计原理"或"可复用技术模式"小节里),说明这是一个跟具体业务无关的通用模式,可以直接搬。

## 定位说明

这份说明书**不是**可以直接复制粘贴运行的模板仓库——07 号模块的 `bootstrap-templates.md` 提供了少量真正可以直接复制的初始文件(知识产物的 frontmatter 契约),但整体上这份文档的价值在于讲清楚"为什么这样设计、拒绝了哪些替代方案",而不是提供一键搭建脚本。照抄一个陌生项目的具体机制、却不理解它解决的是什么问题,往往会在自己的项目里引入不必要的复杂度,或者漏掉真正需要的那部分。
