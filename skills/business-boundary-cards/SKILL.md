# Business Boundary Cards

拆不拆服务、要不要独立数据库、要不要独立部署——这类决策经常被压缩成一句直觉判断("这个模块听起来
挺独立的,拆出去吧"),然后要么过度拆分(增加运维负担,却没有真实收益),要么该拆的时候拖着不拆
(核心系统被一个边缘能力拖垮)。这个 skill 把决策拆成两张**必填、分开产出、有先后顺序**的卡片:
先确定业务边界,再决定物化程度——这两个问题的证据类型完全不同,混在一起判断容易出现"因为业务概念
听起来独立,就顺手把它物理拆开了"这种过度设计。

## 五层术语,先分开再决策

做任何拆分判断之前,先把这五层想清楚,它们可以独立变化,不能互相替代:

1. **业务概念 / 限界上下文(bounded context)**——谁拥有这份业务规则和权威状态。
2. **代码 / 包边界**——是不是独立的目录/模块/package。
3. **进程**——是不是独立的可部署进程(同一个进程可以承载多个业务概念)。
4. **部署 / 物理机**——是不是独立的容器/ECS/服务实例。
5. **数据库 / 存储**——是不是独立的逻辑库或物理库。

**当前几层"恰好挤在一起",不能反推出"它们本来就该是同一个系统"**;反过来,**限界上下文/代码/进程
的数量,也不能直接反推出该有几个服务/容器/数据库**。这五层可以按需要独立升级,而且**只能顺着顺序
升级,不能跳级**——后面提到的"最小充分隔离顺序"就是这个意思。

## 什么时候必须填这张卡

命中下面任意一条,就必须先出 Business Boundary Card,缺所有者/权威状态/交互契约/禁止跨域写/失败
隔离策略任意一项,预检就必须判 blocked:

- 新增或实质性修改一个中等以上规模的业务能力。
- 新建表 / 队列 / worker / 第三方 provider 集成 / 管理后台模块 / 持久化投影。
- 一次改动跨越两个以上的目标限界上下文。
- 一个已有模块新增了 actor、业务目标、权威状态或副作用。
- 准备新建一个 app / 服务 / 进程 / 逻辑数据库。

如果这次改动还会新建持久化存储,**这张卡不能替代** [data-architecture-card](../data-architecture-card/SKILL.md),两张卡要分开填,互不替代。

## Business Boundary Card(业务边界卡)——先填这张

回答的是纯粹的业务/所有权问题,不涉及物理部署形态:

- 谁是这个能力的主要使用者?业务目标是什么?
- 归属哪个限界上下文?谁是权威所有者?
- 权威状态和不变量是什么?
- 流入的查询 / 命令 / 事件有哪些?流出的事件 / 副作用有哪些?
- 允许哪些同步依赖?**禁止**哪些跨上下文的读写/导入?
- 有什么权限 / 审计 / 合规风险?
- 有没有独立失败 / 独立扩容 / 独立发布的需求?
- 当前是不是跟别的东西挤在一起?有没有迁移债务?
- 物理部署现状是什么?未来触发升级的条件是什么?
- 对契约 / 测试 / 文档有什么影响?

## Service Materialization Card(服务物化卡)——业务边界确定后再填这张

回答"现在应该物化到哪一层"的问题:

- 目标限界上下文 / 所有者是谁?
- 当前代码 / 进程 / 部署 / 数据库现状是什么?
- 需不需要跨边界的本地事务或 JOIN?能不能接受异步 / 可重放 / 可重建?
- 核心路径的超时和降级策略是什么?
- 有没有真实的负载证据——**这个证据是"已实测"、"预估",还是"未知"**?
- 有没有安全 / 合规需求?有没有独立扩容 / 独立发布 / 独立迁移的需求?
- 命中了哪些硬触发条件?命中了哪些强触发条件?(见下)
- 当前选择停在哪一级(代码/包边界、进程角色、独立服务、逻辑数据库、独立物理机/数据库实例)?
  为什么不选更高一级?
- 禁止跨边界的哪些导入 / 会话 / 数据库写?
- 独立启动 / 健康检查 / 回滚证明是什么?独立测试集合的根目录在哪?数据库初始化脚本是什么
  (或明确声明没有)?
- 影响哪些测试选择器映射?有哪些契约测试和故障隔离测试?
- 有没有低内存 / 快速扇出场景下的性能证明?
- 量化的"未来需要重新评估"门槛是什么(至少写清楚具体数值,不能只写"以后流量大了再看")?

**一个容易被忽略但很关键的设计**:卡片要求**三个独立的、不能合并成一个字符串的状态**——

- **物化状态**:目标态(target)/ 已配置(configured)
- **每个环境各自的部署状态**:未部署(not_deployed)/ 已部署(deployed)
- **每个环境各自的健康状态**:未知(unknown)/ 健康(healthy)/ 不健康(unhealthy)

代码写完、测试跑通,只能证明代码结构本身是健康的,既证明不了它真的被部署了,也证明不了部署之后
运行时是健康的。把这三件事分开填写,是为了防止"代码合并了"被误读成"已经上线且健康"。

## M0-M4:五道物化门

只有当前一道门通过,才有资格评估下一道门;越过之前的门直接跳到后面的证据,不构成物化理由。

- **M0 所有权(Ownership)**——限界上下文、唯一所有者、权威状态、禁止的跨域写入都已经明确写下来了。
- **M1 接缝就绪(Seam ready)**——跨边界的事务/JOIN 已经收敛成对外的查询/命令/事件/投影/Saga;没有
  跨域的私有 ORM 访问、共享会话或共享写入(所有者内部自己的本地事务不受影响)。
- **M2 物理需求(Physical need)**——命中一条硬触发条件,或者命中 ≥2 条独立的强触发条件。
- **M3 可运维性(Operability)**——有独立的启动/健康检查/就绪探针/超时/降级/可观测性/发布/回滚/
  worker 隔离能力。
- **M4 可测试性(Testability)**——有独立测试根目录、所有者自己的数据库初始化脚本、受影响的测试
  选择器、契约测试和故障隔离测试、正常/快速并行拓扑。

证据状态只能是 `confirmed`(已确认)/ `estimated`(预估)/ `unknown`(未知)三种;`unknown` 永远不能
作为拆分的理由。

## 硬触发条件(Hard trigger)——命中一条就够,但仍要过 M0/M1/M3/M4

- GPU / 模型 / 长时间运行的第三方 provider 调用,存在把核心 API 拖入不可控 CPU/内存/OOM 风险的可能。
- 只追加写入的高写入量 / 批量扫描工作负载,资源曲线明显不像普通 OLTP。
- 支付 / 安全 / 合规 / 凭证 / 审计 / 灾难恢复,需要独立的权限边界和故障域。
- 需要在核心路径继续运行的同时,独立杀掉/迁移某个能力——但当前的部署方式做不到。
- 运行时 / 地域 / 硬件 / 供应商依赖跟核心服务不兼容,没法共存。

## 强触发条件(Strong trigger)——需要 ≥2 条,不能重复计数同一个事实

- 独立的横向扩容 / 队列积压消费 / 单例调度器需求。
- 不同的依赖栈 / 发布节奏 / 回滚方式 / 值班归属。
- 独立的 SLO / 容量 / 连接预算需求,或者需要跨机器迁移的需求。
- 有实测数据或可追溯的估算,证明 CPU/内存/写吞吐/p95-p99/数据库扫描需要隔离。
- 独立的凭证 / RBAC / 恢复演练需求,但还没到合规硬触发的门槛。

## 最小充分隔离顺序——后面的层级不能用来倒推证明前面的层级合理

1. 规则和权威不一样 → 划出限界上下文。
2. 需要拦住跨域导入/写入 → 划代码/包边界。
3. 需要隔离积压/CPU/OOM/单例 → 独立进程角色,仍然是同一个部署镜像。
4. 需要独立发布/扩容/迁移/故障域 → 独立服务。
5. 需要独立连接池/保留期/恢复/权限/扫描隔离 → 逻辑数据库(走 Data Architecture Card 决策)。
6. 只有节点故障域/容量/地域/恢复边界才值得独立物理机/数据库实例——同一台机器上的多个容器仍然是
   同一个故障域。

## 防过度拆分清单——单独出现都不构成拆分理由

有自己的业务名词/目录/schema、"代码/表挺多的"、有队列或第三方 provider 或 webhook 或调度器、
"以后可能要扩容"、"微服务看起来更像样"、"反正能容器化"、"想让目录更整洁"。

## 防拆分不足触发条件——如果不拆,必须写清楚理由和量化复评门槛

可选能力的 OOM/CPU/第三方超时会把核心 API 拖垮;无界的事件写入/分析扫描持续跟核心 OLTP 抢资源;
某个 worker 需要独立扩容但仍然跟 web/调度器共享同一个进程;存在安全兜底方案,但一次部署失败仍然
会把核心路径一起拖垮;支付/安全/合规需要独立凭证/恢复/审计;已经被要求迁移到另一台机器,但当前
连独立启动/测试都做不到。
