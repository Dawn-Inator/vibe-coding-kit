# 对象存储分桶与目录规范

本规范提供新项目默认值和决策依据。示例中的 acme、区域简码及目录名必须替换为项目实际值；
不要求新项目一次创建表中所有 bucket，也不替代供应商的命名限制。

## 什么时候分 bucket，什么时候分目录

| 差异 | 默认选择 | 原因 |
| --- | --- | --- |
| 生产与非生产业务数据 | 分 bucket | 降低测试写入、清理和权限误配影响生产的风险 |
| 用户媒体、下载产物、测试证据、合规证据、备份 | 按实际存在的用途分 bucket | 对外可见性、保留期和责任通常不同 |
| 公开分发与私密文件 | 分 bucket | 避免 CDN／ACL 配置扩大私密文件暴露面 |
| 不同地域、账号、加密／锁定／版本控制要求 | 分 bucket | 这些控制不能单靠目录实现 |
| 同环境、同权限、同保留期的头像与封面等业务分类 | 同 bucket 分目录 | 目录表达业务语义，避免按每张表／每个文件类型建桶 |
| 共享的不可变下载产物 | 可共用 bucket，按渠道／版本分目录 | 须显式登记 writer、读取方式、清理规则与隔离策略 |

前缀授权与 lifecycle 过滤必须落实到实际策略；“有 dev/ 和 prod/ 文件夹”不等于环境隔离。
共享 dev/stg 桶是可登记例外，不是默认要求；生产业务数据默认保持独立。

## Bucket 命名与清单

沿用 repository-layout 的云资源命名规则，常见展开为：

```text
<项目>-oss-[<环境>-]<用途>-<区域>[-序号]
acme-oss-dev-media-sz
acme-oss-prod-media-sz
acme-oss-prod-test-evidence-sz
acme-oss-download-shared-sz
```

shared 在上例是用途的一部分，表示跨环境共享，并非第四种环境。
区域简码在项目内统一映射到供应商 region ID；遵守长度、字符与全局唯一性限制，必要时登记稳定后缀。
已有 bucket 不为形式统一而改名。存储清单至少登记：用途、环境／共享范围、区域、访问主体、
允许前缀、公开分发域名、保留期、版本控制、加密、删除责任及配置／IaC 真源。

## 对象 key 目录模板

对象存储中的目录是 key 前缀。采用小写、清晰的业务名；避免 n1、step2 等位置编码，
不要把邮箱、手机号、原始文件名或密钥放进 key。扩展名来自已验证的实际格式。
多租户项目在需要隔离的对象前缀加入受认证身份约束的租户 ID；单租户项目省略此层。

| 用途 | key 示例模板 |
| --- | --- |
| 用户头像 | user/avatar/<user-id>/<asset-id>.webp |
| 内容封面 | content/cover/<content-id>/<asset-id>.webp |
| 私有附件（独立私密桶） | tenant/<tenant-id>/attachment/<asset-id>.pdf |
| Web 静态发布 | web/<app>/<release-id>/assets/<content-hash>.js |
| 安装包 | android/<region>/<channel>/<version>/<artifact-id>.apk |
| 测试证据（独立证据桶） | test-evidence/<suite>/<run-id>/<artifact-name> |
| 合规证据（独立合规桶） | compliance-evidence/<case-id>/<evidence-id> |
| 临时上传 | tmp/<upload-session-id>/<asset-id> |
| 备份（独立私密桶） | backup/<service>/<yyyy>/<mm>/<dd>/<backup-id> |

这些模板按用途选用，视频托管服务可保留其原生资源标识，不强塞进普通 OSS 路径。
分环境的桶不再机械添加 dev/ 等冗余前缀；共享桶按明确的隔离维度加前缀。
channel、环境、分支是独立词表：安装包目录的 channel 值必须由项目映射决定。
跨服务共用的 key 生成函数集中维护，并覆盖前缀授权和输入校验，避免上传、签名和清理各拼一套路径。

## 访问、发布与回收

- 默认私有读写。公开媒体可用私有源桶加 CDN 回源鉴权；敏感文件经授权接口生成短时签名 URL，
  不进入公开 CDN。若托管静态网站确需公共源站，单独记录用途和公开范围。
- 授权由服务端身份决定；客户端提交的 tenant-id、user-id 或任意 key 不能直接成为授权依据。
- 发布产物采用唯一版本／内容哈希 key，避免覆盖已发布对象；latest 指针或发布 manifest 单独管理。
  业务引用与对象元数据分开，不把供应商原始 endpoint 固化为用户入口。
- tmp、测试证据、合规证据、备份分别定义保留策略；具体天数由业务／合规责任人决定。
  只给目标前缀设过期规则，检查非当前版本与未完成 multipart 的处理，避免前缀过宽误清正式对象。
- 版本控制、WORM／保留锁、条件写与禁止覆盖的兼容性必须按供应商能力验证；不能假定启用版本控制
  就等价于不可覆盖，也不能默认给所有桶套同一份配置。

## 采纳与验证

先登记现状，再选择新资源的默认方案。迁移存量对象需单独列复制、校验、引用切换、回滚与旧对象
清理步骤，执行按项目授权流程进行。
验证时覆盖正确身份可读写、跨租户／跨环境拒绝、签名过期、公开 CDN 不可取得私密对象、
key 与 manifest 对应、生命周期只匹配预期对象；具体测试由项目按变更范围选择。
