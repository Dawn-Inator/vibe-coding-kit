# Repository Layout(仓库根目录布局)

[business-boundary-cards](../business-boundary-cards/SKILL.md) 管的是"业务能力该不该独立成服务",
这个 skill 管的是更基础的一层:**monorepo 的根目录本身**该怎么划分,才不会随着项目变老,变成
"谁想放哪个新东西就随手建一个目录"的产物——今天有人建了个 `scripts/`,明天又建了个 `tools/`,
过一阵子两个目录开始互相重叠,没人说得清新脚本到底该放哪个。

## 核心机制:文档声明 + 机器校验,缺一不可

解法是两步:

1. **写一份文档,给每个顶层目录一句话说清楚它的所有权边界**。不是"这里放脚本"这种模糊描述,
   而是精确到"这个目录只装什么、明确不装什么"。
2. **配一个机器校验脚本,扫描根目录实际存在的每一项,判断它是否落在已声明的分类规则里**。
   不符合就直接报错,而不是留给代码评审去人工发现。

第二步是这套机制真正有约束力的地方。只有文档、没有机器校验,文档很快就会跟实际目录结构脱节,
变成没人再读的历史文件。有了机器校验之后,"往根目录随手加一个新目录"这件事就不再是零成本
的——新增一个顶层目录,必须先想清楚它属于哪个所有权边界、要不要现有分类规则覆盖它,否则校验
脚本会挡住它。

## 怎么写这份目录声明

给每个顶层目录填一行,格式类似这样(具体目录名和数量按你的项目实际情况来,下面只是示例结构,
不是要照抄的清单):

| 目录 | 用途(精确到"只装什么、明确不装什么") |
| --- | --- |
| `<运行产品/服务的目录>` | 可运行的产品/服务代码 |
| `<跨产品共享库的目录>` | 多个产品/服务共用的库,不含任何一个产品自己的业务逻辑 |
| `<基础设施目录>` | 可部署的基础设施声明(云资源、网络、运行时配置)——明确排除测试编排、门禁脚本这类内容 |
| `<工程自动化脚本目录>` | 开发/部署/生成/安全类脚本——跟"可部署的基础设施"分开,因为所有权和变更节奏不一样 |
| `<测试编排目录>` | 测试选择器、门禁编排、端到端测试固件——不算基础设施变更 |
| `<机器可读事实登记表目录>`(如果有) | 给自动化工具读的结构化声明(比如服务拓扑、数据架构登记),这个目录本身不改变任何真实运行时状态,只是声明 |
| `<长期规范性文档目录>` | 给人看的、长期维护的规范文档 |
| `<数据库配置/迁移目录>` | 如果你的数据库迁移有专门的治理要求(参考 [migration-downpath](../migration-downpath/SKILL.md)),值得单独在根目录留一个位置,不要被"基础设施"这个大类稀释掉 |
| `<环境配置形状目录>` | 各环境配置的**形状**,不存放真实密钥(密钥应该走专门的密钥管理系统注入) |
| `<AI 工具技能库目录>`(如果有) | 定位成"执行入口",不是"知识源头"——真正的规范内容应该住在文档目录里,技能库只是路由,避免同一份规范被复制到两个地方后逐渐漂移出不一致的版本 |

几条值得参考的设计判断,来自实际踩过的坑:

- **"基础设施"和"测试/门禁编排"要分开**,即使两者都跟"工程"相关——改测试选择器不应该被当成
  基础设施变更来审查,两者的所有权和变更节奏不一样。
- **目录命名本身也是一种沟通,要主动避免误导**——比如存放"签名相关元数据"的目录,如果起一个
  带"key"或"secret"字样的名字,容易让人误以为这里真的存放密钥本体,从而产生错误的安全预期;
  换一个不那么直觉、但不会引起误解的名字,虽然费解一点,但更安全。
- **有专门治理要求的目录(比如数据库迁移)值得单独留出根目录位置**,不要被塞进一个更大的分类
  目录里被稀释掉——治理要求越严格的东西,越应该在目录结构上显眼、独立。

## "运行产品/服务的目录"这一项:一个常见的最小起点

上面表格里"运行产品/服务的目录"这一行,几乎每个项目都会有,但具体放几个、叫什么名字,新项目
经常在这一步犹豫。这里给一个**通用的起点**,不是唯一答案:

- **给每个可运行单元的目录名加一个角色后缀**,比如 `<name>-client`(面向用户/操作者的前端应用)
  和 `<name>-service`(对外提供接口的后端服务)。这个约定不是强制规则,但是一个自解释、一眼就能
  看出"这是前端还是后端"的合理默认,值得作为起点采用。
- **几乎每个有后端逻辑的项目,都会有至少一个后端服务**——常见的起始命名是 `business-service`
  或类似的通用名(表示"承载核心业务逻辑的服务",不是某个具体业务领域的名字)。**先只有一个后端
  服务**是完全合理的起点,不要因为"以后可能要拆"就一开始就画出好几个服务——要不要在这一个之外
  再拆分独立服务(比如支付、推荐、内容审核各自独立),这个判断走
  [business-boundary-cards](../business-boundary-cards/SKILL.md) 的框架单独决策,不要在这里
  提前假设答案。
- **前端要不要做 web、要不要做 app,这是产品形态决定的,不是技术决定的**——取决于目标用户主要
  通过浏览器还是手机 App 访问,可以只做一个,也可以两个都做(常见组合是 `web-client` +
  `app-client`,或者再加一个面向内部运营/管理人员的 `admin-client`)。这三者之间不是互斥关系,
  是"你的产品面向哪些使用者"这个问题的直接映射。
- **起点越小越好**——一个新项目完全可以从"一个后端服务 + 一个前端客户端"这个最小组合开始,
  随着业务实际长出新的边界需求(参考 `business-boundary-cards` 的物化门框架),再逐步长出新的
  目录,而不是在项目第一天就画出一整套预想中的服务拓扑图。

## 命名原则延伸到云资源:同一套"沟通优先"逻辑

上面"目录命名本身也是一种沟通"这条原则,不只适用于仓库目录——云资源(ECS 实例、数据库实例、
Redis、CDN、OSS bucket……)的命名同样是给人和自动化工具看的沟通媒介,而不是随手起的标签。一个
项目一旦有多台机器、多个环境、多个数据库实例,没有统一命名规则的后果很直接:控制台一排实例名
看不出哪台是哪个环境、跑什么服务,排障时得靠打开控制台核对元数据才能确认"这台是不是我要找的
那台"。

**通用规则**:

```
<项目名>-<资源类型>-[<环境>-]<用途或角色>-<区域>[-序号]
```

- `<项目名>`:项目/产品的简短代号。
- `<资源类型>`:这是什么类型的资源,用固定缩写而不是全称(比如 `ecs`、`pg`、`redis`、`oss`)。
- `<环境>`(可选):`dev`/`stg`/`prod`——**不是每个资源都需要这一段**,不分环境的共享控制面资源
  (比如一台面向所有环境的跳板机/控制台机器)或者浮动的测试机池,直接省略这一段。
- `<用途或角色>`:这台/这个实例具体做什么,含义按资源类型自己的语义来定,不强行统一成一个词——
  计算资源(ECS)这段通常是"跑的是哪个工作负载"(比如 `api`、`ai`、`admin`);数据库这段通常是
  "承载哪个逻辑库/业务域",而且**只有存在多个同类型实例时才需要这一段**——只有一个实例的阶段,
  直接省掉,不要为了格式整齐而编一个没有区分意义的角色名。
- `<区域>`:云厂商的区域简码。
- `<序号>`(可选):只有存在多个用途完全相同的实例(比如一个可伸缩的测试机池)时才加。

**跟目录命名一样,不要为了套用格式而制造假信息**——可选段该省略就省略,省略本身就是在传达
"这个维度对这个资源不适用"这个事实;硬塞一个不区分任何东西的角色名,反而制造了误导。

**一个名字命名的是"宿主的角色",不是"上面跑了几个服务"**——早期环境为了省成本,经常把好几个
逻辑服务塞进同一台机器(比如 dev 环境一台机器同时跑后端主服务和另外三四个周边服务),这台机器
只需要一个体现它主要角色的名字(比如 `<用途或角色>=api`),不需要因为上面挤了好几个服务就编出
好几个资源名,也不需要在名字里列出所有跑在上面的服务。等某个角色的负载或隔离需求大到需要独立
一台机器时,再给拆出来的那部分**起一个新名字**,原来的名字不用改、也不需要因为"名字对应的东西
变少了"而困扰——名字锚定的一直是角色定位,不是某个时间点上面恰好跑了什么。这跟前面"目录架构
从第一天就该是成熟以后会用的名字"是同一个逻辑:资源名字也应该在最开始就按"最终会拆成什么形状"
来起,拆分只是往已有名字体系里添加新条目,不是把旧名字推倒重来。

## 命名原则延伸到业务标识符:一旦跨边界,改名成本就不再是重构成本

"命名本身也是一种沟通"这条原则,还要再延伸到一类更容易被忽视的东西:**跨边界可见的业务标识符**——
URL 路径段、API 枚举/参数值、数据库枚举/CHECK 约束值、CLI 子命令、存储目录/对象 key 前缀、跨服务
事件类型。这类标识符一旦写进 URL、写进数据库、写进对外 API,就会被各层代码原样抄一遍——前端路由、
后端校验、数据库约束、日志、监控面板都会各自留一份拷贝。它们不是"改个变量名"那种本地重构,而是
一旦定型就会随时间被抄得到处都是,改名成本(以及如果已经落库,数据迁移成本)只会越滚越大,不会
越拖越小。

**必须用一眼能读懂语义的词,禁止用序号或位置编码**(比如 `n1`、`step2`、`stage3`、`a`/`b` 这类)——
这类编码在设计阶段的白板上很自然("流程第几步"),但没人能从一个跑起来的系统里的 `n2` 反推出它
到底是哪个业务含义,读代码、读 URL、读数据库的人都得跑去翻设计文档才能确认。URL 路径段用
kebab-case,代码/数据库里的值按所在层已有的惯例用 snake_case 或 kebab-case,统一原则是"命名依据
业务含义,不依据它在流程里排第几"。序号只允许用在两种场景:纯展示排序(比如列表里的显示顺序),
和版本号(`v1`/`v2`)——这两种场景里"第几"本身就是全部语义,不存在"以后要改成别的顺序"的问题。

反例(通用形式,不针对具体项目):某个项目把流水线的几个处理节点按设计图上的顺序编号
`n1`/`n2`/`n3`/`n4`,后来 URL、数据库约束、API 参数、CLI 子命令、存储目录名全都跟着用这套编号——
`/pipeline/n2` 这样的 URL 没人能看出 `n2` 到底对应哪个处理阶段,新人接手只能去翻旧设计图。一旦
流程后续调整(插入新节点、合并两个节点),这套编号还会跟设计图本身一起失真,变成"编号对不上实际
顺序"的历史包袱。

建议配一条机器守卫防回潮:在验收用例里加一条 grep 类检查,扫路由定义、API 枚举定义、DB 迁移里的
`CHECK`/枚举值、CLI 子命令注册表,匹配"纯数字/序号+可选字母"这种模式(比如 `^[a-z]\d$`、
`^(step|stage)\d+$`)就报错,把"业务标识符不能是位置编码"这条规则从人工评审变成提交前必过的门禁。

## 环境名、分支名、产物 channel 名是三套独立词表,不要假设它们同名

一个常见的隐性假设是:"环境叫 `dev`,那分支应该也叫 `dev`,产物目录/发布渠道应该也叫 `dev`"。
现实中这三者**经常故意不同名**,原因各自独立:

- **git 分支名**服务的是协作流程(比如"长期开发分支""预发布候选分支""发布分支"),命名习惯
  常年沿用团队自己的历史叫法(`develop`/`staging`/`main`,或者别的团队约定)。
- **环境名**服务的是"这套配置/这个后端指向哪里"这个运行时概念(`dev`/`stg`/`prod`),它是配置
  文件、部署目标、权限边界的索引键。
- **产物 channel 名**服务的是"这份构建产物是什么性质"(比如安卓的 `debug`/`release` build type,
  或者一个渐进发布场景里的 `preview`/`stable`),这套词表往往是平台/工具链自己规定的,不是项目
  能自由命名的。

三套词表**允许两两不同**,靠一张显式的映射表连接,而不是靠字符串相等隐式对齐:

| 分支 | 环境 | 产物 channel(示例:安卓 build type) |
| --- | --- | --- |
| `develop` | `dev` | `debug` |
| `staging`(或已验证的预发布候选分支) | `stg` | `preview` |
| `main` | `prod` | `release` |

**这张表本身就是契约,值得单独写下来,不要指望它"看名字就能猜到"。** 一个真实的踩坑场景:
某人在环境 `dev` 上构建产物,想当然地去对象存储里找 `.../dev/...` 目录,结果什么都没有——
产物实际落在 `.../debug/...`,因为 `debug` 才是这个环境映射到的 channel 名,不是环境名本身。
`dev`/`stg` 两个环境甚至可能**共用同一个存储桶**,纯靠这段 channel 目录名区分——这是合法的
设计简化(降低桶数量和权限面),不是配置错误,前提是这张映射表写在显眼位置。

写这张表时,把它放在**产物发布链路实际读取这份映射的代码旁边**(比如构建/上传脚本里的一个
常量),而不是只写在一份独立文档里让代码和文档各自漂移;需要给人看的说明,再从代码注释链接到
文档,不要反过来只写文档不落代码。

## 一次性/临时脚本:单独一个根目录,不跟长期工具混放

"工程自动化脚本目录"(上面表格的一行)装的是长期维护、被 lint/type/test 覆盖的正式工具。但项目里
总会不断冒出**真正用一次就完事**的脚本——一次性数据修复、临时排查、验证一个假设——如果这些脚本
随手扔进正式工具目录,时间一长就分不清哪些还有用、哪些早就该删,目录会越堆越乱。

解法是给这类脚本单独开一个根目录,专门用来装"确定是一次性的东西",并且从三个维度让它跟正式
工具目录区分开:

- **命名上用点号前缀**(比如 `.script/`),一眼就能看出"这里的东西是临时的,不是正式代码的一部分"。
- **不打包、不通过模块路径调用**——直接跑文件,不提供 `__init__.py`,不支持类似 `-m 包名.xxx` 的
  导入方式(点号前缀本身也不是合法的模块名,这是刻意的,防止有人把一次性脚本悄悄变成被其它代码
  依赖的正式模块)。真要用到某个 app 自己的依赖,显式指定用哪个 app 的运行环境去跑,而不是让它
  默认继承。
- **不进 lint/type/test 门禁,没有兼容性保证**——可以随时删除,不需要走任何废弃流程。仍然建议纳入
  版本控制(而不是只留在本地),这样其他人或者其它 AI 会话至少能看到"这个一次性问题之前有没有人
  已经写过脚本处理过",避免重复造轮子。

这个目录**不是**给"某个具体产品/服务"用的,而是整个仓库共享一个,按脚本主题分子目录(比如
`.script/<某次排查的名字>/`)——因为一次性脚本本身通常也不需要深度复用某个 app 内部的实现,而是
直连数据库、调已有接口这类轻量操作,没必要绑定在某个 app 目录下面。

## 目录迁移无回退表

当决定要把某个旧目录重命名或迁移到新位置时(比如把散落的脚本目录归并进统一的自动化目录),
应该:

1. 在文档里维护一张**历史迁移记录表**(旧路径 → 新路径),让后来者能查到"这个东西以前在哪"。
2. **迁移必须用 `git mv` 一次性干净完成**,不允许中间状态长期存在。

**明确禁止两种妥协方案**:

- ❌ 建一个符号链接兼容旧路径。
- ❌ 新旧两份都保留、之后再手动同步。

这两种做法看起来都能"暂时省事",但代价是根目录结构文档从此失去了"读起来就是当前准确状态"这个
性质——文档说的是新路径,但实际上还留着一堆兼容层,读文档的人没法单靠读文档判断现实到底是
什么样子,必须再去代码库里交叉核实。这种认知负担一旦引入就很难消除,因为每次新增迁移都会再
叠加一层。坚持"迁移只能一次性干净完成、不留后门"这条纪律,本质上是在保护"文档 = 当前真实状态"
这个更基础的不变量。

## 怎么把这套机制做成机器可强制的门禁

跟这个 starter kit 里其它治理类 skill 一样,价值在自动化脚本落地之前只是写在文档里的约定。
这个 starter kit 直接带了一份可运行的起点——`engineering/automation/root-layout/
check-root-layout.mjs`(随 kit 一起复制进你项目,见 INSTALL.md),做的是:

1. 读取一份 `ALLOWED_ROOT_DIRECTORIES` 声明(默认只有一个占位起点,需要按你项目实际的根目录
   改成真实的分类清单)。
2. 用 `git ls-files` 遍历仓库根目录下实际存在的每一项,判断它是否精确匹配某条已声明的规则。
3. 任何不匹配的新增目录,判定为违规,报错并指出"这属于哪条规则的职责范围不清楚,需要先在
   声明文档里补充分类,或者放进已有的正确目录"。
4. 维护一份 `RETIRED_ROOT_DIRECTORIES`(旧路径 → 新路径),已退役的目录一旦回流,报错直接
   指向该去的地方,而不是笼统地说"未分类"。

把 `pnpm check:root-layout` 接进你的测试/CI 流程,新增一个不属于任何已声明分类的根目录,就会在
提交前被挡下来,而不是等到项目变得杂乱无章之后才有人想起来整理。这份校验脚本只是起点——你项目
真正的根目录分类清单,还是要写进一份长期维护的文档里(参考 `.vibe-coding/tutorial/
06-codebase-architecture/monorepo-layout.md` 的 Nova 案例),脚本只负责把文档里的声明变成
可执行的门禁。

**这套目录命名从第一天就该是你项目成熟以后会用的名字,不是先随便起个名字、以后再迁移**——比如
`engineering/automation/` 下面按关注点分的子目录(`agent-worktrees/`、`agent-skills/`……,这个
kit 自己就是按这个模式组织的),小项目起步时只有几个文件,项目变大之后往同一个子目录里加更多
代码,而不是把整个目录挪到别的位置。目录迁移应该是例外,不是常态——常态应该是"这个目录从建立
那天起,名字和位置就没变过"。

## 与其它 skill 的关系

判断某个业务能力要不要独立成一个 app/服务,走 [business-boundary-cards](../business-boundary-cards/SKILL.md)。
第三方服务接入的目录组织方式,走 [provider-gateway](../provider-gateway/SKILL.md)。服务内部代码
的读写分层,走 [backend-layering](../backend-layering/SKILL.md)。这几个 skill 分别管不同粒度的
目录/边界决策,合起来才是"仓库从根目录到单个业务对象,每一层都有明确的所有权边界"这件事的完整
拼图。
