# Data Architecture Card

新建一张表很容易,但"这张表归谁管、放哪个库、预期能长多大、什么时候该清理、多大流量该重新评估"这些
问题经常没人想清楚就先建了——等真出问题时,已经是几百万行数据摆在那,谁也不敢动。这个 skill 强制
在建表/建队列/建物化视图之前,先把这几件事写成可核对的字段,而不是留在某个人的脑子里。

## 什么时候必须填卡

命中下面任意一条,建表/迁移之前必须先填卡:

- 新建 PostgreSQL 表、物化视图或队列。
- 新建逻辑数据库、外部日志/指标 sink,或者跨库投影。
- 新建日志、指标、事件流、审计、outbox/ledger、分析 mart、快照等持续化存储。
- 把已有存储改成无界追加,或者修改它的保留策略,或者改变数据库/分区/分片边界。

**可以声明"不适用"的情况**:只新增索引、只 ALTER 已有对象、只做 seed/backfill/repair,且不创建
任何新持久化对象的迁移。**`CREATE TABLE`、`CREATE MATERIALIZED VIEW`、创建队列这三类操作,不能
声明"不适用"**。纯读取的查询/投影逻辑变更(比如给查询加一个可见性过滤条件)本身不构成新的持久化
权威,不需要为它伪造一张卡。

**不要因为现有连接/迁移工具/ORM 最容易复用,就默认把新数据放进最方便的那个库**。这份规范也不要求
每个新系统都拆库或分表——继续用现有库和单表完全可以,**但前提是先留下可验证的定量决策和重评阈值**,
不能什么都不写就默认塞进去。

## 卡片必填字段

**顶层字段**:稳定 ID、系统名、负责模块(不能用迁移文件名代替所有权声明)、状态(`active` 或
`legacy_unreviewed`——后者必须同时写清楚"为什么是遗留的"和"什么时候必须复查")、权威性(`authoritative`
本身就是权威数据,还是 `projection` 只读投影)、该卡覆盖的实际存储清单(至少一项)、放置决策、
一致性方法、至少两条独立可量化的重评阈值。

**放置决策(placement)必须包含**:

- **所有者服务**——真正在运行时写入这些存储的服务。只有当卡里全部存储都是外部 sink(没有任何一个
  实体运行时拥有它)时,才允许留空;只要有一个是数据库表,就必须写清楚所有者服务。
- **限界上下文**——业务所有权归属,必须是项目已登记的受控词汇表里的值,不能是自由文本。
- **判据(criteria)**——见下面的封闭清单,至少一条,不能重复。
- **被否决的备选方案(至少一条)**——每条包含"备选项是什么"+"为什么否决"。**这条字段存在的
  唯一原因**:卡片里如果只写了最终选中的库,复核者没办法区分"认真想过其它选项、排除了"和"压根没
  想过"——两种情况写出来的 JSON 长得一模一样。备选项必须是真实可行的选项(所有者服务允许清单里的
  另一个库、已经登记的外部 sink,或者"新建逻辑数据库"/"外部 sink"这两个抽象选项),否决理由必须
  指向可验证的事实,不能写"暂时不需要""以后再说"。

## 判据(criteria)封闭清单——只能是下面七种,不能自己发明理由

| 判据 | 什么情况下成立 | rationale 必须写清楚什么 |
| --- | --- | --- |
| 所有者上下文默认库 | 选中的库是所有者服务允许清单里**唯一**命中的一个 | 点名所有者服务和它的允许清单;清单里有两个以上候选时这条不成立 |
| 事务本地性 | 需要跟同一个库里的某个已有权威保持本地事务或外键关系 | 点名具体的对应表和必须保持原子性的具体不变量,不能只写"方便 join" |
| 容量/负载证据 | 有可量化的容量/负载证据 | 具体数字和来源,已实测或有依据的预估;"未知"不能支撑这条 |
| 凭据爆炸半径 | 命中下面"新建逻辑数据库的三条硬要求"之一 | 具体是哪一类凭据、现在跑在哪个运行时里、拆分后收窄了哪个面 |
| 独立备份/恢复 | 同上 | 为什么这份数据的恢复点必须跟同库其它数据解耦,双方各自的 RTO/RPO |
| 机器强制的唯一写入者 | 同上 | 拆分之后由哪个角色/权限强制执行,不能写"靠代码评审自觉" |
| 必须走外部 sink | 原始技术日志/指标不能进数据库 | 为什么这份数据是技术日志/指标,目标 sink 是什么 |

**这张封闭清单本身就是治理机制**:"方便""复用现有连接""安全""重要""是钱""以后可能要拆"这类
理由在这里**没有对应的选项可以表达**——写不出来就说明它不是一个站得住的理由。

## 容量模型——bounded 和 unbounded 两套字段互相不能混用

- **bounded(有界)**:最大行数、边界机制(必须是真机制——唯一约束、固定租户上限、TTL 删除任务、
  可验证的有限主体集合,"理论上不会很多"不算边界机制)、平均行字节数、索引放大系数、证据状态、
  证据说明。
- **unbounded(无界)**:峰值写入速率、日增行数、平均行字节数、索引放大系数、证据状态、证据说明。

**这两套字段是互斥的闭合形状,不能互相抄**——一个 bounded 的存储填了峰值写入速率会直接不通过校验,
一个 unbounded 的存储少填日增行数同样不通过。derived 出来的容量数字(12 个月/24 个月的预期行数和
存储占用)应该由工具统一计算,不要在卡片里手填,防止手算漏更新。

**证据状态**只能是三选一:`measured`(已实测)、`estimated`(有依据的预估,可以通过严格校验,但必须
在证据说明里写清楚估算依据)、`unknown`(完全未知,新建的 `active` 存储**不能**用这个状态通过严格
校验)。

## 一致性字段

一致性方法必须写清楚这份数据实际用什么机制保证跨存储一致——本地事务、outbox/投影器、幂等重放、
对账重建,四选一或组合说明理由。去重/唯一性机制的变化(加减唯一约束、改冲突处理目标)属于一致性
方法的一部分,不是容量字段,改动时要跟物理设计的理由同步更新——卡片里这部分内容是治理真源的一部分,
不是注释。

## 重评阈值——至少两条独立维度,必须是可比较的数字

至少覆盖两个独立维度(比如:活跃行数/占用字节、峰值写入速率、查询延迟分位数、autovacuum 压力、
分区数量、对账积压)。每条阈值必须是"指标 + 比较符(大于等于/小于等于) + 正数 + 单位 + 越线后要做
什么"这个结构,不能只写一段理由文字。同一张卡里指标不能重复。

## 保留策略——每个存储都要写

每个存储必须声明:热数据保留天数、总保留天数、到期动作(保留/删除/先归档再删除/先压缩再删除/交给
外部生命周期管理)、执行入口。**只有"保留"这个动作允许总保留天数留空**,其它动作都必须给一个正整数。
"不删除"本身是一个显式决策,不是默认值——即使因为法务/财务要求要长期保留,也要写清楚冷热分层、
容量和到期处理方式。执行入口必须指向一个稳定的、真实存在的迁移或运维脚本,不能指向一个还没分配、
可能被重新排序的序号——**更不能写一个代码里根本没有对应实现的执行入口**,那等于伪造了一个"通过了
但什么都没覆盖"的门禁。

## 放置决策的判断步骤(顺序不能颠倒)

放置是唯一必须先于容量和物理设计做的决策:

1. **先只看业务,确定所有者限界上下文**——不看任何数据库连接。**禁止**用"现在 ORM 在哪个包里""哪个
   会话能连到它""已经有外键指向谁"来倒推所有权,这些反映的是历史遗留的迁移债务形状,不是所有权
   证据。
2. **从上下文出发,找到唯一的所有者服务**。找不到唯一所有者就停下来,回去先完成业务边界的判断(见
   [business-boundary-cards](../business-boundary-cards/SKILL.md))——在放置这一层硬凑一个所有者,
   只是把边界问题伪装成数据库问题糊弄过去。
3. **候选数据库只能来自所有者服务自己的允许清单**——清单之外的库不是"需要额外理由才能选",而是
   根本不可选。
4. **允许清单里有多个候选时,判据不能是"唯一命中"**,必须落到"事务本地性"或其它具体判据上。
5. **允许清单里没有一个合适时,只有三条合法出路**:①重新审视上下文(这应该是第一反应——"这张表
   放谁的允许清单里都不合适",通常说明第一步的上下文判断本身就错了)②升级成一次真正的服务边界
   决策,按上面"新建逻辑数据库的三条硬要求"评估③退到已登记的外部 sink。**"反正后端本来就连着某个
   库""先放这里以后再搬"都不是出路**——数据量真的涨起来之后再搬,成本只会更高。
6. 把否决掉的备选方案记录进"被否决的备选方案"字段。

**一张卡只能落在一个数据库里**——同一张卡里除了外部 sink 之外的存储必须都在同一个库;需要跨库
一致性的场景要拆成两张卡,通过对外的查询/命令/事件连接,不允许在一张卡内部写跨库 SQL join。

## 物理设计怎么选

- 需要事务聚合、跨表强一致性、数据量有明确上限的 → 优先继续用现有库和单表。
- 按时间追加、按时间删除/归档的事件/指标/审计类数据 → 认真评估按时间分区。
- 已经有量化证据证明写入热点或单表/单库运维阈值撑不住了 → 再考虑哈希分区、分片,或者新建逻辑
  数据库。
- **容量不是开新逻辑库的唯一理由**——见下面三条硬要求,命中任意一条时即使没有容量证据也可以选新
  建逻辑数据库,但必须在放置决策里写清楚命中的是哪条具体硬要求,而且仍然要登记容量模型(没有实测
  就用预估)和至少两条重评阈值;**不能只用"安全/重要/是钱"这类标签本身当理由,也不能反过来拿这条
  给普通业务表绕开容量判据强行拆库**。
- 不要仅仅因为"以后可能会很大"就提前分库分表,也不要仅仅因为当前数据是空的就判定单表设计是健康的。
- 事件/指标类工作负载选择单表设计时,如果缺保留策略、容量模型或至少两条重评阈值中的任意一项,
  这个决策就应该判不通过。

## 新建逻辑数据库的三条硬要求——命中一条才成立,标签本身不算理由

1. **凭据爆炸半径**——敏感凭据(比如支付密钥、webhook 验签密钥)目前跑在一个通用运行时里,独立
   数据库 + 独立角色/凭据才能把这份凭据的暴露面收窄。
2. **独立备份/恢复**——留在同一个库里意味着要恢复整个库才能恢复这份敏感数据,独立数据库能让这份
   数据有自己独立的恢复点目标/恢复时间目标。
3. **机器强制的唯一写入者**——在共享库里"只有某个模块能写这张表"只是一条靠代码评审自觉遵守的
   约定;独立数据库 + 独立角色权限能让这变成数据库层面真正强制的事实。

**明确不成立的理由**:"钱很重要""资金要安全""这份数据更重要/更敏感/更需要保护"——这类标签本身
不能作为拆库的理由,必须换算成上面三条里具体的哪一条,并给出可验证的细节。

拆库的收益和拆库带来的接缝债务(原来的本地事务/外键必须换成不透明 ID + 对外的查询/命令/事件契约)
要在同一张卡里同时写清楚,不能只写收益不写代价。

还有一类不依赖容量证据的理由是**故障隔离**——比如当用户流量打满核心业务库连接池的时候,恰恰是最
需要用另一个入口(比如管理后台)介入排查的时候,如果两者共享同一个连接池,救火的入口本身也会被
一起打满;独立数据库能让这个救火入口的可用性不跟被打满的那个连接池绑在一起。

## 常见走捷径的坑,不允许出现

- 因为现有连接最容易复用就默认塞进已有库,不写任何决策依据。
- 用"方便""安全""重要""是钱""以后可能要拆"这类标签填判据字段——这些理由在封闭清单里根本没有
  对应选项。
- 被否决的备选方案留空,或者写"暂时不需要""以后再说"这种不指向具体事实的理由。
- 放置校验没通过时,通过"把所有者服务改成能过的那个"或者"把允许清单放宽"来让校验变绿——这是在
  转移问题,不是在解决问题。
- 混用 bounded/unbounded 两套字段,或者手算派生容量数字。
- 新建的 `active` 存储用"未知"当证据状态通过严格校验。
- 用"latest-state"这种说法把本质无界的数据登记成有界。
- 只有"保留"动作才能不写总保留天数,其它动作都要给一个正整数。
- 保留策略的执行入口指向一个代码里根本不存在的删除逻辑。
- 只凭"以后可能会很大"就提前分库分表,或者只凭当前数据是空的就判定设计健康。
- 用文档或卡片状态代替某个环境的真实执行证据——卡片状态是 `active` 只代表治理决策生效了,不代表
  任何一个环境已经真的执行过对应的迁移;判断某个环境是否已经执行,只能看那个环境自己的数据库执行
  账本(参考 [migration-downpath](../migration-downpath/SKILL.md)),不能看文档、不能看 Git 里的
  审计快照。

## 健康结论怎么判——这是证据推导出的结论,不是可以手填的状态

| 结论 | 什么情况下能这样判 |
| --- | --- |
| 健康 | 卡片完整且跟实际存储/迁移状态一致;容量、保留、物理设计、所有权、一致性都有当前证据;没有
  任何重评阈值被越过。 |
| 暂定 | 决策已经完整且可以上线,但容量还是有依据的预估,或者运行时的投影/切换证据还没收集完整——要
  写清楚还差哪些证据没验证。 |
| 未知 | 核心输入缺失,或者只是靠命名约定隔离(没有对着真实数据库校验过),或者只证明了当前测试能读写
  ——这种情况下**禁止**说成"目前够用"或"架构健康"。 |
| 不健康 | 放置/日志边界已经被违反,重评阈值已经越过,或者缺少必要的保留/一致性保护。 |

没有实测的行数/写入速率/存储占用/延迟证据时,正确做法是给一个可追溯的"预估+暂定",或者干脆写
"未知"——**"没有证据显示撑不住"不等于"有证据显示健康"**。
