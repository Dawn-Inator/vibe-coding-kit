# Frontend Design Draft(前端设计稿先行流程)

## 一句话定位

写生产代码前,先用静态自包含 HTML 出一轮可挑选的设计稿——分两个受控阶段(风格 → 布局),
每阶段结束都停下来等 Owner 明确选择,绝不自己往下走到下一阶段或直接写生产代码。

## 何时用 / 何时不用

**默认自动触发**:用户只要表达某个前端页面"不好看",想"优化 / 美化 / 改版 / 重做 / 调整视觉",且没有
给出一套可直接实现的完整视觉方向,就立刻使用本 Skill;不要求用户说出「设计稿」「方案」或任何触发短语。
例如「给个人主页出几个设计稿」「这个列表页想改版,先看看方案」「登录页想要不同风格,出几个选项」都属于
本 Skill。

方向尚未决定本身不是澄清问题。除非无法识别目标页面,或用户要求互相矛盾,**不得**先询问风格偏好、覆盖范围、
是否需要草稿,也不得先输出实现计划;第一步就是产出阶段一草稿。若当前运行模式禁止写入 `.todolist/`,明确报告
这个写入阻塞并停止,不能以提问或计划替代阶段一产物。

**不用**:
- 纯 bug 修复、后端/API/数据类改动、纯文案改字——没有真实的视觉选项空间。
- Owner 已经点名最终视觉方向,只是要求照做——直接进你项目自己的实现流程(参考
  [coding-gate-preflight](../coding-gate-preflight/SKILL.md))。
- 有独立的、不写真实代码的"预览沙盒"流程(比如产品经理用自然语言描述页面调整、只要看预览)不属于本
  skill——本 skill 从不改应用源码,也从不 push 或部署任何东西,如果你的项目有这类沙盒预览机制,那是
  另一个独立流程的职责。

## 目标端判定与视觉语言加载

先按改动落点判定目标端(比如移动端 / 管理后台 / 官网这类不同的前端应用),再加载对应的视觉语言约束
(如果你的项目为某个前端维护了独立的设计规范,比如色板、间距系统、组件视觉 token)。**关键技巧是给
确切文件路径让工具直接 Read,而不是依赖某个 AI 工具独有的 Skill 调用机制**——这样不同的 AI coding
工具(Claude Code / Codex / Cursor 等)才能读到同一份约束,不会出现"这个工具能读到设计规范、那个工具
读不到"的情况。

**这是一张需要你按自己项目填的表**(下面给的是形状示例,不是照抄内容):

| 目标端 | 判定依据 | 视觉语言约束在哪 |
|---|---|---|
| `<你的移动端应用>` | 改动落在对应目录下 | 如果有独立设计规范文件,填它的路径(比如某种 `design-model.yaml` 之类的 hex ↔ CSS 变量 ↔ 语义映射表) |
| `<你的管理后台>` | 同上 | 同上 |
| `<你的官网/其它前端>` | 同上 | 如果没有独立设计语言约束,自由度更大,但定稿后若要把结论沉淀成规范,考虑用
  [manage-knowledge-artifacts](../manage-knowledge-artifacts/SKILL.md) 的思路收进一份文档 |

如果你的项目为某个前端维护了这样一份"色值 ↔ 变量名 ↔ 语义"的精确映射表,手写 `:root{}` 时应该以它
为准,而不是凭感觉现造颜色。

**硬禁令**:本 skill 正文与产出说明中一律不复制任何设计规范文件里的具体色值、字阶或组件表——只给
路径,让执行时去读最新版本,避免这里的摘抄过期漂移。

## 阶段一:风格方案

产出同一目标页面的 **3 个** 静态 HTML 变体。差异必须落在两根可解释的轴上:

- **克制 ↔ 张扬**:留白量、hero 元素强度、装饰密度
- **信息密度 高 ↔ 低**:同屏信息量、卡片紧凑度、次级信息是否默认展开

不做完整 2×2——「张扬 + 高密度」两个方向互相矛盾,站不住。取三个有区分度的点即可,例如
「克制 + 高密度」「克制 + 低密度」「张扬 + 低密度」。

**每个变体的文件名和页内标题必须写明自己在两根轴上的坐标**,禁止用 A/B/C 这种无解释编号——
Owner 挑选时不应该需要打开文件才知道每个方案是什么方向。

**有硬性色板约束的前端(如果你的项目为某个端定义了 token 化的强制色板)**:阶段一**只能变结构性的轴**
(密度、留白、hero 强度),**禁止变色板、禁止发明新颜色或新渐变**——变色即绕开设计语言红线。没有这类
约束的前端(比如自由度更大的官网)没有这条限制,按你项目实际情况判断。

**停止条件**:列出每个变体的坐标 + 文件路径后,**原地结束本轮**。等待 Owner 从三个中选一个
(或指出想融合哪几处方案),**收到明确选择前不得进入阶段二、不得写任何生产代码**——不允许
"猜一个大概率对的方向直接往下做",也不允许把三个方案都实现一遍留给 Owner 事后挑。

## 阶段二:布局方案

前提:Owner 已经从阶段一选定某个变体。**继承并锁定**该变体的风格坐标(色板、密度、留白、
hero 强度全部不变),**不得重新讨论风格**——风格的讨论窗口在阶段一已经关闭。

只变结构轴:信息架构顺序 / 卡片·列表·表格三选一 / 主 CTA 位置与数量 / 单列多列 / 导航入口
形态。产出 2-3 个变体,文件名要能看出继承自阶段一哪个方案。

**停止条件**:同样列出每个变体的坐标 + 文件路径后,**原地结束本轮**,等待 Owner 明确选择,
收到选择前不得把某个变体当作最终结论、不得开始改生产代码。

## 文件产物规范

```
.todolist/design-drafts/<target>-<feature-slug>/
  phase1-a-<轴A取值>-<轴B取值>.html
  phase1-b-...
  phase1-c-...
  phase2-a-<继承自phase1哪个>-<布局标签>.html
  phase2-b-...
```

例:`.todolist/design-drafts/mobile-profile-revamp/phase1-a-restrained-dense.html`

- **单文件自包含**:完整 `<!doctype html>`,`<style>` 内联,图标用内联 SVG,**不引入构建
  步骤、不依赖 dev server**,`file://` 双击即开。
- 不建共享外部 CSS/JS——少量重复换来「打开即所见」,避免不同 AI 工具下相对路径解析行为不一致
  的坑。
- **不要默认把 `.todolist/` 加进 `.gitignore`。** 这些草稿虽然是一次性产物,不是需要长期维护的
  知识产物,但很多项目会刻意让 `.todolist/` 保持 git 跟踪,好让草稿能跨机器/跨会话交接
  (`.gitignore` 里只排除纯执行期草稿 `.workspace/`,`.todolist/` 不排除)——具体按你项目在
  INSTALL 步骤里定的那条规则来,不要凭直觉替项目做这个决定。

## 定稿交接

本 skill 的职责到「Owner 选定阶段二方案」为止,**不把草稿 HTML 直接搬进生产代码目录**。
定稿后交给正常实现流程(参考 [coding-gate-preflight](../coding-gate-preflight/SKILL.md)),从
开工预检开始写生产代码;实现时提醒自己「用真实组件库 / design token 重新实现,草稿只是参照,不是
可合并代码」——草稿里手写的 `:root{}`、内联 SVG 不代表生产代码应该照抄的写法。

## 多工具差异备注

- **有 Skill 调用机制、有阻塞式提问工具的 AI 编码工具**(比如支持 Skill 工具调用和结构化提问的
  Claude Code):可以在加载视觉语言约束时直接用 Skill 调用机制;有阻塞式提问工具时应在每阶段末尾
  用它强制阻塞式提问,作为停止条件的增强手段,但不是唯一的停止机制——即使没有该工具,"原地结束
  本轮回复"本身就已经是停止。
- **没有这些机制的 AI 编码工具**(比如更偏命令行风格的工具):没有显式 Skill 调用、也没有阻塞式
  提问工具——这里的"停止"就是指本轮回复到此为止,不再自主调用工具续跑到下一阶段。
- 所有工具共同底线:产出落同一个 `.todolist/design-drafts/` 路径规范,读的是同一份视觉语言约束
  文件(如果有的话)——工具不同,产物和视觉约束必须一致。
