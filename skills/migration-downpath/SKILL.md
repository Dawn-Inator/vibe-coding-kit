# Migration Downpath(迁移可逆性契约)

大量迁移脚本是加列/加索引/加表这类天然安全的操作,给每一条都写一份严格的回滚 SQL,收益远小于成本。
真正危险的是破坏性/不可逆操作(删列、删表、改类型丢精度、DELETE/backfill 改数据、重命名)——这些才
需要作者停下来想清楚"回滚怎么办"。所以这份契约的核心是**分类 + 声明**,不是"一刀切都写回滚脚本"。

## 版本化迁移目录组织

正式迁移是一条只能往前追加的链(forward-only chain),按目标版本分目录存放,配一份清单文件登记
每条迁移的执行状态:

- 迁移脚本本体:按目标版本分目录存放(比如 `migrations/version/<targetVersion>/`)。
- 清单文件(manifest):记录每条迁移的顺序号、文件名、SQL 路径、所属数据库、部署阶段(先于业务代码
  部署还是后于业务代码部署)、以及每个环境各自的状态。**清单文件只是执行账本的同步副本,不是执行
  真源**,不一致时永远以账本为准,而且只能通过受管命令去同步,不能手改清单 JSON。
- 执行记录归档目录:CI 回写的审计快照,同样会系统性落后于真实账本,只能当审计参考,不能当执行证据。
- `undo/` 目录(可选,只在出现"可逆+破坏性"的迁移时才需要创建):存放人工手跑的回滚 SQL,**不进
  正式迁移链,不进清单,不参与执行账本校验**——它是给人看/手跑的兜底,不是自动化的回滚链条。

## 头部声明:每条新增迁移必须标注可逆性

每条**新增**的版本化迁移,SQL 头部必须加一行声明(跟其它头部元信息比如"用途""是否幂等""目标
数据库"放在同一个区块):

```sql
-- reversibility: reversible | irreversible | forward-only
```

- **`forward-only`**——加性、幂等、天然安全的变更(加可空列、加 `IF NOT EXISTS` 索引、加表、加权限
  策略、加授权)。多数迁移属于这一类。回滚策略是"不需要回滚,出问题直接往前写一条修正的迁移"。
- **`reversible`**——有明确的可逆路径。破坏性操作(DROP、改类型、数据改写)声明成 reversible 时,
  **应该在同一次改动里提供回滚路径**——要么是 `undo/<同名文件>.sql`,要么在头部 `-- down:` 注释块
  里写清楚逆操作 SQL。
- **`irreversible`**——一旦执行就无法机械回滚(比如物理 DROP TABLE 后数据已经丢失、涉及外部系统的
  副作用)。必须在声明旁边或 `-- down:` 里写清楚**为什么不可逆**,以及出问题时的人工补救方向(比如
  "从快照恢复""重新跑一遍 backfill")。

**分类必须跟脚本实际执行的语句一致**——如果一条声明为 `forward-only` 的迁移实际执行了
`DROP TABLE`/`DROP COLUMN`/`TRUNCATE`/`DELETE FROM`,这就是分类错误,必须改成 `reversible` 或
`irreversible`。理想情况下应该有一个自动化检查在执行时交叉校验声明和实际语句,而不是只靠人工审查。

### 一个反直觉的分类案例

给已有列加一条新的 `CHECK` 约束(比如收紧金额的合法上下界),容易被误判成"介于两类之间"——它不销毁
任何数据,但确实会收窄未来写入的合法值范围,看起来不像纯粹的加性变更。实际归类是 **`reversible`**:
`DROP CONSTRAINT` 是干净、无损的逆操作(约束本身不持有数据),回滚路径就是那一条 DROP 语句,写进
头部 `-- down:` 即可,不需要额外的 `undo/` 目录或数据恢复叙述。

## `-- down:` 的范围判据:只回滚这条迁移真正改变过的字段

幂等的 backfill 经常在一条 UPDATE 里同时写好几个字段,但其中一部分字段的目标值可能本来就等于列
默认值——这条迁移对它们并没有构成真实变更。写 `-- down:` 时容易顺手把 SET 列表整个取反,这是错的:
逆转一个本条迁移没有真正改变过的字段,等于用列默认值覆盖掉别处(比如管理后台、更早的人工操作)写
进去的真实业务值,回滚反而成了新的数据损坏源。

判据是一句可检验的话:**"这个字段在本条迁移执行之前,是否可能存在一个不等于列默认值、且不是本条
迁移写进去的值?"**——可能存在,就不要在回滚脚本里碰它。

## 回滚优先级:按代价从低到高,分层兜底

真出问题时,实际的回退不是"跑 undo 脚本",而是按下面顺序,代价从低到高依次尝试:

1. **代码回滚优先**——多数"迁移上线后出问题"其实是应用代码跟新 schema 不兼容,不是 schema 本身
   坏了。先把服务回滚到上一个版本,schema 只要保持向前兼容,绝大多数情况根本不需要动数据库。
2. **前向修复迁移**——schema 本身确实要改,就再写一条新的迁移脚本修正(比如加回被误删的列、放宽
   约束),走正常的迁移流程。这是链式迁移体系的标准回退姿势——永远往前走,不倒带执行账本。
3. **人工执行 undo 脚本**(仅限声明为 reversible 的破坏性迁移)——确实需要机械逆转、且作者写了
   `undo/<name>.sql` 时,人工在对应环境执行。**执行后必须补一条前向迁移或者一次账本对齐记录**,让
   清单和执行账本重新跟实际 schema 保持一致,不能只手跑 undo 脚本让账本产生漂移。
4. **从快照/时间点恢复**(irreversible 且数据已丢的最后兜底)——不可逆变更导致数据确实丢失时,从
   对应环境的数据库快照或时间点恢复(PITR)。

## 执行账本是唯一真源

**判断"某条迁移到底有没有真正执行"这件事,只有目标环境的数据库执行账本能回答**;清单文件里的状态
字段只是账本的同步副本,可能任意陈旧。两者不一致时一律以账本为准,而且只能用受管命令去对齐,**不要
手改清单 JSON,更不要手写 SQL 直接改账本**——手写 SQL 编辑执行账本、伪造历史执行/验证证据、自动跑
`undo/`、或者盲目重放非幂等 SQL,这些都是明确禁止的操作。没有自动化修复命令时,也不允许直接改
数据库里的账本表、或者用复制别处连接串这种手段绕过去。

## 已合入/已执行的迁移文件不可变

迁移文件一旦合入共享分支或在任一环境执行过,就不能再原地修改——修正一律写新的前向迁移。用机制守住:
清单里为每条迁移登记内容校验和(如 SHA-256),检查脚本对照 base 分支的真实 git 历史比较,任何后续
改动都让检查失败(不要只对照本地快照或归档记录,它们能被同一次改动一并改写)。

## 高风险迁移先在生产形态副本上演练

破坏性、类型转换、权限/角色相关的迁移,在真实环境执行前先在"生产形态的一次性副本"上演练:只带结构
(角色、扩展、默认权限、授权、RLS 策略),不带数据和密钥,用与真实执行相同的执行角色、相同的阶段顺序
应用待执行的迁移链。演练结果(通过/失败与原因)记录下来,作为放行证据之一;只在空库或单角色开发库
上验证过,不算演练。

## 执行前先对账,不一致就拒绝执行(fail-closed)

`apply` 之前先做只读对账:把目标环境的执行账本与磁盘上的迁移文件(含顺序、校验和、所属数据库、
阶段)逐项比较,覆盖每个逻辑数据库的全部阶段。有任何不一致、缺失、或无法判定归属的目标,一律拒绝
执行并报出差异,由人决定如何修复;不要默认归到某个库,不要从游标续跑,不要手改账本。失败或修复
之后,完整重跑一遍对账。

## 写迁移脚本时的自查清单

1. 这条是加性/幂等/安全的吗?→ `forward-only`,不需要回滚路径。
2. 有 DROP、改类型、或数据改写吗?→ 想清楚回滚:能机械逆转就标 `reversible` 并写
   `undo/`/`-- down:`;不能就标 `irreversible` 并写清楚人工补救方向。
3. 头部加上 `-- reversibility:` 这一行。
4. 破坏性变更优先考虑"两步走":先加新字段/双写/回填,再删旧字段——把真正不可逆的那一步往后推,
   缩小影响半径。
5. 改动涉及父子表/子类型关系时,检查语句顺序在"中间状态"下是否仍然满足数据不变量(比如触发器校验)
   ——空表容易让顺序缺陷悄悄通过测试,要多问一句"如果这张源表非空,这条迁移是否依然成立"。
6. **约束要晚于回填**——任何新增约束/外键必须排在"让存量数据满足这个约束"的那条数据修改语句
   **之后**。先加约束再灌数据,等于拿约束去校验还没清洗过的数据。
7. **先换校验规则,再动数据**——如果同时修改了校验函数/触发器和数据本身,校验规则的变更必须排在
   "按新规则改写数据"的语句**之前**;顺序反了就是拿旧规则去校验新数据。
8. 不要指望"延迟约束检查"(deferred constraint)能救顺序错误——这类机制通常只在"整份脚本跑在同一个
   事务里"时才生效;写的时候按"每条语句都可能单独提交"来排序,才是在两种执行模型下都安全的写法。
9. 新增了非空且无默认值的列时,记得同步检查测试用的种子数据/fixture 是否也需要补上这个字段。

## 线上安全(摘要,细则见 [references/online-safety.md](references/online-safety.md))

迁移跑在**有流量、且旧版本进程还没退场**的环境里。除可逆性之外,还必须守住:

- **限时**:每条会拿强锁的 DDL 显式写 `lock_timeout` / `statement_timeout`,拿不到锁就快速失败,不排队堵死业务。
- **在线建索引**:需要 `CREATE INDEX CONCURRENTLY` 但迁移工具在事务内执行时,头部注释写明大表上线前的手工等价步骤,迁移本身保持幂等。
- **回填**:大表回填分批、可续跑、每批有界;DROP 之前只读预览将丢的行数。
- **expand/contract**:滚动发布时旧镜像仍在跑,收紧权限/加严约束/删列只能放 post-deploy 阶段。
- **用线上版本自己的校验器验证候选迁移**,不靠人读 SQL;取不到线上版本或无法评估时 fail closed。
- **phase 必须显式声明**:manifest 里缺失的部署阶段不得被静默默认成 pre-deploy(真实事故:未声明的收紧迁移被提前执行,旧镜像启动校验失败)。
- **声明 ↔ 语句交叉校验**:`-- reversibility:` 必须被静态检查对照实际语句;新规则只约束「激活序号」之后的条目,历史空洞带理由逐条登记。
