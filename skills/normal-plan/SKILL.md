# normal-plan:常规计划规范

## 何时使用

只要当前是 Plan Mode,或用户要求先写计划,就触发本 skill。产物始终是**一份**结构化计划,不拆成多个 md
文件的规划包(如果你的项目还想要"大型需求先拆成多份 md 文档、跨多个 AI session 执行"这种更重的流程,
那是一个独立的、只有开发者明确点名才触发的技能——本仓库如果也移植了,叫法通常是 `ultra-plan`)。

不要因为任务跨很多模块、跨前端+后端+基础设施、需要多个 AI session,或者用户说"整套/全套/整个系统/
大型架构",就自动升级到更重的流程。看起来更适合时仍用本 skill,在「需要你拍板」里写升级建议,让开发者
自己决定。

写计划前必须先用 [coding-gate-preflight](../coding-gate-preflight/SKILL.md) 做开工预检;结论填进下文「闭环清单」,不另起一段。

## 小任务白路径

按你项目 gate 工具的 lite / full 分类(判据唯一真源在那里,agent 不得自行改判)归为 lite 时,只输出精简
卡三项(范围与风险、worktree 目标、验证计划)即可实施,不必铺开下面的完整结构。分类为 full、分类器缺失
或结果不明时必须走完整格式——分类结果是唯一入口,不允许因为任务"看起来小"就自行简化。

## 计划前必问

先做只读探查和开工预检,再用你工具里的阻塞式提问机制(结构化问答工具,或者一条明确要求回复的普通
消息)问开发者。用户本轮已明确回答的,在「需要你拍板」里引用原话作为授权凭据。

- 后端受影响时,单独问要不要跑后端测试套件;前端受影响时,单独问 e2e / 浏览器交互验证跑哪些。lite 不问。
  **修 bug 例外**:先读 [bugfix-regression-tests](../bugfix-regression-tests/SKILL.md),弹窗只决定跑哪些
  命令,不能把"要不要写自动化测试"问成可选项。
- 目标分支:如果你的项目有多套环境分支,先确认 worktree 要 base 在哪个分支、完成后合并推送到哪个分支——
  参考 [agent-worktree-lifecycle](../agent-worktree-lifecycle/SKILL.md),按你项目实际的分支拓扑确定,
  能从当前分支推导出来就不必问。

## 输出格式

Markdown,标题固定如下顺序:

1. `## 一图看懂`:先两行文字,再 **1 张文本执行路径图**。不用 Mermaid——多数 AI app、手机端、终端、
   聊天工具不渲染它,只会露出源码。
   - **图前固定两行,顺序不得颠倒**:第 1 行 `**目的**:…` 只写为什么做 / 要达成什么(业务或用户视角,
     不出现命令、文件名、技术名词);第 2 行 `**做法**:…` 才写怎么做、用哪些技术 / 模块。两行都必填,
     不得两行都写成技术描述。
   - **画执行路径,不画文件影响面**:从起点画到终点——开始 → `worktree:begin` → 每个步骤 → 拍板点 `◆` →
     并行 wave `‖` 分叉 / 汇合 → 验证关卡 `✓`(含失败回路)→ `worktree:end` / push → 终点写完成判据。
     节点 `[n]` 与「任务与步骤」编号一一对应;每个节点一行标题 + 至多一行缩进注释(关键命令 / 在哪跑 /
     模型档位)。文件清单写在「任务与步骤」,不进图。
   - **格式**:放在不带语言标记的代码块里;左侧一条竖直主干(`│ ▼ ├ └ ─▶`);**不画闭合右边框**(中文等
     双宽字符在手机等宽字体下会让右边框错位);宽 ≤80 列(双宽字符按 2 列计);≤20 个节点。图只画本次
     计划的真实执行顺序,不画装饰。
   - **固定图例**,图下一行写出:`[n]` 步骤、`◆` 需拍板、`✓` 验证关卡、`‖` 并行分支、`└─ 红 ─▶` 失败回路,
     以及 HTML 视图状态。
   **另出 HTML 视图(可选)**:跨 ≥3 个模块、含 UI 改动、或有 ≥2 个方案需要开发者对比时,额外生成与计划
   md 同目录同名的 `<plan-name>.html`,放在**当前 AI 工具自己的计划 / scratchpad 目录,不写进仓库**。
   HTML 单文件自包含、零外部依赖,用内联 SVG 画同一条执行路径,支持明暗主题;计划 md 里写出该文件路径。
   **md 是唯一真源,HTML 只是视图**,内容冲突以 md 为准。
2. `## 需要你拍板`:会改变实施方向的决策、未知与升级建议(每条给推荐);已弹窗回答的引用原话。无则写「无」。
3. `## 目标与完成判据`:一句话目标(多个任务用分号隔开)+ **可失败的**验收条件(命令、断言或可观察行为)。
   不写"完善""处理好"这类无法判红的话。
4. `## 任务与步骤`:编号步骤;subagent 派发与维护性风险门禁按下文规则写在本段。如果任务会新建持久化存储
   (表、物化视图、队列等),而你的项目维护了类似"数据架构卡"的决策记录机制,在本段写该决策的关键结论
   (所有权归属、容量模型、被否决的备选方案及理由);没有这类机制就跳过,不要现造一套。
5. `## 闭环清单`:**一张表,下列 6 行每行必填**,这是防 AI 漏做模块的强制自检。不适用的行**不得只写“无”**,
   必须写成「无 X,原因:…;剩余风险:…」。

| 项 | 结论 | 依据 / 命令 | 不适用原因与剩余风险 |
| --- | --- | --- | --- |
| Worktree / base | 目标 base、`node .vibe-coding/kit/cli.mjs worktree begin --name "<scope goal>"`(如果项目已启用 kit worktree runtime)、预期临时分支与路径 | [agent-worktree-lifecycle](../agent-worktree-lifecycle/SKILL.md) | — |
| 文档影响 | 需新建 / 修改的文档与生成物;改了 skill 或 `.vibe-coding/loading.md` 后按项目约定同步,若采用 kit package scripts 可用 `pnpm skills:sync` | 你项目的文档影响检查(如有) | 无 doc/ 影响,原因:…;剩余风险:… |
| SQL 迁移 | 每个迁移脚本:路径、状态(待执行 / 已执行)、执行入口、目标环境 | 只走你项目自动化的迁移入口,不安排 AI 用数据库客户端手动执行原始 SQL;规则见 [migration-downpath](../migration-downpath/SKILL.md) | 无 SQL 迁移脚本,原因:… |
| 测试 spec 变更 | 需新建 / 修改的测试脚本、fixture、契约测试及覆盖目标;bugfix 写「原自动化覆盖缺口 / 逃逸原因」与两层「回归覆盖路径」(本处回归 + 同类防线) | [bugfix-regression-tests](../bugfix-regression-tests/SKILL.md) | 无测试脚本 / spec 变更,原因:…;原自动化覆盖缺口 / 逃逸原因:…;回归覆盖路径缺失原因:…;剩余风险:… |
| 验证命令 | 按弹窗选择与影响面列精确命令,每条注明在哪跑(本机 / 远端)及依据 | [test-gate-router](../test-gate-router/SKILL.md) | 用户选择不跑,风险:… |
| 目标分支与收尾 | 目标分支、`worktree:end` 合并与 push 行为 | 完成前硬自检:`worktree:end` 已执行并拿到终态结果;临时分支与临时 worktree 已删除 | — |

「测试 spec 变更」与「验证命令」必须分开填,互不替代:跑了测试不等于补了 spec,用户选择不跑也不免除补 spec 的判断。

## 任务与步骤段的附加规则

Subagent 派发(默认单 agent,写明不派原因)与维护性风险门禁(无新增风险写「无新增质量风险,原因:…」)的规则见 [references/subagent-and-risk-gate.md](references/subagent-and-risk-gate.md)。

## 写计划的硬要求

不写 `TBD` / `TODO` 等占位话;闭环清单 6 行全填;bugfix 写覆盖缺口与两层回归路径;数据库变更只走自动化入口。完整 7 条见 [references/hard-requirements.md](references/hard-requirements.md)。

## 常用计划模板

````markdown
# <任务名>

## 一图看懂

**目的**:<为什么做 / 用户或业务要达成什么,不写技术>
**做法**:<怎么做、用哪些技术 / 模块>

<文本执行路径图,样例见 references/example-diagram.md>

图例:`[n]` 步骤,`◆` 需拍板,`✓` 验证关卡,`‖` 并行分支,`└─ 红 ─▶` 失败回路。HTML 视图:<路径,或「未触发:原因」>

## 需要你拍板

- <决策 / 未知 + 推荐>;或「无」

## 目标与完成判据

- 目标:<一句话>
- 完成判据:<可判红的命令 / 断言 / 行为>

## 任务与步骤

1. <步骤>
2. <步骤>

- Subagent:<不派原因,或 Wave 表>
- 风险门禁:<风险表,或「无新增质量风险,原因:…」>

## 闭环清单

| 项 | 结论 | 依据 / 命令 | 不适用原因与剩余风险 |
| --- | --- | --- | --- |
| Worktree / base | | | |
| 文档影响 | | | |
| SQL 迁移 | | | |
| 测试 spec 变更 | | | |
| 验证命令 | | | |
| 目标分支与收尾 | | | |
````

## 可选示例:执行完成报告

如果项目希望使用固定的完成报告格式,可以参考下面的模板并按本项目习惯调整。示例中的图使用纯文本;它不是本 kit 强制的报告政策。

采用该模板时,计划与完成报告保持对应关系;具体标题和内容以项目自己的报告要求为准。

````markdown
# 执行完成报告

## 计划 vs 实际

**目的是否达成**:<是 / 否 / 部分 + 一句话依据>

```
[✓] [1] <实际完成的步骤>
│
▼
[✓] [2] <验证关卡及结果>
│
▼
[✓] [3] <收尾结果及完成判据>
```

图例：`[✓]` 完成、`[≈]` 偏差、`[✗]` 放弃、`[…]` 未做；沿用原编号，无计划按实际顺序编号。

计划有 HTML 视图时,在同目录产出 `<plan-name>.recap.html`(同样不进仓库)。

## 偏差

- <偏离计划的地方 + 原因 + 是否需要开发者认可>;无偏差写「无」。图上有 `[≈]` / `[✗]` / `[…]` 节点却没在此说明,报告无效。

## 状态

- 实现候选:<待定 / 通过 / 失败 + 精确 commit SHA>
- 代码验证:<待定 / 通过 / 失败 + 精确 commit SHA>
- 运行验收:<待定 / 通过 / 失败 / 不适用 + 精确 commit SHA>
- 未完成或阻塞:<无,或原因>

## 闭环清单(实际)

| 项 | 实际结果 | 证据 | 未做原因与剩余风险 |
| --- | --- | --- | --- |
| Worktree / 临时分支清理 | 实际 `worktree:begin` / `worktree:end` 命令与终态结果;临时 worktree 与临时分支是否已删除 | 命令输出 / 日志路径 | 未删除:保留路径、分支、失败命令、阻塞原因 |
| 已新建/修改文档 | 路径 + 变更类型(新建 / 修改 / 同步生成) | | 无已新建/修改文档,原因:… |
| 已执行 SQL / migration | 路径、目标环境、自动化入口、结果 | 你项目的迁移执行记录 | 无已执行 SQL,原因:… |
| 测试脚本 / spec 变更 | 路径、变更类型、覆盖目标;bugfix 写逃逸原因与回归覆盖路径 | | 无测试脚本 / spec 变更,原因:…;回归覆盖路径缺失原因:…;剩余风险:… |
| 验证情况 | 实际运行的命令与 pass / fail,以及在哪跑 | 输出摘要 | 未运行:原因和风险 |
| 目标分支和 push 状态 | 目标分支、合并 / push 状态 | push 结果 | |
````

报告每行同样不得只写「无」。验证情况只记录实际跑过 / 没跑的命令,不能替代测试脚本 / spec 变更行。
